<a id="what-restarts-and-when"></a>
# Что и когда перезапускается

Основное описание последовательности для каждого пути изменения символической ссылки `current` и для загрузки. Оно понадобилось потому, что три документа по-разному отвечали, какая служба и когда перезапускается, а именно от ответа зависит диагностика расхождения версий.

Всё ниже прочитано из кода; каждый шаг называет отвечающую за него функцию. Если поясняющий комментарий в другом месте противоречит странице, ошибочен комментарий.

<a id="1-the-seven-daemons-and-the-unit-that-is-not-one"></a>
## 1. Семь служб и ещё один unit, который к ним не относится

Выпуск содержит семь служб: `robotd`, `configd`, `btd`, `padd`, `mediad`, `tofd`, `updaterd`. Каждая выполняет `ExecStart` из `/opt/robot/daemon/current/bin/`, поэтому сразу после смены ссылки её процесс остаётся на прежнем выпуске. Каждая перезапускается либо во время обновления, либо после него.

Поставляется также `robot-boot-check.service`, **не входящий** в этот набор и никогда не перезапускаемый обновлением. Он проверяет, поднялся ли загруженный выпуск, и при неудаче передаёт управление `robot-rescue`. Запуск посреди обновления направил бы проверку отката на законно перезапускающиеся службы. У него нет секции `[Install]`; именно это исключает его из набора, см. §1.1.

| Служба | Перезапуск во время обновления | Перезапуск примерно через 5 s после ответа |
|---|---|---|
| `robotd` | Да | — |
| `configd` | Да | — |
| `padd` | Да | — |
| `mediad` | Да | — |
| `tofd` | Да | — |
| `updaterd` | **Никогда:** это выполняющий обновление процесс. | Да |
| `btd` | **Никогда:** обновление могло прийти через него. | Да |

Обе половины — одно решение. Тест `every_unit_held_back_is_restarted_once_the_answer_is_out` проверяет совпадение наборов `NEVER_RESTART` и `RESTART_AFTER_REPLYING` в `engine.rs`.

Ничто не откладывается до перезагрузки системы. Это было верно до появления `RESTART_AFTER_REPLYING` и остаётся самым распространённым устаревшим утверждением о системе.

Поскольку планирование перезапуска не доказывает его выполнения, следующий запуск `updaterd` сравнивает каждую службу с активным выпуском и перезапускает несовпадающие — §5.

<a id="11-what-counts-as-a-unit-an-update-starts"></a>
### 1.1 Какие службы запускает обновление

Файл `systemd/*.service` с секцией `[Install]`. Службу без неё запускает другой механизм — таймер или зависимая служба, — и обновление не владеет её жизненным циклом. Решение принимает `engine.rs::has_install_section`.

Используется правило, а не список имён: два места уже применяли его по-разному. `hooks/postinstall` отказывался выполнять `enable --now` для unit без `[Install]`, прямо объясняя: *«это запустило бы проверку отката посреди устанавливающего её обновления, когда службы законно перезапускаются»*. Движок же читал все `*.service` и всё равно перезапускал такую службу чуть позже. Проверка секции согласует оба места по построению и не требует помнить о следующем похожем unit.

Нечитаемый unit считается требующим перезапуска: вероятнее проблема прав, чем намеренно особый жизненный цикл. Громкая ошибка перезапуска лучше молчаливого пропуска.

<a id="how-the-set-is-computed"></a>
### Вычисление набора

Два набора с разницей в одну функцию. `engine.rs::units_shipped` — всё предоставляемое выпуском:

```
(the release's own systemd/*.service stems)  ∪  (on_apply.units from /etc/robot/updater.toml)
```

Набор сортируется и очищается от дублей. `engine.rs::units_to_restart` — тот же набор за вычетом `NEVER_RESTART`:

```
units_shipped(…)  −  {updaterd, btd}
```

Обновление перезапускает `units_to_restart`; сверка при запуске в §5 читает `units_shipped`, поскольку две недоступные обновлению службы как раз и являются основной целью наблюдения.

В текущем на момент записи выпуске `units_to_restart` равен:

```
configd, mediad, padd, robotd, tofd
```

Именно в таком алфавитном порядке, одинаковом на каждой плате и в каждом тесте. Для добавления `mediad` и `tofd` в список ничего не дописывали в `deploy/updater.toml`: обе поставляют unit с `[Install]`, и этого достаточно.

Два следствия вычисления по выпуску, а не по плате:

- `padd` перезапускается, хотя `deploy/updater.toml` его не упоминает. Конфигурационный список **дополняющий**, не главный; в нём нужны только службы, которых выпуск *не* поставляет.
- Плата с `updater.toml`, созданным до появления службы, всё равно её перезапускает. Файл принадлежит оператору и сохраняется `install.sh`; именно поэтому некоторое время не перезапускался `configd` (`../project/install-path-gap.md` §4).

Каждая служба перезапускается отдельным `systemctl restart <unit>`, никогда пакетом: один `systemctl restart a b` при неизвестной службе целиком завершается ошибкой, *не* перезапуская существующую. `LoadState=not-found` пропускается с предупреждением; существующая служба, чей перезапуск не удался, **вызывает ошибку обновления и откат**.

<a id="2-robotctl-update-apply-updateapply-over-ble"></a>
## 2. `robotctl update apply` / `update.apply` через BLE

<a id="2-robotctl-update-apply--updateapply-over-ble"></a>
`engine.rs::apply` → `apply_inner` → `stage_and_swap` → `post_swap`. До шага 8 рабочие пути не затрагиваются.

| № | Шаг | Есть перезапуск? |
|---|---|---|
| 1 | Предварительная проверка: часы, робот остановлен, активной сессии нет. | Нет |
| 2 | Получить манифест, проверить подпись, канал, закрепление, понижение версии и совместимость. | Нет |
| 3 | Повторная предварительная проверка, теперь места на диске по требованиям манифеста. | Нет |
| 4 | Скачать в `releases/.staging-<ver>/dl/`. | Нет |
| 5 | Проверить sha256, затем подпись артефакта. | Нет |
| 6 | Распаковать в `releases/.staging-<ver>/root/`, записать `.updater-manifest.json`. | Нет |
| 7 | **`hooks/preinstall`** с cwd подготовленного дерева: установить ONNX Runtime, если версия ниже минимума, затем запустить `scripts/setup-gstreamer.sh` нового выпуска для стека `mediad`. | Нет |

**Скрипт хука берётся из нового выпуска; запускающий его код — нет.** `updaterd` не перезапускает себя посреди обновления (§1), поэтому каждый шаг таблицы выполняет уже работающий `updaterd` *предыдущего* выпуска. Изменение запуска, журналирования или ограничений хуков вступает в силу на одно apply позже: при первом обновлении после перезапуска `updaterd` на выпуск с изменением. Однажды это вызвало путаницу «хук выполнился, но ничего не записал». `cat /run/updaterd/identity.json` показывает сборку, которая будет запускать хук.

| 8 | `rename` подготовленного дерева в `releases/<ver>/`. | Нет |
| 9 | Активировать счётчик загрузок (`pending.json`) *до* переключения. | Нет |
| 10 | Переключить `current` → `releases/<ver>`. | Нет |
| 11 | **`hooks/postinstall`**, cwd = `releases/<ver>`. | **Запускает новые службы выпуска** |
| 12 | `on_apply`: отдельный `systemctl restart` для каждой службы §1. | **configd, mediad, padd, robotd, tofd** |
| 13 | `releases/<ver>/bin/updaterd --self-test`. | Нет |
| 14 | Проверка работоспособности: опрос сокета `robotd` каждые 500 ms, до 30 s. | Нет |
| 15 | Подтвердить счётчик загрузок, очистить старые выпуски. | Нет |
| 16 | Освободить блокировку обновления, запланировать отложенные перезапуски. | **Планирует updaterd, btd** |
| 17 | Отправить ответ `robotctl` / приложению. | — |
| 18 | Примерно через 5 s после шага 16. | **updaterd, btd** |

Любая ошибка с шага 11 вызывает откат: вернуть `current`, повторить `on_apply` для предыдущего выпуска, подтвердить счётчик загрузок, записать журнал. Ошибки шагов 1–10 оставляют старый выпуск работающим, отменять нечего.

**Шаг 2 тоже может завершить операцию, причём не всегда без перезапусков.** Если манифест называет уже установленный выпуск, возвращается `already_current`: ничего не скачивается и не переключается. Перед ответом выполняется чтение из §5 для служб этого выпуска; работающие на другом перечисляются в `stale` и планируются так же, как отложенная пара на шагах 16–18. Поэтому apply на полностью актуальном роботе ничего не делает, а на роботе с расходящимися процессами — исправляет их. `select` уже активного выпуска делает то же по той же причине.

<a id="step-11-in-detail-hookspostinstall"></a>
### Подробнее о шаге 11: `hooks/postinstall`

<a id="step-11-in-detail--hookspostinstall"></a>
Хук находится в подписанном артефакте и работает с cwd каталога выпуска. Порядок:

1. Установить каждый `systemd/sysusers.d/*.conf` в `/usr/lib/sysusers.d/`, затем выполнить `systemd-sysusers`. Учётные записи до служб: отсутствующий `User=` мешает запуску и выглядит как неисправная служба.
2. Установить с перезаписью каждый `systemd/*.service` в `/etc/systemd/system/`. **Все**, включая `updaterd.service` и `btd.service`: список исключений хуку не нужен.
3. `systemctl daemon-reload`.
4. `systemctl enable --now` для каждого unit с `[Install]` (§1.1); остальные только установить. `.timer` включить без `--now`.

Именно поэтому исключения §1 сохраняются: `--now` означает *запустить*, а запуск уже работающей службы ничего не делает. `updaterd` и `btd` не перезапускаются. Но новая для платы служба запускается, что и является целью хука. Поэтому **впервые добавленная служба стартует дважды в своём первом выпуске**: здесь и затем на шаге 12.

Любая ошибка хука — предупреждение, кроме неудачного `install` unit или sysusers-файла: ненулевой код вызывает откат. Неспособность службы стартовать намеренно не фатальна: `btd` законно не запускается на плате, где радио ещё не появилось.

<a id="step-13-the-self-test"></a>
### Шаг 13: самопроверка

<a id="step-13--the-self-test"></a>
Поскольку `updaterd` не перезапускается во время обновления, невозможность запуска замены иначе обнаружилась бы при следующей загрузке после фиксации, когда восстановление находится внутри отказавшего процесса. Вместо этого *новый* `bin/updaterd` запускается с `--self-test`: загружает `/etc/robot/updater.toml`, создаёт движок и завершается до обращения к состоянию. Предел — 10 s.

Ошибка — `Error::SelfTest` с последней строкой stderr бинарника; она вызывает откат. Выпуск без `bin/updaterd`, например компонент моделей, проходит автоматически. Проверка полностью пропускается, если `on_apply` не является перезапуском, чтобы не мешать начальной установке.

<a id="steps-1618-the-deferred-restarts"></a>
### Шаги 16–18: отложенные перезапуски

<a id="steps-1618--the-deferred-restarts"></a>
`engine.rs::schedule_deferred_restarts`, сначала для `updaterd`, затем `btd`:

```
systemd-run --on-active=5s --timer-property=AccuracySec=100ms -- systemctl restart <unit>
```

Критически важные детали:

- **Временная служба, не дочерний процесс.** `systemctl restart updaterd` уничтожает всю cgroup `updaterd`, а его дочерний процесс находится *внутри* неё и погиб бы посреди перезапуска родителя. Таймер `systemd-run` находится снаружи.
- **Сначала снимается блокировка обновления**: шаг 16 до spawn. Fork дублирует все открытые дескрипторы; запуск с удерживаемой блокировкой передал бы её копию потомку.
- **При `Applied` и при `already_current` с отставшими службами.** Только `engine.rs::restarts_owed` выбирает набор. В первом случае нужна фиксированная пара; во втором — всё, что §2 обнаружил на другом выпуске, обычно сам `updaterd`. Откат ничего не требует: работающий `updaterd` уже соответствует `current`, и перезапуск был бы лишним.
- **Все службы идут через таймер**, даже обычно перезапускаемые на месте на шаге 12. Отдельный немедленный путь для `configd` и `robotd` сэкономил бы пять секунд ценой нового механизма.
- **Ошибки только журналируются, не возвращаются.** Успешное обновление не объявляется неудачным из-за невозможности запланировать перезапуск. Цена — служба на старом бинарнике до следующей загрузки.

Таймер создаётся *до* записи ответа, поскольку движок работает внутри `update.apply`. Пять секунд отсчитываются от шага 16, а не от получения ответа клиентом. Клиент видит результат, затем разрыв; для BLE это обычное переподключение.

<a id="what-the-restarted-updaterd-then-does"></a>
### Что делает перезапущенный `updaterd`

Обычный запуск выполняет всю последовательность §4: `clean_staging`, `record_boot`, сверку §5, которая обнаружит несостоявшийся перезапуск `btd`, затем обслуживание запросов. Два неочевидных следствия:

- **Счётчик загрузок считает запуски `updaterd`, а не буквальные загрузки ОС.** Успешный apply подтверждает своё испытание на шаге 15, поэтому увеличивать нечего; но оставленное *раньше* прерванным обновлением испытание продвинется при этом перезапуске.
- **Таймер периодических проверок начинается заново.** `INITIAL_CHECK_DELAY` — 60 s от старта процесса, затем отсчитывается `check_interval`.

<a id="3-the-other-transitions"></a>
## 3. Другие переходы

`select`, `rollback`, `reset-to-golden` используют `engine.rs::transition_to`: активация испытания, переключение, `on_apply`, проверка работоспособности, возврат при ошибке. Хуки и самопроверка **не выполняются**: новый артефакт не распаковывался, устанавливать и доказывать нечего.

| | Хуки | `on_apply` (§1) | Самопроверка | Отложенный перезапуск updaterd/btd |
|---|---|---|---|---|
| `update apply` | Да | Да | Да | **Да** |
| `update select <ver>` | Нет | Да | Нет | **Да** |
| `update rollback` | Нет | Да | Нет | **Нет** |
| `update reset-to-golden` | Нет | Да | Нет | **Нет** |
| Автооткат внутри неудачного apply | Нет | Да | Нет | **Нет** |
| Возврат по счётчику загрузок при старте | Нет | Да | Нет | **Нет** |

Два нижних «нет» корректны по построению: при неудачном apply и возврате по счётчику `updaterd` и `btd` ещё не перезапускались и остаются бинарниками выпуска, к которому возвращаются.

«Нет» у явного `rollback`/`reset-to-golden` — другой случай: если покидаемый выпуск ранее успешно применился, `updaterd` и `btd` уже перезапустились на него. Явный откат оставляет их там. `robotd`, `configd`, `padd` возвращаются, а эти два процесса остаются **новее** активного выпуска.

Это разрешается при следующем запуске `updaterd`, необязательно при перезагрузке ОС: §5 сравнивает в обоих направлениях, поэтому более новый, чем `current`, `btd` тоже считается несоответствующим и перезапускается. Сам `updaterd` намеренно не исправляет себя.

Поскольку select и возвраты пропускают `hooks/postinstall`, они также никогда не *удаляют* unit-файл. Понижение до выпуска без какой-либо службы оставляет её unit, указывающий на отсутствующий бинарник. Он не запускается; находясь в наборе перезапуска, вызывает неудачу всего перехода (`../project/install-path-gap.md`).

<a id="4-at-boot"></a>
## 4. При загрузке

systemd запускает службы из `multi-user.target`; `robot-boot-check.timer` назначает проверку восстановления через 180 секунд. **Порядка между службами нет**, кроме `padd` после `robotd` (рекомендательно: при отсутствии сокета `padd` завершается и повторяет раз в 5 s) и `btd` после `dbus`/`bluetooth`. Ничто не ждёт `updaterd`, а он сам ждёт только `network-online.target` через `Wants`, не `Requires`.

На этой плате `hci0` появляется примерно через 73 s после включения, поэтому `btd` повторно ищет адаптер вместо отказа.

Собственная последовательность `updaterd` (`main.rs::serve`):

1. Записать идентичность запуска на уровне `warn`: версия, ревизия, **путь `exe`**, pid. Именно `exe` показывает каталог выпуска, из которого действительно пришёл процесс.
2. Загрузить `/etc/robot/updater.toml` и доверенные ключи. Ошибка любого шага фатальна.
3. Создать движок.
4. `--self-test` завершается здесь, не трогая состояние.
5. `Engine::recover_on_start` **до открытия сокета**: загрузившийся в плохой выпуск робот уже начинает возврат, прежде чем ему можно запросить что-либо ещё.
   - `clean_staging` каждого компонента удаляет `releases/.staging-*`.
   - `record_rescue`: наличие `<state_dir>/rescued` означает, что внешнее восстановление переключило `current` на golden, пока службы не работали. Перенести запись в журнал как откат, **очистить испытание компонента**, удалить файл. Порядок до `record_boot` намеренный: восстановление уже пошло дальше испытания, и оставленное активным испытание через одну-две загрузки увело бы `current` с golden. Удаление файла также снимает защиту восстановления от цикла.
   - `refresh_golden_links`: опубликовать настроенный golden каждого компонента ссылкой рядом с `current`, чтобы восстановлению хватило одного `readlink`, без парсера.
   - `record_boot`: увеличить `boots` каждого активного испытания в `pending.json`.
   - Для `boots >= 2` (`MAX_BOOT_ATTEMPTS`) спросить `robotd` и возвращаться только при ответе, который не healthy и не degraded. Запрос **повторяется в течение `health.timeout` компонента**; причину объясняет `updater-design.md` §8. Следствие: до открытия сокета шаг может ждать весь таймаут, 30s в поставляемой конфигурации. Только на загрузке с откатом и только если `robotd` вообще не отвечает.
   - Возврат идёт на `previous`, а при отсутствии, отсутствии на диске или записи об откате previous — на `golden`. Переключить ссылку, подтвердить испытание, повторить `on_apply`: **возврат по счётчику перезапускает `configd`, `padd`, `robotd`**. Хуки не выполняются, ничего не планируется; только что запущенные systemd процессы `updaterd` и `btd` остаются из покидаемого выпуска. Шаг 6 поймает `btd`, сравнивая уже с новым активным выпуском; `updaterd` будет только отмечен и останется несоответствующим до следующей загрузки.
   - Записать результат. Ошибка журналируется, но обслуживание продолжается: отказ убрал бы единственный способ исправления.
6. `Engine::reconcile_running_units`, §5, **после** восстановления: оно может сменить активный выпуск, и более ранняя сверка сравнивала бы с уже покидаемой версией. Здесь возможны перезапуски.
7. `--check-only` завершается здесь. Он **выполняет** восстановление и сверку шага 6: это операторский инструмент, не безвредная проба; он может откатить выпуск и перезапустить службы.
8. Обслуживать `/run/updaterd.sock`.
9. При заданном `check_interval` запустить планировщик: первый проход через 60 s от старта, затем каждый интервал. `auto_apply` определяет установки без клиента.

Испытание существует только если apply прервали между шагами 9 и 15 §2: отключение питания, `kill -9`, отменённый RPC после переключения. Зафиксированное обновление не оставляет активного испытания. Поскольку `exhausted` — `boots >= 2`, а `arm` записывает `boots = 0`, *первый* старт `updaterd` после прерывания пишет «update still on trial», *второй* возвращает старый выпуск.

**Все шаги предполагают запускающийся `updaterd`.** Если не выполняется ни один, при загрузке есть ещё один механизм: через 180 s `robot-boot-check.timer` проверяет `robotd`, `configd`, `btd`, `updaterd` и передаёт управление `/bin/sh`-восстановлению, которое переключает `current` на golden и перезагружает. Оно намеренно находится вне всех описанных процессов. Его определяет [`boot-recovery-net.md`](boot-recovery-net.ru.md), включая причины выбора срока вместо `OnFailure=`.

<a id="5-the-startup-reconciliation-did-the-restarts-happen"></a>
## 5. Сверка при запуске: состоялись ли перезапуски?

<a id="5-the-startup-reconciliation--did-the-restarts-happen"></a>
Успех `systemd-run` означает создание временного таймера, но не выполнение перезапуска и не успешный старт нового бинарника. Шаг 16 §2 намеренно не возвращает эти ошибки. Так остаётся молчаливый путь к роботу, исполняющему не установленный выпуск, причём у двух служб без другого наблюдателя. Его закрывает `updater/src/reconcile.rs`.

<a id="what-it-reads"></a>
### Что читается

Каждая служба публикует свою идентичность при запуске через `duck_ipc_proto::publish_identity`, вызываемый начальным макросом `log_startup_identity!`:

```
/run/<service>/identity.json    { service, version, revision, built_at, exe, pid }
```

Поле `exe` берётся из `/proc/self/exe`, поэтому разрешается через `current` и называет фактический каталог выпуска запуска. `Identity::release()` извлекает компонент `releases/<ver>`.

Служба публикует сама, а не читается снаружи: процесс знает свою версию и ревизию и читает свой `exe` без привилегий, тогда как чужой требует root. `RuntimeDirectory=<service>` создаёт каталог владельца `User=`, работает с `ProtectSystem=strict` и **удаляется systemd при остановке службы**. Поэтому остановленный процесс не оставляет ложного заявления о работе.

<a id="what-it-decides"></a>
### Какие решения принимаются

Для каждого компонента и unit в `units_shipped` (§1), включая `updaterd` и `btd`, опубликованный выпуск сравнивается с активным. `verdict_for` — чистая функция; системные вызовы находятся снаружи.

| Вердикт | Условие | Действие |
|---|---|---|
| `Current` | Опубликованный выпуск равен активному. | Ничего, без сообщения. |
| `Restarted` | Они различаются. | `systemctl restart <unit>`, запись `warn`. |
| `ReportedOnly` | Различаются, **unit — `updaterd`**. | Только запись, без действия. |
| `RestartFailed` | Перезапуск предпринят и не удался. | Запись `error`. |
| `Unknown` | Файла идентичности нет. | Ничего. |

Три намеренных бездействия:

- **`updaterd` здесь никогда не перезапускает себя.** Новый процесс с другим представлением об активном выпуске перезапускался бы снова и снова. Цикл возник бы в единственном владельце восстановления, и разорвать его было бы некому. Только сообщить безопасно: процесс только что стартовал, и причина его несоответствия возникла до этого кода. Исправление приходит с другой стороны, см. ниже.
- **Остановленная служба остаётся остановленной.** Нет файла идентичности — либо остановлена, либо слишком стара для публикации. Запуск переопределял бы решение оператора при каждом старте `updaterd`.
- **Ничего не опубликовавшая служба не считается несоответствующей.** Перезапуск лишь за старость никто не запрашивал; следующее обновление научит её отвечать.

Сравнение не зависит от направления: любое различие означает несоответствие. Поэтому оно покрывает и процесс, оставшийся *новее* `current` после явного отката, а не только старее.

Проверка выполняется при каждом старте `updaterd`; при обычной загрузке ничего не делает, поскольку все стартовали по одной ссылке. Цена — одно чтение файла на unit.

<a id="the-same-reading-from-apply"></a>
### То же чтение из `apply`

`reconcile::stale_units` применяет `verdict_for` к тем же файлам без выполнения действий. `apply` и `select` вызывают её на пути already-current (§2). Это необходимо из-за исключения выше: несоответствующий `updaterd` — единственный случай, который модуль не исправляет. Позже на него посмотрит только человек, запускающий apply из-за подозрительной работы. Раньше ответ `already_current` ничего не планировал и выглядел подтверждением отсутствия проблемы.

Два свойства предотвращают цикл, от которого защищает §5: запуск по запросу, а не при каждом старте; планирование через `systemd-run`, а не прямой `systemctl` из перезапускаемого процесса. Действие сопровождается отчётом: службы перечислены в исходе `already_current`, чтобы `robotctl` или приложение видели, кто не исполнял установленный выпуск.

Оба вердикта несоответствия (`Restarted` и `ReportedOnly`) здесь считаются stale: различие касается только права выполнять перезапуск, не сути ошибки. Остальные правила таблицы прежние: остановленная и ничего не опубликовавшая службы не stale.

<a id="6-first-install"></a>
## 6. Первая установка

`scripts/install.sh` на чистой плате, порядок `main`:

1. Записать `/etc/robot/updater.toml` и доверенные ключи.
2. `bootstrap_first_release`: получить отдельный `updaterd` и выполнить `updaterd install [--from <dir>]`. Это обычный `Engine::apply` с двумя принудительными настройками, которые на пустой плате являются фактами: `on_apply = none`, поскольку unit находятся внутри устанавливаемого выпуска; `health = none`, поскольку проверять `robotd` ещё нельзя. §2 выполняется без шагов 12, 13, 14, но **шаг 11 сохраняется**: `hooks/postinstall` устанавливает unit и делает `enable --now` каждому с `[Install]`. Именно внутри хука службы запускаются впервые. Шаг 16 тоже сохраняется: начальная установка назначает перезапуски `updaterd` и `btd` через 5 s, пока `install.sh` ещё работает.
3. `install_units`: снова скопировать unit, выполнить `daemon-reload`, затем `enable --now` для `updaterd`, `robotd`, `configd`, `btd`, `padd`, `mediad` в этом порядке. `configd` раньше `btd`, поскольку тот спрашивает PIN; `mediad` последним из-за `After=` трёх других. Ошибки `btd`, `padd`, `mediad` не проваливают установку: без радио, геймпада или камеры робот всё ещё обновляется и ходит. Затем включить `robot-boot-check.timer` *без* `--now`. Это безвредно повторяет хук и также поддерживает более старый выпуск без него. Неизвестный функции unit выпуска устанавливается, отмечается и остаётся без действий. `tofd` известен, но отдельного `enable_unit` нет: хук уже включил его, зависимостей от него нет, определять порядок незачем.
4. `install_token_dropin`: записать drop-in `GITHUB_TOKEN`, выполнить `daemon-reload` и `systemctl try-restart updaterd`. Одного reload недостаточно: уже *работающий* `updaterd` каждой платы остался бы без токена.

`DUCK_FORCE_REINSTALL=1` добавляет перед шагом 2 `stop_for_reinstall`: `systemctl stop` для `padd`, `tofd`, `btd`, `configd`, `robotd`, `updaterd` именно в этом порядке. Во время переключения ничего не работает; проверки работоспособности после него нет.

<a id="7-diagnosing-a-skew"></a>
## 7. Диагностика расхождения

Два разных номера версии одновременно могут быть нормой; диагноз зависит от конкретной пары.

| Наблюдение | Значение |
|---|---|
| `updaterd` или `btd` старее установленного выпуска несколько секунд после обновления. | Ожидаемо: отложенный перезапуск ещё не сработал. |
| `btd`, `robotd`, `configd`, `padd`, `mediad` или `tofd` устойчиво отличаются от `current`. | Перезапуск не подействовал **и** §5 не исправил ситуацию. Значит `updaterd` ещё не стартовал после этого либо перезапуск службы не удался; журнал уровня `error`. |
| `updaterd` устойчиво старее. | Отложенный перезапуск не состоялся; §5 его не исправляет. `robotctl update apply daemon` сообщит `already_current`, включит `updaterd` в `stale` и назначит перезапуск. `systemctl restart updaterd` — то же вручную. Причина первоначальной неудачи в журнале. |
| Любая служба сообщает `restarting`. | Процесс завершился, systemd возвращает его. Несколько секунд после обновления — сам перезапуск. Постоянно — полная неспособность стартовать; пример — `mediad` с отключённым шлейфом камеры. §5 её не трогает: у неработающей службы нет идентичности. Причина в `journalctl -u <name> -b`. |
| Любая служба сообщает `failed`. | Не смогла запуститься, systemd прекратил попытки. Тот же журнал; в отличие от `stopped`, это никто не выбрал. |
| Любая служба сообщает `build unknown`. | Работает, но не опубликовала идентичность: старая сборка либо мгновение между `exec` и первой строкой. §5 оставляет её. Одно обновление научит старую сборку отвечать. |

Спрашивайте робота, а не делайте выводы косвенно:

```bash
robotctl health
```

Блок `units` выводит выпуск, из которого запущен процесс каждой службы, и предупреждает о несовпадении с установленным.

Вручную тот же ответ из опубликованного службой файла:

```bash
cat /run/configd/identity.json; readlink /opt/robot/daemon/current
```
