# Минимальная конфигурация, в которой геймпад создаёт сопряжение

Записано 2026-08-18 на Radxa Zero 3W `50:37:CD:16:2A:39` с Xbox Wireless Controller `78:86:2E:92:47:67`. Подтверждено на второй Zero 3W с той же картой.

<a id="the-sequence-that-works"></a>
## Рабочая последовательность

Запишите Armbian для Radxa Zero 3, Minimal. В программе записи укажите Wi-Fi и имя пользователя. Больше ничего не устанавливайте: ни служб, ни подготовки окружения.

```bash
sudo sed -i -E 's|^[[:space:]]*#?[[:space:]]*Privacy[[:space:]]*=.*|Privacy = device|' /etc/bluetooth/main.conf
```

```bash
grep -n "^Privacy" /etc/bluetooth/main.conf
```

```bash
sudo reboot
```

Нужна перезагрузка, а не `systemctl restart bluetooth`: перезапуск иногда оставляет hci0 занятым ядром с `No default controller available`; помогает только перезагрузка.

Удерживайте кнопку сопряжения геймпада до быстрого мигания, затем:

```bash
bluetoothctl
```

```
scan on
```

Дождитесь `[NEW] Device 78:86:2E:92:47:67 Xbox Wireless Controller`, затем:

```
scan off
```

```
connect 78:86:2E:92:47:67
```

Ответьте `yes` на `Request authorization`, затем:

```
trust 78:86:2E:92:47:67
```

Команду `pair` ни разу не вводят.

<a id="what-it-looks-like-when-it-worked"></a>
## Признаки успеха

```bash
ls /dev/input/js*
```

```bash
dmesg | tail -3
```

```
input: Xbox Wireless Controller as /devices/virtual/misc/uhid/0005:045E:0B13.0001/input/input5
microsoft 0005:045E:0B13.0001: input,hidraw0: BLUETOOTH HID v5.09 Gamepad [Xbox Wireless Controller]
```

Проверка реального потока ввода: всё время двигайте левый стик и после первых 184 байтов ищите события с `type 0x02` и растущими временными метками:

```bash
sudo timeout 5 cat /dev/input/js0 | od -Ad -tx1 | head -20
```

Сопряжение переживает выключение геймпада: удерживайте Xbox около 6 с, затем включите снова:

```bash
ls /dev/input/js*; bluetoothctl info 78:86:2E:92:47:67 | grep -E "Connected|Bonded|Trusted"
```

<a id="the-board-it-worked-on"></a>
## Плата, на которой это работало

Конфигурация оказалась неожиданной, поэтому каждый пункт записан:

| | |
|---|---|
| `cat /sys/module/aic8800_bsp/srcversion` | `738316A2E9D9825966BDB6B` (86016) |
| `conn_min_interval` / `conn_max_interval` | 24 / 40 — значения ядра по умолчанию, 30–50 мс |
| `/etc/bluetooth/main.conf` | `Privacy = device` |
| Запущенные службы | Нет |

Это сборка драйвера, названная неисправной в `design/pad-bond-failure.md`. Интервал соединения не менялся. Ни один из них не определяет возможность сопряжения.

<a id="what-has-failed"></a>
## Что не сработало

| Конфигурация | Результат |
|---|---|
| Чистый Armbian, `Privacy = off` либо не задано — BlueZ по умолчанию использует `off` | `connect` возвращает `le-connection-abort-by-local`; `Paired: no`; обмена SMP вообще нет |
| Чистый Armbian, строка `Privacy` отсутствует, сначала `pair`, а не `connect` | Сопрягается, затем каждое повторное соединение падает с `Encryption Change: PIN or Key Missing (0x06)`, переключаясь примерно раз/с |
| Подготовленная плата, `Privacy = device` подтверждено в строке 99, `padd` и `btd` остановлены, ручной `connect` | `Request authorization` принят, затем `ServicesResolved: no`; геймпад сразу отключается, `js0` нет |

Третья строка остаётся открытой: тот же образ карты и то же `Privacy` перестают работать после подготовки платы. Значит, причина в изменениях установки, а не просто работающем процессе: остановка `padd` и `btd` не вернула сопряжение.

<a id="making-a-bond-and-keeping-one-are-different"></a>
## Создать сопряжение и сохранить его — разные задачи

На полностью подготовленной плате со всеми работающими службами **уже сопряжённый** геймпад подключается и управляет роботом. **Новое** `robotctl pad pair` после `pad forget`, когда геймпад находится в режиме сопряжения, не срабатывает.

Ничто здесь не ломает существующую пару. Что-то в установленной системе мешает создать новую. Журналы `configd` и `btd` ничего полезного не сообщают.

<a id="tomorrow-add-one-thing-at-a-time"></a>
## Следующий день: добавлять по одному изменению

Начав с заново прошитой платы, на которой проверена последовательность в начале страницы, добавляйте один слой, перезагружайтесь и проверяйте новое сопряжение перед следующим.

Копируйте скрипты в `~`, **не** в `/tmp`: каждый шаг перезагружает плату, а `/tmp` её не переживает. То же относится к ценным записям `btmon`.

```bash
scp scripts/setup-board.sh scripts/migrate-network.sh pierre@BOARD:~/
```

| Шаг | Что добавлено | Сопряжение работает? | Примечания |
|---|---|---|---|
| 0 | Ничего — минимальная последовательность выше | Да | Контрольная конфигурация |
| 1 | `sudo sh ~/setup-board.sh` — overlays, `console=display`, маска getty, onnxruntime | **Да** | |
| 2 | `sudo sh ~/migrate-network.sh` — netplan → NetworkManager | **Да** | |
| 3 | `sudo -E sh ~/install.sh` | **Нет** | Первые попытки; службы работали |
| 3b | `DUCK_NO_START=1`, затем перезагрузка | **Да** | Значит, записанные install.sh файлы не виноваты |
| 4 | `systemctl enable --now updaterd` | | |
| 5 | `... robotd` | | |
| 6 | `... configd` | | |
| 7 | `... btd` | | |
| 8 | `... padd` | | |

Проверено 2026-08-19: на каждом шаге ручное сопряжение через `bluetoothctl`, затем удаление геймпада. Шаги 1 и 2 работают; сбой начинается с `install.sh`. Подготовка платы, overlays device tree, перенос консоли и переход на NetworkManager исключены.

Разделение внутри `install.sh` 2026-08-19: с `DUCK_NO_START=1` и перезагрузкой геймпад сопрягается. Не виноваты файлы на диске: unit, пользователи, группы, дерево выпуска и drop-in токена. Причина — одна из пяти работающих служб.

До получения результата три попытки измерения были потрачены впустую по одной причине: `hooks/postinstall` внутри выпуска выполняет `systemctl enable --now` для каждого unit во время `updaterd install`, *до* `install_units`. Службы работали при каждом тесте, а последующее `systemctl disable --now` не отменяет их изменений адаптера. `btd` оставляет `Pairable`, экземпляр advertising и IO capability от своего агента сопряжения по умолчанию. **Перед измерением перезагружайтесь.**

<a id="it-is-btd"></a>
## Причина — `btd`

2026-08-19, одна переменная, воспроизводится в обе стороны на `2A:39`:

| | |
|---|---|
| `btd` включён, перезагрузка, сброс геймпада, новое сопряжение | **Ошибка** |
| `btd` выключен, перезагрузка, сброс геймпада, новое сопряжение | **Работает** |

Для успешного запуска `/var/lib/bluetooth` **не** очищали. Поэтому оба файла, запись которых в BlueZ вызывает `btd`, — `attributes` с локальной GATT-базой и `identity` с локальным IRK адаптера — исключены, как и всё прочее сохранённое состояние.

Более ранняя попытка, в которой отключение `btd` *не* помогло, была испорчена слотом сопряжения самого геймпада. Xbox хранит одну пару с хостом; незавершённая попытка оставляет ключ, которого у платы уже нет. **Между попытками сбрасывайте геймпад на ноутбуке**, иначе неисправность неотличима от испорченного состояния пары. На это ушла большая часть двух дней.

Работающие процессы не мешают существующей паре: сопряжённый геймпад подключается и управляет при полностью работающем стеке. Ошибка возникает только при *создании* пары.

<a id="the-mechanism-not-yet-measured"></a>
### Механизм пока не измерен

`btd` непрерывно объявляет себя периферийным устройством. С `Privacy = device` используется разрешаемый приватный адрес, пока тот же адаптер действует как central для сопряжения геймпада. Проверка SMP DHKey вычисляется по адресам обоих устройств: такая конфигурация соответствует `DHKey check failed (0x0b)`, из-за которой дерево когда-то отказалось от `Privacy = device`, хотя тогда работал `btd`. Разобраться позволит запись неуспешного сопряжения `btmon` с типом собственного адреса и причиной SMP.

<a id="two-faults-and-they-were-being-read-as-one"></a>
### Две ошибки принимали за одну

Повторно проверено со сброшенным геймпадом, поэтому результаты не зависят от испорченного слота пары:

1. **Различие плат.** На чистом Armbian без установок некоторые Zero 3W сопрягаются при стандартном BlueZ `Privacy = off`. Другие с `off` не сопрягаются вообще, работает только `device`. Примерно половина из десяти в каждой группе; измеримой разницы между ними не найдено.
2. **`device` и `btd`.** При `device` геймпад не создаёт новую пару, пока `btd` ведёт advertising.

Вместе они объясняют первоначальное `DHKey check failed (0x0b)`, приведшее к `Privacy = off`: ошибка 2 на плате, которой нужен `device` из-за ошибки 1, была воспринята как доказательство поломки сопряжения режимом `device`. В итоге две недели половина плат не могла сопрягать геймпад.

Одной остановки `btd` недостаточно: внесённое в контроллер состояние переживает процесс, поэтому каждая успешная ручная попытка включала **перезагрузку** после остановки. Перезапуск питания адаптера (`bluetoothctl power off && power on`) заменяет её: измерено 2026-08-19, `pad pair` прошёл с первого раза на полностью установленной плате. Благодаря этому сопряжение остаётся одной командой.

Оба обходных решения включаются через `provision-board.sh --weird-ble`, чтобы не затрагивать платы, которым они не нужны. Флаг устанавливает `Privacy = device` и оставляет `/var/lib/robot/weird-ble`; `robotctl pad pair` приостанавливает `btd` только при этом маркере. Сначала пробуйте без флага. Оба решения уйдут вместе с aic8800.

Перезагружайтесь после каждого шага и очищайте **обе** стороны пары перед попыткой: `pad forget` либо `bluetoothctl remove` на плате, геймпад — в режиме сопряжения. Xbox хранит одну пару с хостом; незавершённая попытка оставляет ключ без пары на плате и выглядит точно как сама ошибка.

Шаг 3 требует переменных окружения, читаемых `install.sh`:

```bash
export DUCK_TOKEN=github_pat_replace_with_your_token
```

```bash
export DUCK_REF=pad-privacy-device-not-off
```

```bash
export DUCK_DEV_KEY=$HOME/team.dev.pub
```

Шагам 1 и 2 не нужны ни токен, ни сеть.

<a id="untested-differences-against-microduckruntime"></a>
## Непроверенные различия относительно `microduck_runtime`

Установщик `microduck_runtime` отключает энергосбережение Wi-Fi на активном соединении NetworkManager (`install.sh:244`, `:383`):

```
sudo nmcli con mod "$WIFI_CON" wifi.powersave 2
```

В `scripts/` эквивалента нет. aic8800 объединяет Wi-Fi и Bluetooth с общим радио через SDIO; это возможная причина третьей строки выше. Но значение на работавшей чистой плате не прочитали: это кандидат, а не установленный факт.

```bash
iw dev wlan0 get power_save
```

<a id="fault-3-a-bonded-pad-cannot-reconnect-while-a-phone-is-connected-measured-2026-09-17"></a>
## Ошибка 3: сопряжённый геймпад не может подключиться, пока подключён телефон · **измерено** (2026-09-17)

<a id="fault-3-a-bonded-pad-cannot-reconnect-while-a-phone-is-connected---measured-2026-09-17"></a>
Две ошибки выше касаются *создания пары*. Эта — повторного подключения, она отдельная и первой встречается пользователю приложения телефона.

На `lavandiere`, подготовленной с `--weird-ble`, то есть `Privacy = device`, с уже сопряжённым доверенным Xbox:

| | |
|---|---|
| Приложение подключено, геймпад включают | Геймпад так и не подключается |
| Приложение закрыто, геймпад включают | Подключается немедленно |
| Сначала геймпад, затем приложение | **Работают оба** |

Причина не в паре и не в геймпаде. Первое соединение сохраняется, второе можно добавить, но *новое* central-соединение нельзя начать, пока `btd` держит peripheral-соединение.

Явное подключение с платы сообщает причину вместо простого тайм-аута:

```
Failed to connect: org.bluez.Error.Failed le-connection-abort-by-local
```

Это отказ локального хоста, а не геймпада. Обычно этот вызов делает фоновое автоматическое подключение BlueZ для доверенного устройства; оно падает так же, поэтому геймпад просто остаётся без связи.

**В это время `btd` не ведёт advertising.** Он останавливает его при подключённом central; поэтому `duckctl scan` не видит робота, с которым говорит чей-то телефон. Это не повтор ошибки 2: advertising выключен, а инициация всё равно не работает. Вероятнее, контроллер отказывается быть инициатором, пока он peripheral, чем причина в решениях служб.

<a id="what-is-not-worth-building"></a>
### Что не стоит реализовывать

Очевидное решение — опрашивать доверенный, но отключённый геймпад в `configd` или `padd` и подключать его — **не работает**, поскольку это ровно вызов, возвращающий ошибку выше.

Два рабочих варианта для этого радио невыгодны. `btd` мог бы рвать связь при запросе геймпада, превращая телефон в случайно отключающееся устройство; при этом он не может узнать, что геймпад запрашивает связь. Либо сопряжение и повторное подключение можно проводить последовательностью из приложения с намеренным разрывом связи — значительная работа для микросхемы, которую вся эта страница предлагает заменить.

<a id="what-to-do-instead"></a>
### Что делать

**Включайте геймпад до открытия приложения.** Оба работают; весь обходной способ — порядок. `pad.status` отдельно сообщает `paired` и `connected`, поэтому клиент видит состояние «сопряжён, доверен, не подключён» и может объяснить его, вместо повторных нажатий Xbox возле игнорирующего робота.

Как и две другие ошибки, эта уйдёт вместе с aic8800.
