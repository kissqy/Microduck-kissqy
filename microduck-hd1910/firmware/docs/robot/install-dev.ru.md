# Установка на плату разработчика

Подготовка платы с нуля до робота, на который можно отправлять сборки веток.

Плата разработчика доверяет командному ключу разработки, поэтому устанавливает любую сборку любого участника команды. Пользовательский робот настроен иначе и намеренно отклоняет такие сборки. Всё ниже относится к плате разработчика, а не к пользовательскому роботу.

Для сборки разработки проверки не ослабляются: те же подписи и хеши, тот же контроль работоспособности и автоматический откат. Отличается только ключ подписи. Это и не пускает такие сборки на пользовательских роботов: они защищены от ключа разработки двумя условиями. `allow_dev_keys = false`, а доверенный ключ считается ключом разработки только при имени файла, заканчивающемся на `.dev.pub`. Две части настройки ниже меняют именно эти условия.

<a id="flash-the-board"></a>
## Запись образа на плату

Используйте [Armbian imager](https://www.armbian.com/radxa-zero-3/). Выберите **Radxa Zero 3**, затем **Armbian 26.2.1 Minimal**.

Перед записью заполните профиль в imager: сеть Wi-Fi и пароль, желаемое имя пользователя и пароль. Это избавит от последовательной консоли: при первой загрузке плата подключится к вашей сети и сразу станет доступна по SSH.

Затем добавьте SSH-ключ, чтобы подготовка системы могла переподключиться после перезагрузки платы:

```bash
ssh-copy-id microduck@192.168.1.42
```

<a id="what-you-need"></a>
## Что понадобится

- **IP-адрес** платы. mDNS в этом образе ненадёжен, поэтому имя `.local` разрешается не всегда. `duckctl ip` спрашивает адрес у робота по Bluetooth без собственной сети и просмотра DHCP-аренды. Если плата ещё не передаёт рекламные объявления, запасной вариант — таблица аренд маршрутизатора.
- **Доступ по SSH-ключу**, настроенный выше. Подготовка перезагружает плату и переподключается автоматически; запрос пароля этому мешает.
- **Токен GitHub**, пока репозиторий закрыт: без него недоступны файлы выпусков. После открытия репозитория токен необязателен и даёт только увеличенный лимит API (`docs/design/updater-design.md` §6.1).
- **Клон этого репозитория**. Нужный открытый ключ разработки уже включён в `deploy/dev-key/team.dev.pub`, поэтому запрашивать его у кого-либо не требуется.

<a id="install"></a>
## Установка

Две команды из клона на своём компьютере:

```bash
export DUCK_TOKEN=github_pat_replace_with_your_token
```

```bash
./scripts/provision-board.sh --pause-btd-on-pair --name <MY_COOL_ROBOT_NAME> microduck@192.168.1.42
```

Они отправляют ключ разработки, запускают подготовку, дожидаются перезагрузки, передают журнал и завершаются командой `robotctl health`.

<a id="why---pause-btd-on-pair-is-in-that-command"></a>
### Почему в команде есть `--pause-btd-on-pair`

На радиомодуле aic8800 геймпад не может создать **новое** сопряжение, пока `btd` передаёт рекламные объявления. Флаг оставляет маркер, по которому `robotctl pad pair` останавливает `btd` и выключает/включает адаптер на время окна сопряжения, затем снова запускает службу. Существующее сопряжение не страдает: уже сопряжённый геймпад подключается и управляет при работающем полном стеке. Цена обходного решения — недоступность одной службы на время сопряжения.

Здесь этот флаг выбран по умолчанию: если нуждающуюся в нём плату подготовить без него, симптомом станет несопрягающийся геймпад, а все правдоподобные причины, которые обычно проверяют сначала, будут в других местах.

<a id="the-three-configurations-and-how-to-tell-which-you-have"></a>
### Три конфигурации и определение нужной

Есть две независимые неисправности и поэтому два флага. **Сопрягите геймпад и прочитайте ошибку**, затем выберите вариант:

| Наблюдение | Что нужно плате |
|---|---|
| Геймпад сопрягается и управляет. | Ничего: подготовка без флагов. |
| Геймпад не сопрягается; последний шаг SMP не завершается. | `--pause-btd-on-pair`. |
| Геймпад не сопрягается даже при остановленном `btd`. | `--weird-ble` (включает паузу и добавляет `Privacy = device`). |
| Геймпад сопрягается, затем **постоянно переподключается**: `PIN or Key Missing (0x06)`, устройства ввода нет. | `--weird-ble` этой плате не подходит: уберите его, оставьте паузу. |

Особенно важна последняя строка. `Privacy = device` на плате, которой нужна только пауза, создаёт сопряжение, немедленно перестающее работать. Это сложнее диагностировать, чем явную невозможность сопряжения. Измерено на `50:37:CD:16:1D:90`: `off` с паузой даёт устойчивое сопряжение, а `device` вызывает 46 переподключений за 45 секунд. Поэтому `--weird-ble` больше **не** используется по умолчанию.

Переход с `--weird-ble` на одну паузу с сохранением маркера:

```bash
sudo sed -i 's/^Privacy = device/Privacy = off/' /etc/bluetooth/main.conf && sudo reboot
```

Обратный переход через копию скрипта, оставленную подготовкой на плате:

```bash
sudo DUCK_WEIRD_BLE=1 /usr/local/sbin/robot-setup-board && sudo reboot
```

Чтобы проверить, не обходится ли плата без обоих механизмов, отключите их и сопрягите геймпад:

```bash
sudo rm /var/lib/robot/weird-ble
sudo sed -i '/^Privacy = /d' /etc/bluetooth/main.conf && sudo reboot
```

После каждого изменения `Privacy` выполняйте сопряжение заново: меняется адрес, для которого получены сохранённые ключи, поэтому старые пары перестают совпадать и переподключаются с `PIN or Key Missing`, пока их не создать заново.

Все эти меры обходят особенности aic8800, а не являются свойством архитектуры; с заменой радиомодуля они больше не нужны. Подробности — в [`pair-a-gamepad.md`](pair-a-gamepad.ru.md).

Запущенная на компьютере команда — **просмотрщик**, а не исполнитель работы. Подготовка устанавливает systemd-службу, возобновляющуюся при загрузке, поэтому плата завершит работу независимо от того, наблюдаете ли вы за ней. Ctrl-C ничего не нарушает; журнал можно открыть снова:

```bash
ssh -t microduck@192.168.1.42 'sudo tail -f /var/lib/robot/provision.log'
```

`--ref BRANCH` подготавливает систему из ветки: её скрипты выполняют настройку платы, поверх устанавливается её сборка службы. `golden` остаётся стабильным выпуском — это резерв для восстановления при загрузке. Если сделать golden сборкой ветки, неисправная ветка получит такой же неисправный резерв. `current` при этом указывает на ветку.

Подготовка **завершается ошибкой**, если сборка не устанавливается или устанавливается, но затем откатывается проверкой работоспособности. Самый трудный случай диагностики — плата, молча оставшаяся на стабильном выпуске, хотя запросили ветку: всё выглядит установленным, а проверяемого кода нет. Дайте CI минуту-две перед подготовкой; при остановке проверьте `gh run list --branch BRANCH`. `--name` применяется перед сборкой ветки, поэтому имя останется даже после ошибки на этом этапе.

Другие полезные флаги: `--name Ducky` задаёт имя вместо вычисленного из серийного номера `duck-7f3a` (позже его можно изменить через `robotctl system set-name`, флаг лишь экономит команду); `--local` отправляет `provision.sh` из текущего клона вместо загрузки из сети (так проверяют изменения скриптов до слияния); `--no-dev-key` делает плату, принимающую только релизы.

<a id="check-it-worked"></a>
## Проверка результата

```bash
robotctl health
```

Плата считается платой разработчика, только если ключ действительно установлен. Это можно проверить, а не держать в памяти:

```bash
grep -c 'DEV BOARD' /var/lib/robot/provision.log
```

`1` означает, что ключ есть. `0` — ключ не установлен, и позднее `--ref` будет отклонён с ошибкой, похожей на повреждённый выпуск. Проверка помогает обнаружить именно эту проблему заранее.

Затем настоящая проверка — установите сборку ветки:

```bash
sudo robotctl update apply --ref main daemon
```

<a id="when-ssh-refuses-to-connect-after-a-reflash"></a>
## SSH отказывается подключаться после перезаписи образа

Запись нового образа заново создаёт ключи хоста платы, поэтому прежний адрес теперь предъявляет другой ключ. `StrictHostKeyChecking=accept-new` здесь не помогает: новым является ключ, а не хост. Исходная ошибка SSH в таком случае — большой текст о возможной атаке.

```bash
./scripts/provision-board.sh microduck@192.168.1.42 --forget-host-key
```

Это особенно важно из-за повторного использования DHCP-аренд: адрес прошлой недели сегодня может принадлежать другой плате с другим ключом.

<a id="when-the-board-comes-back-at-a-different-address"></a>
## Плата возвращается с другим адресом

Переключение Wi-Fi посреди подготовки может выдать плате не тот адрес, который был указан вначале. `provision-board.sh` ищет её: ожидая SSH, он одновременно спрашивает новый адрес у робота по Bluetooth и начинает использовать ответ.

```
  bluetooth: the robot reports 192.168.1.57, and 192.168.1.42 was its old lease.
```

Делать ничего не нужно: дальнейшая работа продолжается по этому адресу.

Есть три препятствия, о которых скрипт сообщает:

- Нужны `cargo` и этот клон, поскольку `duckctl` здесь запускается как пример, а не установленный исполняемый файл.
- Запрос возможен только после запуска `btd`; на впервые подготавливаемой плате это происходит через несколько минут после начала фазы 2.
- Робот сообщает адрес **Wi-Fi**, поэтому доступная по Ethernet плата этим механизмом не покрывается.

`--no-ble` отключает функцию. Если роботу задан собственный PIN сопряжения, укажите его в `DUCK_PIN`.

<a id="making-an-existing-board-take-dev-builds"></a>
## Разрешение сборок разработки на существующей плате

Для платы, подготовленной иначе или до получения ключа. Нужны обе части настройки: каждая по отдельности оставляет запрет на сборки веток.

Проще всего повторить установщик с ключом: он проверит его и переключит флаг за один шаг:

```bash
sudo DUCK_TOKEN="$DUCK_TOKEN" DUCK_DEV_KEY=/tmp/team.dev.pub sh /tmp/install.sh
```

Независимо от исходного имени файл устанавливается как `team.dev.pub`. Имя важно: вставка `.dev.` классифицирует ключ как ключ разработки; под другим именем он считается доверенным ключом **релиза**.

Вручную, если нужно видеть каждый шаг:

```bash
sudo cp team.dev.pub /etc/robot/trusted_keys/team.dev.pub
```

```bash
sudo sed -i 's/^allow_dev_keys.*/allow_dev_keys        = true/' /etc/robot/updater.toml
```

```bash
sudo systemctl restart updaterd
```

<a id="the-token-by-hand"></a>
## Ручная настройка токена

`scripts/install.sh` делает это сам при переданном `DUCK_TOKEN`. Следующие шаги нужны для платы, подготовленной иначе, и только пока репозиторий закрыт либо плата загружает достаточно часто, чтобы требовался повышенный лимит токена.

`updaterd` читает `GITHUB_TOKEN` из собственного окружения. Экспорт переменной в вашей оболочке не передаёт её службе: нужен systemd drop-in.

```bash
sudo mkdir -p /etc/systemd/system/updaterd.service.d
```

В следующем блоке подставьте свой токен — это единственный заполнитель:

```bash
sudo tee /etc/systemd/system/updaterd.service.d/token.conf > /dev/null <<'EOF'
[Service]
Environment=GITHUB_TOKEN=ghp_replace_with_your_token
EOF
```

Drop-in по умолчанию доступен на чтение всем, а этот содержит учётные данные:

```bash
sudo chmod 600 /etc/systemd/system/updaterd.service.d/token.conf
```

```bash
sudo systemctl daemon-reload
```

```bash
sudo systemctl restart updaterd
```

Токен на плате *разработчика* допустим. На пользовательском роботе — нет: общие для всего парка учётные данные в образе невозможно сменить без перезаписи. Поэтому решение — открытый репозиторий, а не поставляемый токен (`docs/design/updater-design.md` §6.1). Плата без токена всё равно может устанавливать из локального каталога или через dev push.

<a id="installing-without-a-network"></a>
## Установка без сети

Если на плате уже есть выпуск, установите локальный каталог обычным способом: через службу, с проверкой работоспособности и автоматическим откатом:

```bash
sudo robotctl update apply daemon --from /media/usb/release
```

Этим же заканчивается `scripts/dev-push.sh`; путь от ноутбука к плате описан в [`dev-push.md`](dev-push.ru.md).

Остальная часть раздела посвящена **чистой плате**: заводской или автономной установке до появления службы, к которой можно обратиться. Поэтому используется `updaterd`, а не `robotctl`; `updaterd` намеренно отсутствует в `PATH`:

```bash
sudo /opt/robot/daemon/current/bin/updaterd install --from /media/usb/release
```

Каталог содержит состав выпуска: `<version>.manifest.json`, его `.minisig`, артефакт и `.minisig` артефакта. Подписи, хеши и совместимость проверяются так же, как после скачивания. `--from` меняет источник байтов, а не правила доверия.

Команда отказывается работать после активации выпуска, поскольку принудительно отключает `on_apply` и проверку работоспособности; для работающего робота это означало бы молчаливую потерю автоматического отката. Но есть ситуация, когда это необходимо и `robotctl update apply` не помогает: установленный `updaterd` слишком стар для выпуска, который *исправляет* эту несовместимость. Он каждый раз откатывает новую версию, а проверку выполняет именно тот файл, который заменяется. Остановите робота и явно подтвердите такой режим:

```bash
sudo systemctl stop robotd
```

```bash
sudo /opt/robot/daemon/current/bin/updaterd install --from /media/usb/release --force
```

Сам `--force` отклоняется, пока отвечает `robotd`, поскольку речь о потере защиты *работающим* роботом. Он отключает автоматический откат только для данной установки и ничего больше: подписи, хеши и совместимость продолжают проверяться. Если выпуск работает неправильно, путь восстановления — `sudo robotctl update rollback daemon`.
