# Дорожная карта

Статус: переписано · Дата: 2026-08-26, первоначально 2026-08-05 · Ответственный: pierre

Дополнение к [`architecture.md`](../design/architecture.ru.md), описывающему создаваемую систему, и [`updater-design.md`](../design/updater-design.ru.md), описывающему её поставку. Здесь *порядок и последовательность работ*: они будут меняться, в отличие от проектных документов.

> Примечание переводчика: это историческая дорожная карта upstream. Разделы дополнялись в разное время и сохраняют одновременно выполненные пункты и более ранние формулировки «не реализовано», особенно в M8. Они не определяют текущую готовность адаптации HD1910; её версии и проверки приведены в [базовой версии выпуска](../../../docs/BASELINE.ru.md).

<a id="the-first-roadmap-reached-its-target"></a>
## Первая дорожная карта достигла цели

M1–M4 были единой последовательностью к одной цели: робот ходит, обновляется по воздуху и не превращается при этом в «кирпич». Цель достигнута. Каждый выпуск после `0.2.0` прошёл через механизмы M1 и M2, а `0.9.x` — утка, которая ходит, кувыркается, видит, говорит и поёт.

Дальше не продолжение очереди: оставшаяся работа — независимые направления с разными рисками без общего порядка, поэтому **числа ниже — идентификаторы, а не последовательность**. [Порядок работы](#the-order-of-work) выделен отдельно.

**Исходное утверждение было верно наполовину.** «Сложность в доведении до продукта, а не в возможностях» правильно оценивало трудность: обновление, здоровье, восстановление, BLE созданы и работают. Но объём оценён неверно: почти всё после `0.5` — возможности: кинематика, одометрия, ToF, взгляд, голос, хор, камера. Крупнейшая часть, автономный мозг, ещё не перенесена.

<a id="milestones"></a>
## Этапы

У каждого есть проверяемое условие готовности: без него этапы расплываются.

<a id="m1-close-the-loop-done"></a>
### M1 — Замкнуть контур · **готово**

<a id="m1--close-the-loop--done"></a>
Обновлятор получил настоящий объект контроля, команда — общие границы crate: каркас `robotd` с состоянием на атомиках вместо mutex, чтобы застрявший цикл мог ответить «я нездоров»; выделенный `duck-ipc-proto`, чтобы восстановление не линковало http/tar/crypto; настоящее сокетное измерение здоровья; единый путь сокета `robotd`; строка идентичности уровня `warn` до возможного сбоя каждой службы; первая установка обычным механизмом.

**Готово:** `robotd/tests/updater_gate.rs` проверяет обновление через настоящий сокет настоящего `robotd` и фиксирует; `robotd --unhealthy` откатывает содержимое `current`.

<a id="m2-dev-channel-done"></a>
### M2 — Канал разработки · **готово**

<a id="m2--dev-channel--done"></a>
`sudo robotctl update apply daemon --ref my-branch` ставит сборку ветки, `scripts/dev-push.sh` — сборку ноутбука по SSH вообще без CI. Два свойства обеспечены вне workflow: dev-сборка **не может стать `latest`**, поскольку версия — semver prerelease, а `version_under` отказывается читать dev-тег как выпуск; **не может установиться на клиентский робот**, где `allow_dev_keys` выключен, а dev-ключом считается только файл с окончанием `.dev.pub`.

**Готово:** проверено с настоящим репозиторием: `dev.yml` опубликовал сборку, `--ref main` установил её по сети, клиентская конфигурация отвергла ту же сборку.

**Открытый вопрос решён:** артефакты закрытого репозитория доступны с токеном, которого у клиентского робота нет; пока репозиторий закрыт, полевые роботы ничего не скачают. **Решено открыть его**, что устраняет проблему без изменения кода: путь API механизма работает и с открытыми репозиториями ([`updater-design.md`](../design/updater-design.ru.md), §6.1).

<a id="m3-robotd-for-real-done-in-two-slices"></a>
### M3 — Настоящий `robotd` · **готово**, в два шага

<a id="m3--robotd-for-real--done-in-two-slices"></a>
`robotd` **заменил** `microduck_runtime`, выделив ядро в `duck-control`, а не переписав его. Совпадение возможностей стало следствием выделения, не гонки с движущейся целью. Slice 1 — настоящий цикл Dynamixel 50 Гц с удержанием позы: `robot.health` означает *соблюдение сроков цикла*. Slice 2 — построитель наблюдений 61-D, основная и стоячая политики, API намерений и клиент геймпада.

**Полномочия безопасности появились здесь, а не в M6:** единственный записывающий дескриптор шины, поэтому ни политика, ни клиент *не могут* обойти ограничение суставов, переход в свободное состояние при падении и deadman намерений.

**Сначала оборудование, потом симуляция.** Плата выявила неуловимую тестами ошибку: `ort` *паникует*, а не возвращает ошибку для слишком старого runtime, убивая поток управления и искажая причину health.

**Готово:** все три условия на Radxa Zero 3W: ходьба через API намерений; чистый перезапуск после `robotctl` с успешной проверкой здоровья; самостоятельный откат нездорового выпуска.

<a id="m4-hardware-bring-up-closing"></a>
### M4 — Запуск оборудования · **завершается**

<a id="m4--hardware-bring-up--closing"></a>
Измерительный, а не функциональный этап: превращает догадки в числа на настоящей Radxa. Почти всё выяснилось при поставке: 50.0 Гц на ядре без RT (`missed=3` из 15022), ответы шины и `imu_to_dxl` на `/dev/ttyS2`, реальные температуры всех зон, работа `systemctl restart` в `on_apply`, настоящие фиксации и откаты.

**Сохранность журналов определена решением, не измерением.** `/var/log` в образе — zram; `Storage=persistent` создаёт journald каталог в памяти. Он переживает штатный `reboot`, но теряет недавние записи при обрыве питания. Это намеренно: устойчивый журнал обновлений находится в `/var/lib` с `fsync` каждой записи ([`deploy/README.md`](../../deploy/README.ru.md)). Критерий «журналы переживают отключение питания» снят: проект решил не обеспечивать его.

**Готово, когда:** робот ходит; обновление через `robotctl` чисто перезапускает `robotd` и проходит контроль; после reboot `journalctl --list-boots` показывает предыдущую загрузку. Первые два выполнены, осталось выполнить одну команду на плате для третьего.

**Два числа намеренно не измерены**, поскольку никто их не ждёт: время записи eMMC и батарея под нагрузкой. Они относятся к M7, диагностике состояния платы.

<a id="m5-mediad-webrtc-sdk-in-progress"></a>
### M5 — `mediad`, WebRTC, SDK · **в работе**

<a id="m5--mediad-webrtc-sdk--in-progress"></a>
**Реализовано на оборудовании.** `mediad` поставляется и работает отдельным unit. Камера через VPU передаёт видео браузеру LAN: `mpph264enc` → `webrtcsink`, constrained baseline, datachannel `control` с общим JSON-RPC. Консоль обслуживает сам робот: достаточно URL, установка не нужна ([`remote-webrtc.md`](../design/remote-webrtc.ru.md), §0; [`webrtc-console.md`](../design/webrtc-console.ru.md)). Пришлось собрать два плагина GStreamer ([`media-bringup.md`](media-bringup.ru.md)); затем камера получила 3A через `rkaiq`.

**Три незакрытых направления.**

**За пределами LAN.** Та же схема с rendezvous и TURN (§7), намеренно второй этап. Теперь за неё отвечает [`remote-access-design.md`](../design/remote-access-design.ru.md): учётная запись Hugging Face через OAuth device flow и мост от rendezvous Space, уже используемого парком mini, к серверу сигнализации на роботе.

**Учётная запись** реализована первой половиной: `robotctl account login` печатает код, человек подтверждает на hf.co/oauth/device, робот хранит и сам обновляет учётные данные. Те же три вызова работают через BLE, единственный транспорт без Wi-Fi, и datachannel. Данные пока никто не использует: следующий **мост**, где протокол rendezvous Space оказывается HTTP, а не WebSocket клиента LAN.

Перед поставкой нужно исправить область токена: клиент device-code первой стороны не принимает `scope`, поэтому токен получает все выдаваемые Hugging Face права. Сужение до `openid profile read-repos` требует публичного OAuth-приложения организации и изменения одной константы.

**SDK и небольшой Python-клиент.** Управление идёт по rendezvous control lane ([`remote-access-design.md`](../design/remote-access-design.ru.md), §3.8): JSON-RPC через HTTP без WebRTC, доступный из дата-центра. Видео — необязательное дополнение через WebRTC с резервом `media.stream`. В `spaces/shared/` уже есть три части: `rendezvous.py` для поиска утки, `wire.py` для передачи, `control.py` для сопоставления ответов. SDK — их упаковка с импортом из Spaces вместо собственных копий.

**Приватность — теперь два пункта.** *Согласие*: явное одобрение каждой сессии перед трансляцией, изменение слоя сессий `mediad`, ничем не заблокировано. *Видимый индикатор* требует программно управляемого LED, которого нет ([`remote-webrtc.md`](../design/remote-webrtc.ru.md), §11). Это вопрос электроники, а не отложенный программный этап. `architecture.md`, §7, верно говорит, что оба дёшевы сейчас и дороги потом; согласие не должно ждать LED.

**Готово, когда:** телеприсутствие работает вне LAN, а серверный скрипт получает кадр и отправляет намерение несколькими десятками строк.

<a id="m6-ship-readiness"></a>
### M6 — Готовность к поставке

<a id="m6--ship-readiness"></a>
Что нужно незнакомому пользователю. Предзаказы открыты; порядок определяется **сроками подготовки**, а не сложностью: пункты с минимумом кода требуют больше времени.

- **PIN сопряжения.** Безопасность BLE основана на индивидуальном PIN. Заводской `000000` открыт в репозитории, поэтому штатное сопряжение доказывает лишь физическое присутствие. PIN нужно создать, напечатать и записать напечатанное: производственный процесс, не патч. Его нельзя выводить из идентичности, опубликованной в advertising.
- **Калибровка**, вторая половина подготовки. Идентичность больше её не ждёт: робот выводит её из серийного номера SoC и называет себя `duck-c51b`.
- **Проверка восстановления на плате.** Сеть восстановления создана и поставляется, но никогда не работала против выпуска с незапускаемыми службами — единственного важного сценария. Самый дешёвый пункт: одна плата, один намеренно сломанный выпуск.
- **Согласие**, из M5.
- ~~**Сообщение об устаревшем манифесте**~~ (§8.4.2), **готово**: `robotctl health` показывает время последнего ответа источника и причину последней ошибки, предупреждает после недели тишины.
- **Арбитраж полномочий** завершён, включая крайний случай #52: `Call::is_mutating()` не охватывает `robot.enable`, поэтому запуск политики идущего робота классифицировался вместе с `hello`.
- **Приложение.** #107 проектирует, но не реализует. Блокер — проба scan, connect, `hello`, authenticate, `system.info` с `--require-pairing` на настоящих iPhone и Android: §5.5 пока описывает CoreBluetooth ноутбука.

Один вопрос вышел из M6 после решения: источник загрузки клиентского робота. Репозиторий открывается, робот получает выпуски без токена и второго хоста. Остался бюджет, не блокер: анонимный GitHub API ограничен 60 запросами в час на IP. Одна утка далеко от предела, двадцать в одной Wi-Fi-сети — уже нет (§6.1).

**Готово, когда:** пользователь без навыков разработки обновляет робот с телефона, а намеренно сломанный выпуск восстанавливается без ноутбука.

<a id="m7-knowing-what-a-board-is-doing"></a>
### M7 — Понимание состояния платы

<a id="m7--knowing-what-a-board-is-doing"></a>
Утка у другого человека однажды сломается; сейчас на вопрос *что именно* отвечает разработчик, читающий журнал по SSH. Решения пока нет; этап — открытое исследование вопросов.

**Уже есть** больше, чем кажется: `robotctl health` сообщает шину, IMU, батарею, температуры моторов и SoC; `robotctl monitor` отображает цикл, геймпад, ToF, 3D и питание; `scripts/pad-stack-report.sh` показывает пример сбора истории подсистемы для отправки; `board-test.sh` выполняет 60 проверок на эмулированном aarch64 CI, а не на вашей плате.

**Недостающее в форме вопросов:**

- **Пакет поддержки.** Одна команда после сбоя создаёт отправляемый файл. Ничто вместе не собирает здоровье, версии, журнал, историю обновлений и состояния unit. `robotctl update show` делает это для одной подсистемы: устойчивую запись запуска с журналом нужного интервала, только для обновлений.
- **Аппаратная проверка «прошло/не прошло» для неспециалиста.** Сканирование шины и ответ каждого сервопривода, корректность IMU, наличие ToF, камеры, NPU, микрофона и динамика, батарея под нагрузкой. По смыслу близко `board-test.sh`, но для оборудования, не выпуска.
- **История**, поскольку кратковременные сбои не видны в снимке: ошибки шины, пропущенные такты, пики температур, просадки. Журнал намеренно не переживает обрыв питания (M4); важным данным нужна устойчивость истории обновлений.
- **Пересечение с #52.** Проект IPC-монитора — программная половина того же вопроса. Его запись падения, последние события в ограниченном файле `/var/lib` вне выпусков, переживающем обновления и откаты, имеет как раз нужную устойчивость. Решать следует вместе, а не создавать два ответа.

Сюда переходят неизмеренные время записи eMMC и батарея под нагрузкой из M4.

**Готово, когда:** неспециалист одной командой после сбоя получает имя неисправной части либо подтверждение исправности оборудования.

<a id="m8-the-policy-channel-policies-from-the-hub"></a>
### M8 — Канал политик: модели из Hub

<a id="m8--the-policy-channel-policies-from-the-hub"></a>
Раньше каждая политика поставлялась **в артефакте службы**: новая походка требовала выпуска службы, а модель с ноутбука попадала на утку только через CI или загрузку всей службы. Цель: независимо публиковать, устанавливать и пробовать политику из закрытого тренировочного `microduck_rl` со своей линией версий; пробовать чужую и возвращаться назад.

**Спроектировано** в [`policy-channel-design.md`](../design/policy-channel-design.ru.md), которому принадлежат прежние открытые решения. Слот имеет один из трёх источников: официальный (`pollen-robotics/*`, цель reset), сообщество (иной Hub-репозиторий, неподписанный, видимый, но без автоприменения), локальный путь платы. `policy load` пишет ключ конфигурации, `policy reset` удаляет: сохранение и отмена используют существующий механизм. Официальный набор — один компонент `policies`, а не компонент на слот.

**Большая часть механизма уже создана:** источник `hf_hub` разрешает и проверяет; компонент имеет свою версию, откат, закрепление, boot trial, историю плохих версий; `on_apply = reload` существует, `xtask sign` подписывает любой каталог артефактов.

**Три шага, каждый полезен самостоятельно:**

1. **Локальный цикл без сети.** `robot.loadPolicy`, перезагрузка в домашней позе, `robotctl policy list` / `load` / `reset`. Полностью даёт «попробовать без правки toml», не касается Hub и публикации. `API_VERSION` 17 → 18.
2. **Официальные политики покидают артефакт.** *Готово.* `robotd` читает `/opt/robot/policies/current`; `scripts/seed-policies.sh` скачивает закреплённый набор из `pollen-robotics/microduck-policies`, как `setup-board.sh` уже делает для ONNX Runtime. `policies/` и три списка `--include` удалены; для поставки походки достаточно повысить `[workspace.metadata.policies]`.
3. **Переход выше закреплённой версии.** *Готово.* `policy.*` в `updaterd`, `robot.reloadPolicies`, `robotctl policy check` / `update`: переобученная походка приходит без выпуска службы, что и было целью. Каждый набор записывает исходный репозиторий, исключая двойную настройку.
4. **Библиотека сообщества.** *Готово.* `policy load <slot> <org/repo>` получает политику любого Hub в `/var/lib/robot/policies/<org>/<name>/<rev>/`; `origin` сообщает `community` для чужой, `policy search` показывает доступное. Уже опубликованные репозитории имеют `manifest.json` с `obs_len`, `action_len`, `model_api`: несовместимая политика отклоняется до загрузки. Здесь же `model_api` перестал быть только проектом.

Во всех трёх случаях `reset` означает «убрать переопределение и заново разрешить». Шаг 1 даёт правильный reset к копиям выпуска, шаг 2 меняет цель без изменения команды.

**Действительно недостающее — по краям, не в середине:**

- **`robotd` не может перезагрузить по запросу.** Механизм есть: `robot.setMode` пересоздаёт все ONNX-сессии в домашней позе. Но нет триггера на слот, а неудачная загрузка должна сохранить действующий контроллер вместо лишения походки.
- **Ничто не публикует комплект.** `xtask package --channel` близок, но сравнивает `--version` с версией crate, которой у набора политик нет; структуры HF-репозитория тоже нет.
- **`model_api`** спроектирован, но не реализован с обеих сторон. `robot.modelApi` отвечает, но никто не обращается.
- **Цикл обучения.** `microduck_rl` экспортирует ONNX, ничто не переносит результат на плату. Шаг 1 делает «обучить и попробовать» минутным делом вместо CI.

**Готово, когда:** политика из `microduck_rl` опубликована в Hub, установлена, испытана и отменена через `robotctl policy reset` без потери управления моторами; другой человек может найти и попробовать её с робота.

<a id="m9-the-autonomous-brain"></a>
### M9 — Автономный мозг

<a id="m9--the-autonomous-brain"></a>
Крупнейший неучтённый пробел: `autonomous.rs` прототипа отсутствует в службе, проектного документа нет. [`ideas/autonomous_behavior.md`](../ideas/autonomous_behavior.ru.md) хранит идеи: автомат из 16 состояний с энергией и настроением, исследование сетки новизны, избегание ToF, испуг, звуковые реакции, игра в мяч, сон, поглаживание.

Все необходимые входы уже есть, включая ранее отсутствовавшие: окружающие звуки, глубина, классифицированные препятствия в координатах корпуса, голосовые метки, стабильные ID соседних уток, общий ритм, RSSI как грубая дистанция, живой синтезатор, расстояние до руки по ToF.

**Структура важнее состояний.** Присутствие, настроение и ритм — *входы одного мозга*, а не соседние режимы. Хор и терменвокс выросли отдельными режимами из-за отсутствия мозга; хор занимает 55 KB `robotd`. Этап должен прекратить повторение такого шаблона. Сначала проектный документ, потом код.

**Готово, когда:** оставленная в комнате утка десять минут делает нечто интересное, а хор становится её решением, не результатом команды.

<a id="the-order-of-work"></a>
## Порядок работы

Числа выше — идентификаторы. Порядок такой:

1. **M8, канал политик.** Следующая функция. Ничего иного не блокирует, но открывает цикл реального поведения: обучение, публикация, установка, проба, откат.
2. **Исследование транспорта M5.** Дёшево; ответ определяет, будет Python-клиент пятьюдесятью строками или проектом.
3. **M6 по мере приближения поставки**, по срокам подготовки: источник загрузки, PIN, аппаратная проверка восстановления. Согласие можно реализовать в любое время, лучше раньше.
4. **M7**, исследование без даты. Получит приоритет при первом непонятном отказе утки у другого человека. Дешевле подготовиться решением вместе с #52, а не после.
5. **M9, мозг**, намеренно позже: крупнейшая оставшаяся работа, наиболее склонная разрастаться при реализации.

<a id="decisions-that-shape-work-rather-than-follow-it"></a>
## Решения, определяющие работу, а не следующие за ней

1. ~~**Хранение ключей подписи**~~ — **готово** для службы. Три зашифрованных release-ключа и незашифрованный dev-ключ в `~/.duck-keys`, в secrets только `release-1`. Подпись CI с `environment: release` ограничивает область секретов, но **ничего не блокирует**: нет обязательных проверяющих и политики веток. Принято, пока нет роботов у пользователей; объявление позволит включить настоящий барьер одним изменением настройки. См. [`ci-setup.md`](ci-setup.ru.md). **Откроется снова с M8**: публикация политики — третий тип ключа.
2. **Полномочия безопасности** (§6) — реализованы в M3.
3. **Подготовка платы** — идентичность готова, калибровка и PIN нет; PIN — производственный процесс, не код (M6).
4. **Приватность** — согласие в M5 ничем не заблокировано; индикатор — вопрос электроники.
5. ~~**Источник загрузки клиентского робота**~~ — **решено 2026-08-26:** открыть репозиторий и скачивать напрямую. §6.1 сохраняет альтернативы с обоснованием на случай повторного закрытия.
6. **Вынос политик из артефакта службы** — **склоняемся к да**, не решено. Они уходят; отсутствие модели даёт `degraded`, не unhealthy, поэтому контроль фиксирует выпуск; подготовка устанавливает начальный набор. M8 описывает преимущества альтернативы, если решение хрупкое.
7. **Отобранные модели или открытый набор** — открытый; решение о доверии, а не о транспорте (M8).

<a id="not-doing-on-purpose"></a>
## Что намеренно не делаем

Зафиксировано, чтобы не пересматривать случайно: обновления образов A/B, OTA ОС/ядра, панели парка и телеметрия, дельта-обновления, поэтапное развёртывание, матрица аппаратных возможностей, конкурирующие модели одного слота (§17), OTA прошивок периферии (§11.1).
