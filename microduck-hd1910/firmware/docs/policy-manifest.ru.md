# Манифест политики, схема 2

Что описывает `manifest.json`, расположенный рядом с файлом microduck `.onnx`, и как робот использует каждое поле. Единый словарь для двух форматов: **репозиторий одной политики** (`<user>/microduck-<name>` на Hub, один `policy.onnx`, поля на верхнем уровне) и **официальный комплект** (`pollen-robotics/microduck-policies`, десять файлов, те же поля у каждой записи внутри `policies`). Один обработчик понимает оба формата. Требование к автору модели формулируется как «добавьте поле», а не «перейдите на наш формат».

`uv run publish` в `pollen-robotics/microduck_rl` создаёт соответствующий контракту репозиторий одной политики из контрольной точки или ONNX-файла. Его читают `robotctl policy load <slot> <repo>` и `robotctl policy add <name> <repo>`. Обоснование находится в `docs/design/policy-channel-design.md` §9; этот файл задаёт контракт.

<a id="the-two-axes"></a>
## Две независимые характеристики

**`kind` определяет, кто завершает политику.**

| `kind` | Значение | Результат |
| --- | --- | --- |
| `episodic` | Выполняется `duration_s` и сама возвращается в безопасную позу. | Навык, если команда постоянна. |
| `perpetual` | Выполняется до внешней команды: походка или поза, которую должен завершить человек. | Походка слота (`policy load`); при наличии `unwind_s` — навык с `--hold`. |
| `scripted` | Эпизодическая, но прерываемая: служба может менять команду во время выполнения. | Сохраняется; тайминги читает соответствующая ветвь логики службы. |

**`command.encoding` определяет, что служба подаёт на вход.**

| `encoding` | Команда twist | Использование |
| --- | --- | --- |
| Отсутствует или `constant` | Фиксированный twist на время действия, `idle` при возврате. | Все удары, кувырок и пока все одноразовые действия сообщества. |
| `phase` | `[cos 2πφ, sin 2πφ, 0]`, φ растёт от 0 за `period_s` секунд, управление возвращается при `end_phase`. | Подбор с земли; приседание на роликах. |
| `posture_flag` | Один компонент несёт `sit` или `stand`. | Переход сидя↔стоя. |

Универсальным одноразовым действием может быть только `episodic` с постоянной командой. `policy add` отклоняет политики `phase` и `posture_flag`: их следует ставить в слот, которым управляет служба (`policy load ground_pick …`, `policy load sitstand …`). Проверка основана на кодировании, а не на имени.

<a id="fields"></a>
## Поля

Все поля необязательны, кроме `file` внутри комплекта. Отсутствующее поле ничего не подтверждает: робот отклоняет политику только при наличии явно заявленного несовместимого значения.

| Поле | Тип | Кто читает | Значение |
| --- | --- | --- | --- |
| `schema_version` | int | Отображение | `2`. Надмножество схемы 1; версия не служит условием допуска. |
| `model_api` | int | Загрузка | API службы, необходимый политике; более новая версия, чем у службы, отклоняется. |
| `obs_len` | int | Загрузка | `61`; несовпадение с роботом отклоняется. |
| `action_len` | int | Загрузка | `14`; несовпадение отклоняется. |
| `robot.model` | str | Загрузка | `microduck`; другая модель робота отклоняется. |
| `robot.hw_rev`, `robot.servos`, `robot.control_hz` | | Отображение | `1`, `xl330`, `50`. |
| `name` | str | Навыки | Имя, которое запрашивает клиент; по умолчанию имя файла без расширения. |
| `description` | str | Отображение | Одна строка недоверенного текста: её показывает `policy search` под каждым результатом и `policy fetch` при загрузке. |
| `kind` | str | Навыки, слоты | См. выше. |
| `duration_s` | float | Навыки | Длительность выполнения в секундах; для фазовой политики `period_s × end_phase`. |
| `chain` | bool | Навыки | Удерживаемая кнопка запускает следующий проход после завершения текущего. |
| `action_scale` | float | Навыки | Собственный масштаб выхода на время выполнения. |
| `unwind_s` | float | Навыки, sitstand | Секунды подачи `command.idle` перед возвратом управления; для сидя↔стоя — подъём. |
| `ramp_s` | float | sitstand | Время стабилизации сидячей позы; приседание перед выключением ждёт вдвое дольше. |
| `mode` | str | Комплект | `walk` (по умолчанию) или `roller`; определяет режим подбора с земли для фазовой записи. |
| `slot` | str | Отображение | Для непрерывной походки: предназначенный слот (`walk`, `stand`, …), чтобы строкой установки была `policy load <slot> <repo>`. |
| `entry_pose` | str | Отображение | Ожидаемая начальная поза, например `standing`. |
| `command.encoding` | str | Навыки | См. выше. |
| `command.idle` | [3] | Навыки | Twist со значением «прекратить действие». |
| `command.period_s`, `command.end_phase` | float | Подбор с земли | Параметры фазового цикла. |
| `command.sit`, `command.stand`, `command.slot` | | Отображение | Значения флага и компонент, в котором он передаётся. |
| `command.twist`, `command.head`, `command.body` | Текст | Отображение | Человекочитаемое описание каждого блока. |
| `training` | object | Отображение | `task_id`, `repo`, `commit`, `branch`, `dirty`, `run`, `checkpoint`, `exported`. |
| `eval` | object | Отображение | Свободная форма: что проверялось, в каком симуляторе и с каким результатом. |
| `policies[]` | array | Комплект | По одной записи на файл, содержащей `file` и любые перечисленные выше поля политики. |

Для рекуррентного экспорта LSTM требуется `model_api: 2`; существующие модели прямого распространения сохраняют API 1. Контракт тензоров, жизненный цикл памяти и проверка без оборудования описаны в [рекуррентных политиках](recurrent-policies.ru.md).

<a id="a-single-policy-repo"></a>
## Репозиторий одной политики

```json
{
  "schema_version": 2,
  "model_api": 1,
  "obs_len": 61,
  "action_len": 14,
  "robot": { "model": "microduck", "hw_rev": 1, "servos": "xl330", "control_hz": 50 },
  "name": "polite-bow",
  "kind": "episodic",
  "duration_s": 4.0,
  "chain": false,
  "entry_pose": "standing",
  "description": "Bows from a two-foot stand and comes back up.",
  "command": { "encoding": "constant", "idle": [0, 0, 0],
               "twist": "unused (zeros)", "head": "unused (zeros)", "body": "unused (zeros)" },
  "training": { "task_id": "Mjlab-PoliteBow-Flat-MicroDuck", "repo": "pollen-robotics/microduck_rl",
                "commit": "0bf9897", "branch": "bow", "dirty": false,
                "run": "pollen-robotics/mjlab_microduck/abc123", "checkpoint": 3000,
                "exported": "2026-09-02T14:05:00Z" }
}
```

В репозитории ровно один `.onnx` с именем `policy.onnx`. `robotctl policy add polite-bow <user>/microduck-polite-bow` читает `duration_s`, `chain`, `action_scale`, `command.idle` и `unwind_s`, отклоняет несовместимые `obs_len`, `action_len`, `model_api`, `robot.model` либо непостоянное кодирование и записывает навык. `RemiFabre/microduck-flamingo-cycle` — опубликованный пример `perpetual`: `duration_s` отсутствует, поэтому требуется `--hold`, а возврат выполняется с его `command.idle`.

<a id="the-official-set"></a>
## Официальный комплект

Те же поля задаются у каждой записи внутри `policies` вместе с `file`. Рабочая копия: `https://huggingface.co/pollen-robotics/microduck-policies/blob/main/manifest.json`. Записи `phase` задают тайминги подбора с земли для каждого режима, а запись `scripted` — перехода сидя↔стоя. Поэтому переобученный подбор с более длинным циклом требует нового тега комплекта, а не выпуска службы.

Каждый `file` — простое имя файла, без каталога и без точки в начале. Если запись манифеста содержит путь, её пропускают как первоначальный установщик моделей, так и `robotctl policy update`.

Манифест устанавливается **внутрь комплекта**, поэтому `robotd` читает навыки из `/opt/robot/policies/current/manifest.json`. Это также список загрузки: для добавления политики достаточно записи здесь и нового тега. Первоначальная установка на плату и все последующие `policy update` берут список из устанавливаемой ревизии.

<a id="the-preview-clip-which-is-not-a-field"></a>
## Видеопревью, которое не является полем

Репозиторий может содержать **видео работы политики**; `robotctl policy search` показывает ссылку рядом с описанием. Используется путь, а не поле манифеста: авторы уже размещали видео именно так, и [policy playground](https://huggingface.co/spaces/pollen-robotics/microduck-policy-playground) уже читает эти пути. Требование поля `preview` заставило бы повторно описывать то, что и так задано путём.

Разместите файл как **`media/preview.mp4`**. Так делает большинство опубликованных политик, и этот путь проверяется первым. Полный порядок для репозитория с другим расположением:

1. `media/preview.mp4`
2. `preview.mp4`
3. Любой `.mp4`, `.webm` или `.mov` с именем файла, начинающимся с `preview`, в любом каталоге.
4. Любой `.mp4`, `.webm` или `.mov`.
5. Любой `.gif`.

При нескольких вариантах на одном шаге выбирается самый неглубокий путь, затем самое короткое имя, затем алфавитный порядок. Поэтому репозиторий с отдельным роликом для каждого варианта — например, `10cm/preview.mp4` и `100cm/preview.mp4` — получает одинаковый результат при каждом поиске, независимо от порядка списка Hub.

Шаг 4 объясняет, почему единственная запись экрана просмотрщика также будет показана: выбранный автором ролик предпочтительнее отсутствия ролика, а определить его содержание здесь невозможно. Если автор предпочитает ничего не показывать, видео не должно быть в репозитории Hub.

Поиск берёт превью из уже возвращаемого Hub списка файлов, без дополнительного запроса. Для описания нужен один GET `manifest.json` на каждый репозиторий, где он есть. Запрос ограничен по времени и отбрасывается через несколько секунд, поскольку простой список политик полезнее запоздавшего подробного.

<a id="changes-from-schema-1"></a>
## Отличия от схемы 1

Схема 1 была первым форматом официального комплекта: `kind` имел значения `perpetual`, `episodic`, `scripted`, где `scripted` означало «команду генерирует служба» и применялось к подбору с земли. Схема 2 переносит это значение в `command.encoding`, меняет смысл `scripted` на прерываемое эпизодическое действие (сидя↔стоя) и добавляет `chain`, `ramp_s`, `mode`, `entry_pose`, `training`, `eval` и поля таймингов `command.*`. При чтении схемы 1 служба использует для всего тайминги прототипа и те же три навыка; сама версия не вызывает отказа.
