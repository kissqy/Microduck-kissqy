# Запуск медиатракта на оборудовании

Как Radxa Zero 3W работает с видео. Всё ниже наблюдалось на плате, а не выводилось предположениями; оставшиеся предположения явно обозначены.

<a id="what-this-settles"></a>
## Что удалось установить

`mediad` нужен аппаратный H.264: программное кодирование здесь не просто медленнее, оно непригодно. Даже один `jpegenc` не удерживает 30 кадров/с при 640x480 на этом SoC (`microduck_runtime/src/camera.rs:500`), а H.264 дороже JPEG на кадр. При этом четыре Cortex-A55 уже заняты в том числе циклом управления `robotd` на 50 Гц.

**VPU кодирует H.264, битовый поток корректен, доступ к кодировщику идёт через Rockchip MPP, а не V4L2.** Для использования нужно собрать два плагина GStreamer из исходников; неизвестных препятствий для них нет.

| | |
|---|---|
| VPU кодирует H.264 720p | Да — 60 кадров, 428 KB, через `mpi_enc_test` |
| Поток корректен на этом ядре | Да — чистое декодирование `avdec_h264`, High profile level 4, 4:2:0 8-bit |
| Интерфейс доступа | `/dev/mpp_service` (Rockchip MPP), **не** V4L2 M2M |
| ABI плагинов GStreamer между 1.x | Риска не показал — плагин для 1.14 нормально регистрируется в 1.26.2 |
| Элемент `mpph264enc` | Нужно собрать, см. [необходимые сборки](#what-has-to-be-built) |
| `webrtcsink` / `webrtcsrc` | Нужно собрать отдельно |

<a id="what-the-board-has"></a>
## Что есть на плате

На подготовленной плате ничего для мультимедиа не установлено. `scripts/setup-gstreamer.sh` устанавливает необходимое и сообщает возможности оборудования. Этот скрипт — исполняемая форма страницы; повторно нужные команды должны попадать туда.

GStreamer поступает из **обычного Debian trixie**: `apt-cache policy` показывает `deb.debian.org` и `security.debian.org` без мультимедийного overlay Armbian, поэтому версии архива применимы точно:

| Пакет | Версия |
|---|---|
| `gstreamer1.0-plugins-bad`, содержит `webrtcbin` | 1.26.2-3+deb13u3 |
| `libgstreamer-plugins-bad1.0-dev`, содержит `gstreamer-webrtc-1.0.pc` | 1.26.2-3+deb13u3 |
| `gstreamer1.0-nice` | 0.1.22-1 |
| `gstreamer1.0-plugins-rs` | **Не существует ни в одном выпуске Debian** |

Ядро — `6.1.115-vendor-rk35xx`. Это важно дважды: драйвер захвата MIPI-CSI ISP и узлы VPU существуют только в vendor-ветке Armbian. `setup-board.sh` уже устанавливает это ядро ради дерева I²S аудиокодека, а не видео; условие было выполнено заранее. Неосторожный `apt upgrade`, установивший ядро `current` и перенаправивший `/boot`, лишит обоих.

<a id="the-camera-needs-an-overlay-mirrored-under-a-prefix"></a>
## Камере нужен overlay с копией под именем с префиксом

Подключённая CSI-камера не создаёт **ни `/dev/video*`, ни сообщений dmesg**, пока не включён её device-tree overlay. Это выглядит точно как неподключённая камера.

Есть отдельная ловушка: Armbian поставляет `radxa-zero3-rpi-camera-v2.dtbo` **без префикса `rk3568-`**, а плата использует `overlay_prefix=rk3568`. Слово в `overlays=` превращается в `rk3568-radxa-zero3-rpi-camera-v2.dtbo`; загрузчик ничего не находит, плата спокойно загружается без камеры. Это такой же тихий сбой, какой `configure_overlay` предотвращает для `uart2-m0`. Файл нужно **сначала скопировать под именем с префиксом**, затем указать в `overlays=`. `microduck_runtime/install.sh` столкнулся с этим и делает то же.

`configure_camera` в `setup-board.sh` выполняет оба действия в каталоге overlay *vendor*-ядра. Драйвер MIPI-CSI есть только в этой ветке — вторая причина обязательности vendor-ядра. `DUCK_CAMERA_OVERLAY` выбирает иной модуль: Armbian имеет отдельный для каждого датчика; на этой плате это `radxa-zero3-rpi-camera-v2` (Pi Cam v2 / IMX219) либо `radxa-zero3-rpi-camera-v1.3` (Pi Cam v1.3 / OV5647). Здесь использовался только первый.

<a id="the-encoder-is-mpp-not-v4l2"></a>
## Кодировщик — MPP, а не V4L2

Отсутствуют `v4l2h264enc` и `/dev/video*`. Ни то ни другое не означает неисправности:

- В BSP-ядре Rockchip VPU доступен как `/dev/mpp_service`, не как кодировщик V4L2 M2M. `gstreamer1.0-plugins-good` регистрирует `v4l2h264enc`, только найдя узел кодировщика. Его отсутствие ожидаемо и не указывает на недостающий пакет.
- Полное отсутствие `/dev/video*` также соответствует **неподключённой камере**: узлы rkisp появляются только после обнаружения датчика.

Это точка выбора пути. Если бы ядро предоставляло V4L2-кодировщик, аппаратный H.264 не потребовал бы внешних компонентов.

<a id="the-permission-trap"></a>
### Ловушка прав доступа

`/dev/mpp_service` появляется как `crw------- root root`, режим 0600. Процесс без root не может открыть его, при этом **`mpi_enc_test` пишет пустой файл и завершается с кодом 0**. Без ошибки и строки в журнале. Поэтому нулевой код не доказывает ничего; доказательство — размер файла.

`mediad`, как остальные службы, работает от своего пользователя: `tofd` входит в `i2c`, `padd` — в `input`, `btd` — в `bluetooth`. VPU требует того же: правила udev с группой узла и `SupplementaryGroups=` в unit. `scripts/setup-gstreamer.sh` ставит правило `99-robot-mpp.rules`, группу `video`, режим 0660 по образцу правила i2c в `configure_tof` из `setup-board.sh`.

Именно `video`, не `robot`: `robot` ограничивает определяемые *нами* IPC-сокеты ([`app-path-design.md`](../design/app-path-design.ru.md), раздел о сочетании режима сокета и группы). Узел устройства ядра не наш для переопределения; `video` — соглашение дистрибутива для этого класса, поэтому разработчик с `gst-launch` получает доступ так же, как `mediad`.

<a id="what-radxas-pool-provides"></a>
## Что предоставляет репозиторий Radxa

Rockchip MPP отсутствует в Debian. Radxa публикует apt-репозиторий на GitHub Pages; пакеты скачиваются **напрямую как `.deb`**, без добавления в `sources.list`. Так уже поступает `microduck_runtime/radxa_setup/setup_rkaiq.sh` для `rkaiq_3A_server`. База: `https://radxa-repo.github.io/bullseye/pool/main`.

| Пакет | Версия | Назначение |
|---|---|---|
| `m/mpp/librockchip-mpp1` | 1.5.0-1 | Пользовательская библиотека MPP |
| `m/mpp/librockchip-vpu0` | 1.5.0-1 | `rockchip-mpp-demos` требует именно эту версию |
| `m/mpp/rockchip-mpp-demos` | 1.5.0-1 | `mpi_enc_test`, проверяющий VPU без GStreamer |
| `m/mpp/librockchip-mpp-dev` | 1.5.0-1 | Заголовки для сборки плагина кодировщика |
| `libr/librga/librga2` | 2.2.0-1 | 2D-ускоритель Rockchip, зависимость плагина |
| `libr/librga/librga-dev` | 2.2.0-1 | Заголовки для той же сборки |
| `g/gstreamer1.0-rockchip/gstreamer1.0-rockchip1` | 1.14-4 | Плагин MPP GStreamer, см. ниже |

Это сборки bullseye; они нормально настраиваются с glibc 2.41 на trixie.

**`dpkg -i` не разрешает зависимости**, поскольку пакеты не из настроенного apt-источника. Недостающая зависимость оставляет ненастроенный пакет, а не автоматически исправляемую установку. Нужно перечислять всё замыкание зависимостей. На выяснение ушло три подхода.

<a id="radxas-prebuilt-plugin-is-not-decode-only-and-this-page-said-it-was"></a>
### Готовый плагин Radxa не ограничен декодированием, хотя страница это утверждала

`gstreamer1.0-rockchip1_1.14-4` нормально ставится и регистрируется в GStreamer 1.26.2, показывая только `mppvideodec` и `mppjpegdec`. Это похоже на отсутствие кодировщиков, и страница ошибочно так утверждала. `strings` в `.so` показывает `mpph264enc`, `mpph265enc`, `mppjpegenc`, `mppvp8enc`. Все присутствуют.

**Полное объяснение — права доступа. До выяснения они дали четыре разных ложных впечатления:**

| Как выглядело | Что было на самом деле |
|---|---|
| `mpi_enc_test` ничего не записал и **завершился с 0** | Узел не открывался; код 0 ничего не доказывает |
| DEB Radxa содержит только декодеры | В нём все кодировщики |
| Сторонний DEB 1.14-8 тоже не показывает `mpph264enc` | Та же причина |
| Собственная сборка CI показывает только два декодера | В контейнере тоже нет `/dev/mpp_service`: ожидаемо, не ошибка |

Плагин MPP **безусловно регистрирует декодеры, а перед регистрацией кодировщиков проверяет MPP**. При `0600 root:root` проверка тихо падает; кодировщики не регистрируются, хотя присутствуют в плагине.

Список только декодеров говорит об *узле устройства*, а не составе плагина. `gst-inspect-1.0 mpph264enc` ничего не значит до установки udev-правила.

Один вывод установки остаётся верным: **плагин для GStreamer 1.14 регистрируется без замечаний в 1.26.2.** Опасение по поводу ABI не подтвердилось.

<a id="what-has-to-be-built"></a>
## Что нужно собрать

Два плагина по двум несвязанным причинам. Они не заменяют друг друга.

| Плагин | Исходники | Что даёт | Почему нельзя просто установить |
|---|---|---|---|
| `gstreamer-rockchip` | [`JeffyCN/mirrors`](https://github.com/JeffyCN/mirrors), ветка `gstreamer-rockchip`, meson | `mpph264enc`, аппаратный кодировщик | В Debian нет кодировщика Rockchip. У Radxa он есть; собственная сборка нужна ради контролируемой версии, отказа от `libx11-6` и совместной поставки со следующим плагином |
| `gst-plugin-webrtc` | [`gst-plugins-rs`](https://gitlab.freedesktop.org/gstreamer/gst-plugins-rs) 0.15.3, cargo-c | `webrtcsink`, `webrtcsrc` | `gst-plugins-rs` не упакован **ни в одном** выпуске Debian |

0.15.3 вместо 0.14.5 из SDK `reachy_mini`: важная нижняя граница — 0.14.5. Ранее отсутствует исправление взаимной блокировки `webrtcsink` между remote description и ICE; клиент бесконечно показывает «connecting». 0.15.3 просто новее. Обе серии требуют GStreamer `v1_22`, робот использует 1.26.2, поэтому новая версия ничего дополнительно не стоит.

`webrtcbin` **установлен** из `gstreamer1.0-plugins-bad`. Сессию WebRTC можно получить без второй сборки, но придётся самим реализовать протокол сигнализации. Предпочтителен `webrtcsink`: его протокол проксируется ретранслятором и позволяет повторно использовать центральный сервер сигнализации.

<a id="why-not-a-prebuilt-one"></a>
### Почему не готовый плагин

Оборудование, драйвер ядра и пользовательская библиотека MPP работают **без компиляции**: `mpi_enc_test` из DEB с первой попытки закодировал H.264 720p. Не хватает лишь *привязки GStreamer*: плагина, представляющего `librockchip-mpp` элементом конвейера. `mpi_enc_test` — самостоятельная программа, о которой GStreamer ничего не знает. Так же устроен ONNX Runtime: `libonnxruntime.so` ставится из tarball без компиляции, а `ort` делает его доступным.

Готовые привязки:

| Источник | Содержимое |
|---|---|
| Radxa `bullseye` | `gstreamer1.0-rockchip1_1.14-4`, установлено и исследовано: только `mppvideodec` + `mppjpegdec` |
| Radxa `rk3588s2-bookworm` | Тот же `1.14-4`, побайтово идентичен |
| [`numbqq/gstreamer-rockchip-debs`](https://github.com/numbqq/gstreamer-rockchip-debs) | `1.14-8`, **все кодировщики** |

Последний стоит попробовать до сборки. Пути `bookworm/arm64/<board>/` — символьные ссылки в `jammy/arm64/`; это сборка Ubuntu 22.04 из `rockchip-linux/gstreamer-rockchip`, теперь 404, с сопровождающим Jeffy Chen. Тот же upstream, что у Radxa, но ревизия с включёнными кодировщиками. Все `mpph264enc`, `mpph265enc`, `mppjpegenc`, `mppvp8enc` присутствуют в `.so`.

Его `DT_NEEDED` удовлетворяется платой после установки DEB выше: `librockchip_mpp.so.1`, `librga.so.2`, `libgstreamer-1.0.so.0`, `libgstvideo`, `libgstallocators`, `libgstpbutils`, `libdrm2`, `libglib2.0-0`, `libx11-6`, `libc6 >= 2.33` при glibc 2.41. Специфики RK3588 в нём нет: различия SoC находятся внутри MPP. `Depends` ограничивает GStreamer лишь снизу (`>= 1.14`).

Наши плагины собираются в [`microduck-gst-plugins`](https://github.com/pollen-robotics/microduck-gst-plugins), намеренно отдельном репозитории:

- **Не на плате.** RK3566 компилирует Rust-часть слишком долго.
- **Также не кросс-компиляцией.** Службы кросс-собираются через `cargo-zigbuild`. `scripts/ci-cross-deps.sh` прямо называет единственную C-зависимость ценой исключения, которую стоит изучить перед добавлением следующего. GStreamer был бы гораздо более крупным вторым исключением. И x86 multiarch, и sysroot с cross-файлом meson линкуются с приближением целевой системы.
- **Нативно на runner arm64 в контейнере `debian:trixie`**, то есть пользовательской системе робота. Никаких приближений. В открытых репозиториях arm64 runner бесплатны.
- **Открыто**, что важнее: скачивание выполняется при подготовке и из `preinstall` обновлятора с очищенным окружением **без токена**. Так службы уже получают ONNX Runtime.

Сборка создаёт оба плагина, закрепляет upstream коммитом или тегом в одном `pins.env`, отключает `rkximage` и `kmssrc` — X11- и KMS-выводы того же дерева, ненужные роботу без экрана и вызывающие зависимость DEB Radxa от `libx11-6`. Публикуются tarball, sha256 и `MANIFEST` с точной ссылкой upstream каждого плагина. Именно происхождение не объяснял сторонний DEB.

Учтены две ловушки, найденные чтением исходников, а не падениями: `gst/rockchipmpp/meson.build` заканчивается `if not mpp_dep.found() → subdir_done()`, поэтому отсутствие `librockchip-mpp-dev` заставляет meson **пропустить плагин и успешно завершиться**. И `dpkg -i` для прямых DEB не разрешает зависимости, поэтому всё замыкание Radxa устанавливается одним вызовом.

**`mediad.service` должен задавать `GST_PLUGIN_PATH`.** Плагины ставятся в `/usr/local/lib/gstreamer-1.0`, который GStreamer **не** ищет по умолчанию. Встроенный путь — `/usr/lib/aarch64-linux-gnu/gstreamer-1.0`; его намеренно избегают, чтобы `apt` не заменил и не удалил файлы. Unit требует:

```
Environment=GST_PLUGIN_PATH=/usr/local/lib/gstreamer-1.0
```

вместе с `SupplementaryGroups=video` для VPU. Оба легко забыть, и оба проявляются одинаково: кодировщика будто нет, без объяснения причины.

`scripts/setup-gstreamer.sh` использует **закреплённую** версию, никогда не «latest». Две подготовки с разницей в день и разными незафиксированными плагинами создают невоспроизводимую ошибку мультимедиа. Версия хранится в `[workspace.metadata.gst-plugins]` в `Cargo.toml`; скрипт содержит литерал, поскольку скачивается отдельно через `curl`. Тест `xtask` проверяет совпадение — тот же механизм и причина, что у `ONNX_VERSION`.

**Попробовать сторонний DEB не значит зависеть от него.** Это набор сборок одного человека для отдельных плат без контролируемого происхождения; он исчезнет вместе с репозиторием. Дешёвая проба отвечает на единственный реальный вопрос сборки: работает ли плагин с *нашими* MPP и GStreamer. При успехе собственная сборка того же исходника становится менее рискованной, а не ненужной. Конечная цель — своя закреплённая сборка.

**Сборки можно избежать полностью**, вызвав C API MPP из `mediad` через Rust FFI: работоспособность доказывает `mpi_enc_test`. Но вместо meson придётся вручную писать и поддерживать привязки к библиотеке производителя. Это менее выгодный обмен, хотя реальный запасной путь, если плагин несовместим с GStreamer 1.26.

<a id="the-upstream"></a>
### Upstream

`rockchip-linux/gstreamer-rockchip` исчез, 404. Рабочее зеркало — `JeffyCN/mirrors@gstreamer-rockchip`, последний коммит 2026-05-21; `gst/rockchipmpp` содержит `gstmpph264enc.c`, `gstmpph265enc.c`, `gstmppjpegenc.c`, `gstmppvp8enc.c`. Вокруг много форков; выбранные форк и тег нужно закрепить и записать по той же причине, что и `gst-plugin-webrtc` ≥ 0.14.5 ниже.

<a id="the-pin-on-gst-plugin-webrtc"></a>
### Закреплённая версия `gst-plugin-webrtc`

**0.14.5 или новее, не 0.14.4.** Ранние теги не имеют исправления deadlock `webrtcsink` между remote description и ICE, проявляющегося бесконечным «connecting». Это записано в инструкции SDK `reachy_mini`; `reachy-mini-desktop-app` включает 0.14.4 и находится по неверную сторону границы.

Pollen уже включает плагин для **x86_64**: нативная сборка `cargo cinstall`, удаление символов, коммит по архитектурам, использование CI с закреплённым commit ref и sha256. Соседний `aarch64/` там может потребовать меньше общей работы, чем второй конвейер здесь.

<a id="where-a-built-plugin-belongs"></a>
### Где должен находиться собранный плагин

В составе выпуска службы, с `GST_PLUGIN_PATH` в `current`, а не в apt или `/opt` каждой машины.

Версия плагина и код `mediad` связаны: случай 0.14.5 показывает, как версия определяет необходимость обходного кода службы. Несовпадение — ошибка `mediad`, поэтому нужен его жизненный цикл: атомарное переключение, откат, контроль здоровья. `librockchip-mpp`, напротив, системная библиотека в паре с *ядром*, нужна любому пользователю VPU и должна находиться под управлением пакетного менеджера.

<a id="measured-and-not"></a>
## Что измерено, а что нет

**Измерено на плате:** GStreamer 1.26.2 и источник пакетов; наличие `webrtcbin`; отсутствие `webrtcsink`/`webrtcsrc`, `v4l2h264enc` и `/dev/video*`; `/dev/mpp_service` с 0600 root:root; тихая запись пустого файла `mpi_enc_test` без root и 428 KB от root; чистое декодирование High/4.0; замыкание зависимостей DEB Radxa; загрузка rockchip-плагина в 1.26.2 с двумя декодерами.

**Путь кодирования полностью проверен на оборудовании.** Последовательность:

1. `v1` скачан из открытого выпуска, sha256 проверен, установлен в `/usr/local/lib/gstreamer-1.0`.
2. `gst-inspect-1.0 mpph264enc` отвечает `provided-by /usr/local/lib/gstreamer-1.0/libgstrockchipmpp.so`: наша сборка. Сторонний DEB заранее удалён, чтобы однозначно установить источник результата.
3. Он **кодирует**: `videotestsrc ! mpph264enc profile=baseline header-mode=each-idr bps=2000000 ! h264parse ! filesink` создал 476 KB для 60 кадров 720p за **0.44 с реального времени**, включая генерацию и настройку конвейера, значительно быстрее реального времени. Результат чисто декодируется `avdec_h264`.
4. Работает **без root**: после назначения `/dev/mpp_service` режима `660 root:video` через udev и включения пользователя в `video`, `gst-inspect` отвечает от него. Именно так работает `mediad`; все предшествующие проверки выполнялись через `sudo`.

**Вся медиасвязка проверена на оборудовании:** от датчика до потока, пригодного для согласования WebRTC:

| Шаг | Подтверждение |
|---|---|
| Overlay применён | `csi2-dphy0` обнаружен, `rkisp` работает, десять `/dev/videoN` |
| Датчик определён | `imx219 2-0010: Model ID 0x0219, Lot ID 0x5a8e73, Chip ID 0x0773` |
| Узел захвата | `/dev/video0`, имя карты `rkisp_mainpath`, форматы до 3280x2464 |
| Кадры | Ровно 13,824,000 байтов для `--stream-count=10` при 720p NV12 |
| Аппаратное кодирование | `v4l2-ctl … --stream-to=-` в `fdsrc ! rawvideoparse ! mpph264enc` |
| Поток | Чисто декодируется; `h264parse` сообщает **1280x720 constrained-baseline** |

Номера узлов непостоянны между загрузками; узел захвата ищется по имени карты `rkisp_mainpath` в `/sys/class/video4linux/*/name`, как в `camera.rs:219`.

<a id="three-device-nodes-need-the-video-group-not-one"></a>
### Группа `video` нужна трём узлам, не одному

На это ушли три отдельных отладки; каждый сбой называл другую причину:

| Узел | Симптом доступа только root |
|---|---|
| `/dev/mpp_service` | `mpi_enc_test` ничего не пишет и **завершается с 0**; `mpph264enc` вообще не регистрируется |
| `/dev/rga` | Элемент есть, конвейер стартует, затем `Try to use uninit rgaCtx=(nil)` и множество `rga call blit fail` |
| `/dev/video0` | Уже появляется как `root:video`, поэтому не создаёт проблемы |

`setup-gstreamer.sh` ставит одно udev-правило для первых двух. **`mediad.service` требует `SupplementaryGroups=video`**: вместе с `Environment=GST_PLUGIN_PATH` всего две строки отделяют рабочий конвейер от четырёх запутывающих сбоев.

<a id="the-rotation-that-cost-22-fps"></a>
### Поворот, стоивший 22 кадров/с

Камера установлена с поворотом на четверть оборота. Очевидное решение — `videoflip` до tee, чтобы все потребители получили прямое изображение, — оказалось неверным по измерениям робота:

| | Ошибки RGA | Потери кадров `v4l2src` | Кадров/с | SoC |
|---|---|---|---|---|
| Без поворота | 0 | 0 | Около 30 | Нормально |
| С поворотом | 5522 за сессию | 1565 | 7–8 | 97 °C, CPU 408 МГц |

`mpph264enc` поручает преобразование UYVY→NV12 2D-блоку SoC почти бесплатно. Буфер выхода `videoflip` RGA отвергает: `10000 is unsupport format`, затем `RGA_BLIT fail: Bad address` на `rect[0, 0, 720, 1280]`. MPP переходит к преобразованию **каждого кадра программно**. CPU насыщается, SoC достигает температурного предела, частота падает до 408 МГц, камера теряет кадры. Сам поворот составляет меньшую часть затрат.

Поэтому конвейер ничего не поворачивает. Ориентация крепления *сообщается* через `media.video` один раз на канал управления; отображающий потребитель поворачивает сам. Консоль использует бесплатный CSS transform, обработчик восприятия объединяет поворот с уже выполняемым пересчётом. `--flip-in-pipeline` возвращает старое поведение потребителю, который сам поворачивать не умеет и может позволить себе затраты.

Если когда-либо действительно потребуется прямой поток, правильное решение — элемент RGA в наборе плагинов: 2D-движок выполняет поворот почти бесплатно, поэтому кодировщик и пользуется им.

<a id="the-3a-engine-has-to-be-waiting-before-the-stream-starts"></a>
### Механизм 3A должен ждать до запуска потока

`rkaiq_3A_server` подключается к ISP, затем ждёт события **запуска потока**; уже произошедшее событие он пропускает. Если перезапустить его во время передачи `mediad`, он навсегда останется на:

```
DBG: /dev/media0: wait stream start event...
```

Нет цикла статистики, автоэкспозиции и баланса белого, изображение зелёное. Перезагрузка «исправляет» лишь потому, что случайно обеспечивает правильный порядок.

Это стало регрессией без очевидной причины: **каждый `robotctl update apply` перезапускал механизм под работающим потоком**. Pre-install вызывает `setup-rkaiq.sh`, а скрипт перезапускает `rkaiq_3A`. Он даже печатал «restart the camera stream for it to take effect», но совет никто не выполнял и ничто не обеспечивало.

Теперь устанавливаемый скриптом drop-in закрепляет инвариант:

```ini
ExecStartPost=-/bin/systemctl --no-block try-restart mediad.service
```

При каждом запуске механизма поток перезапускается следом, поэтому ожидаемое событие ещё впереди. `try-restart` не трогает плату без `mediad`; `--no-block` предотвращает deadlock systemd, когда unit ждёт задания другого unit. При ручном восстановлении весь секрет — порядок:

```bash
sudo systemctl stop mediad && sudo systemctl restart rkaiq_3A && sleep 2 && sudo systemctl start mediad
```

<a id="rkaiqs-auto-exposure-fires-once-and-only-if-it-caught-the-stream"></a>
### Автоэкспозиция rkaiq срабатывает один раз и только если поймала поток

Изначально `scripts/setup-rkaiq.sh` оставлял AE rkaiq **включённой**. Рассуждение: прототип отключал её, чтобы избежать борьбы с собственным управлением экспозицией; в `mediad` экспозицией никто не владел, значит, пусть владеет механизм. Он действительно пишет в датчик, но не продолжает это делать.

Измерено на роботе с правильным порядком старта: `rkaiq_3A` в 17:24:01, `mediad` в 17:24:11, `wait stream start event success` в 17:24:17:

| Что | Значение |
|---|---|
| Запись `mediad` в 17:24:17 | `exposure=600 analogue_gain=1024` |
| `/dev/v4l-subdev3` через несколько минут | `exposure: 1589  analogue_gain: 1536` |
| Ручная запись `exposure=300 analogue_gain=256`, затем наблюдение 25 с | `300 / 256`, без коррекции |

Механизм один раз сошёлся к явно собственному значению и остановился. Уменьшение яркости вчетверо под ним не вызвало реакции. Одна сходимость при запуске — не автоэкспозиция: утка, ушедшая от окна в коридор, сохранит экспозицию окна.

**Если механизм пропустил запуск потока, как в предыдущем разделе, даже однократной коррекции нет.** Это измерили первым и неверно истолковали: датчик всё время оставался на `600 / 1024`, ручная запись сохранялась. Это выглядело как никогда не работавшая AE, хотя ей просто не дали поток. Одно чтение датчика не различает состояния; исправления нужны вместе, поскольку только правильный порядок делает разницу наблюдаемой.

`mediad::exposure` замыкает контур, перенесённый из `ae_loop` прототипа: средняя яркость сырой ветки tee дважды в секунду сравнивается с целью 90. Демпфированный мультипликативный шаг распределяется по регуляторам в порядке роста шума: выдержка до 600 строк, около 11 мс, чтобы не смазывать идущего робота; аналоговое усиление до 11×; затем выдержка до 1200 строк; затем цифровое усиление ISP. Жёсткий предел выдержки реален: вместо ограничения превышения длины кадра драйвер *растягивает время кадра*, поэтому 3500 строк тихо дают 15 кадров/с.

Здесь два отличия от прототипа, благодаря более подходящему месту в `mediad`. Яркость берётся из кадров tee для детектора утки: нет декодирования JPEG и повторного открытия камеры. Первая версия прототипа измеряла через ISP self path параллельным `v4l2-ctl`, конкурировала с собственным захватом на уровне драйвера и периодически убивала конвейер. Кроме того, первая запись считывается обратно: иначе узел без регулятора, отказ доступа или отсутствие `v4l2-ctl` оставляют постоянную экспозицию, неотличимую от исправляемой ошибки.

Теперь `setup-rkaiq.sh` устанавливает `CommCtrl.Enable = 0`. AE механизма не бесполезна: она срабатывает как раз при запуске потока, когда контур mediad сходится от собственных начальных значений. Это два конкурирующих писателя одного регулятора.

**Ловушка `v4l2-ctl` при измерениях:** одно неизвестное имя регулятора ломает весь `--set-ctrl` или `--get-ctrl`. `--get-ctrl=exposure,analogue_gain,digital_gain` возвращает `unknown control 'digital_gain'` без экспозиции, словно узел не содержит ни одного регулятора. Поэтому `mediad::exposure` записывает пару датчика и цифровое усиление ISP двумя вызовами.

<a id="two-things-known-to-be-unfinished"></a>
### Два известных незавершённых вопроса

**Битрейт оказался примерно в 50 раз ниже цели.** 15,553 байта за 3.3 с при `bps=2000000` — около 37 кбит/с. Либо сцена настолько статична, что CBR резко снизился, что правдоподобно: ISP на сырых настройках, изображение зелёное и шумное до `scripts/setup-rkaiq.sh`, перенесённого из прототипа и теперь запускаемого подготовкой и pre-install. Либо захват значительно ниже 30 кадров/с. Число кадров не измерено. Во втором случае подозревается режим датчика: IMX219 стартует в 3280x2464, прототип фиксирует режим через `media-ctl` перед каждым захватом (`camera.rs:277`).

**`rawvideoparse blocksize=1382400` — временный приём запуска, не проектное решение.** Он работает, поскольку `v4l2-ctl` выдаёт плотно упакованный NV12 вычисленного размера, и тихо ломается при появлении дополнения stride на другом разрешении. `camera.rs` это отмечает. Собственный цикл V4L2 mmap в `mediad` с подачей в `appsrc` получает настоящий stride драйвера вместо предположений.

<a id="two-things-the-pipeline-will-have-to-decide"></a>
## Два решения для конвейера

**Захват не может использовать `v4l2src`.** rkisp выдаёт ему пул из двух буферов, возврат буферов слишком медленен, теряется каждый третий кадр: около 20 кадров/с от датчика 30 кадров/с с «lost frames detected». `v4l2-ctl --stream-mmap` удерживает полную частоту, поэтому `microduck_runtime` захватывает через него и передаёт сырые кадры в `fdsrc` (`camera.rs:487`). `mediad` нужен либо такой подпроцесс, либо свой V4L2 mmap с подачей в `appsrc`.

**Четыре свойства `mpph264enc` требуют явного решения, а не наследования умолчаний.** Прочитано с элемента на плате:

| Свойство | По умолчанию | Что задавать в `mediad` | Почему |
|---|---|---|---|
| `profile` | `high` | **`baseline`** | Совместимый минимум WebRTC — Constrained Baseline (`profile-level-id 42e01f`). Новые браузеры согласуют High, старые нет. `baseline` даёт поток, который `h264parse` определяет как `constrained-baseline`; это проверено, а не предположено по enum с названием «baseline» |
| `header-mode` | `first-frame` | **`each-idr`** | SPS/PPS только в первом кадре означают, что присоединившийся позже или потерявший пакет партнёр ничего не декодирует. Конвейер Pi у `reachy_mini` делает то же через `repeat_sequence_header=1` для `v4l2h264enc`: требование одинаково, имя другое |
| `rotation` | `0` | **`180`** на alpha | IMX219 установлен вверх ногами. `microduck_runtime` исправляет это через `videoflip method=rotate-180`, полный проход CPU по каждому кадру на общем с `robotd` SoC. Кодировщик делает это аппаратно почти бесплатно |
| `bps` | `0`, авто | Явная цель | `rc-mode` уже `cbr`, подходящий для канала с потерями; битрейт не стоит оставлять автоматическому расчёту |

Два вопроса не требуют решения:

- **Регулятора B-кадров вообще нет**, поэтому требование «без B-кадров» из §5.5 выполнено конструктивно, а не настройкой.
- **Входной pad принимает `NV12`**, ровно формат rkisp. Между захватом и кодированием не нужны ни `videoconvert`, ни цветовое преобразование RGA.

Ключевые кадры должны задаваться через `min-force-key-unit-interval`, а не периодический `gop`: WebRTC запрашивает их по PLI партнёра; `gop` по умолчанию делает IDR каждую секунду независимо от необходимости.

<a id="the-constraint-flags-were-worth-reading-and-the-template-was-worse-than-the-flags"></a>
### Флаги ограничений стоило прочитать; шаблон оказался хуже флагов

Ранее страница заканчивалась просьбой проверить, а не предположить: enum `profile` называет `baseline` (66), а WebRTC согласует *Constrained* Baseline. Декодер constrained-baseline ожидает Baseline без FMO, ASO и избыточных slices. Прочитано на плате:

```
gst-launch-1.0 -v videotestsrc num-buffers=60 ! video/x-raw,format=NV12,width=1280,height=720,framerate=30/1 ! mpph264enc profile=baseline ! h264parse ! fakesink
```

На src pad `h264parse` согласует `profile=(string)constrained-baseline`. Поток верен: `profile=baseline` отключает CABAC и преобразование 8x8, MPP не создаёт FMO, ASO или избыточные slices; SPS содержит `profile_idc=66` с `constraint_set1_flag`.

**Неверен был шаблон pad; на это ушёл день.** Src-шаблон `mpph264enc` перечислял `profile = { baseline, main, high }` без `constrained-baseline`, запрашиваемого WebRTC. Это важно только когда кодировщик внутри `webrtcsink`, а не перед ним, поэтому здесь сначала ничего не заметили:

1. Обнаружение кодеков `webrtcsink` строит цепочку кодирования без выходных caps; `force_profile` равен true, вставляется capsfilter с `profile=constrained-baseline`.
2. `h264parse` удаляет из caps-запроса `alignment`, `stream-format`, `parsed`, но **не `profile`**. Требование достигает src pad кодировщика.
3. Пересечение с шаблоном пустое. Sink getcaps `GstVideoEncoder` ничего не возвращает; ошибка проявляется на четыре элемента выше как сообщение `videorate`, что он «could not transform NV12 … in anything we support».
4. Обнаружение исключает H.264 через `gst::warning!`, согласуется VP8, сессия умирает в `rtpvp8pay`. **Ни одна ошибка не называет профиль.**

Выводов два. Репозиторий плагинов теперь содержит расширяющий шаблон патч из одного слова, выпущенный как `v3`. Также `mediad` пришлось направить журнал GStreamer и bus конвейера в системный журнал, прежде чем что-либо стало видно. До этого все медиаошибки, включая обрыв сессии посреди согласования, были молчаливы.

<a id="pre-encoding-is-no-longer-the-shape"></a>
### Предварительное кодирование больше не используется

Ранее страница отмечала, что `webrtcsink` принимает готовый H.264 на sink pad; `appsrc ! mpph264enc ! h264parse ! webrtcsink` полностью исключает кодировщик из согласования. Это верно и сначала работало, но теряет две трудно возвращаемые функции. `webrtcsink` не управляет чужим кодировщиком, поэтому контроль перегрузки не адаптирует битрейт, а PLI не создаёт ключевой кадр: потерявший его зритель остаётся без изображения до очередного GOP.

Теперь `mediad` передаёт сырой NV12 и позволяет `webrtcsink` построить кодировщик, настраивая каждый через сигнал `encoder-setup`; именно там применяется таблица выше. Цена — участие кодировщика в согласовании, благодаря чему и нашёлся пробел шаблона.
