# Запуск этапа slice 2 на оборудовании

Заметки о запуске slice 2 на настоящем роботе. Всё ниже наблюдалось на Radxa Zero 3W, а не выводилось предположениями.

<a id="status"></a>
## Состояние

Slice 2 объединён. Единственная выявленная платой проблема — **паника `ort` вместо возврата ошибки, убивавшая поток управления и заставлявшая `robot.health` указывать неверную причину** — исправлена: `duck-control::policy::catching_ort_panics` преобразует её в `PolicyError`, используя существующий путь «удерживать позу и сообщить причину».

**Оба вопроса теперь закрыты на оборудовании.** Исправление проверили на плате, направив `robotd` через `ORT_DYLIB_PATH` на runtime 1.20.1: цикл продолжал работать, health сообщал несовпадение версий вместо сообщения мёртвого потока «has not completed a cycle yet». Затем slice 2 работал с инференсом внутри такта, а `0.2.0`, первый включающий это выпуск, установили из stable.

На этот файл больше ничто не ссылается. Он сохранён как запись фактических результатов платы; повторно применимая часть — процедура ниже, а команды для повторного использования должны попадать в [`cheatsheet.md`](../robot/cheatsheet.ru.md).

<a id="what-already-works-verified-on-the-board"></a>
## Что уже работает и проверено на плате

Версия `0.1.4` (slice 1), робот с подключённой проводкой:

- 15 сервоприводов и плата `imu_to_dxl` отвечают на `/dev/ttyS2`;
- цикл управления **50.0 Гц**, `missed=3` из 15022 тактов (0.02%);
- `robotctl health` → `healthy`;
- весь путь обновления проверен: установка, контроль здоровья, фиксация и автоматический откат.

Значит, шина, сервоприводы, IMU, частота и обновлятор **не подозреваются**. Новая ошибка относится к коду slice 2 или ONNX Runtime платы.

<a id="the-failure"></a>
## Сбой

`sudo robotctl update apply daemon --ref slice-2-walk-stand` откатился:

```
  HealthGate
  RollingBack
{
  "attempted": "0.1.4-dev.58.6781f98",
  "outcome": "rolled_back",
  "reason": "health check failed: not healthy within 30s:
             control loop has not completed a cycle yet",
  "reverted_to": "0.1.4"
}
```

Журнал показал настоящую причину:

```
thread 'control' panicked at ort-2.0.0-rc.11/src/lib.rs:191:41:
Failed to load ONNX Runtime dylib: Error { code: GenericFailure, msg:
  "ort 2.0.0-rc.11 is not compatible with the ONNX Runtime binary found at
   `libonnxruntime.so`; expected version >= '1.23.x', but got '1.20.1'" }
```

<a id="why-the-health-reason-was-useless"></a>
### Почему сообщение health оказалось бесполезным

`RobotState::health` сообщает `control loop has not completed a cycle yet`, когда `ticks == 0 && startup_bus_failures == 0`. Паника *потока* управления не убивает процесс, поэтому `robotd` продолжает обслуживать сокет и возвращает именно это сообщение, не называющее причину. Читать его следует как «цикл ни разу не начал работу и не сохранил причину», а не «ещё запускается».

<a id="two-causes-one-is-fixed"></a>
## Две причины. Одна исправлена.

**1. На плате был несовместимый runtime — исправлено в #17, объединено.** `setup-board.sh` закреплял ONNX Runtime 1.20.1; `ort 2.0.0-rc.11` требует >= 1.23. Проверка теперь учитывает версию: повторный запуск скрипта заменяет неверную вместо сообщения «уже установлен».

Нижняя граница и целевая версия находятся в `[workspace.metadata.onnxruntime]` корневого `Cargo.toml`; #18 формирует из них `hooks/preinstall`, чтобы устаревшая плата исправлялась либо обновление прерывалось *до переключения*, а не устанавливалось с последующей паникой.

**2. `ort` вызывает панику вместо ошибки — исправлено.**

`ensure_runtime()` проверяет dylib через `libloading` прежде, чем дать `ort` доступ. Ранее комментарий утверждал:

> успешная проба означает успешную загрузку, поэтому паника невозможна

**Плата это опровергла.** Проба доказывает лишь возможность *загрузки* библиотеки; 1.20.1 загружается нормально. Затем собственная проверка совместимости `ort` отклоняет *версию* и вызывает панику внутри `setup_api`, невидимую `ensure_runtime`. Защита закрывает случай отсутствия, но не неверной версии; по конструкции она не могла закрыть и все будущие паники `ort`.

Исправление этого не пытается делать. `catching_ort_panics` оборачивает вызовы `ort` внутри `Policy::load` и переводит любую панику в `PolicyError::RuntimePanic` с её сообщением: числа версий выше составляют весь диагноз; потеря их сделала бы причину health бесполезной. Паника попадает в существующий путь незагружаемой политики: записать `policy unavailable; holding the pose`, сохранить причину, оставить `controller` равным `None`, **продолжить такты с нужной частотой** и сообщить `policy unavailable: <reason>`, чтобы обновлятор откатил выпуск с названной причиной.

Два уточнения:

- Перехватывается только работа `ort`, а не весь `load`, чтобы наша собственная ошибка не переименовывалась в «policy unavailable». `AssertUnwindSafe` нужен, поскольку `Session` не является `UnwindSafe`; при успехе сессии перемещаются в `Policy`, при ошибке уничтожаются, поэтому после перехвата наше состояние не используется.
- **`panic = "abort"` лишит это смысла.** Сейчас в корневом `Cargo.toml` нет `[profile.release]`; добавление такого режима незаметно вернуло бы остановку управления из-за паники.

<a id="what-the-tests-cover-and-what-they-do-not"></a>
### Что покрывают тесты, а что нет

Офлайн в `duck-control` и `robotd` проверено: паника пути `ort` становится ошибкой и сохраняет сообщение; успех проходит без изменений; непечатаемые данные паники всё равно дают причину. `an_unloadable_policy_holds_the_pose_and_reports_why` проверяет, что незагружаемая политика оставляет цикл работающим, а исходная причина присутствует в строке health.

Офлайн не проверено прохождение *настоящей* паники `ort` через цикл управления. Для воспроизведения нужна неверная версия runtime на плате; имитация внутри `Policy::load` потребовала бы поставлять переключатель внедрения ошибок в `duck-control` ради проверки трёх строк. Это закрывает проверка на плате ниже.

<a id="verifying-on-the-board"></a>
## Проверка на плате

Плате однократно нужен ключ разработки, иначе `--ref` отклоняется. `install.sh` устанавливает ключ и переключает `allow_dev_keys`, если передать путь к открытой части:

```bash
sudo DUCK_TOKEN="$DUCK_TOKEN" DUCK_DEV_KEY=/tmp/team.dev.pub sh /tmp/install.sh
```

`team.dev.pub` хранится в `deploy/dev-key/` вне `trusted_keys/`, поэтому по умолчанию не устанавливается. Ручной эквивалент приведён в [`../deploy/README.md`](../../deploy/README.ru.md).

Затем:

```bash
sudo robotctl update apply daemon --ref slice-2-walk-stand
```

**Заново скачайте `setup-board.sh`, прежде чем доверять ему.** `/usr/local/sbin/robot-setup-board` — снимок последнего запуска, не обновляющий себя. Он может незаметно исполнять логику до #17 и говорить «уже установлен» о несовместимом runtime.

Успех — `ONNX Runtime  1.28.0` в блоке состояния, фиксация обновления вместо отката и:

```bash
journalctl -u robotd -b --no-pager | grep -E 'policy|control loop'
```

где после `policy loaded` следует `control loop running driving=true`. Затем повторно измерьте частоту: slice 2 добавляет инференс в тот же такт; сравнивайте с baseline slice 1 выше (50.0 Гц, `missed=3`). Большой рост `missed` — стоимость инференса, а не джиттер.

<a id="conventions"></a>
## Соглашения

- **Создавайте ветку в свежем клоне под `/tmp`**, а не в рабочей копии. Устаревшее рабочее дерево общего клона привело к тому, что #13 незаметно отменил #12: `git checkout -b` перенёс незакоммиченные изменения в новую ветку, а `git add -A` зафиксировал их как удаления.
- Trailer коммита — `Assisted-by: Claude:claude-opus-5`. Никогда `Co-Authored-By`.
- Ограничивайте тесты: `cargo test -p <crate>`, один раз. `--workspace` оставляйте для проверки перед PR.
- Согласовывайте архитектурные решения.
- Исправляйте ошибки пути выпуска и выпускайте обновление; не передавайте локальный обходной способ.

<a id="deliberately-not-done"></a>
## Намеренно не сделано

- Backend MuJoCo и оставшиеся шесть навыков.
- Ограничения отдельных суставов. `duck-control/src/safety.rs` ограничивает ход актуатора (±π), а не диапазон каждого сустава; для этого нужен включённый в проект alpha MJCF.
- Эталонные векторы наблюдений из `microduck_brain`, закрепляющие кодирование 61-D относительно прототипа. Тесты раскладки проверяют форму, а не совпадение с оригиналом.
- `hooks/postinstall`: #18 поставляет только `preinstall`.
