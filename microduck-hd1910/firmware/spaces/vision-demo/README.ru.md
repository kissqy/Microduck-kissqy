<a id="microduck-vision-demo"></a>
# Демонстрация зрения microduck

Робот в домашней сети передаёт камеру в этот Space как H.264, а OpenCV здесь обрабатывает каждый декодированный кадр. Ничто не находится в сети робота, ретранслятор не используется.

**Не редактируйте Space напрямую.** Исходники — `spaces/vision-demo/` в `pollen-robotics/microduck`, публикация — `scripts/publish-space.sh vision-demo`.

<a id="the-robot-dials-us-and-that-is-the-whole-design"></a>
## Робот подключается к нам — в этом весь принцип

Получение камеры через rendezvous означает WebRTC; между роботом за домашним роутером и контейнером дата-центра ему нужен резервный **relay candidate**. Всю историю Space его не было: стандартный relay роботов называл хост без DNS. Ожидаемый результат был «сигнализация работает, медиа нет». Умолчание исправлено (`remote-access-design.md`, §6), но обратное направление всё ещё подходит Space: ретрансляция расходует оплачиваемый владельцем лимит на каждый кадр, а здесь их декодирует только программа.

Поэтому направление перевёрнуто:

```
this Space ──media.stream {url: "wss://…/frames"}──► rendezvous ──► the duck
the duck   ═════════ H.264, outbound wss, direct ═════════════════►  this Space
```

Исходящий WebSocket работает: робот уже держит такой к Space всё время доступности, благодаря чему появляется в списке. NAT перестаёт участвовать, прокси учётных данных не нужен, **rendezvous передаёт инструкцию, не пиксели**. Это масштабируется лучше передачи данных через сервис, от которого зависит парк mini.

Вызов — `media.stream`, отвечает сам `mediad` (`mediad/src/stream.rs`); один ключ имеет три формы: `url` запускает поток, `url: null` останавливает, отсутствие `url` запрашивает текущее состояние.

<a id="what-that-costs"></a>
## Цена решения

**Нет обратного медиапути.** Так нельзя управлять роботом или наблюдать его в реальном времени; зрителю нужен WebRTC и требования §6. Это случай программного потребителя.

**Несколько кадров в секунду, не тридцать.** Пяти при ширине 640 пикселей достаточно модели; это малая доля кодирования видеодорожки. Частоту на роботе обеспечивает `videorate` ветки, не вежливая просьба получателя.

**H.264 с доступным JPEG.** Аппаратный кодировщик нагружает VPU, не ядро; межкадровое предсказание экономит байты. На синтетике измерено 0.5 KB против 6.5 KB JPEG; реальная камера даст меньшую, но однонаправленную разницу. Цена — получатель не декодирует до ключевого кадра, а потерянная единица портит всё до следующего ключевого. Оба случая обработаны: `mediad` просит ключевой кадр при открытии клапана, повторяет SPS/PPS перед каждым и при пропуске ждёт следующего ключевого вместо передачи через разрыв. `media.stream {"encoding": "jpeg"}` подходит часто переподключающемуся получателю, которому мгновенный старт важнее полосы.

**Кадры приходят правильно ориентированными.** Поворот конвейера выполняется до tee; видеодорожка и эта ветка несут прямое изображение, hello сообщает `rotate: 0`, а угол крепления — справочно. `filters.upright` здесь не используется, но сохранён для WebRTC-потребителя, которому сообщается угол и который поворачивает сам.

> Примечание переводчика: выше сохранено описание именно этой исторической демонстрации. В [записи запуска медиатракта](../../docs/project/media-bringup.ru.md#the-rotation-that-cost-22-fps) описан последующий отказ от поворота каждого кадра в основном конвейере и передача угла потребителю. При работе с конкретной версией проверяйте `rotate` в её ответе.

<a id="whose-camera-this-is"></a>
## Чья это камера

Endpoint кадров открыт, как URL любого Space. Робот предъявляет **собственный токен учётной записи** при handshake; он разрешается через `whoami-v2`, как в rendezvous. Кадры относятся к полученному имени пользователя, посетитель видит только роботов своей учётной записи. Иначе кто угодно мог бы отправлять кадры и, хуже, посетитель увидел бы чужую камеру. Токен разрешается один раз на соединение и не сохраняется.

<a id="running-it-yourself"></a>
## Самостоятельный запуск

Однократно:

```bash
uv venv && uv pip install -r requirements.txt
```

Затем:

```bash
DUCK_RECEIVER=ws://192.168.1.50:7860/frames uv run app.py
```

`DUCK_RECEIVER` должен быть адресом, **доступным роботу**, например адресом компьютера в его сети, не `localhost`. В Space он выводится из `SPACE_HOST` без настройки. `HF_TOKEN` либо данные `hf auth login` заменяют кнопку входа, имитируемую вне Space.

<a id="why-this-is-a-docker-space"></a>
## Почему это Docker Space

Сервером владеет FastAPI, в него монтируется Gradio: кадры приходят по собственному WebSocket-маршруту. Это задокументированное направление; обратное добавление маршрутов в приложение Gradio имеет известные проблемы WebSocket. Собственный `uvicorn` снимает вопрос поддержки маршрута платформой. `microduck-console` использует Docker Space по другой причине (§5.0); это второй случай.

<a id="there-is-no-webrtc-stack-in-here-any-more"></a>
## Стека WebRTC здесь больше нет

Раньше кадры получали через `reachy_mini[central-consumer]`: `aiortc`, `av` и shim DTLS-шифра поверх приватного метода, без возможности подключиться из дата-центра. Теперь звонит робот; остались `gradio`, `fastapi`, `opencv`, `requests`, `av`. Последний вернулся для H.264 как декодер, не транспорт: без ICE, DTLS, сигнализации и участия NAT.
