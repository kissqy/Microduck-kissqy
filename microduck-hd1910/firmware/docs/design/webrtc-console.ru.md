# Клиент WebRTC: от тестовой страницы к консоли робота

Состояние: включено в основную ветку · Дата: 2026-08-25 · Ответственный: pierre

`mediad/webclient/index.html` подтвердил работоспособность транспорта. Этот документ описывает превращение страницы в пользовательский инструмент: её отдаёт робот вместо `python3`, робот находится по уже передаваемому `btd` адресу, а управление использует действительно разрешённые `route.rs` вызовы.

Парный документ [`remote-webrtc.md`](remote-webrtc.ru.md) определяет транспорт: сигнализацию, модель сессии, авторизацию и разрешённые вызовы участника. На пересечениях главным источником остаётся он, а эта страница ссылается на него.

**Все четыре изменения реализованы.** Страница была написана до первой строки кода, чтобы решения можно было обсуждать, а не выводить из diff. Она сохранена ради рассмотренных альтернатив. Если текст и код разойдутся, ответ даёт код: `mediad/src/web.rs` обслуживает страницу, `mediad/src/producer.rs` заполняет `meta`, команды `ip` и `open` в `duckctl` находят робота, `mediad/webclient/index.html` является консолью. Остаток работ описан в §7.

<a id="0-what-was-wrong-with-it"></a>
## 0. Что было не так

Для исходной цели — почти ничего. Страница отвечала на вопрос «получает ли браузер видео и datachannel», и ответ был положительным. Но как у *клиента* у неё шесть проблем:

| | |
|---|---|
| Нужен `python3 -m http.server`. | Второй инструмент и второй терминал; страницу отдаёт ноутбук для общения с роботом. |
| URL вводится вручную. | `ws://radxa-zero3.local:8443`, причём `radxa-zero3` — hostname **каждой** платы из одного образа (это сказано в месте резервного выбора `configd/src/main.rs`), поэтому два робота в одной сети конфликтуют. |
| Блок комментариев состоит в основном из предупреждений. | `file://`, Private Network Access, http вместо https; заголовок уже дважды исправляли (`7f52a34`). |
| Проверяется протокол, а не робот. | `route.rs` разрешает move, head, look, pose, mouth, do, sound, enable, init, relax, stop, subscribe, `tof.stream`, `pad.input`. Страница предлагает `robot.health` и поле JSON. |
| Нигде не поставляется. | Ни один `--include` её не называет, поэтому установленный робот не имеет клиента. |
| Нельзя понять, к какому роботу подключились. | `meta` отправителя не задано, и `list` возвращает только ID. |

Каждый пункт — лишний шаг между человеком и работающим роботом, и ни один не связан непосредственно с WebRTC.

<a id="1-mediad-serves-the-page"></a>
## 1. Страницу отдаёт `mediad`

**Реализовано:** `mediad/src/web.rs`, `--web-port`, по умолчанию 8080.

HTTP-слушатель в `mediad`, один маршрут, возвращающий страницу. `http://<robot>:8080/` — больше ничего запускать не нужно.

Это устраняет сразу четыре проблемы:

- **Без `python3`.** Инструкция превращается в адрес.
- **Без ручного URL сигнализации.** По умолчанию страница использует `ws://${location.hostname}:8443`: её отдал робот, поэтому она знает собеседника.
- **Private Network Access больше не применяется.** Chrome блокирует запрос из *публичного или непрозрачного* origin к частному адресу. У страницы с `192.168.x` частный origin, поэтому проверка, ломавшая `file://`, вообще не достигается. Предупреждение в заголовке исчезает вместе с самой возможностью этой ошибки.
- **Одна версия.** Страница и бинарник поставляются вместе (§1.2), поэтому клиент из рабочего клона больше нельзя случайно направить на робота из другого выпуска.

<a id="11-which-http-server"></a>
### 1.1 Какой HTTP-сервер

**Решено: `axum`.** Он уже есть в `Cargo.lock`: `updater` использует его как dev-dependency тестового зеркала. Значит crate проверен с этим инструментариями и кросс-сборкой.

Альтернатива — самописный ответчик HTTP/1.1: один файл и один метод, возможно, около шестидесяти строк. Но шестьдесят строк ручного разбора запросов на `0.0.0.0` — это доступный всем в сети парсер ради отказа от уже разрешаемой сборкой зависимости. При этом лежащий под `axum` `hyper` — наиболее изученная реализация такого парсера на этом языке.

`RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` в `mediad.service` уже разрешает слушатель; unit не меняется.

<a id="12-the-page-is-embedded-not-installed"></a>
### 1.2 Страница встраивается, а не устанавливается

`include_str!("../webclient/index.html")`, обслуживание из памяти.

Альтернатива — установить её в `/opt/robot/daemon/current/webclient/` и читать при запросе. Тогда нужна строка `--include` в *трёх* местах (`_build-release.yml`, `dev.yml`, `scripts/dev-push.sh`), согласованность которых охраняют проверки упаковки `xtask` и которые уже расходились раньше. Кроме того, сетевой запрос вызывал бы файловое чтение из службы с `ProtectSystem=strict`, а вопрос «какую страницу отдаёт этот робот» получил бы два ответа.

Встраивание требует пересборки ради изменения стилей. Для страницы, являющейся частью интерфейса службы, это правильный компромисс.

<a id="13-two-ports-and-nobody-has-to-know-there-are-two"></a>
### 1.3 Два порта, о которых пользователю не нужно знать

Слушатель 8443 принадлежит `webrtcsink` (`run-signalling-server`, настраиваются только `-host` и `-port`), поэтому добавить туда маршрут страницы нельзя. Два порта: 8080 отдаёт страницу, 8443 остаётся сервером сигнализации. Путь медиа не меняется; это главный довод начать именно так.

**Два порта — деталь реализации, которая не должна стать действием пользователя.** Три обязательных условия удерживают её внутри:

- **Вводится один адрес:** `http://<robot>:8080`. К 8443 обращается JavaScript страницы, не человек. `duckctl open` (§2) убирает даже этот единственный ввод.
- **`mediad` подставляет URL сигнализации при отдаче страницы**, вместо константы в ней. Он знает хост запроса и собственный `--port`, поэтому страница получает действительное значение: один `str::replace` встроенной строки при запуске. Так `--port` можно безопасно менять, не оставляя вторую устаревшую копию.
- **Единственная ошибка двух портов описывается словами.** Если 8080 отвечает, а 8443 нет, вероятнее всего из-за межсетевого экрана, страница должна сообщить: *страница получена от этого робота, но порт сигнализации не ответил*, а не `websocket error`. Только через такую диагностику второй порт должен становиться виден человеку.

Вариант одного порта — запускать сервер сигнализации самим: upstream публикует его библиотекой рядом с плагином. Signaller `webrtcsink` тогда указывает на `ws://127.0.0.1:8080/ws`, а один `axum` обслуживает страницу и протокол на одном origin. Это больше работы и вторая версия протокола, которую нужно согласовывать с поставляемой `.so`, поэтому в первое изменение не входит.

**Но именно к этому придётся прийти.** Браузер не даёт микрофон странице, полученной по простому http с частного адреса, а в некоторых браузерах и геймпад: это API безопасного контекста, которым `http://192.168.1.42` не является. `http://localhost` является — потому проблему пока никто не заметил. Двустороннее аудио описано в `remote-webrtc.md` §2. Роботу потребуется TLS; встроенный сервер `webrtcsink` не позволяет настроить сертификат, обычный сервер `axum` позволяет. Последовательность: сейчас два порта, собственная сигнализация при появлении аудио или браузерного геймпада, TLS в тот же день.

Это стоит записать заранее, а не выяснять во время подключения микрофона.

<a id="2-finding-the-robot-two-commands-and-one-of-them-is-already-hand-rolled"></a>
## 2. Поиск робота: две команды, одна уже написана вручную

**Реализовано:** `duckctl ip` и `duckctl open`, сначала реклама, затем резервный `net.status`.

`btd` помещает IPv4 робота в рекламное объявление под company id `0xFFFF`, а `duckctl` уже разбирает его: `Address::At`, `Unassigned`, `Unsaid` — три ответа вместо двух. `scan` уже выводит адрес. Значит нужна команда, а не новый механизм.

### 2.1 `duckctl ip`

Только адрес робота в stdout, чтобы работало `ssh microduck@$(duckctl ip)`: инструмент уже разделяет диагностику в stderr и данные в stdout.

**Идея не новая для репозитория: её уже однажды реализовали неудачно.** `scripts/dev-push.sh` требуется ровно это. Его `resolve_board()` вызывает `duckctl wifi status` и пропускает JSON через встроенную в shell шестистрочную программу Python, извлекающую `result.ip4`. Это готовая команда, пока не получившая своего места.

Чтение объявления лучше `net.status` в трёх отношениях, каждое видно по обходам в `dev-push.sh`:

- **Нет подключения, значит нет сопряжения и PIN.** У `resolve_board` есть целая ветвь «робот отказал в `net.status`, чаще всего неверный PIN». Чтение объявления невозможно отклонить, и ветвь исчезает.
- **Секунды вместо десятков секунд.** `dev-push.sh` кеширует адрес каждого робота именно потому, что BLE-обнаружение занимает десять-двадцать секунд. Сканирование до первого подходящего объявления занимает около секунды: `duckctl` уже опрашивает до появления кандидата вместо ожидания всего `SCAN_TIME`.
- **Адрес не устарел.** `reconcile_advertisement` в `btd` перечитывает `net.status` каждые `ADV_POLL` (5s) и обновляет объявление при изменении. Реклама — это `net.status` с пятисекундной задержкой, намного меньше времени, за которое новая аренда уже нарушает SSH.

**Но обязательна одна резервная попытка.** Сопряжённый с этим Mac робот часто перестаёт рекламировать ему службу; ради этого у `duckctl` есть уровни поиска. Поэтому, не увидев объявления, `ip` подключается и спрашивает `net.status`, как сейчас делает `dev-push.sh`. Сначала дешёвое чтение, затем вызов. Без резерва команда ломалась бы именно на ноутбуках, использующих её чаще всего.

Трёхвариантный `Address` уже содержит правильные объяснения ошибок:

- `Unassigned`: у робота нет сети. Исправление — `duckctl wifi connect` по BLE, поскольку `net.connect` намеренно запрещён через WebRTC: «робота, никогда не видевшего сеть, нельзя настроить через эту сеть».
- `Unsaid`: выпуск старше появления адреса в рекламе `btd`. Резервный вызов всё равно ответит; обновление ускорит поиск.

Третий потребитель, помимо двух описанных: `install-dev.md` начинается с требования **IP-адреса платы**, отмечая ненадёжный mDNS, но не объясняет получение адреса.

### 2.2 `duckctl open`

Найти адрес и открыть `http://<address>:8080/` в браузере. `--print` вместо этого печатает URL для скрипта или машины без браузера; `--port` нужен роботу с нестандартным `--web-port`.

Отдельная команда вместо документированной shell-подстановки нужна по одной причине: **порт по умолчанию должен быть задан ровно в одном месте, которое человеку не приходится читать**. `open "http://$(duckctl ip):8080"` работает, но это строка, которую однажды пишут, а потом бесконечно ищут.

<a id="23-not-these"></a>
### 2.3 Не эти варианты

- **`duckctl url`.** Это уже `open --print`: третья команда, всё содержание которой — номер порта.
- **Столбец URL в `scan`.** Он показывает также наушники, а строки роботов уже содержат адрес. Достаточно примечания под списком с указанием `open`.
- **Обязательное подключение.** Обе команды читают рекламу с резервным подключением. Команда, *требующая* сопряжения, была бы другого рода и относилась бы к `wifi` и `update`, а не поиску робота.

<a id="24-the-loop-this-closes-and-the-one-follow-on"></a>
### 2.4 Какой цикл замыкается и что следует дальше

BLE настраивает сеть, затем передаёт URL для неё. Два транспорта становятся последовательностью, а не альтернативами. Это важно, поскольку `route.rs` намеренно запрещает `net.connect` по WebRTC, а здесь описана вторая половина такого решения.

Следующий шаг — отдельным изменением, не в этих четырёх: `resolve_board` в `dev-push.sh` превращается в `client --name "$1" ip`, удаляя встроенный Python и ветвь неверного PIN. Отдельно потому, что затрагивается установка сборок, и это должно произойти после нескольких ручных использований `ip`.

`duckctl` — временная замена телефонному приложению, поэтому здесь остаются две команды без нового механизма. Долговечные части — передача адреса `btd` и обслуживание страницы `mediad` на известном порту. Приложение выполнит те же два шага нативно.

<a id="3-the-tool-is-named-after-a-transport-it-is-about-to-stop-being"></a>
## 3. Инструмент назван по транспорту, которым скоро перестанет ограничиваться

**Решено и реализовано:** `duck-btctl` стал `duckctl` в собственном crate. Далее сохранено обоснование ради рассмотренных альтернатив.

`open` запускает браузер по http URL, а имя инструмента содержало `bt`. Это оказалось указанием на проблему шире одной команды.

**Сама `open` находится на своём месте.** Её суть — Bluetooth: сканирование рекламы для поиска робота; заключительный `xdg-open` занимает одну строку. `duckctl open` читается как «найди робота по радио и покажи консоль» — именно это она делает. Так же `wifi connect` является Wi-Fi-командой, полностью реализованной через BLE.

**Но имя неверно по причине появления `mediad`, а не `open`.** У робота появляется второй транспорт; они по проекту имеют *разные* наборы методов: `robot.move` запрещён по BLE и разрешён по WebRTC, `net.connect` — наоборот. Человеку понадобятся оба, но ему нужен не выбор исполняемого файла, а инструмент, знающий подходящий транспорт и сообщающий, когда не подходит ни один:

> `wifi connect` работает только через Bluetooth, а этот робот не передаёт рекламные объявления.

Такой инструмент не может называться `btctl`. Имя `btctl` ещё и незаметно учит всех, что Bluetooth — способ обращения к роботу, именно когда он перестаёт быть единственным.

<a id="31-it-is-a-move-not-a-rename-and-that-fixes-two-existing-warts"></a>
### 3.1 Перенос, а не переименование: исправляются две старые шероховатости

Независимый от транспорта клиент не может остаться `btd/examples/duck-btctl.rs`. Ему потребуются и `btleplug`, и WebSocket-клиент, тогда как `btd` — служба BLE; пример её использования не подходит половине функциональности. Поэтому правильная форма — отдельный участник workspace, попутно устраняющий две неудобные особенности:

- **Команда установки.** `cargo install --path btd --example duck-btctl` достаточно необычна, чтобы `dev-push.sh` имел резерв для клонов, где её не запускали: `cargo run -q -p btd --example duck-btctl`. Для `cargo install --path duckctl` резерв не нужен.
- **Пример, который на самом деле продукт.** Формат примера удерживал `btleplug` вне робота: dev-dependencies примера не попадают в артефакт. Собственный crate даёт то же, не будучи зависимостью ни одной службы. Гарантия выражена прямо, а не побочным эффектом расположения файла.

### 3.2 `duckctl`

Пара с `robotctl` соответствует использованию: `robotctl` — на роботе, `duckctl` — обращение к нему. Сохраняется семейство `duck-`, уже используемое репозиторием; имя достаточно короткое без alias.

Один `duck` короче, но занят: Cyberduck поставляет такой CLI, вполне вероятный на Mac. `microduck` — имя репозитория и слишком длинно для команды, вводимой двадцать раз в час.

<a id="33-what-was-not-rewritten"></a>
### 3.3 Что не переписывалось

196 ссылок примерно в двадцати файлах, в основном в прозе. **Датированные записи сохраняют старое имя.** `update-over-ble.md` и `install-path-gap.md` описывают конкретный момент: сеанс обновления, четыре ошибки установки и их устранение. Подстановка имени, которого тогда ещё не было, сделала бы запись слегка неверной. Их *ссылки* исправлены для работоспособности; текст — нет.

`roadmap.md` в том же каталоге — исключение: это не запись момента, а описание текущего репозитория вплоть до таблицы crates. Таблица с несуществующим каталогом просто ошибочна.

**Без слоя совместимости и alias.** Один пользователь и один робот: работающий `duck-btctl` означал бы второе согласуемое имя и причину ещё год хранить старое в истории оболочки.

<a id="34-what-keeps-it-off-the-board"></a>
### 3.4 Что удерживает клиент вне платы

`cargo board --bins` в `dev-push.sh` и workflow выпуска собирает всех участников по умолчанию для aarch64. Пример исключался автоматически; crate стал бы кросс-компилироваться, то есть путь выпуска собирал бы Bluetooth-стек для платы, которой он не нужен.

**`default-members` в корне workspace: всё, кроме `duckctl`.** Один список вместо перечисления бинарников в двух местах вызова `--bins` и ручного согласования — именно о таком сбое репозиторий постоянно пишет. `--workspace` не меняется, поэтому CI проверяет lint и тесты как раньше.

<a id="4-the-page-becomes-a-console"></a>
## 4. Страница становится консолью

**Реализовано:** `mediad/webclient/index.html`, по-прежнему один файл без этапа сборки.

Разрешённое подмножество велико, но почти недоступно со страницы. Новая организация — по целям человека:

| | |
|---|---|
| **Заголовок** | Имя робота, выпуск, версия API из `hello` и `system.info`; запросы отправляются автоматически при открытии канала. |
| **Видео** | Плюс качество связи через `getStats()`: битрейт, fps, потери, RTT. До изменения ухудшение потока давало лишь худшую картинку и молчащий журнал. |
| **Управление** | Клавиши и экранный стик → `robot.move` с постоянной частотой; перетаскивание по видео → `robot.look`. |
| **Поза** | `robot.enable`, `init`, `relax`, `stop`, `shutdown`; последние два требуют подтверждения. |
| **Действия / звук** | Перечисления `Do` и `Sound` в меню. |
| **Телеметрия** | `robot.subscribe` на 2 Hz в живую панель: режим и здоровье. |
| **Консоль** | Поле сырого JSON, журнал и две кнопки проверки отказов свёрнуты: они проверяют маршрутизацию, а не управляют роботом. |

Три ограничения:

- **Кнопка stop не должна выглядеть аварийным выключателем.** `route.rs` разрешает `robot.stop`, поскольку канал надёжен, а deadman и так останавливает робота при прекращении намерений. Там прямо сказано, что интерфейс не должен подразумевать физический e-stop. Текстовая кнопка, не большой красный круг.
- **Разница версий — баннер, а не закрытая дверь.** При несовпадении в `hello` страница сообщает об этом и продолжает работать; то же правило принял `duck-btctl` в #102.
- **Всё ещё один файл без сборки.** Благодаря этому клиент вообще запускают. Если одного файла станет мало, будут три — `index.html`, `app.js`, `app.css` и три `include_str!`; по-прежнему без сборки и npm.

Управление со страницы также впервые по-настоящему проверяет два пока не испытанных утверждения `remote-webrtc.md`: deadman останавливает робота при разрыве сессии (§6), а упорядоченности `control` достаточно для корректности `intents.rs` (там же). В них легко поверить, но дорого ошибиться.

<a id="5-the-robot-names-itself-before-the-session-starts"></a>
## 5. Робот сообщает имя до начала сессии

**Реализовано:** `mediad/src/producer.rs`.

`webrtcsink` принимает структуру `meta`, которую сервер сигнализации отдаёт каждому участнику в `list`. Страница уже пишет её в журнал, но она пустая. Заполнить из `configd`: имя, серийный номер, выпуск, `API_VERSION`.

Маленькое изменение даёт три результата: страница называет робота до сессии; клиент с двумя отправителями различает их; rendezvous из §7 получает необходимое поле маршрутизации. Самая дешёвая задача списка.

<a id="6-what-it-opens-but-is-not"></a>
## 6. Какую возможность это открывает, но не реализует

Интерфейс для серверных программ. Сервер `axum` консоли делает соседний со страницей WebSocket похожим на ещё один маршрут, но управляющая роботом программа по определению находится вне LAN, а транспорт уже есть: канал управления rendezvous ([`remote-access-design.md`](remote-access-design.ru.md) §3.8). Этот слушатель предоставляет программам только `/frame` для снимка в LAN, ничего больше.

<a id="7-order-and-what-is-left"></a>
## 7. Порядок и оставшаяся работа

Четыре независимых изменения вошли отдельно в таком порядке:

1. **Раздача страницы с подстановкой URL сигнализации.** Удалены инструкция python и предупреждения. Небольшая основа упростила всё остальное. Версия API подставляется так же для баннера §4: литерал в странице стал бы второй копией `API_VERSION`, устаревающей при повышении и ошибочно сообщающей совпадение.
2. **`meta` отправителя.** Ещё меньшее и независимое изменение.
3. **`ip` и `open` в `duckctl`.** Только клиент, без изменения служб.
4. **Консоль.** Крупная часть, выполненная последней на уже доступной странице.

**Не сделано и намеренно отделено:** `resolve_board` в `dev-push.sh` всё ещё использует ручной путь `duckctl wifi status` и шесть строк Python (§2.4). Он должен стать `duckctl ip`, удалив Python и ветвь неверного PIN. Отдельно, поскольку затрагивает отправку сборок и должно следовать после нескольких ручных проверок `ip`.

<a id="8-not-doing"></a>
## 8. Что не делается

- **Ограничение доступа к консоли.** Решение принадлежит §4 `remote-webrtc.md`; здесь его условия не меняются. Флаг `--no-web` для отключения страницы полезен в описанном там домашнем случае: один флаг, не новый механизм.
- **JS-фреймворк, сборщик или `gstwebrtc-api`.** Страница реализует протокол вручную, потому что требующий npm клиент никто не запускает. Это остаётся верным и при четырёхкратном росте размера.
- **TLS.** §1.3 объясняет, когда он понадобится и почему не сейчас.
- **Порт в рекламном объявлении.** Оно содержит четыре байта IPv4; нестандартный `--web-port` робота означает `--port` в `duckctl open`, а не изменение формата передачи.
