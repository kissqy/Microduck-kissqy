# Шпаргалка

`robotctl` запускается на роботе. Все команды взяты из `--help` поставляющей их ветки, а не по памяти.

Для чтения привилегии не нужны. Всё **изменяющее** робота требует `sudo` либо пользователя из `--allow-user`/`--allow-group` у `configd`, `allow_uids`/`allow_gids` в `updater.toml` у `updaterd`.

Сборки веток, кандидаты выпусков и ловушки перезапуска описаны в [`cheatsheet-dev.md`](cheatsheet-dev.ru.md): им нужна плата разработки. Управление тем же роботом с ноутбука по Bluetooth без сети и SSH — [`duckctl.md`](duckctl.ru.md).

<a id="on-the-robot-robotctl"></a>
## На роботе — `robotctl`

<a id="on-the-robot--robotctl"></a>
<a id="the-first-thing-to-run"></a>
### Что запускать сначала

```
robotctl version
```

Что каждая служба *исполняет* относительно *установленного*, с предупреждениями о несовпадении. Запускайте до доверия любому другому диагнозу: старый процесс после обновления выглядит как ошибка только что поставленного исправления. См. раздел после обновления ниже.

```
robotctl health
```

Оборудование и ПО в одном отчёте. Ненулевой код при unhealthy или недоступности позволяет использовать в скрипте. Горячий мотор и закреплённый компонент сообщаются без оценки и не влияют на код. `--json` для поддержки; `--check` сначала проверяет источник обновлений, чтобы строка отражала доступность сейчас.

<a id="watching-the-loop"></a>
### Наблюдение за циклом

```
robotctl monitor
```

Запрошенное клиентом рядом с фактически применённым и причиной различия: безопасность постоянно ограничивает команды; без этого «стик вперёд, робот стоит» непонятно. Ограничение объясняется, а не просто называется: `deadman — no intent arrived recently, velocity zeroed` — давно не было намерения, скорость обнулена.

Также показаны измеренные и заданные суставы, проекция гравитации IMU с решением о падении, график достигнутой частоты: уже прошедшая остановка остаётся видна. Проекция гравитации — единственная величина IMU в этом потоке; вертикально примерно `[0, 0, -1]`, по ней определяется `fallen`. Счётчики устаревших чтений и необходимые для их оценки отношения находятся в `robotctl health`.

Последняя строка заголовка отражает состояние, не поведение: напряжение и долю заряда, самый горячий сервопривод, температуру платы. Она приходит из `robot.health` каждые две секунды, поскольку в потоке состояния этих данных нет. Здесь называется ошибка: `unhealthy: control loop at 43.9 Hz`, `degraded: no robot on the motor bus after 3 attempts` либо `orientation frozen — 25 stale reads`. Последнее есть только в этой строке: плата, переставшая объединять данные IMU, продолжает отвечать по шине без ошибок, а гравитация бесконечно выглядит правдоподобно.

0% — `BATTERY_EMPTY_V`, при котором `robotd` сажает робота и отключает питание; это отсчёт до отключения, не просто шкала: жёлтый на 30%, красный на 15%. До первого измерения — `batt not read yet`, а не `0.00 V`: так выглядят первая секунда работы и неотвечающая шина. Строка рисуется даже без состояния, когда особенно нужна: плата без питания сервоприводов не завершает такт и ничего не присылает, причина доступна только в health.

Нижняя граница называет загруженную политику, файлы `.onnx` и наличие standing-сети: режим `walk` одинаков для двух выпусков с разными походками. Отсутствие политики и ошибка загрузки различаются, в отличие от `held` потока.

Справа **робот нарисован в своей фактической позе**: та же визуальная модель, на которой обучались политики, измеренные углы и наклон по гравитации IMU. Неправильно сложенная нога, голова в полу и лежащая утка очевидны, хотя в таблице это лишь числа. Вид включён по умолчанию при достаточной ширине терминала, около 110 колонок: таблицы первыми, робот занимает остаток. **`d`** скрывает его; **`[`**, **`]`** или `←`/`→` вращают обзор.

Когда ToF присылает кадры, его точки рисуются в той же сцене: жёлтые препятствия, зелёный пол, с проверкой глубины относительно тела. Точку за клювом скрывает клюв. Это отвечает на вопрос «датчик видит руку или самого себя?». Клавиша не нужна: точки появляются и исчезают с кадрами.

Ниже, при достаточной высоте, **карта пройденного пути**: контактная одометрия и IMU символами Брайля. Панель не растёт, мир уменьшается вместе с траекторией, сохраняя весь путь. `+` — старт, `●` с лучом — робот и направление, верх экрана — направление при загрузке. Без магнитометра движение относительное и дрейфует; карта отвечает «прошёл ли круг», не «где находится».

`q` — выход; `↑`/`↓` прокручивают суставы в низком окне; `u` меняет градусы/радианы; `t` открывает [матрицу ToF](#the-tof-sensor-tofd); `c` — [камеру](#the-camera-mediad); `d` переключает робота, `[`/`]` вращают; `p` открывает сырые evdev-отчёты геймпада с промежутками, единственное место наблюдения зависшего радио ([сопряжение](pair-a-gamepad.ru.md#when-it-drops-while-you-are-driving)). У геймпада с IMU, например клонов Pro Controller, но не Xbox, появляется панель: каркас геймпада повторяет наклон/поворот, pitch/roll и дрейфующий yaw, сырые ускорения/скорости, состояние изучения смещения гироскопа в покое — держите неподвижно полсекунды. Жёлтая полоса — передний край. Экранные углы суставов, головы и скорость yaw — в градусах. При перенаправлении или pipe печатается строка на такт: работают `> run.log` и `| grep FALLEN`, числа всегда в радианах независимо от экрана. Векторы суставов доступны в `--json`: всё состояние по объекту на строку:

```
robotctl monitor --json --hz 50 > run.jsonl
```

<a id="configuring-the-robot"></a>
### Настройка робота

```
sudo robotctl configure
```

Только изменённое на этом роботе:

```
robotctl configure --list
```

Нетронутый робот ничего не выводит — это и есть ответ. `--json` для пакета поддержки. Root и терминал не нужны: это первый вопрос к странно ведущему себя роботу, раньше требовавший полноэкранного SSH-редактора.

Интерактивный редактор `/etc/robot/robotd.toml`: все известные службам ключи, сначала переключатели — политика, walk/roller, limp-fall, звук, поглаживания, отключение по батарее, камера и качество. Текущее значение против умолчания, строка пояснения. SPACE переключает, ENTER вводит, `u` возвращает умолчание, `ctrl+f` открывает нечёткий поиск по экрану; выбор следует вводу, ENTER/ESC оставляют его. Жёлтые значения с `•` отличаются от умолчаний; остальное встроено, необязательные поля `unset` показывают разрешённое `(auto)`.

Три свойства:

- **Не расходится со службой.** Схема, умолчания, валидация — из crate, которым `robotd` читает файл. Полнота списка закреплена тестом: новая `[section]` появляется здесь либо сборка падает.
- **Не уничтожает файл.** Комментарии, порядок и ключи других выпусков сохраняются; записывается только изменённое. Возврат удаляет ключ с его комментарием, а не закрепляет умолчание. Файл остаётся списком *решений*, не копией умолчаний.
- **Не пишет файл, с которым robotd откажет в запуске.** Каждое сохранение сначала проходит собственный загрузчик службы, затем атомарную запись через временный файл и rename; отказ содержит причину.

После сохранения предлагается нужное считывающей службе действие: перезапуск для большинства ключей (`[media]`, `[duck_detector]` принадлежат `mediad`, `[head_imu]` — `tofd`); *reload* `robotd` для `[policy]` без отключения моторов; ничего для `[pad]`, `[pad_imu_head_control]`, которые `padd` подхватывает за секунду. Файл принадлежит root: без `sudo` редактор только читает и сообщает это при первой записи. `--file` выбирает стендовую копию. Поставляемый `deploy/robotd.toml` объясняет *зачем* настройки; редактор нужен для переключения.

<a id="video-quality"></a>
#### Качество видео

```
sudo robotctl configure
```

Задайте `media.quality`: `1080p30`, `720p30`, `720p15`, `360p30`, согласитесь на перезапуск. `media.source` со значением `test` передаёт тестовый шаблон для платы без камеры: WebRTC-*управление* привязано к видеодорожке, отказ конвейера лишает обоих. Шаблон игнорирует `media.quality`, работает в 256x144@5 для существования сессии; рисование 720p стоит впятеро больше CPU настоящей камеры. Без явного значения `media.bitrate` следует качеству, единица — бит/с.

`media.congestion_control` управляет главным расходом CPU: `disabled` отключает оценщик полосы, крупнейшего потребителя `mediad` — 7.6% ядра против 0.3% захвата. `media.bitrate` становится фиксированной частотой вместо исходной точки. Цена — отсутствие адаптации: на ухудшающейся связи изображение остановится вместо снижения битрейта.

Измерения конвейера выполнялись при 720p30. Непосильная ступень работает медленнее, а не падает. `robotctl monitor` показывает фактическую частоту снизу, жёлтым с `of <target>` при падении ниже 90% цели. Фактически применённое:

```
journalctl -u mediad -b | grep streaming
```

<a id="policies-and-skills"></a>
### Политики и навыки

**Слот** — обычная работа робота, походка или standing-сеть. **Навык** — действие по запросу: удар, кувырок, поклон. Оба — файлы Hub, меняющиеся без выпуска службы; ниже ничего не требует перезапуска.

Что робот исполняет сейчас:

```
robotctl policy list
```

Две таблицы: семь слотов, затем навыки — работа по умолчанию и по запросу.

```text
   SKILL        RUNS FOR  POLICY
   kick_left       0.5 s  ball_kick_left.onnx
   roulade           1 s  roulade.onnx
 * polite-bow        4 s  fffiloni/microduck-polite-bow-b1d864/main/policy.onnx
   ground_pick         —  driven by the robot itself
   sit_toggle          —  driven by the robot itself
```

`*` отмечает строки с настройкой, число приведено снизу. Отключённый слот пишет `switched off`, отличаясь от никогда не существовавшего. Каталог убран из пути, поскольку его уже называет `ORIGIN`.

У `ground_pick` и `sit_toggle` нет длительности: робот управляет ими сам. Они отвечают на `robot do`, но не являются изменяемыми записями.

<a id="a-newer-official-set"></a>
#### Новый официальный набор

Набор походок находится в Hub и имеет собственную линию версий:

```
robotctl policy check
```

```
sudo robotctl policy update
```

`check` показывает установленное, новейшее и остальные версии; ничего не меняет, явно сообщает недоступность Hub. `update` берёт новейшее, если не указана версия; `--version v1` возвращает назад. Робот идёт в домашнюю позу, перечитывает слоты и продолжает. **Самостоятельно загруженный слот остаётся**, поскольку указывает на другой источник.

<a id="a-newer-duck-detector"></a>
#### Новый детектор утки

Модель поиска других уток для `mediad` находится аналогично в Hub (`pollen-robotics/microduck-duck-detector`) со своей версией:

```
robotctl duck-detector check
```

```
sudo robotctl duck-detector update
```

Как для политик: `--version <tag>` выбирает, `check` не меняет. `update` перезапускает `mediad`, ненадолго отключая видео консоли. Включён ли детектор, определяет `[duck_detector] enabled` в `robotctl configure`.

<a id="trying-your-own-file"></a>
#### Свой файл

Без выпуска, правки файла и перезапуска:

```
sudo robotctl policy load walk /home/microduck/my_walking.onnx
```

Идущий робот возвращается домой, загружает модель и продолжает. Если сидит или неподвижно стоит, ничего не движется: заменяемая сеть сейчас не активна. `sudo robotctl policy reset walk` возвращает слот; без слота — все семь.

<a id="trying-somebody-elses"></a>
#### Чужая модель

Другие люди публикуют политики для робота:

```
robotctl policy search microduck
```

```
sudo robotctl policy load walk RemiFabre/microduck-flamingo-cycle
```

Достаточно имени репозитория: скачивание и загрузка одним шагом. `@v2` выбирает ревизию, `:policy.onnx` — файл репозитория с несколькими. `policy list` отмечает `community`.

**Ничто опубликованное незнакомцем никем не проверено.** Безопасность пробы дают ограничения суставов, рефлекс падения, проверка формы, не описание. Первую пробу выполняйте на подставке.

Если манифест сообщает несовместимость — ширина наблюдений, новая служба, иной робот, — отказ до скачивания. Без манифеста модель принимается и проверяется при загрузке обычным способом.

<a id="adding-a-skill"></a>
#### Добавление навыка

Политика слота walk заменяет походку. Политика-*навык* существует рядом и исполняется по запросу, как большинство публикуемых разовых действий:

```
sudo robotctl policy add polite-bow fffiloni/microduck-polite-bow-b1d864
```

```
robotctl robot do polite-bow
```

Длительность берётся из манифеста. Для удерживающей позу до отмены политики, например стойки на одной ноге, задайте длительность и читаемый ею twist:

```
sudo robotctl policy add flamingo RemiFabre/microduck-flamingo-cycle --hold 5 --command 1,1,0
```

`--command` подаётся сети при исполнении. Большинству не нужен: обучение на нулях, выбор уже является триггером. Если twist имеет иной смысл, как `[flag, side, 0]` у flamingo, его нужно указать; README объясняет значения.

`sudo robotctl policy remove <name>` удаляет навык. Поставляемый выпуском вернётся: удаление убирает лишь переопределение.

Для навыка робот должен двигаться с включённой политикой: сначала **Start** геймпада, иначе явный отказ.

<a id="putting-a-skill-on-a-button"></a>
#### Назначение навыка кнопке

```
robotctl pad bindings
```
```text
a           ground_pick
x           roulade
lb          kick_left
rb          kick_right
dpad_down   sit_toggle

`robotctl pad bind <button> <skill>` changes one; padd picks it up within a second.
```

```
sudo robotctl pad bind x polite-bow
```
```text
a           ground_pick
x           polite-bow
lb          kick_left
rb          kick_right
dpad_down   sit_toggle
```

Записывается одна строка только названной кнопки:

```toml
[pad]
x = "polite-bow"
```

Возврат:

```
sudo robotctl pad reset
```

**Ничего не перезапускается**: `padd` замечает за секунду.

Привязка отсутствующего навыка отмечается в списке, не игнорируется при нажатии.

Пять назначаемых кнопок: `a`, `x`, `lb`, `rb`, `dpad_down`. **`lb`/`rb` — бамперы**, не аналоговые курки клюва/кряканья. Пустое имя отключает, `pad reset <button>` возвращает. Умолчания — раскладка прототипа, без `[pad]` робот ведёт себя как раньше.

Остальное не переназначается: Start переключает политику, Y/B — смысл стиков, удержание Select выключает питание. Останавливающую кнопку нельзя потерять правкой конфигурации. Имя проверяется по имеющимся навыкам, опечатка отклоняется со списком, не создаёт мёртвую кнопку.

<a id="putting-it-all-back"></a>
#### Возврат всего

```
sudo robotctl policy reset
```
```
sudo robotctl pad reset
```

```
robotctl configure --list
```

Последняя команда выводит только отличия от умолчаний; нетронутый робот сообщает об их отсутствии одной строкой. Это первая проверка странного поведения, если непонятно, что оставили настроенным.

<a id="the-slots-and-four-things-worth-knowing"></a>
#### Слоты и четыре важных свойства

Слоты: `walk`, `stand`, `sitstand`, `ground_pick`, `kick_left`, `kick_right`, `roulade`. `load` записывает выбор в `/etc/robot/robotd.toml`, переживающий reboot и обновления: выпуск заменяет бинарники и свои политики, не строку со ссылкой в другое место.

- **Повторный reset ничего не делает и сообщает это.** Без HOME, reload и необходимости `sudo`, если писать тоже нечего.
- **Не `obs[1,61] -> actions[1,14]` отклоняется до изменений.** Файл открывается и проверяется при ещё работающей старой модели.
- **Даже последующая ошибка загрузки сохраняет действующую политику.** Проба не лишает прежней походки.
- **Исчезнувший к следующей загрузке файл лишает слота, не робота.** Слот возвращается к собственной политике, `robotctl health` сообщает *degraded* с файлом; `policy reset <slot>` очищает переопределение. Не загружающаяся официальная политика всё ещё **unhealthy**: это плохой выпуск, его обновлятор откатывает.

`none` выключает любой слот, кроме `walk`, на который опираются остальные и который нельзя оставить пустым. Самостоятельно стоящей политике это нужно: иначе при нулевой команде робот переключится на standing-сеть.

<a id="publishing-a-policy-for-every-robot"></a>
#### Публикация политики для всех роботов

Официальный набор достигает каждого робота. Добавление — четыре шага без выпуска службы:

1. Загрузить `.onnx` в `pollen-robotics/microduck-policies`.
2. Добавить запись в `manifest.json`:
   ```json
   { "file": "polite-bow.onnx", "kind": "episodic", "duration_s": 4.0 }
   ```
   Манифест набора имеет `schema_version: 2`; обычному разовому действию достаточно этих трёх полей.
3. Создать тег: `hf repos tag create pollen-robotics/microduck-policies v4`.
4. На роботе: `sudo robotctl policy update`.

Только это нужно разовому действию: **`episodic` с `duration_s` на тренировочной нулевой команде становится именованным навыком**, доступным `robot do` и кнопке без иных правок. **`perpetual`** — походка, на которую нужно направить слот.

Политика, которой служба должна *управлять*, меняя фазу со временем или флаг позы, объявляет `command.encoding`; числа становятся временными параметрами соответствующей ветви, а не новым навыком. Поднятие предмета и sit↔stand — два таких случая, их записи требуют особой внимательности.

Полный манифест с каждым полем и последствиями: [`../policy-manifest.md`](../policy-manifest.ru.md).

Форма политики и проверки загрузки — [`../design/robotd-design.md`](../design/robotd-design.ru.md), §2.3; источники, значение `official`, объявление навыка — [`../design/policy-channel-design.md`](../design/policy-channel-design.ru.md).

<a id="power-to-the-joints-robotd"></a>
### Питание суставов (`robotd`)

```
sudo robotctl robot init
```

```
sudo robotctl robot relax --yes
sudo robotctl robot reboot-motors           # every servo; or `reboot-motors 3 11` for just those. Torque off, then init / Start
```

`init` включает момент и примерно за две секунды ведёт в домашнюю позу: **двигается каждый сустав**, поставьте робота на подставку. Политика не нужна; то же делает Start перед движением, поэтому ручной запуск — стендовый сценарий.

`relax` отключает момент: **робот упадёт**, если не удерживать, поэтому требует `--yes`. Это единственный возврат к свободным суставам без извлечения питания: повторный Start останавливает политику и сохраняет стойку, `robot.stop` обнуляет скорость, тоже стоя.

Обе команды проходят через владельца шины `robotd`. Подкоманда `robotd init` остаётся для неработающей службы и требует её остановить: два писателя UART повреждают ответы друг друга:

```
sudo systemctl stop robotd && sudo /opt/robot/daemon/current/bin/robotd init && sudo systemctl start robotd
```

`reboot-motors` доступен также по Bluetooth как `duckctl reboot-motors` ([`duckctl.md`](duckctl.ru.md)), `relax` — нет.

**Замена мотора** не требует отдельной программы настройки. Установите новый из коробки, ID 1 и 57 600 бод, включите питание; `robotd` либо `robotd init` обнаружит единственный отсутствующий сустав, назначит новому его ID, настроит регистры и перезагрузит. Журнал: `factory-fresh servo on the bus; flashing it as the missing joint`, затем `replacement servo adopted`. Только по одному: при двух отсутствующих он не знает назначение, ждёт и объясняет.

`init` работает и после падения: по умолчанию падение — *сообщение* в `robotctl monitor`, не запрет, как у прототипа. `[safety] fall_limp` либо `fall_recover` в `robotd.toml` включает защиту: упавший робот снимает момент, отвергает `init`/`enable`/навыки до установки вертикально.

<a id="gamepad-configd"></a>
### Геймпад (`configd`)

Действия кнопок и переназначение описаны выше в **«Политики и навыки»**, `robotctl pad bindings`. Здесь — само подключение.

```
robotctl pad status
```

```
sudo robotctl pad pair
```

```
sudo robotctl pad pair 78:86:2E:BB:13:28
```

```
sudo robotctl pad forget 78:86:2E:BB:13:28
```

Сопряжение однократно на геймпад, подробно в [`pair-a-gamepad.md`](pair-a-gamepad.ru.md): кнопка режима, второй геймпад без удаления первого, отказ пары. Чаще всего ответ — `Privacy` в `/etc/bluetooth/main.conf`.

`padd.service` работает с загрузки и использует подключённый геймпад; достаточно сопряжения. Раскладка прототипа сохраняет привычные действия:

| Управление | Действие |
| --- | --- |
| Левый стик | Движение: вперёд/назад и боком; голова: yaw/pitch; поза корпуса: высота и приседание |
| Правый стик | Движение: поворот; голова: наклон шеи и roll головы; корпус: pitch/roll |
| **Start** | Первое нажатие включает момент, рампа 2 с в домашнюю позу, затем удержание; второе включает политику; далее переключает политику |
| **Y** / треугольник | Режим головы: стики двигают голову, тело удерживается. При `[pad_imu_head_control] enabled` и IMU геймпада голову задаёт наклон геймпада, стики продолжают движение; ниже |
| **B** / круг | Режим корпуса: стики наклоняют и присаживают стоящего робота |
| **A** / крест | Поднятие с пола |
| **X** / квадрат | Кувырок вперёд; удержание связывает кувырки |
| **LB / RB** | Удар левой/правой ногой |
| **DPad-Down** | Сесть ↔ встать |
| **RT / LT** | Клюв любым курком; RT также крякает, LT удерживает звук «wheee» |
| **DPad-Up**, удержать 3 с | Режим walk ⇄ roller |
| **DPad-Right** | Перезагрузка всех сервоприводов после перегрузки без извлечения батареи; момент выключается, затем Start |
| **Select**, коротко | Снятие момента (`robot.relax`) **при отпускании**, аварийная остановка. Удерживайте падающего робота; затем Start поднимет его |
| **Select**, удержать 2 с | Сесть, снять момент, выключить питание; отпускание больше ничего не делает |

**Управление головой самим геймпадом.** В Pro Controller есть IMU; при:

```bash
sudo robotctl configure      # Controller-IMU head control → enabled
```

Y меняет смысл: первое нажатие передаёт голову наклонам/поворотам геймпада, а стики продолжают вести тело. Второе удерживает голову, стики всё ещё ведут. Третье снова включает голову **от текущего положения геймпада**: yaw гироскопа дрейфует, повторное центрирование при входе компенсирует это без магнитометра. `gain` — радианы головы на радиан геймпада, по умолчанию 1. У Xbox или выключенной функции Y означает прежний режим головы стиками. `padd` замечает изменение за секунду без перезапуска.

Отдельной кнопки остановки движения нет: отпустите стики — робот стоит; deadman `robotd` остановит при смерти `padd`. Для роликов (`mode = "roller"` в `robotd.toml`) стики автоматически получают асимметричные разгон/торможение без бокового хода, A запускает приседание. Остальные навыки — посадка, удары, кувырок — работают и на колёсах, как в прототипе.

**Удержание DPad-Up переключает режимы** после установки/снятия колёс: один кряк для ходьбы, два для роликов; домашняя поза, загрузка политик, продолжение движения. Несколько секунд с моментом, без рестарта. `robotd.toml` не меняется, reboot вернёт настроенный режим; сохраните через `robotctl configure` или `[policy] mode`. Удержание нужно против случайного нажатия вверх во время движения.

`pad status` отдельно отвечает на два вопроса: подключённый геймпад с мёртвым драйвером внешне неотличим от исправного:

```
pad     Xbox Wireless Controller 78:86:2E:BB:13:28  connected
padd    active — driving whatever pad connects
```

Перед нестандартными ограничениями остановите службу, иначе процессы будут конкурировать за стики:

```
sudo systemctl stop padd
```

```
sudo -u padd /opt/robot/daemon/current/bin/padd --max-linear 0.25
```

Подозрительную связь наблюдайте через `robotctl monitor`, затем `p`. Это работает без робота: при выключенных сервоприводах или остановленном `robotd` монитор открывает блок геймпада, не отказывает. Для оценки интервала скопируйте измеритель из клона:

```
scp scripts/pad-link-test.sh microduck@<board>:/tmp/
```

Уже записанные обрывы журнала `padd`, без геймпада и ожидания:

```
sudo sh /tmp/pad-link-test.sh --history
```

Или измеряйте сейчас, непрерывно двигая стики две минуты:

```
sudo sh /tmp/pad-link-test.sh
```

Учитываются причины обрывов ядра и промежутки отчётов: сбой, невидимый `padd`, когда связь формально есть, а робот идёт по старой команде. [Разбор чисел](pair-a-gamepad.ru.md#when-it-drops-while-you-are-driving).

При разном поведении двух плат с одним геймпадом различается нижележащий стек:

```
scp scripts/pad-stack-report.sh microduck@<board>:/tmp/
```

```
sudo sh /tmp/pad-stack-report.sh
```

Ядро, BlueZ, прошивки контроллера и геймпада, LE или BR/EDR печатаются и сохраняются в `/tmp/pad-stack-<host>-<when>.log`. `--fingerprint` выводит лишь обязанные совпадать значения для `diff`. [Сравнение](pair-a-gamepad.ru.md#is-this-board-running-the-same-stack-as-that-one).

<a id="the-voice"></a>
### Голос

```
robotctl quack
```

Самый громкий способ различать уток: голосовой банк генерируется из серийного номера SoC (`sounds ensure-bank` при каждой установке), поэтому отвечает своим голосом именно робот SSH-сессии. При выключенном звуке или отсутствии банка робот сообщает причину вместо 🦆; молчание означает не ту утку. Робот приветствует при запуске `robotd`, прощается клювом перед выключением, по запросу воркует при обнаруженном микрофоном почёсывании головы. Последнее по умолчанию выключено в обоих режимах: `audio.pet_detect = true` включает поставляемый классификатор; постоянно включённый реагировал на случайные касания и надоедал. Для часто перезапускающих службу приветствие имеет свой переключатель:

```
sudo robotctl configure
```

`audio.greet = false` с предлагаемым перезапуском заглушает один кряк, сохраняя курки и микрофон, в отличие от `audio.enabled = false`. Драйвер кодека, overlays, микшер настраиваются аудиоразделом `setup-board.sh` один раз на плату.

Выпуск содержит генератор для прослушивания и пересоздания банка:

```
/opt/robot/daemon/current/bin/sounds show
sudo /opt/robot/daemon/current/bin/sounds ensure-bank --force
```

`sounds theremin` воспроизводит *живой* синтезатор с программным движением руки на частоте ToF. `--out sweep.wav` записывает вместо воспроизведения, позволяя услышать изменение голоса без робота.

<a id="the-duck-chorale"></a>
### Хор уток

```
robotctl chorale
```

Две утки в комнате вместе поют четырёхголосную пьесу; остальные присоединяются к уже идущему исполнению. До Ctrl-C, `--off` останавливает одну.

**По умолчанию выключен:** `[chorale] accept` в `robotd.toml` каждой участвующей утки. Хор двигает клюв/голову; автоматическое оживление от вошедшей утки было бы незапрошенным движением. Выключенная утка также *невидима*: ничего не передаёт, а не вежливо отказывается.

Как работает:

- **Начальника нет.** Обе видят маяки; меньший ID дирижирует без выборов и гарантированно доставляемого сообщения.
- **Общих часов нет.** Нет согласованных NTP/RTC, поэтому счётчик дирижёра — время: байт BLE advertising меняется раз на долю, приход нового — сильная доля. Последователи усредняют фазу около 25 долей, укладывая джиттер радио в требуемые ±20 мс.
- **Партии вычисляются, не назначаются.** Младший ID поёт бас. Дирижёр передаёт состав, все одинаково рассаживаются по нему; это предотвращает одну партию у двух уток, видящих разные части комнаты.
- **Присоединение не меняет чужую партию.** Пришедшая занимает свободную; ушедшая сохраняет *место*, её партия молчит, как у покинувшего хор человека. Перерассаживания посреди пьесы избегают.

Партия выводится сразу после выбора и сохраняется в прокрутке:

```
listening for other ducks — Ctrl-C to stop
  singing tenor    with 3 voices
  tenor    bar   12  beat  45.2  3 voices
```

Дирижёр выбирает пьесу на исполнение; после последней ноты все возвращаются к слушанию, определяются заново, после паузы поют другое. `robotctl chorale --piece 2` закрепляет выбор робота **только если он дирижирует**; последователи поют названное маяком, поэтому для гарантии задайте всем. Неизвестный ID отклоняется с каталогом. ID: 1 wistful, 2 duck-strut, 3 outer-wilds — тестовый ресурс, не для выпуска. `DUCK_CHORALE_PIECE=<id>` в окружении **robotd**, не `robotctl`, задаёт постоянный резерв.

Целый ансамбль на одной машине без уток:

```
sounds chorale --voices 4                 # or --seeds 100,7,42 for particular ducks
sounds chorale --score my-piece.mid       # anything a notation editor exported
sounds chorale --rolloff 0                # for a full-range speaker, not a duck's
```

Партитуры — `sounds/scores/*.duckscore`, построчный текст с описанием в поставляемом `wistful.duckscore`, либо MIDI — предпочтительный путь. **MuseScore — редактор партитуры.** Один инструмент на голос, не один фортепианный стан; назовите партии и экспортируйте MIDI. Сопоставление по средней высоте отправит бас в бас даже при верхнем стане первым; имя дорожки "Soprano" важнее высоты нот.

<a id="play-the-duck-the-tof-theremin"></a>
### Игра на утке — ToF-терменвокс

```
robotctl theremin
```

Датчик глубины головы становится инструментом: рука перед клювом задаёт высоту, ближе — выше. Клюв открывается с нотой, шире на верхней границе. До Ctrl-C с выключением при выходе; `--off` выключает оставленный клиентом режим.

**По умолчанию выключен:** `[theremin] enabled` каждой утки, как хор. `robotctl configure` предлагает нужный перезапуск `robotd`; до него `robotctl theremin` отказывает, называя ключ. Остальное не выключается: `tofd` работает независимо, матрица глубины доступна никогда не игравшей утке.

Явный режим без хитростей: ближайшее отражение в рабочем диапазоне считается рукой. Открытое пространство — тишина, стена в 40 см — постоянная нота. Играет сидя, стоя, на ходу: клюв не относится к политике.

Последний столбец — **что датчик сообщил об этом кадре**, ответ на вопрос «почему перестало играть»:

```
  0.34 m    438.1 Hz   60% ██████    14 usable · 255:38 4*:9 5*:5 1:12
```

Число зон с доверенным статусом, затем число по кодам ST со `*` у доверенных. `~` перед нотой — *удержанная* через пропуск, не измеренная сейчас.

Столбец появился из-за ошибки, которую выявил бы за минуту: ST называет 5/9 «range valid», но вера только им **теряет руку примерно на 30 см**. Дальше движущаяся рука получает 4/13 — consistency failed, слишком большая sigma — с вполне пригодной для ноты дальностью. Мал радиус — добавьте коды в `[theremin] statuses`; фантомные ноты в воздухе — уберите. `hold_ms` сглаживает мерцание зоны.

Матрица ToF `robotctl monitor` строже: всё вне 5/9 — `x`, «не удалось измерить». Полная `x` сетка не доказывает поломку: она пессимистична к имеющимся числам.

<a id="the-tof-sensor-tofd"></a>
### Датчик ToF (`tofd`)

Матрица глубины головы 8×8. `robotctl monitor`, затем **`t`**:

```
┌ tof VL53L8CX · 15 Hz · 8×8 · 48/64 ranged · 0.12–3.54 m ─────────────┐
│ 0.12 0.15    x 1.44 1.86    · 2.70 3.12                              │
└ · nothing in range · x could not measure · near→far ── seq 412 · 6 ms ┘
```

Дальности в метрах, цвет от тёплого ближнего к холодному дальнему. `·` — *измерено, в диапазоне ничего нет*: свободное пространство тоже информация. `x` — *измерить не удалось*, о пространстве ничего не известно. Пустое отображение обоих скрыло бы различие.

Это кадр датчика, не робота: до кинематики перепроецирования нет. Здесь удобно проверять угол крепления.

`tofd` владеет датчиком, никто другой не читает шину. Обычная служба: `sudo systemctl stop tofd` безопасен, зависимых нет; `monitor` пишет «no depth stream» и продолжает. Различаются три случая с разными решениями:

| Сообщение | Значение |
| --- | --- |
| `connecting to tofd…` / `no depth stream` | Служба не работает |
| `no sensor: …` | `tofd` работает, шина не получила ответа, как у большинства уток |
| `waiting for the first frame…` | Датчик измеряет, первый скан примерно через 66 мс |

Ручная проверка шины или кадров без терминального UI:

```
sudo i2cdetect -y -r 3
journalctl -u tofd -b
```

Датчик делит I²C с кодеком, поэтому аудиораздел `setup-board.sh` уже подготавливает шину; ToF лишь добавляет стабильный `/dev/i2c-pihat`. Поддерживаются VL53L5CX и VL53L8CX, взаимозаменяемые на плате; драйвер определяется чтением ID.

<a id="the-head-imu-headimustream"></a>
#### IMU головы (`head_imu.stream`)

`tofd` также обслуживает BMI088 головы: гироскоп, ускорение, ориентацию Madgwick. **По умолчанию выключено:** `[head_imu] enabled` в `robotd.toml` через `robotctl configure` с перезапуском `tofd`. Чтение стоит около 4% ядра на 100 Гц; подписчиков пока нет, утка без картографирования платила с загрузки. Выключенный датчик отвечает причиной с ключом вместо молчания отсутствующего. `tofd --imu` включает на сессию без файла; `--imu-hz` линейно меняет частоту и стоимость.

Глубина не затрагивается: ToF измеряет в любом случае, сетка работает с никогда не включавшимся IMU головы.

<a id="the-camera-mediad"></a>
### Камера (`mediad`)

Кадр камеры головы в терминале: `robotctl monitor`, затем **`c`**:

```
camera 1280×720 · mount 90° · answered in 41 ms                    0.5 s ago
```

Два пикселя на знакоместо, правильная ориентация при любом креплении. Изображение маленькое: после четверти оборота на этом роботе портретное, около 16 пикселей по ширине. Достаточно понять недоступное числам: куда смотрит голова, хватает ли света, не испачкана ли линза и не закрыта ли пальцем.

**При закрытом блоке ничего не запрашивается.** Кадр — 1.84 MiB, копируемые `mediad` только по запросу; закрытый монитор камере ничего не стоит. Открытый спрашивает дважды в секунду, `answered in 41 ms` подтверждает живую камеру: запрос ждёт *следующий* кадр, исправные 30 кадров/с отвечают примерно за период, остановленная камера — тайм-аутом. Закрытие забывает картинку; повторное открытие показывает свежую, не комнату десятиминутной давности.

| Сообщение | Значение |
| --- | --- |
| `asking mediad for a frame…` | Первый запрос ещё выполняется |
| `no picture: connection refused` | `mediad` не работает |
| `no picture: no frame arrived within the capture timeout` | `mediad` работает, камера кадров не производит |

Полноразмерный снимок:

```
robotctl frame --output /tmp/frame.uyvy
```

Один сырой UYVY с геометрией и углом крепления в stderr. Консоль `mediad` на `:8080` отдаёт тот же кадр правильно повёрнутым PNG по `GET /frame`.

<a id="the-hugging-face-account-updaterd"></a>
### Учётная запись Hugging Face (`updaterd`)

Вход робота даст доступ вне его сети. Пока больше ничего не требует учётной записи.

```
sudo robotctl account login
```

Появится код. На любом устройстве откройте <https://hf.co/oauth/device>, введите код, команда завершится:

```
Open https://hf.co/oauth/device and enter this code:

    A6MY-0314

Waiting for approval…
Signed in as PierreRouanet.
```

```
robotctl account status
```

```
sudo robotctl account logout
```

Ctrl-C во время ожидания не мешает: робот продолжает опрос, `account status` покажет одобрение. Код действует пять минут; затем повторите `login`.

Уже вошедший робот отказывает, называя учётную запись:

```
sudo robotctl account login --force
```

Тот же флаг отменяет ещё ожидающий одобрения код, если кто-то начал и ушёл. Старый код перестаёт работать; позднее одобрение ничего не делает.

Токен действует тридцать дней, робот обновляет самостоятельно. Выключенный дольше требует нового `login`, о чём явно сообщает `account status`.

<a id="switching-without-a-download"></a>
### Переключение без загрузки

На уже распакованное, без сети:

```
sudo robotctl update select daemon 0.1.4
```

```
sudo robotctl update rollback daemon
```

```
sudo robotctl update reset-to-golden daemon
```

`select` активирует установленное, `rollback` — предыдущее, `reset-to-golden` — никогда не очищаемое заведомо рабочее.

Запрет движения по версиям:

```
sudo robotctl update pin daemon 0.1.4
```

```
sudo robotctl update pin daemon
```

Вторая форма снимает закрепление.

<a id="when-updaterd-itself-will-not-start"></a>
### Если сам `updaterd` не запускается

Всё выше идёт через `updaterd`, поэтому при его отказе не работает. Определите проблемную службу:

```
systemctl status updaterd robotd btd configd
```

Вернитесь в golden без неё:

```
sudo robot-rescue --dry-run
```

```
sudo robot-rescue --reboot
```

`--dry-run` сообщает план без изменений. Без `--reboot` переключает выпуск и печатает команду перезагрузки, не выполняет: процессы используют `current` лишь при следующем старте. Сначала поддержите стоящего робота.

Без настроенного golden или при уже активном golden команда объясняет отказ: если службы не работают и на нём, нужен журнал, не откат:

```
journalctl -b -u robotd -u updaterd -u btd -u configd
```

<a id="the-robot-may-have-done-this-already"></a>
### Возможно, робот уже сделал это

Через три минуты каждой загрузки таймер проверяет запуск служб и возвращает golden при отказе. Самоперезагрузившийся робот на более старой версии, вероятно, спас себя. Его действия:

```
robotctl update log
```

Запись — откат с именем отказавшей службы в причине. Решение, а не результат:

```
journalctl -b -u robot-boot-check
```

```
sudo robot-boot-check --dry-run
```

Действие однократно. Повторный rescue запрещён, пока предыдущий записан; `updaterd` очищает запись при старте. Отказ означает, что службы и на golden не поднялись: нужен journal, не ещё один reboot. Если журнал прочитан и решение принято:

```
sudo robot-rescue --force --reboot
```

<a id="three-things-that-are-easy-to-get-wrong"></a>
### Три частые ошибки понимания

**`rollback` требует предшественника, но обновление его создаёт.** На только подготовленной плате один выпуск, назад идти некуда. Автооткат защищён: новый распаковывается рядом, затем меняется `current`; к health gate уже два выпуска, исходный — цель. `rollback_target` выбирает наивысшую установленную версию ниже `current`, не помеченную плохой. Плата с одним выпуском защищена с первого обновления.

Не защищён лишь сам bootstrap без предшественника. Его покрыл бы `golden`, намеренно не заданный до 1.0.0; поэтому `reset-to-golden` честно сообщает отсутствие вместо сюрприза.

**`version` показывает активный выпуск компонента, не хранилище.** Две версии не перечислит независимо от числа распакованных. Спросите хранилище:

```
ls -l /opt/robot/daemon/releases/ /opt/robot/daemon/current
```

**`apply --version` требует существования upstream, `select` — нет.** Плохие выпуски удаляют из GitHub: `apply --version 0.1.3` намеренно откажет, а `select 0.1.3` работает у уже распаковавшей платы. Новая плата не получит плохое, существующая сохранит выход.

### Установка без сети

Локальная доставка, заводская установка, спасение `updaterd`, слишком старого для исправляющего его выпуска: [`install-dev.md`](install-dev.ru.md), `updaterd install --from`. Перед `--force` прочитайте условия.

<a id="logs"></a>
### Журналы

```
robotctl logs robotd
```

```
robotctl logs robotd -n 300 -b -1
```

`-b -1` — предыдущая загрузка. `sudo` не нужен: journal читает `configd`. Допустимы `robotd`, `btd`, `configd`, `updaterd`, `padd`, `mediad`, `tofd`, `bluetooth`, `NetworkManager`.

Наблюдение или поиск через `journalctl`:

```
sudo journalctl -u configd -b --no-pager | tail -40
```

```
journalctl -u btd -f
```

Подставьте `robotd` или `updaterd`. `-f` следит, `-b` ограничивает текущей загрузкой.

Строка старта содержит версию, git-ревизию и каталог запуска на `warn`, сохраняясь при любом уровне логов.

История обновлений намеренно отдельно: `/var/lib/robot/updater/` с `fsync` каждой записи переживает непостоянные журналы:

```
robotctl update log
```

Последние двадцать запусков сохраняют полный пошаговый transcript под `runs/`:

```
robotctl update show 42
```

Оба переживают переключение, откат, обрыв питания, в отличие от journal на zram `/var/log`. Если сломан сам `robotctl`, файлы — JSON по строке, читаются `cat`:

```
sudo cat /var/lib/robot/updater/runs/000042.jsonl
```

<a id="tab-completion"></a>
### Дополнение по Tab

`install.sh` ставит в `/usr/share/bash-completion/completions/` загрузчик, запрашивающий дополнения у бинарника: они следуют версии и новым командам. Не `/etc/bash_completion.d/`, чтобы загружать при первом `robotctl<TAB>`, не каждом входе; обновление переносит старую копию. Для другой оболочки или сборки из `target/`:

```
eval "$(robotctl completions bash)"
```

Вместо `bash` поддерживаются `zsh`, `fish`, `elvish`, `powershell`.
