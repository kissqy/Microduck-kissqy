# Архитектура демона робота

Статус: черновик · Дата: 2026-07-22 · Ответственный: pierre

Порядок работ и этапы описаны в [`roadmap.md`](../project/roadmap.ru.md).

Этот документ дополняет [`updater-design.md`](updater-design.ru.md), где подробно разобрана система обновлений. Здесь описаны разделение на службы, обмен данными между ними, размещение состояния и управление роботом — локально, из приложения и удалённо.

Область действия: это целевая архитектура **первой выпускаемой версии**, а не текущего прототипа (`microduck_runtime`, который служит для экспериментов и будет переписан). Для v1 предусмотрена **одна точно определённая аппаратная конфигурация**.

<a id="the-shape-of-it"></a>
## Общая схема

На одной плате работают семь демонов, обменивающихся данными через Unix-сокеты. Один управляет роботом; три других позволяют восстановить доступ, даже если он сломается; остальные отвечают за транспорт и датчики, не владея состоянием робота.

```text
   gamepad          phone          you, on a laptop     a peer, anywhere    a GitHub release
      │ BLE/USB        │ BLE             │ ssh                 │ WebRTC              │ https
      ▼                ▼                 ▼                     ▼                     │
  ┌────────┐      ┌────────┐       ┌──────────┐          ┌──────────┐                │
  │  padd  │      │  btd   │       │ robotctl │          │  mediad  │                │
  └───┬────┘      └───┬────┘       └────┬─────┘          └────┬─────┘                │
      │               │  a subset of the same API             │                      │
      │  robot.*      │  robot.health · update.* · net.* · pad.* · system.*           │
      ▼               ▼                 ▼                     ▼                      │
  ┌──────────────────────────────────────────────────────────────────┐               │
  │   one unix socket per service · JSON-RPC 2.0, one object a line  │               │
  └────┬──────────────────────┬─────────────────────────┬────────────┘               │
       ▼                      ▼                         ▼                            │
  ┌───────────┐        ┌─────────────┐           ┌─────────────┐                     │
  │  robotd   │        │  configd    │           │  updaterd   │◄────────────────────┘
  │ robot.*   │        │ net.* pad.* │           │ update.*    │
  │ 50 Hz     │        │ system.*    │           │ verify      │
  │ loop      │        │ wifi, name, │           │ swap        │
  │ safety    │        │ pad bonding │           │ health gate │
  └─────┬─────┘        └──────┬──────┘           └──────┬──────┘
        │ Dynamixel           │ D-Bus                   │ systemctl restart,
        ▼                     ▼                         │ then robot.health
  15 servos + IMU      BlueZ · NetworkManager           ▼
  on one UART                                    /opt/robot/daemon/current

  ┌ publishes, answers nothing ───────────────────────────────────────┐
  │  tofd — the head's 8×8 depth matrix, on /run/tofd/tof.sock.       │
  │         mediad and robotd read it; it reads no one.               │
  └───────────────────────────────────────────────────────────────────┘
```

**Только `robotd` непосредственно взаимодействует с роботом.** Пятнадцать сервоприводов и плата IMU используют общую последовательную шину, которой владеет контур управления с частотой 50 Гц. Клиенты передают *намерения* — «двигайся с такой скоростью», «смотри туда», «встань» — а слой безопасности внутри `robotd` решает, что действительно можно выполнить. Ни один другой компонент системы не может подать команду двигателю ([`robotd-design.md`](robotd-design.ru.md)).

**Три службы продолжают работать при отказе `robotd`.** `configd`, `updaterd` и `btd` не зависят от него на уровне systemd и не требуют среды ML или медиастека: через них восстанавливают робот, у которого не запускается контур управления. Именно поэтому конфигурация находится в `configd`, а не в `robotd` (§1.1). `mediad` и `padd` зависят от `robotd`, и это допустимо: робот без камеры и геймпада всё ещё может получить обновление.

**`btd`, `padd` и `mediad` не владеют состоянием робота.** Это транспортные службы. `btd` пересылает подмножество API из BLE в отвечающий сокет; `padd` читает геймпад и отправляет те же намерения, что и приложение; `mediad` передаёт те же вызовы по каналу данных WebRTC и владеет только медиаконвейером. Любую из трёх служб можно заменить, не изменяя поведение робота. Все три используются ежедневно, поэтому API приложения не останется незаметно без проверки. `tofd` — исключение: он владеет одним датчиком, публикует кадры и ничего не читает (§1).

**Выпуски заменяются целиком, а не исправляются на месте.** Сборка помещается в отдельный каталог `/opt/robot/daemon/releases/<version>/`; `updaterd` проверяет её подпись, переключает символьную ссылку `current`, перезапускает службы и запрашивает у `robotd` состояние здоровья. Если проверка не проходит, служба самостоятельно возвращает прежний выпуск. Зацикливание падений, пережившее эту проверку, обнаруживает счётчик загрузок ([`updater-design.md`](updater-design.ru.md)).

| Служба | Чем владеет | Где принимает подключения | К чему обращается |
|---|---|---|---|
| `robotd` | управление двигателями, получение данных датчиков, политики, безопасность, `robot.health` | `/run/robotd.sock` | шина Dynamixel |
| `configd` | Wi-Fi, идентификатор и имя робота, PIN сопряжения, привязка геймпада, перезагрузка | `/run/configd.sock` | BlueZ и NetworkManager через D-Bus |
| `updaterd` | выпуски: проверка, установка, переключение, проверка работоспособности и откат | `/run/updaterd.sock` | GitHub Releases, `systemctl`, `robotd` |
| `btd` | ничем — транспорт BLE для подмножества API | служба BLE GATT | `robotd`, `configd`, `updaterd`; не `padd` и не `tofd`, потоки которых не помещаются в столь узкий радиоканал |
| `padd` | ничем — транспорт геймпада; предоставляет доступ к необработанному вводу | `/run/padd/pad.sock` (только `pad.input`) | `/run/robotd.sock` |
| `mediad` | конвейер камеры и звука; ничем в части состояния робота — транспорт WebRTC и точка входа удалённого доступа (§5.2) | TCP: консоль и PNG `GET /frame` на `:8080`, сигнализация на `:8443`; собственный Unix-сокет `/run/mediad/media.sock`, предоставляющий `media.frame` локальной записи или процессу восприятия, а также блоку камеры в `robotctl monitor`. Открытый блок запрашивает кадр дважды в секунду, закрытый не запрашивает его. Необработанный кадр занимает около 1.8 MiB, поэтому его сознательно не передают по каналу управления WebRTC | `robotd`, `configd`, `updaterd` |
| `tofd` | датчик ToF в голове: матрица глубины 8×8, которую он публикует и которую никто другой не читает | `/run/tofd/tof.sock` (`tof.stream`) | шина I²C платы HAT |
| `robotctl` | ничем — CLI, которое должно работать и на неисправном роботе | — | все перечисленные сокеты |

Где хранится состояние и что переживает обновление:

| Путь | Назначение |
|---|---|
| `/etc/robot/robotd.toml`, `updater.toml` | Конфигурация платы; установщик записывает её один раз и больше не перезаписывает. `robotd.toml` читает `robotd`, а раздел `[media]`, описывающий потоки камеры, также читает `mediad`; изменение этого раздела перезапускает `mediad`, а не `robotd`. |
| `/var/lib/robot/config/config.json` | Имя робота и PIN сопряжения — файл с `flock`, за который отвечает `configd` (§3.1). |
| Профили NetworkManager | Учётные данные Wi-Fi; мы их не храним (§3). |
| `/opt/robot/daemon/releases/<ver>/` | Исполняемые файлы, политики и поставляемые настройки по умолчанию; каталог заменяется атомарно. |
| `/opt/robot/daemon/current` | Символьная ссылка на действующий выпуск. |
| `/run/<service>/identity.json` | Данные о фактически запущенной версии каждого демона, публикуемые при запуске. |

Всё, что находится вне `releases/<ver>/`, сохраняется и при обновлении, и при откате. Это общее правило: конфигурацию конкретной платы нельзя включать в выпуск.

Путь изменения до робота целиком:

```text
  push a branch ──► CI builds and signs a release ──► robotctl update apply
                                                            │
                                                            ▼
                                          updaterd: verify signature, unpack,
                                          move `current`, restart the units
                                                            │
                                                            ▼
                                          health gate: ask robot.health
                                            ├─ healthy  ──► keep it
                                            └─ not      ──► put the old one back
```

Далее объясняются разделение служб (§1), обмен данными (§2), владение состоянием (§3), API и его транспорты (§4), удалённый доступ (§5) и распределение полномочий безопасности (§6).

<a id="1-services"></a>
## 1. Службы

`systemd` управляет жизненным циклом, перезапуском после сбоя, порядком запуска и watchdog.

| Служба | Чем владеет | Примечания |
|---|---|---|
| `robotd` | управление двигателями, кинематика, одометрия, политики походки, цикл опроса датчиков, безопасность | Ядро с требованиями, близкими к реальному времени; окончательное решение обо всём, что может повредить робота. Одометрия — структура внутри цикла, а не отдельная служба: её входные данные уже прочитаны этим циклом. |
| `mediad` | камера/микрофон, кодирование, восприятие, WebRTC и удалённый шлюз | Самая тяжёлая служба; также точка входа удалённого API (§5.2). |
| `btd` | сервер BLE GATT | **Только транспортный адаптер**, не владеет состоянием (§4.1). См. [`app-path-design.md`](app-path-design.ru.md). |
| `configd` | Wi-Fi, идентификатор робота, питание, сопряжение геймпада | Конфигурация должна быть доступна при отказе `robotd` (§3.1), а `btd` не должен владеть состоянием (§4.1); значит, за неё отвечает отдельная служба. Сопряжение геймпада находится здесь, а не в `padd`, потому что привязка устройства требует root и BlueZ, а `padd` намеренно работает как непривилегированный клиент (§4.1). |
| `tofd` | датчик ToF в голове: матрица глубины 8×8 на шине I²C платы HAT | Это восприятие, поэтому его отделяют от `robotd` по приведённой ниже причине. Владеет одним датчиком, публикует кадры и ничего не читает. Запускается даже на плате без датчика и сообщает об этом. |
| `updaterd` | механизм обновления | См. `updater-design.md`. |

`mediad` намеренно отделён от `robotd`: сбой медиа или восприятия не должен останавливать управление двигателями. К `tofd` применяется то же правило, хотя его датчик меньше. Запуск VL53L5/8CX требует передачи около 90 KB прошивки по I²C и занимает секунды; эта шина общая со звуковым кодеком, а у большинства роботов датчик вообще не установлен. Циклу повторных попыток не место в процессе, управляющем двигателями. Контур управления не читает глубину, поэтому вынесение датчика ничего у него не отнимает. `tofd` намеренно **не** входит в `mediad`: глубина поступает от датчика на шине, а не из медиаконвейера, и полезна ещё до появления камеры, изображение которой нужно размечать.

Потребители обращаются к нему так же, как к необработанному потоку геймпада: подписываются на сокете владеющего демона (`tof.stream`), не через `robotd`. Для пересчёта кадра в систему координат робота данные объединяют с положениями сочленений из `robot.state` и прямой кинематикой головы (FK) из крейта `kinematics`; `tofd` публикует вид самого датчика и не выдаёт его за геометрию, которую не может вычислить.

<a id="11-invariants"></a>
### 1.1 Инварианты

1. **`btd`, `configd` и `updaterd` переживают отказ `robotd`.** Это путь восстановления, который обязан работать именно при неисправности. Нет зависимости systemd от `robotd`, любое IPC необязательно и ограничено тайм-аутом, набор зависимостей минимален (без среды ML и медиастека). Подробнее в §4.1 `updater-design.md`.

   `configd` включён сюда по практической причине: при неисправности робота пользователю может понадобиться настроить Wi-Fi. Размещение конфигурации в `robotd` лишило бы доступа как раз тогда, когда он нужен.
2. **`robotd` принимает окончательные решения по безопасности.** Ни удалённый, ни локальный клиент не может обойти обнаружение падения, ограничения сочленений и температуры или логику безопасной позы. Клиенты посылают *намерения*, а `robotd` решает, что исполнимо.
3. **Контур управления `robotd` никогда не ждёт другую службу.** Все чтения от других служб используют локальный кеш с приоритетом последнего значения; синхронных RPC нет (§2.4).
4. **У каждого элемента состояния один писатель.** Каждому значению принадлежит ровно одна служба; остальные читают его или подписываются на обновления.

<a id="2-inter-service-communication"></a>
## 2. Обмен данными между службами

<a id="21-control-plane-vs-data-plane"></a>
### 2.1 Плоскость управления и плоскость данных

У двух видов трафика разные требования. Смешивать их здесь было бы типичной ошибкой.

| | Плоскость управления | Плоскость данных |
|---|---|---|
| Содержимое | команды, конфигурация, состояние, события восприятия | кадры видео/аудио |
| Размер и частота | десятки байт, ≤100 Hz | около 27 MB/s для RGB 640×480 при 30 fps |
| Механизм | RPC через Unix-сокет | **никогда не проходит через сокет** |

<a id="22-control-plane-json-rpc-20-over-unix-sockets"></a>
### 2.2 Плоскость управления: JSON-RPC 2.0 через Unix-сокеты

- Каждая служба владеет **одним Unix-сокетом**. Клиенты подключаются напрямую. При N=4 брокер не нужен: шина стала бы дополнительной точкой отказа и противоречила бы инварианту (1).
- **Формат сообщений: JSON-RPC 2.0, один объект на строку (NDJSON).** Стандартный протокол вместо собственного: сопоставление запросов и ответов, стандартные объекты ошибок и стандартные **уведомления**, подходящие для передачи прогресса и потоков событий. Границы сообщений определяет `tokio_util::codec::LinesCodec`; типы сообщений — обычные структуры `serde`.
- **Асинхронность и тайм-ауты повсюду, без исключений.** Любой узел может быть недоступен. Закрытый или молчащий сокет — нормальный ожидаемый исход.
- Подписка представляет собой поток уведомлений по открытому соединению.

**Измеренные альтернативы** (число уникальных зависимостей для ARM Linux):

| Вариант | Зависимости | Причина отказа |
|---|---|---|
| **JSON-RPC/NDJSON + tokio** | **30** | выбран |
| Только `jsonrpsee-types` (с собственным транспортом) | 36 | приемлемо, но замена кода по зафиксированной спецификации зависимостью версии `0.x` |
| `varlink` | 24 | близок по идее, однако менее знаком и почти ничего не даёт по сравнению с JSON-RPC |
| `zbus` (D-Bus, p2p+blocking) | 66 | см. ниже |
| `axum` через UDS | 66 | допустимо; см. «HTTP/WS» ниже |
| `tarpc` | 71 | удобен для Rust↔Rust, но сообщения нельзя читать глазами, а отправка с сервера неудобна |
| `tonic` (gRPC) | 81 | нагрузка `.proto` и генерации кода ради нескольких методов |
| `jsonrpsee-server` | 112 | **не может обслуживать Unix-сокет** — только HTTP/WS; `jsonrpsee-ipc` так и не реализован |

Число зависимостей приведено для справки и не было решающим критерием.

**Почему Unix-сокет, а не HTTP/WS на localhost.** По возможностям они почти одинаковы; различия касаются контроля доступа и последствий ошибок:

- **Права файловой системы дают авторизацию без отдельного механизма.** Сокет с режимом 0660 и отдельной группой доступен только разрешённым процессам. TCP-порт доступен любому процессу и пользователю на плате; для равнозначной защиты пришлось бы строить слой авторизации.
- **`SO_PEERCRED`** предоставляет uid/gid/pid вызывающей стороны для журнала аудита («кто инициировал откат» — первый вопрос поддержки) и для **проверки полномочий**. Уровней два, поскольку они отвечают на разные вопросы:
  - группа сокета (режим 0660) определяет, кто вправе **обращаться** к демону;
  - `allow_uids`/`allow_gids` определяют, кто вправе **изменять робота**, и применяются только к изменяющим вызовам. UID, от которого работает демон, разрешён всегда (он в любом случае может заменить демон); остальные должны быть перечислены, неизвестному участнику отказано.
  Чтение сознательно не ограничено этими списками: поддержке нужно осмотреть робота, даже когда она не вправе его менять. Одного членства в группе для разрешения «может заменить прошивку» слишком мало, если клиентом служит компонент, открытый в сторону BLE.
- **Класс ошибок с неправильным сетевым интерфейсом исчезает.** Опечатка, конфигурация или правка «чтобы заработало с ноутбука» могли бы привязать сервер к `0.0.0.0` и открыть *управление обновлением прошивки* для сети. С Unix-сокетом такую ошибку нельзя совершить. Этот довод имеет наибольший вес: речь не о сегодняшней модели угроз, а о возможном типе отказа.
- Для будущего **SDK** важно и другое: сторонний или пользовательский код на плате сможет открыть порт localhost, но не сокет, защищённый группой.

**Почему не HTTP/WS в плоскости управления** (независимо от транспорта: `axum` также обслуживает UDS): протоколу нужна отправка прогресса от сервера к клиенту. Для HTTP понадобились бы POST для вызовов **плюс** WebSocket/SSE для уведомлений — два механизма; `curl` не умеет работать с этой потоковой частью, поэтому удобство отладки ограничилось бы запросами и ответами. Вариант с одними WebSocket возвращает единый механизм, но добавляет рукопожатие ради JSON с границами сообщений и снова теряет `curl`. В постоянном соединении NDJSON вызовы и уведомления работают одним механизмом без рукопожатия: **меньше понятий — именно этого мы добиваемся.**

**Возможность на будущее, если для диагностики понадобится `curl`:** небольшой HTTP-интерфейс *только для чтения* на том же Unix-сокете (`GET /status`, `GET /log`). Он позволит вызвать `curl --unix-socket … http://x/status`, не перенося управляющие операции на HTTP и не дублируя потоковую передачу. Диагностика и управление предъявляют разные требования; их разделение помогает обеим задачам.

**Почему не D-Bus:** BlueZ (через `bluer`) уже подтягивает его, и `zbus` поддерживает прямое соединение без шины. Но одинаковые типы сообщений должны передаваться и через **BLE и WebRTC/WebSocket** (§4.1, §5.2), где обычные структуры `serde` подходят, а типы D-Bus — нет. Цель — одно определение на несколько транспортов; JSON позволяет добиться этого без дополнительных преобразований. Мы используем D-Bus только там, где его требует ОС (BlueZ, NetworkManager).

**Условие пересмотра:** если `btd` всё равно будет глубоко работать с D-Bus ради BlueZ, предоставление интерфейса обновлений через `zbus` почти ничего не стоило бы *для `btd`* и дало бы диагностику через `busctl`. Изменение невелико: типы остаются, меняется только обрамление сообщений.

<a id="23-async-where-it-waits-sync-where-it-computes"></a>
### 2.3 Асинхронность при ожидании, синхронность при вычислении

Асинхронный tokio применяется там, где служба действительно ждёт: обслуживает IPC во время длительной операции, ограничивает время запроса к другой службе или дочернего процесса, отменяет выполняемую работу.

Вычисления, загружающие CPU, и длительные операции с файловой системой остаются **синхронными**; асинхронный вызывающий код передаёт их в `spawn_blocking`. В обновляющем компоненте это, в частности, расчёт SHA-256 артефакта, потоковая проверка minisign, извлечение `zstd`+`tar` и рекурсивное удаление распакованных каталогов. На Pi они занимают секунды; если оставить их в асинхронном рабочем потоке, они задержат задачи IPC, которые должны продолжать отвечать на `status`/`subscribe` во время обновления.

Действительно быстрые операции с файловой системой — `rename` символьной ссылки, `fsync`, небольшое добавление в файл — вызываются напрямую. Передача их пулу потоков стоила бы больше, чем сэкономила.

<a id="24-data-plane-features-not-frames"></a>
### 2.4 Плоскость данных: признаки, а не кадры

`robotd` не нужны кадры камеры. Ему нужны *производные признаки* («мяч в точке (x,y)», «обнаружен человек», «громкий звук»): десятки байт при 10–30 Hz легко проходят через сокет.

**Принцип: размещать восприятие рядом с датчиком.** `mediad` владеет камерой, выполняет вывод модели и публикует признаки. Передача кадров в `robotd` для собственного компьютерного зрения израсходовала бы большую часть пропускной способности памяти платы.

**Внутри контура управления:** `robotd` подписывается один раз и читает локально кешированный *последний* снимок, без блокировки. Остановка `mediad` тогда ухудшает восприятие, а не добавляет дрожание времени управления двигателями.

**Если кадры когда-либо придётся передавать между процессами** (крайний случай): общая память (кольцевой буфер shm/dmabuf), а через сокет передавать только «кадр N готов по смещению X». libcamera поддерживает dmabuf, поэтому возможно копирование без промежуточных копий. Предпочтительны признаки вместо кадров, чтобы этого не потребовалось.

<a id="3-state-ownership"></a>
## 3. Владение состоянием

Есть три отдельных класса состояния; последствия для обновления и отката описаны в §5.7 `updater-design.md`.

| Состояние | Владелец | Механизм |
|---|---|---|
| Учётные данные Wi-Fi | **NetworkManager** | Мы их не храним. `configd` управляет NM через D-Bus; NM сохраняет профили с доступом только для root и переподключается самостоятельно. |
| Идентификатор робота, предпочтения пользователя, настраиваемые параметры | **хранилище конфигурации** (§3.1) | Файл + `flock` + `rename(2)` под управлением `configd`. |
| Калибровка, обученное состояние, создаваемые для конкретного устройства ресурсы | соответствующая служба | Вне каталогов выпусков; переживают и обновление, и откат. |
| Поставляемые значения по умолчанию, исполняемые файлы, пакеты политик | система обновлений | В `releases/<ver>/`, переключаются атомарно. |

Хранение учётных данных Wi-Fi в NetworkManager сокращает код, улучшает безопасность и убирает одну задачу миграции.

**На новой плате NetworkManager отсутствует**, хотя исходная версия этой строки таблицы предполагала обратное. Безголовый образ Armbian использует netplan + `systemd-networkd` + `wpa_supplicant`; netplan — *генератор* конфигурации. У него нет API сканирования, а `netplan apply` сообщает, что конфигурация применена, а не что соединение установлено. Приложению для настройки робота особенно нужны две вещи: «покажи сети» и «этот пароль неверен». Поэтому решение сохраняется, а `scripts/migrate-network.sh` однократно переводит плату на NM. Обоснование и результаты измерений на плате приведены в §2 [`app-path-design.md`](app-path-design.ru.md).

<a id="31-config-store"></a>
### 3.1 Хранилище конфигурации

Обычный файл и небольшой общий крейт — **намеренно не служба**:

- `flock` сериализует запись; запись во временный файл и `rename(2)` обеспечивают атомарность.
- `inotify` уведомляет об изменениях.
- Нет единой точки отказа: файл читается при остановке любой службы, а обновляющий компонент его не затрагивает (§5.7 `updater-design.md`).

Реализация находится в `configd/src/store.rs` и хранит имя робота и его PIN сопряжения Bluetooth. `inotify` там **пока сознательно отсутствует**: он потребуется, когда файл начнёт читать *второй* процесс; сегодня его читает только `configd`. Наблюдать за файлом, единственным писателем которого являешься сам, было бы лишней формальностью.

Конфигурация **должна быть доступна при отказе `robotd`**: настройка Wi-Fi нужна клиенту именно тогда, когда что-то сломалось. Поэтому хранить её внутри `robotd` нельзя.

**Конфигурация — это состояние, а не действия.** «Подключиться к этой Wi-Fi-сети», «перезапуститься», «применить обновление», «выбрать модель» — действия, которые направляются через RPC службе-владельцу.

<a id="4-the-robot-api"></a>
## 4. API робота

<a id="41-one-definition-many-transports"></a>
### 4.1 Одно определение, несколько транспортов

`btd` **ничем не владеет**. BLE — один из нескольких способов доступа. Если бы конфигурация или первичная настройка жили внутри `btd`, другие службы зависели бы от него, а SDK пришлось бы нелепым образом проходить через BLE.

```
        ┌──────── one API definition (shared crate: types + operations)
        │
   ┌────┴─────┬────────────┬──────────────┬────────────────┐
  BLE       unix socket   rendezvous    WebRTC datachannel
 (btd)      robotctl,     control lane  telepresence,
  subset    on-robot SDK  agents/LLM    full fidelity
```

Каждый транспорт — тонкий адаптер одного API. BLE предоставляет **подмножество** (первичную настройку, статус, запуск обновления и его прогресс): он слишком медленный и ограниченный для полного интерфейса, а большие данные через него вообще не передаются.

<a id="42-cross-cutting-rules"></a>
### 4.2 Общие правила

- **Авторизация для каждого транспорта.** BLE предполагает физическую близость и сопряжение; сетевому транспорту нужен токен. API один, но авторизация различается — место проверки следует определить с самого начала.
- **Согласование версии API.** Версии SDK и демона *обязательно* будут расходиться. Достаточно одного целого числа; при несовпадении — отказ с ясным сообщением (как у `model_api`).
- **Намерения, а не команды двигателям.** См. §6.

<a id="5-remote-access"></a>
## 5. Удалённый доступ

<a id="51-requirement"></a>
### 5.1 Требование

Все данные робота и медиа должны быть доступны по соединению **WebRTC** для (a) телеприсутствия и (b) серверной программы (например, LLM), наблюдающей за роботом и управляющей им. Последний сценарий должен быть *простым*.

<a id="52-webrtc-session"></a>
### 5.2 Сеанс WebRTC

Одно соединение PeerConnection переносит всё:

```
peer (browser / phone / server)
   ├── video track(s)   ── camera
   ├── audio track(s)   ── mic + speaker (two-way for telepresence)
   ├── datachannel "control"   reliable, ordered      → the robot API (§4)
   └── datachannel "teleop"    unreliable, unordered  → input + high-rate telemetry
```

Два канала данных отражают разделение из §2.1: команды телеуправления и телеметрия идут **без гарантии доставки** (`maxRetransmits: 0`), поскольку повторно доставленная через 80 ms команда джойстика хуже бесполезной. Всегда берётся самая свежая команда.

**PeerConnection принадлежит `mediad`.** Одно соединение PC нельзя разделить между процессами (потоки и каналы данных используют общую ассоциацию DTLS/SCTP). Ему также нужны закодированные медиа, поэтому оно находится в `mediad`, который пересылает сообщения `control` соответствующим службам через их Unix-сокеты. Таким образом, `mediad` — **удалённый шлюз**.

Цена такого размещения приемлема: сеанс телеприсутствия без медиа бесполезен, поэтому разделение процессов здесь ничего не сохранило бы. Локальное восстановление остаётся независимым через BLE / `robotctl` (инвариант 1).

<a id="53-server-side-agents-dont-force-them-through-webrtc"></a>
### 5.3 Серверным агентам не нужно навязывать WebRTC

Для контроллера на основе LLM WebRTC — *более сложный* путь. Агенту не нужен поток H.264 с 30 fps для декодирования: ему нужен один кадр раз в секунду или две и структура состояния. Требование сначала настроить ICE/DTLS/SDP и конвейер декодирования плохо оправдано.

| Потребитель | Управление | Медиа |
|---|---|---|
| Телеприсутствие (человек) | канал данных WebRTC | потоки с низкой задержкой |
| Серверный агент / LLM | **канал управления через посредника** — JSON-RPC поверх HTTP/SSE, без WebRTC | поток WebRTC; `media.stream` для долго работающей программы |
| SDK на роботе, `robotctl` | Unix-сокет | API снимков |
| Приложение | BLE + WebRTC | по необходимости |

За каждым способом доступа стоит тот же API. «Запустить на сервере LLM, управляющую роботом» означает войти в учётную запись, посылать намерения через посредника и получать видео, только если оно нужно. Канал управления достигает робота из центра обработки данных без ICE, DTLS и TURN — это и делает задачу действительно простой. Его устройство описано в §3.8 [`remote-access-design.md`](remote-access-design.ru.md), а выбор медиапути — в [`faq.md`](../faq.ru.md).

Задержка LLM (от сотен миллисекунд до секунд) означает, что агент управляет на **высоком уровне**: «иди на кухню», «посмотри на человека». Реактивное управление остаётся локальным в `robotd`. Такое разделение правильно независимо от транспорта.

<a id="54-infrastructure-reality-check"></a>
### 5.4 Проверка инфраструктурных предпосылок

«У робота есть собственный Wi-Fi» **не означает** «он доступен из интернета». Удалённому WebRTC нужны:

- путь **сигнализации** (обмен SDP/ICE);
- **STUN** и **TURN** как резервный релей для симметричного NAT — реальная инфраструктура с реальной стоимостью трафика.

Это противоречит предпосылке системы обновлений об отсутствии серверной части. **Телеприсутствию только в LAN всё это не нужно; телеприсутствию через интернет — нужно.** Вопрос остаётся открытым (§9).

<a id="55-implementation-note"></a>
### 5.5 Замечание по реализации

Выбор библиотеки зависит от аппаратного кодирования: GStreamer `webrtcbin` практичнее при использовании аппаратного H.264 через V4L2 M2M; `webrtc-rs` полностью написан на Rust и проще для понимания, но конвейер придётся строить самостоятельно. Это существенно определяет устройство `mediad`, поэтому решение нужно принять заранее.

Бюджет задержки для телеприсутствия с управлением: целевое значение **<200 ms от камеры до экрана**. Отсюда следуют настройки кодировщика на низкую задержку, отсутствие B-кадров и обновление внутри кадра вместо больших ключевых кадров.

<a id="6-safety-and-authority"></a>
## 6. Безопасность и полномочия

Речь об удалённом управлении шагающим роботом через соединение с потерями. Всё перечисленное дешевле предусмотреть при проектировании, чем добавлять потом.

- **Контроль активности / heartbeat.** Если команды перестают приходить или RTT превышает порог, `robotd` останавливает робота самостоятельно. Это обязательное требование: сеть может разорваться, LLM зависнуть во время вычисления, ноутбук уснуть.
- **Намерения, а не команды двигателям.** Удалённые клиенты задают скорость, направление взгляда, команду «сесть», но никогда сырые значения сочленений. `robotd` сохраняет окончательное решение при обнаружении падения, проверке ограничений сочленений и температуры, выборе безопасных поз. Ошибка агента не должна заставить робота выполнить движение в стену.
- **Явное распределение полномочий.** Физический контроллер, приложение, удалённый участник и слой автономного поведения могут одновременно требовать управления. Нужны заданные приоритеты и правила передачи управления, а не победа последнего отправителя. Локальный/физический контроллер должен иметь возможность вытеснить удалённый.
- **Ограничения сеансов.** В v1 одновременно один медиасеанс и M клиентов только для управления. Видео для нескольких участников (simulcast, однократное кодирование с рассылкой многим) отложено.

<a id="7-privacy"></a>
## 7. Конфиденциальность

Камера и микрофон находятся в чьём-то доме.

- **Явное согласие** на начало удалённого сеанса (для каждого сеанса либо понятное постоянное разрешение, которое пользователь может отозвать).
- **Видимый индикатор на роботе** во время потоковой передачи.
- DTLS-SRTP шифрует медиа сквозным образом **даже через релей TURN** — это следует прямо объяснять клиентам.
- При настройке через BLE передаются учётные данные Wi-Fi: соответствующая характеристика должна требовать сопряжения и шифрования.

<a id="8-observability-logs-and-versions"></a>
## 8. Наблюдаемость: журналы и версии

Эти требования общие для всех служб: робота в доме пользователя нельзя отлаживать, подключив к нему отладчик. Всё, что может понадобиться поддержке, уже должно находиться на роботе.

Подробности развёртывания — настройки journald, шаги установки и команды проверки — находятся в [`../deploy/README.md`](../../deploy/README.ru.md). Здесь установлен контракт для каждой службы.

<a id="81-every-service-logs-to-stderr"></a>
### 8.1 Каждая служба пишет в stderr

`tracing` → stderr → journald; уровень задаётся через `RUST_LOG` (`info` в поставляемых unit-файлах). Службы не ведут собственные файлы журналов: один механизм, одна политика хранения, одно место поиска.

**Первая строка каждого демона сообщает его идентичность**, причём с уровнем `warn`, чтобы она сохранялась при `RUST_LOG=warn` на долго работающей плате:

```
WARN starting service="robotd" build=0.2.0 (rev a1b2c3d, built 2026-07-28T13:50:00Z)
     exe=/opt/robot/daemon/releases/0.2.0/bin/robotd pid=814
```

Поле `exe` нужно потому, что указывает каталог выпуска, из которого процесс действительно запустился. Это позволяет отличить «обновление сработало» от «ссылка переключилась, но systemd по-прежнему исполняет старый файл».

**Объём журнала — вопрос хранения, а не внешнего вида.** Сообщение `robotd` для каждого такта имеет уровень `debug`; при `info` раз в пять минут записывается сводка с достигнутой частотой тактов в процентах от целевой. Запись каждого такта при `info` дала бы около 86k записей в день даже для неподвижного робота. При ограничении размера журнала именно они вытеснили бы сообщения, нужные для анализа инцидента. Сводка сообщает больше: контур на 60% целевой частоты остаётся живым и проходит проверку здоровья, а иначе это отклонение нигде не было бы видно.

<a id="82-two-records-deliberately-different-durability"></a>
### 8.2 Две записи с намеренно разной устойчивостью

| | Где хранится | Переживает потерю питания | Чем ограничено |
|---|---|---|---|
| журналы служб | journald | только при соответствующей настройке, см. `deploy/README.md` | `SystemMaxUse` |
| **история обновлений** | `/var/lib/robot/updater/update-log.jsonl` | **да** | 200 записей |

История обновлений намеренно не находится в журнале. Она хранится в `state_dir` механизма под `/var/lib`; для каждой новой записи вызывается `fsync`, а перезапись происходит атомарно (временный файл + rename + `fsync` родительского каталога). Поэтому на вопрос «что этот робот устанавливал и чем это закончилось» можно ответить и при непостоянном или очищенном журнале — именно с таким случаем поддержка, вероятнее всего, столкнётся.

<a id="83-the-running-version-and-the-installed-version-are-different-questions"></a>
### 8.3 Запущенная и установленная версии — разные вопросы

`updaterd` не может перезапустить себя посреди обновления (§4.1 `updater-design.md`), поэтому в течение нескольких секунд после него версия работающего процесса закономерно отстаёт от установленного выпуска. Инструмент, показывающий только одно число версии, в этот момент сообщает неверную картину, причём так, что исправный робот выглядит неисправным.

Речь о секундах, а не о времени «до перезагрузки»: механизм планирует собственный перезапуск и перезапуск `btd` через 5 s после ответа. При следующем запуске `updaterd` проверяет, что перезапуски состоялись, и перезапускает оставшиеся службы (§5 `restart-order.md`).

`robotctl version` показывает обе версии и поясняет различие:

- `updaterd` отстаёт от установленного выпуска → кратковременно это ожидаемо, но это единственное расхождение, которое не исправляется само: следующий процесс сообщает о нём, а не перезапускает себя. Если оно сохраняется, запланированный перезапуск не сработал;
- `robotd` отстаёт → это *неожиданно*, потому что он входит в список перезапуска `on_apply`, и перезапуск не вступил в силу.

Это разные диагнозы, поэтому сообщение не должно быть одинаковым. `--json` возвращает те же сведения для пакета поддержки. Команда работает и когда `updaterd` **не запущен**: она сообщает об этом отдельной строкой, а не завершается, ведь именно тогда пользователь к ней обратится.

Версию можно восстановить из четырёх независимых мест: первой строки журнала запуска; IPC-запроса `robotctl version`; `--version` каждого исполняемого файла; `version.toml` внутри каталога каждого выпуска. Кроме того, `robotctl update list` показывает ревизию, из которой собран каждый установленный выпуск. Потеря одного источника не лишает нас сведений.

`revision` встраивается при компиляции из `DUCK_REVISION`, который задаёт CI. При локальной сборке его нет, и программа честно сообщает `rev unknown, not a CI build`. Во время работы читать Git нельзя: у выпущенного робота нет репозитория. Это существеннее, чем кажется: когда появятся установки из веток (этап M2 дорожной карты), несколько сборок получат один номер версии и различить их можно будет только по ревизии.

<a id="84-health-is-one-question-so-it-is-one-command"></a>
### 8.4 Состояние здоровья — один вопрос и одна команда

`robotctl health` показывает в одном ответе сведения об оборудовании от `robotd` и о программной части от `updaterd`. Это не просто удобство: вопрос «что не так с этим роботом» невозможно разделить на оборудование и ПО *до получения* ответа. Робот, час назад откативший выпуск, может выглядеть точно так же, как робот с обесточенными сервоприводами, пока обе части не показаны вместе. Разделение вынудило бы заранее угадывать, где неисправность.

Команда **возвращает ненулевой код выхода, когда робот нездоров или недоступен**, и потому может служить условием в скрипте. Это контракт для любого вызывающего кода. Ничто другое не влияет на код выхода: разряженная батарея, горячий двигатель и закреплённый компонент отображаются, но не получают здесь оценку. Выпуск нельзя откатывать из-за состояния платы, на которую его установили.

`--json` возвращает то же содержимое для пакета поддержки.

<a id="9-open-questions"></a>
## 9. Открытые вопросы

1. **Телеприсутствие через интернет в v1 или только в LAN?** Главный вопрос: разница между отсутствием серверной части и необходимостью содержать сигнализацию + TURN (§5.4).
2. **SDK только для внутренней команды или для конечных пользователей?** От этого зависит строгость обязательств по совместимости API (§4.2).
3. **Приоритет полномочий** при разногласиях приложения, удалённого участника и автономного поведения: достаточно даже грубого фиксированного порядка, но его нужно решить явно, а не получать случайно (§6).
4. **Восприятие внутри `mediad` или в отдельном `perceptiond`?** Совмещение оставляет вывод модели рядом с камерой и проще; разделение не позволит сбою восприятия прервать видео. Решение зависит от сложности компьютерного зрения.
5. **Слой поведения/«мозга»** (побуждения, настроение, привычки): часть `robotd` или собственная служба и канал обновления? Обученное состояние в любом случае относится к §5.7 `updater-design.md`.
6. **Отзыв привязки через BLE.** Сейчас телефон нельзя отвязать через API; ручной выход — `bluetoothctl untrust`. Нужны метод API и правило, кто его вправе вызывать (§5 [`app-path-design.md`](app-path-design.ru.md)).
7. **Состояние первичной настройки конкретного устройства** — сейчас только индивидуальный PIN сопряжения. Серийный номер раньше тоже требовал отдельного места, но больше не требует: он записан в SoC и читается из `/proc/device-tree/serial-number` (§5.6 `updater-design.md`, §8.2 [`app-path-design.md`](app-path-design.ru.md)). PIN не может выводиться из идентификатора, как планировалось: идентификатор публикуется в рекламном объявлении, значит всё производное от него публично. Секрет по-прежнему нужно сгенерировать, записать и напечатать при изготовлении.

<a id="10-build-order"></a>
## 10. Порядок реализации

`updaterd` создаётся **первым**, а затем через него выпускается каждая следующая версия остальных компонентов архитектуры. Так риск системы обновлений проверяется рано, когда ошибки ещё ничего не стоят (нет клиентов и ценных данных), а путь обновления проходит сотни проверок до выпуска робота.

При этом следует учитывать последствия:

- `updaterd` строится относительно **интерфейса** `robotd` (проверка здоровья, разрешение безопасного перезапуска), а не реализации. Сначала применяется заглушка, что одновременно делает механизм проверяемым.
- Первые проверки здоровья будут слабыми («процесс жив»). Уверенность в автоматическом откате растёт по мере развития `robotd`; сначала проверяется сам *механизм*.
- **На ранних этапах разработки сохраняйте ручной путь восстановления (SSH / повторная запись образа).** Обновляющий компонент ещё не проверен и быстро меняется, а распространяется он внутри собственного артефакта: нельзя оставлять только его как путь назад.
- Поля схемы, которые трудно добавить позднее (`min_supported`, `schema_version`, `model_api`), включаются с первого выпуска, даже если пока не используются.
