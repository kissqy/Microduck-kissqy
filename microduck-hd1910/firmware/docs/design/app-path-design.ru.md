# Путь приложения — `btd` и `configd`

<a id="the-app-path--btd-and-configd"></a>
Статус: черновик · Дата: 2026-08-04 · Ответственный: pierre

Как телефон настраивает робота: Wi-Fi, имя, перезагрузка, версия и запуск обновления.

Дополнение к [`architecture.md`](architecture.ru.md), определяющему разделение служб и общий контракт. Здесь описаны две службы, появившиеся вместе, поскольку **они реализуют одну возможность** и решения в одной ограничивают другую: `btd` ничем не владеет, поэтому существует `configd`; `configd` предоставляет PIN, позволяя `btd` выполнять сопряжение; направляемый через `btd` метод должен получать ответ от `configd`.

Это сторона робота. Телефон на другом конце описан в [`mobile-app.md`](mobile-app.ru.md).

Разделы с пометкой **измерено** основаны на проверках Radxa Zero 3W, а не только рассуждениях.

**Полный путь работает на оборудовании** (2026-08-05): Mac обнаружил робота, выполнил сопряжение, прочитал версию API, прошёл проверку PIN и получил настоящий ответ `system.info`. Проверены обнаружение GATT, передача NDJSON частями в обе стороны, проверка PIN, таблица маршрутизации и обращение к `configd` через Unix-сокет. `configd` также работает с настоящим NetworkManager, сообщая текущие SSID и адрес.

Что **ещё не выполнено**: соединение не шифруется (§5.5), `net.connect` не проверен через BLE, вместо телефона тестировался только ноутбук.

<a id="1-the-shape"></a>
## 1. Устройство

```
        phone ──BLE──▸ btd ──┐
     robotctl ──unix socket──┼──▸ configd ──D-Bus──▸ NetworkManager   (wifi)
    (mediad) ──WebSocket────┘                    └──▸ logind          (reboot)
                             │                    └──▸ config file     (name, PIN)
                             └──▸ updaterd  (update.*)
                             └──▸ robotd    (robot.health)
```

Эту схему определяют два правила `architecture.md`, не оставляющие других вариантов:

- **§4.1: `btd` ничем не владеет.** Если бы первичная настройка или конфигурация находились в BLE-службе, все остальные зависели бы от неё, а SDK пришлось бы обращаться через Bluetooth даже для изменения имени робота.
- **§3.1: конфигурация должна быть доступна при неработающем `robotd`.** Настройка Wi-Fi особенно нужна при неисправности робота, поэтому её нельзя помещать в демон управления.

Другой службы для `net.*` и `system.*` не остаётся — отсюда пятая служба.

**Большая часть работы не относилась к Bluetooth.** Этот API и владеющая им служба одинаково нужны приложению телефона, SDK, `robotctl` и удалённому шлюзу `mediad`. `btd` — тонкий канал поверх них. Подтверждение: добавление семи методов `net.*`/`system.*` потребовало от `btd` по одной строке в таблице маршрутизации.

<a id="2-wifi-networkmanager-and-why-a-board-has-to-be-migrated-to-it-measured"></a>
## 2. Wi-Fi: NetworkManager и необходимость миграции платы · **измерено**

<a id="2-wifi-networkmanager-and-why-a-board-has-to-be-migrated-to-it---measured"></a>
В §3 `architecture.md` выбран NetworkManager. На плате его нет.

Образ Armbian без графического интерфейса использует netplan + `systemd-networkd` + `wpa_supplicant`. Три наблюдения заставили заново обосновать выбор:

- **Экземпляр `wpa_supplicant` с D-Bus не владеет интерфейсами.** Имя `fi.w1.wpa_supplicant1` занято, но `Interfaces` пуст; netplan запускает *второй* экземпляр, настроенный через `-c`, владеющий `wlan0` и не имеющий D-Bus. Прямое управление `wpa_supplicant` всё равно потребовало бы замены netplan, но без диагностики NM.
- **netplan не сообщает нужные телефону сведения.** Это *генератор* конфигурации: API сканирования отсутствует на всех уровнях, а `netplan apply` сообщает о применении настройки, не об успешности подключения. Он не отвечает на два главных запроса первичной настройки: «покажи сети» и «пароль неверен».
- **`RequiredForOnline=no` ухудшает загрузку.** Дополнение Armbian включает для `systemd-networkd-wait-online` режим `--any`: достаточно любого подключённого интерфейса networkd. Когда Wi-Fi передан NM, у networkd остаётся обычно не подключённый Ethernet, поэтому условие невыполнимо. Пометка этого интерфейса необязательным удаляет единственного кандидата и гарантирует ошибку. Решение — маскировать юнит; корректное ожидание обеспечивает `NetworkManager-wait-online`.

`scripts/migrate-network.sh` однократно выполняет миграцию и отказывается переключаться до копирования существующих сетевых реквизитов в профиль NM: иначе плата без монитора потеряет связь без возможности возврата. Скрипт включает защиту загрузки: если через 90s у `wlan0` нет адреса, восстанавливаются netplan и перезагрузка. Это идея счётчика загрузок обновляющего механизма, применённая к смене сети.

<a id="21-badkey-is-the-whole-point"></a>
### 2.1 Главный смысл — `BadKey`

`ConnectFailure::BadKey` оправдывает миграцию на NM. Неверная парольная фраза — наиболее частая ошибка настройки; без понятного сообщения пользователь не знает, что делать. NM обозначает её причиной состояния устройства 7. `configd` преобразует причины NM в `BadKey`, `NotFound`, `Timeout`, `Unsupported` и `Other`. Неизвестная причина никогда не должна становиться `BadKey`, иначе пользователя заставят снова вводить уже правильный пароль.

После `AddAndActivateConnection` служба `configd` опрашивает NM, а не возвращается при *начале* активации: ответ «конфигурация применена» уже даёт netplan, и именно он был отвергнут.

<a id="22-provisioning-a-new-network-which-is-the-point-of-the-whole-path"></a>
### 2.2 Настройка новой сети — назначение всего пути

Сценарий, оправдывающий BLE: плата попала в новое место, известной сети нет и по сети до неё не добраться. Его обеспечивают три свойства, причём исправления требовало только третье.

- **Демоны не ждут сеть.** У `btd` задано `After=dbus.service bluetooth.service`, у `configd` — `After=NetworkManager.service`; ни один не зависит от `network-online.target`. Даже без доступной точки доступа плата запускает BLE.
- **Созданный профиль переживает перезагрузку.** `AddAndActivateConnection` оставляет сохранённый профиль с включённым по умолчанию `autoconnect`. Повторным подключением занимается NM; `configd` вообще не входит в цикл восстановления связи.
- **Сканирование ждёт окончания сканирования.** · **измерено** `RequestScan` возвращается, когда NM *принял* запрос, а не когда радио обошло каналы. NM удаляет давно не виденные точки доступа, поэтому во время подключения в кеше часто остаётся лишь текущая точка робота. Немедленное чтение возвращало *предыдущее* сканирование: одна сеть при первом вызове и восемь при идентичном втором. Теперь `configd` ждёт изменения `LastScan` не более 10s и трактует ограничение частоты запросов как «кеш уже свежий», а не ошибку. Для выбора сети в незнакомом месте контракт «спроси дважды» неприемлем.
- **Результат читается из активации, не из устройства.** · **измерено** Самая серьёзная ошибка этого пути: `connect` опрашивал состояние *устройства*, которое остаётся `ACTIVATED` в прежней сети, пока новая активация рядом завершается неудачей. Поэтому `connect("Tehaupoo", psk: "lol")` для отсутствующей в зоне сети возвращал `{"outcome":"connected","ssid":"SFR-e994"}` — имя прежней сети. Ложный успех подключения хуже любого другого ответа: телефон считает настройку завершённой.

  Теперь опрашивается объект активного соединения, возвращённый `AddAndActivateConnection`; сообщается запрошенный SSID, а не текущий из `status`; невидимая сеть заранее отклоняется как `NotFound`. Неудачная активация удаляет созданный NM профиль, иначе autoconnect бесконечно повторяет заведомо плохой пароль, а `net.status` показывает сеть как `saved`.

  Скрытый SSID также отклоняется предварительной проверкой. Для него нужны `802-11-wireless.hidden` и возможность клиента указать «эта сеть скрытая», которой в API пока нет.
- **Повторная настройка заменяет профиль, а не накапливает их.** · **измерено** `AddAndActivateConnection` всегда добавляет, а NM допускает два профиля с одинаковым id. Обычная последовательность — опечатка в пароле, `BadKey`, верный пароль — оставляла оба профиля без гарантии, какой выберет NM после перезагрузки. `net.forget` ухудшал ситуацию, удаляя лишь один и сообщая об успехе. Теперь все профили SSID перечисляются как *множество* и удаляются до подключения; `net.forget` также удаляет их все.

  Удаление происходит до добавления: иначе успешное добавление и неудачная очистка оставляют дубликаты. Если затем добавление не удаётся, SSID остаётся без профиля — честный результат замены конфигурации, сообщаемый клиенту.

  При замене активного профиля робот отключается от сети. Это неизбежно: изменение ключа требует повторной ассоциации. На BLE-клиент это не влияет — свойство, на котором держится вся схема.

<a id="3-the-gatt-surface-a-pipe-not-an-api"></a>
## 3. Интерфейс GATT: канал, а не отдельный API

Одна служба, **одна характеристика**. Клиент однократно читает её для версии API робота, записывает байты NDJSON-запросов и подписывается на ответы: те же строки JSON-RPC, что во всех транспортах. Чтение обязательно; причина в §5.

**Версия сообщается для информирования, не для отказа.** `API_VERSION` показывает, что стороны собраны не вместе, но не определяет, какие вызовы несовместимы; обычно на этом соединении — никакие. Ничто не блокирует по этому числу: `configd` не проверяет версию для `net.*` и `system.*`, `updaterd` не требует handshake перед `update.status`, и его `hello` также больше не отказывает по версии. Клиентский отказ при несовпадении запрещает вызовы, на которые робот ответил бы, причём на транспорте для робота без сети, где именно `net.connect` позволяет исправить расхождение. `duckctl` предупреждает и продолжает. Приложению следует так же показать несовпадение, выполнить вызов и сообщить JSON-RPC-ошибку, если изменившийся метод действительно встретится. Ошибки самодостаточны: `METHOD_NOT_FOUND` для отсутствующего маршрута, `INVALID_PARAMS` для неизвестного параметра. Поэтому продолжение безопасно, а не просто оптимистично.

**Заголовка кадрирования нет.** Разделитель в обе стороны — уже разделяющий NDJSON перевод строки. Это безопасно: `serde_json` кодирует перевод строки внутри строки как `\n`, поэтому сырой `0x0A` внутри сериализованного объекта не появляется. Благодаря тому же свойству NDJSON работает через Unix-сокет. Префикс длины создал бы отдельный диалект BLE для каждого клиента; вместо него телефон, как `robotctl`, пишет байты и читает до перевода строки.

Буфер сборки ограничен 8 KiB, поскольку доступен любому в радиусе радио.

**Отвергнутые варианты:**

| | почему нет |
|---|---|
| Характеристики на каждое поле (name, ssid, ip, connect…) | Удобны для просмотра в универсальном BLE-приложении, но создают второй диалект API: каждое поле требует UUID и кода `btd`; список `net.scan` и поток `update.subscribe` плохо вписываются |
| Две характеристики, write и notify | Обычная схема, сначала реализованная именно так. BlueZ сообщает запись и подписку как *раздельные события*, поэтому характеристики приходится связывать по адресу устройства. Одна характеристика обеспечивает связь конструктивно |

Цена единственной характеристики — необычный вид в nRF Connect, где одна строка выполняет обе роли.

<a id="31-the-routed-subset-is-the-security-boundary"></a>
### 3.1 Разрешённое подмножество маршрутов — граница защиты

BLE открывает подмножество (§4.1). Одна таблица `btd/src/route.rs` определяет, *разрешён ли* вызов, *какой сокет* отвечает и *какое соединение* к нему используется. Первые два вопроса совпадают: вызов разрешён ровно тогда, когда таблица назначает ему службу. Третий включён туда же, чтобы нельзя было добавить метод без решения о соединении (§3.5).

**Сопоставление `Call` намеренно исчерпывающее.** Новый метод протокола ломает сборку `btd`, пока для него не принято решение. Шаблон `_ => None` был бы безопасным сейчас, но вредным со временем: новые методы молча запрещались бы, а первым признаком стало бы отсутствие функции в приложении, которую забыли маршрутизировать. Это уже сработало: семь методов `net.*`/`system.*` сломали сборку, как и аналогичное сопоставление в `updaterd`.

У каждого отказа есть причина:

| запрещено | почему |
|---|---|
| `update.pin` | Случайное закрепление заставляет робота отклонять все будущие обновления, показывая актуальность. Это единственная ошибка, выглядящая как правильное поведение. Оставлено для `robotctl` и намеренного действия человека |
| `update.resetToGolden` | Практически заводской сброс. Никогда по радио |
| `robot.safeToRestart`, `robot.modelApi`, `robot.remoteSessionActive` | Внутренние вопросы `updaterd` к `robotd`; телефон не получает полезных для действия сведений |
| `system.pairingPin`, `system.setPairingPin` | **Критически важно.** Если несопряжённый узел может прочитать или заменить ключ, сопряжение бессмысленно. `btd` читает его через Unix-сокет |

**`update.rollback` и `update.select` раньше запрещались, теперь нет.** Отказ объяснялся автоматическим откатом плохого выпуска, но он касается только провалившего проверку работоспособности. Пользователь берёт телефон при другом случае: выпуск установлен, прошёл проверку, но работает *хуже* — робот ходит неустойчиво или геймпад перестал переподключаться. Это исправляет только человек, у которого телефон и нет SSH. Обе команды переходят к уже работавшему на плате выпуску, ничего не скачивают, проходят проверки и автоматически отменяются при неуспехе, как любой переход. `update.apply` уже был разрешён и имеет более серьёзные последствия, поэтому расширение возможностей ближайшего радиоклиента минимально. Решение и компромиссы описаны в §2.4 `docs/project/update-over-ble.md`.

<a id="4-authorisation-two-layers-kept-apart"></a>
## 4. Авторизация: два раздельных слоя

| слой | механизм | решение |
|---|---|---|
| 1 | режим сокета `0660`, группа `robot` | кто может **подключаться и обмениваться данными** |
| 2 | `allow_users` / `--allow-user` | кто может выполнять **изменяющие** вызовы |

Вызовы чтения полностью обходят второй слой: поддержка может осматривать робота без права менять его.

Слоёв два, поскольку `btd` обязан состоять в `robot` для доступа к сокетам, но членство не должно давать право заменять прошивку. Обе службы предоставляют изменение **конкретной службе**: `allow_users = ["btd"]` в `updater.toml`, `--allow-user btd` в `configd.service`. Обе имеют тест, отклоняющий группу `robot`.

**По имени, никогда по uid.** `systemd-sysusers` выделяет номера динамически: номер в поставляемой конфигурации верен для одной платы и неверен для следующей. Имена разрешаются при старте; неизвестное имя вызывает предупреждение, а не остановку, поскольку отсутствие необязательной службы не должно лишать статуса.

`SO_PEERCRED` сообщает только **основной** gid. `SupplementaryGroups=` обеспечивает прохождение режима сокета, но не последующей проверки. Из-за этого все изменяющие BLE-вызовы возвращали `PERMISSION_DENIED`, а чтение работало: ошибка выглядела загадкой вместо понятной проблемы конфигурации.

<a id="41-privilege-and-where-the-parser-sits"></a>
### 4.1 Привилегии и расположение парсера

`btd` непривилегирован, `configd` работает от root. Это выглядит обратным, но обосновано.

`btd` разбирает байты любого находящегося рядом радиоклиента. `configd` получает лишь типизированный JSON через локальный сокет с проверкой учётных данных. **Размещение парсера по безопасную сторону границы важнее усиления диспетчера.**

Root нужен `configd` по узкой причине: изменение соединений NM и `Reboot` logind защищены polkit, но **polkit в этом образе нет**, а systemd запрещает оба действия непривилегированному процессу без сеанса. Альтернативой была установка движка JS-политик ради двух вызовов. В отличие от `robotd`, служба не обращается к оборудованию, поэтому юнит полноценно изолирует её: `ProtectSystem=strict`, один доступный для записи путь, только `AF_UNIX`, пустой `CapabilityBoundingSet`. `CAP_SYS_BOOT` намеренно отсутствует: перезагрузку выполняет logind, `configd` только просит. Capability разрешила бы некорректный `reboot(2)`, от которого схема защищает.

Если polkit появится по другой причине, `configd` следует перевести на отдельного пользователя с двумя правилами.

<a id="32-one-session-per-subscription-and-the-bug-that-decided-it-measured"></a>
### 3.2 Один сеанс на подписку и определившая это ошибка · **измерено**

<a id="32-one-session-per-subscription-and-the-bug-that-decided-it---measured"></a>
`btd` хранит один сеанс: буфер сборки, исходящую очередь и состояние авторизации. Вопрос — его время жизни. Первоначальный ответ: «пока работает служба», поскольку callback-модель BlueZ не даёт подписке идентификатор клиента и хранит только *одно* состояние notify на характеристику. Отдельные сеансы казались лишними; устаревшая часть строки — риском максимум одного неверного запроса.

Но страдал *следующий* клиент, что хуже. Это выявили три симптома на плате:

| симптом | причина |
|---|---|
| один запрос отвечает, следующий завершается тайм-аутом | первый передатчик забирал приёмник исходящей очереди из общего слота; у второй подписки не было передатчика, ответ записывался в никем не читаемый канал |
| `":0,"result":{"authenticated":true}}` — ответ без начала | потерянные фрагменты всплывали через следующий notifier |
| `no robot found`, затем та же команда работает | отдельная ошибка клиента: единственный снимок сканирования после фиксированной задержки случайно захватывал или пропускал объявление |

Только третья ошибка была клиентской. Первые две — один дефект: **состояние живёт дольше своего клиента**. Отключение в этой модели невидимо, поэтому сброса не происходило.

Теперь сеанс создаётся при подписке central и удаляется при его уходе вместе с буфером и очередью. Переподключившийся телефон начинает без авторизации, как уже обещал §5.2. Две критические детали сначала были неверны:

- Передатчик ждёт и очередь, и `notifier.stopped()`. Обнаружение ухода только по ошибке notify требует исходящего ответа; отключившийся в простое клиент иначе удерживает слот до запроса в никуда.
- Очистка удаляет слот только если там ещё *его собственный* sender. Notify исчезнувшему клиенту может ждать, пока сдастся BlueZ; за это время новый клиент уже создаст сеанс, который безусловная очистка уничтожила бы.

Запись без активной подписки по-прежнему запрещена: принимать её бессмысленно, поскольку ответ отправить некуда.

<a id="33-one-thing-the-mobile-app-will-hit-do-not-scan-with-a-service-filter-measured"></a>
### 3.3 Особенность для приложения: не фильтровать сканирование по службе · **измерено**

<a id="33-one-thing-the-mobile-app-will-hit-do-not-scan-with-a-service-filter---measured"></a>
`duckctl` намеренно остаётся главным образом тестовым инструментом; настоящий клиент — приложение телефона. Но одна ошибка относится к CoreBluetooth и заслуживает описания до повторного обнаружения на iOS.

`btd` объявляет UUID службы и hostname. При фильтре по службе робот всё же обнаруживается лишь *иногда*: **CoreBluetooth строго соблюдает фильтр, а сопряжённое периферийное устройство часто объявляется с пустым списком служб**. Тогда оно полностью отсутствует в результатах, а не показывается без служб. Отсюда `no robot found` и успешный следующий запуск без изменений. Первое исправление не помогло: резервный поиск по имени мог проверять лишь устройства, уже пропущенные фильтром.

Приложению нужно сканировать без фильтра, затем отбирать кандидатов по убыванию надёжности: объявленный UUID, известное имя или сохранённый идентификатор устройства. Единственное окончательное подтверждение — наличие нашей характеристики, проверяемое после подключения. В iOS есть более надёжный третий способ, чем у `duckctl`: `retrievePeripherals(withIdentifiers:)`, недоступный через `btleplug`. Сохранение идентификатора после первого успеха полностью убирает догадки при повторном подключении.

Одного снимка после фиксированной задержки тоже недостаточно. Объявления периодичны, сопряжённое устройство появляется и исчезает из представления адаптера; нужно опрашивать до появления кандидата.

<a id="34-the-robot-has-to-advertise-often-enough-to-be-caught-measured"></a>
### 3.4 Робот должен объявляться достаточно часто · **измерено**

<a id="34-the-robot-has-to-advertise-often-enough-to-be-caught---measured"></a>
`duckctl` сообщал `no robot found` примерно в половине запусков. Это считали нестабильностью инструмента или влиянием геймпада, чей LE-канал использует то же радио. Причина была иной: `btd` регистрировал объявление без интервала, и BlueZ использовал значение ядра **1.28 s**. Сканирующий с малой долей активности central ненадёжно ловит такое объявление.

Двухминутное непрерывное сканирование Mac с подсчётом объявлений по устройствам:

| устройство | сигнал | объявлений за 120 s |
|---|---|---|
| умная розетка | −66 dBm | 130 |
| маяк | −91 dBm | 159 |
| робот | **−36 dBm** | **16** |

У робота был самый сильный сигнал, но объявлений на порядок меньше. Дальность, помехи и клиент были исключены измерением. Средний интервал — 7.5 s, паузы — 9 s, 14 s, 17 s и однажды 31 s. Большие паузы почти кратны 1.28 s, что и выявило интервал. Восьмисекундный поиск в такой паузе ничего не находит.

Два вывода для приложения.

**Телефон не избегает проблемы лишь потому, что это телефон.** Первое подключение начинается со сканирования и попадает в те же паузы именно тогда, когда робот особенно должен находиться. Польза `retrievePeripherals(withIdentifiers:)` из §3.3 ограничена: сохранённый идентификатор позволяет iOS подключиться *без* нового обнаружения, превращая сбой повторного подключения в задержку. Для первого, наиболее важного подключения он не помогает.

**Интервал объявлений — свойство робота, ответственность `btd`**: 100–150 ms, в 8–12 раз чаще исходного, как у обычной периферии. Не разрешённые спецификацией 20 ms: одна антенна обслуживает объявления, LE геймпада и Wi-Fi, и лишнее эфирное время отнимается у основной работы.

Измерение сохранено в `duckctl/examples/advwatch.rs`, чтобы результат можно было воспроизвести: число объявлений и сигнал по устройствам, затем паузы робота.

**Подтверждено на плате.** После установки 100–150 ms повторён тот же двухминутный тест на том же Mac:

| | объявлений за 120 s | средний интервал | максимальная пауза | пауз ≥ 8 s |
|---|---|---|---|---|
| исходные 1.28 s | 16 | 7.5 s | 30.8 s | 7 |
| 100–150 ms | 151 | 0.8 s | 3.8 s | **0** |

Объявления приходят в девять раз чаще; главное, максимальная пауза меньше половины восьмисекундного окна `duckctl`, поэтому диагностированный сбой невозможен. Робот поднялся с 34-го места среди 106 устройств до 7-го среди 74.

<a id="35-one-connection-per-lane-because-a-daemon-serves-one-request-at-a-time"></a>
### 3.5 Соединение на каждую полосу: демон обслуживает запросы последовательно

`btd` открывает сокеты к `updaterd`, `robotd` и `configd` по необходимости и сохраняет на сеанс (`btd/src/upstream.rs`). Раньше был **один сокет на службу**, а оба обслуживающих демона обрабатывают соединение последовательно: прочитать строку, дождаться полного вызова, читать следующую (`updater/src/ipc.rs::handle_connection`, `configd/src/main.rs::handle`). Поэтому все запросы ждали самого медленного. Нарушались два первейших сценария приложения:

| действие клиента | результат |
|---|---|
| `update.apply`, затем `update.status` во время работы | статус оставался в сокете, который `updaterd` не читал несколько минут; клиент завершался по тайм-ауту, хотя робот нормально обновлялся |
| `update.subscribe`, затем `update.apply` | `stream_progress` владеет соединением до ухода клиента и больше не читает запросы; apply попадал в никем не читаемый сокет, не исполнялся, не отвечал и не выдавал ошибку |

Особенно важен второй случай: пользователь нажимает «обновить», робот ничего не делает, а ошибки нигде нет — запрос лежит в сокетном буфере.

Теперь вызовы группируются по **длительности владения соединением**, каждая группа получает своё соединение. Полоса назначается в `route.rs` рядом с разрешением и службой (§3.1), поэтому исчерпывающее сопоставление требует выбрать её для каждого нового долгого метода.

| полоса | время владения | вызовы |
|---|---|---|
| `Prompt` | время поиска значения | `hello`, `update.status`, `update.log`, `update.listInstalled`, `robot.health`, `net.status`, `net.forget`, `system.*`, `pad.status`, `pad.forget` |
| `Slow` | секунды — сеть или сканирование радио | `update.check`, `net.scan` |
| `Operation` | сколько потребуется; меняет робота | `update.apply`, `update.rollback`, `update.select`, `net.connect`, `pad.pair` |
| `Stream` | бесконечно; другие запросы не обслуживает | `update.subscribe` |

Общая полоса означает очередь, и для каждой группы это правильно. `updaterd` допускает одну изменяющую операцию под файловой блокировкой, отвечая `BUSY` второй; две радиооперации одновременно в `configd` тоже не нужны. `update.check` намеренно **не** относится к `Operation`: во время обновления у него есть немедленный ответ, а очередь превратила бы `BUSY` в индикатор ожидания на несколько минут.

Максимум четыре сокета на службу и сеанс, обычно два. Соединение на каждый вызов было бы аккуратнее, но тогда `btd` должен знать завершение вызова и разбирать ответы. Он никогда этого не делает (§3); благодаря этому остаётся транспортом, не второй реализацией API.

<a id="36-a-reply-bigger-than-one-burst-and-the-mtu-the-notify-side-cannot-ask-measured"></a>
### 3.6 Ответ длиннее одного пакета и MTU, недоступный стороне notify · **измерено**

<a id="36-a-reply-bigger-than-one-burst-and-the-mtu-the-notify-side-cannot-ask---measured"></a>
Работающая здесь callback-модель `bluer` (причина в заголовке `btd/src/bluez.rs`) не даёт стороне notify двух нужных свойств: согласованного размера и сигнала готовности радио. `notify` возвращается после постановки D-Bus-сигнала в очередь. Обходным решением были фрагменты по минимальным 20 байтам, отправляемые с максимальной скоростью цикла.

Измерение с Mac против платы: `system.logs` запрашивает конец журнала.

| ответ | уведомлений при минимуме | результат |
|---|---|---|
| ~5 KiB (24 строки) | ≈265 | доставлен за 1.83 s |
| ~7 KiB (32 строки) | ≈350 | сеанс уведомлений разорван через 150 ms |

Вторую строку удалось обнаружить только на плате. `btd` записал INFO об отписке central, хотя CoreBluetooth сохранял соединение. Клиент 60 секунд ждал в простое с половиной ответа в сборщике, не имея ошибки. Передатчик трактовал единственную ошибку `notify` как уход central, но переполненная очередь и уход возвращают одинаковый `Err`; различает их только `is_stopped()`.

Три изменения, ни одно не является полноценным решением из-за отсутствия сигнала готовности:

- **Размер берётся со стороны записи.** BlueZ сообщает согласованный MTU при каждой входящей записи; ATT MTU общий для направлений, а central всегда пишет до ответа — первым вызовом сеанса служит `system.authenticate`. Сеанс начинается с минимума, но первый же ответ имеет правильный размер, уменьшая число уведомлений примерно в десять раз.
- **После каждых 16 фрагментов передатчик делает паузу**, примерно на интервал соединения. Малый ответ не задерживается.
- **Отклонённый фрагмент повторяется**, а не считается отключением; окончательный отказ теперь явно журналируется как предупреждение.

Полное решение — `sendable()` IO-модели, но оно обслуживает только fd-пути `Acquire*`, которыми CoreBluetooth central не пользуется.

**Телефон согласует 515, что меняет масштаб проблемы** · **измерено** (2026-09-15). Всё выше измерено с Mac. iPhone 17 с iOS 26.6.2 через `tauri-plugin-blec` сообщает ATT MTU **515**: `maximumWriteValueLength` CoreBluetooth 512 плюс трёхбайтный заголовок. Демон вычитает его для полезной нагрузки, поэтому после первой входящей записи `btd` использует **512 байт вместо 20**.

Ответ ~5 KiB с ≈265 уведомлениями и 1.83 s превращается примерно в одиннадцать уведомлений; ~7 KiB, разрывавшие сеанс при ≈350, — примерно в четырнадцать. Сам дефект этим не исправлен: защищают три изменения выше. Но нагрузку создавали сотни фрагментов без сигнала готовности, а телефон до неё не доходит. Это определяет, можно ли предлагать `system.logs` в приложении.

<a id="37-a-robot-serving-one-central-is-still-findable-measured-2026-09-21"></a>
### 3.7 Робот с подключённым central остаётся обнаруживаемым · **измерено** (2026-09-21)

<a id="37-a-robot-serving-one-central-is-still-findable---measured-2026-09-21"></a>
При подключённом приложении робот полностью исчезал из `duckctl scan`: не под другим именем, не без служб, а вовсе. Команда для ответа «куда подключать SSH?» молчала, пока кто-то пользовался приложением, а её сообщение об ошибке советовало отключить другого клиента.

Сочетаются два механизма, очевиден только первый:

- Соединение **останавливает породивший его набор объявлений**. Так требует спецификация; BlueZ и ядро не восстанавливают его до разрыва связи.
- Linux вообще не **включает подключаемые объявления** при открытом соединении в роли peripheral, если контроллер не поддерживает это. `is_advertising_allowed` в `net/bluetooth/hci_sync.c` читает LE Supported States: неподключаемые объявления при периферийном соединении требуют состояния 20, подключаемые — 38 и 21.

Измерено на плате (AIC8800, HCI 5.4), с ежесекундной проверкой соединения телефона со стороны робота:

| регистрация при подключённом телефоне | появилось в эфире? |
|---|---|
| неподключаемое объявление с UUID службы утки | **да** — найдено ноутбуком через 8 s |
| подключаемое с тем же содержимым | нет — BlueZ зарегистрировал, сканирование не обнаружило |

`hciconfig hci0 lestates` подтверждает состояния 20 и 21; декодирование не доходит до 38. Отсутствие 38 установлено таблицей измерений.

**Поэтому при активном сеансе `btd` объявляет broadcast, иначе — peripheral.** Содержимое то же: имя, UUID службы, четыре байта IPv4. Робот обнаруживается, и `duckctl ip`, `ssh`, `scp`, `open` работают при занятом приложением соединении, поскольку им не требуется
радио после получения списка.

Это и правдивое состояние, и единственное доступное для broadcast. `bluer` хранит одно состояние уведомлений на характеристику (§3.2), поэтому второй central не получает отдельный сеанс, а *заменяет* первый. Подключаемое объявление приглашало к действию, которое демон не поддерживает, а принявший приглашение клиент ломал чужой сеанс.

Два ограничения. Адрес **меняется**: ядро требует приватность для неподключаемого набора и выдаёт неразрешимый частный адрес. Занятый робот поэтому имеет другую периферийную идентичность и сопоставляется по имени и UUID, не адресу. Если central отписался, но не отключился, `btd` регистрирует подключаемое объявление, которое ядро не включает, хотя BlueZ принимает регистрацию. До разрыва связи остаётся прежнее поведение; после него всё восстанавливается.

<a id="38-a-linux-laptop-connects-through-a-second-extended-advertisement-measured-2026-10-01"></a>
### 3.8 Ноутбук Linux подключается через второе расширенное объявление · **измерено** (2026-10-01)

<a id="38-a-linux-laptop-connects-through-a-second-extended-advertisement---measured-2026-10-01"></a>
`duckctl` на Linux-ноутбуке (Intel BE200, BlueZ 5.64) находил робота, но каждая попытка подключения завершалась `le-connection-abort-by-local`. Соседний Mac подключался сразу. Сопряжения ни с одной стороны не было, никто не занимал робота, журнал `btd` молчал.

HCI-записи обеих сторон одних и тех же попыток:

| central | алгоритм central | алгоритм робота | результат |
|---|---|---|---|
| ноутбук Linux, Intel BE200 | CSA #1 | **CSA #2** | `0x3e` Connection Failed to be Established с обеих сторон за 200 ms |
| Mac | CSA #1 | CSA #1 | подключается |

Алгоритм выбора канала #2 используется, только когда его предлагают **и** объявление, **и** запрос подключения. Контроллер ноутбука поддерживает #2, но выбрал #1: значит, legacy-объявление робота не предлагает #2. Однако AIC8800 всё равно использует #2, если central его предлагает. Стороны слушают разные каналы и теряют друг друга ниже уровня хостов. Параметры соединения ни при чём: supervision timeout 2000 ms дал тот же сбой.

При подключении через **extended**-объявление спецификация требует #2 с обеих сторон, и выбор контроллера становится правильным. Измерено: тот же ноутбук подключился к вручную зарегистрированному расширенному объявлению, обе стороны использовали #2, служба утки обнаружилась, `duckctl info` ответил.

**Поэтому свободный `btd` объявляется дважды**: прежний legacy-вариант, видимый любому central, и extended-двойник с тем же содержимым для Linux-ноутбука. Занятый робот убирает двойника, поскольку подключение невозможно через оба. В поле адреса двойника добавлен байт `duck_ble::adv::EXTENDED_MARK`: у объявлений разные случайные адреса, иначе они выглядели бы двумя роботами с одним именем, что `duckctl` отклоняет как конфликт. `duckctl` сопоставляет их по имени и адресу, оставляет двойника и ждёт его до секунды после legacy-объявления.

Пока не установлено, видят ли extended-объявление Mac и приложение телефона и через какое подключаются. Legacy-вариант остаётся доступным в любом случае.

<a id="5-pairing-just-works-and-a-pin-the-transport-checks"></a>
## 5. Сопряжение: just-works и PIN, проверяемый транспортом

Шестизначный PIN хранится `configd` и проверяется `btd` перед обслуживанием. **Не** Bluetooth-сопряжением: это диктуется спецификацией.

<a id="51-why-ble-cannot-carry-a-printed-pin-measured"></a>
### 5.1 Почему BLE не поддерживает напечатанный PIN · **измерено**

<a id="51-why-ble-cannot-carry-a-printed-pin---measured"></a>
Первоначально робот отвечал на запрос ключа BlueZ сохранённым PIN. На оборудовании macOS показывала *свой* случайный шестизначный код и ждала его ввода на роботе.

В LE passkey entry одна сторона **показывает** ключ, другая **вводит**; роли определяются заявленными возможностями ввода-вывода. Реализация `request_passkey` заявляет возможность ввода, поэтому macOS взяла показ на себя. Робот без клавиатуры не может выполнить свою роль.

Обратное тоже не помогает. `DisplayPasskey` назначает роботу показ, но **спецификация требует случайной генерации ключа показывающей стороной**. BlueZ выбирает его и передаёт агенту; подставить сохранённый нельзя, а показывать на роботе без экрана негде.

Фиксированный PIN на корпусе не выражается через BLE passkey entry. Остаются три варианта:

| | |
|---|---|
| Только just-works | Шифрование без аутентификации и PIN; защита основана на физическом присутствии. Так работает большинство BLE-устройств без экрана |
| Внеполосный канал (QR) | Настоящая аутентификация и индивидуальность робота. Поддержка OOB в BlueZ ограничена, приложения для неё нет; слишком большая работа для v1 |
| **Just-works плюс PIN уровня приложения** | **Выбран.** Сопряжение обеспечивает шифрование; PIN проверяется внутри сеанса по нашим правилам |

<a id="52-how-it-works"></a>
### 5.2 Как это работает

Сопряжение — just-works: все обработчики агента `None`, что `bluer` публикует как `NoInputNoOutput`. Чтение RPC-характеристики требует `encrypt_read`, вынуждая central сопрягаться. Нужна обычная криптозащита, не `encrypt_authenticated_*`: just-works никогда не удовлетворяет аутентифицированным вариантам, и их требование запретило бы всех клиентов.

Затем `btd` ничего не обслуживает до `system.authenticate`. На вызов отвечает сам транспорт, не пересылая дальше, поэтому таблица маршрутизации имеет третий результат `Route::Local` наряду с пересылкой и отказом. Единственное другое исключение — `hello`: он сообщает только версии, как чтение GATT, и запрет лишил бы несовместимого клиента объяснения проблемы.

Три принципиальные детали:

- **PIN запрашивается у `configd` при каждой попытке**, не кешируется. Поэтому `robotctl system set-pin` действует со следующей попытки, не перезагрузки. Если `configd` не отвечает, доступ запрещается.
- **Сравнение строковое.** `042042` и `42042` — разные секреты; числовой разбор уравнял бы их. Это проверено отдельным тестом.
- **Три попытки, затем закрытие сеанса.** Шестизначный PIN даёт миллион вариантов на зашифрованном, но неаутентифицированном канале. Ограничение делает перебор затратным: повтор требует полного BLE-подключения и сопряжения. `attempts_remaining` позволяет показать «осталось две», а не молча потерять связь.

<a id="53-what-this-is-and-is-not-worth"></a>
### 5.3 Что даёт эта защита и чего не даёт

**PIN проходит через зашифрованное, но неаутентифицированное соединение**, поэтому атакующий, присутствующий *при сопряжении*, может его перехватить. Это цена компромисса и причина предпочесть OOB позже, если модель угроз оправдает. Преимущество перед одним just-works: устройство, просто выполнившее доступное любому рядом сопряжение, всё ещё ничего не может делать.

**Заводской PIN `000000` открыт в репозитории.** Из коробки это подтверждает лишь физическое присутствие. `btd` предупреждает при каждой аутентификации с ним, `robotctl system pin` тоже отмечает это. Защита полностью зависит от индивидуальности PIN, поэтому создание, печать и учёт напечатанного — **обязанность первичной подготовки**. Это данные устройства из §5.7 `updater-design.md`, там же должен появиться серийный номер.

**Окна сопряжения нет — это решение, не отсрочка.** Робот доступен для сопряжения всегда, когда объявляется. Индивидуальный PIN уже даёт то, что добавило бы окно: знание напечатанного кода требует физического доступа, а прочитавший наклейку может взять робота. Кнопка добавила бы явное согласие, восстановление при потере PIN и дополнительную защиту от фотографии наклейки. Для v1 это не требуется; позже корпус с кнопкой сможет ограничивать `set_pairable` без смены схемы.

<a id="55-encryption-is-currently-off-and-that-is-not-settled-measured"></a>
### 5.5 Шифрование сейчас отключено; вопрос не решён · **измерено**

<a id="55-encryption-is-currently-off-and-that-is-not-settled---measured"></a>
`encrypt_read` заставляет чтение **зависать** на macOS: CoreBluetooth отправляет Read Request, BlueZ отклоняет из-за недостаточного шифрования, но нет ни запроса пользователю, ни ошибки, ни повтора. Клиент ждёт тайм-аута при исправном роботе. Без флага ответ мгновенный, значит причина в требовании.

На тестовой плате `btd` поэтому запускается с `--insecure-no-pairing`, и **PIN передаётся без шифрования**. Это хуже §5.3: нет ни шифрования, ни аутентификации. Любой в радиусе обмена может прочитать PIN и затем выполнить всё разрешённое клиенту.

Следует выяснить, существует ли вообще сопряжение: `Paired: no` в `bluetoothctl info <mac>` означало бы невозможность установить шифрование, а флаг был бы симптомом. До проверки перенос требования на запись — догадка: без сопряжения результат тот же.

**По умолчанию сейчас намеренно небезопасно.** Флаг называется `--require-pairing` и **выключен**. Установленная из выпуска плата предоставляет незашифрованное, но работающее соединение.

Сначала пробовали обязательное сопряжение и отвергли: новая установка защищена, но **непригодна к использованию**, поскольку все клиенты зависают при чтении версии — именно эта конфигурация ломает CoreBluetooth. Робот, с которым никто не может связаться, ничем не помогает; проект далёк от поставки, и инструменты разработки выбирают работающий вариант.

Цена заявлена прямо: **у каждого такого робота наблюдатель может прочитать реквизиты Wi-Fi и PIN**. `btd` предупреждает об этом при каждом старте, чтобы решение не забылось. Старый `--insecure-no-pairing` принимается и игнорируется только ради совместимости с дополнениями systemd, иначе удалившее его обновление сломало бы запуск.

До передачи кому-либо флаг необходимо включить по умолчанию и закрыть проблему. Робота с доступным наблюдателю секретом первичной настройки нельзя отдавать постороннему.

<a id="ios-is-not-macos-and-that-is-all-that-was-established-measured-2026-09-14"></a>
#### iOS отличается от macOS — установлено только это · **измерено** (2026-09-14)

<a id="ios-is-not-macos-and-that-is-all-that-was-established---measured-2026-09-14"></a>
Короткий A/B-тест на olducky: телефон против платы, между запусками `btd` перезапускался через дополнение systemd с настоящими `SupplementaryGroups` юнита.

При **выключенном** `--require-pairing`, как у Reachy Mini ниже, iPhone без жалоб подключился и обнаружил службу. При **включённом** iOS показала запрос сопряжения. Это существенный факт: **CoreBluetooth телефона начинает SMP там, где CoreBluetooth ноутбука не начинает**. Зависание §5.5 не является общим свойством стека, а утверждение «сопряжение невозможно» неверно.

Запуск остановили, поэтому *не установлено*, завершилось ли зашифрованное чтение и что показывал `bluetoothctl info`. Строки `version read` в журнале не было, но она записывается через `debug!`, а юнит задаёт `RUST_LOG=info`; отсутствие ничего не доказывает. Следующий исследователь должен добавить `Environment=RUST_LOG=debug` в то же дополнение, подключиться и нажать чтение, а не только подключение.

<a id="the-reference-implementation-does-not-use-link-layer-encryption-at-all"></a>
#### Эталонная реализация вообще не шифрует канальный уровень

Это стоит знать до следующего дня экспериментов с флагом. BLE-служба первичной настройки `reachy_mini` (`daemon/app/services/bluetooth/bluetooth_service.py`) объявляет характеристики `["write"]` и `["read", "notify"]`, без флагов шифрования. Регистрируется агент `NoInputNoOutput`, включается `Pairable`: central *может* сопрягаться, но это нигде не требуется. Поэтому iOS работает: телефон не просят шифровать.

Рассуждение то же, но вывод иной:

> Здесь BLE-сопряжение использует Just-Works: оборудование робота `NoInputNoOutput`, поэтому защита сопряжения от MITM невозможна. Мы шифруем на уровне приложения и включаем PIN устройства в выработку ключа.

Это тот же тупик, что описан в `crate::pairing`. Здесь решили *исправить канальный уровень*, а там — *не требовать от него конфиденциальности, а зашифровать важный секрет*: `x25519-hkdf-sha256-aesgcm`, временный ECDH со сменяемым ключом робота, HKDF с PIN как солью, AES-256-GCM с SSID как AAD. Это защищает от пассивного прослушивания, но не активного MITM при настройке; авторы прямо говорят об этом и планируют PAKE.

**В §8.1 появляется третий кандидат и наше собственное ограничение.** Невозможность восстановить пароль Wi-Fi обеспечивается временным ECDH, не PIN. PIN как соль мешает клиенту с неправильным PIN сформировать расшифровываемый блок; при `000000` это ничего не даёт. У них PIN — последние пять символов серийного номера, напечатанные на роботе. Это работает потому, что объявления анонимны: все называются `ReachyMini`. Наше имя выводится из серийного номера (§8.2), поэтому этот приём закрыт более важным ранее принятым решением.

**Намеренно отложено, не отвергнуто.** Ничего не поставляется и никому не передавали робота; соединение остаётся открытым, `--require-pairing` выключен по умолчанию. Условие неизменно: закрыть вопрос до передачи робота.

<a id="56-open"></a>
### 5.6 Открытые вопросы

- **Отзыв сопряжения.** API для отключения телефона нет; вручную используется `bluetoothctl untrust`. Нужны метод и правило доступа, вероятно не через сам BLE.
- **Ограничение попыток действует лишь в сеансе.** Три ошибки закрывают его, но между переподключениями счётчика нет. Настойчивый клиент может бесконечно повторять, оплачивая сопряжением каждые три попытки. Следующий очевидный шаг — задержка по адресу в `btd` с хранением состояния между сеансами.

<a id="23-the-fake-is-the-specification-and-nothing-checks-nm-against-it"></a>
### 2.3 Имитация задаёт спецификацию, но NM с ней не сверяется

Стоит сказать явно: это описывает уже три ошибки. Во всех найденных на плате сбоях Wi-Fi **`FakeNet` уже работал правильно, а реализация NetworkManager отклонилась от него**:

| поведение | `FakeNet` | поставленный путь NM |
|---|---|---|
| радио не видит SSID | `NotFound` | `connected` с именем другой сети |
| неудачная попытка | ничего не сохраняет | оставляет профиль с плохим ключом |
| повторная настройка SSID | заменяет | добавляет второй профиль |

Trait — не только точка подмены в тестах, но единственная письменная форма контракта. Проблема в направлении проверки: тесты проверяют fake по контракту, но NM не сравнивается ни с одним. Оба реализуют `Net`, и одни проверки *могли бы* работать для обоих. Однако NM нужны настоящий NetworkManager и радио, то есть плата, не CI. См. «What would close it» в `install-path-gap.md`: плата по замыслу используется по запросу, не как CI-runner.

Пока такого теста нет, честный вывод: поведение Wi-Fi `configd` протестировано, а выполняющийся на роботе код — нет. Все указанные ошибки найдены вручную на оборудовании за один сеанс.

<a id="24-what-has-actually-run-on-a-board"></a>
### 2.4 Что действительно проверено на плате

Это записано потому, что «собрано» и «работает» слишком долго означали здесь одно, а четыре «исправления» проверялись против не запущенных бинарных файлов.

На Radxa Zero 3 с Mac-клиентом полностью проверены обнаружение, подключение, чтение версии, PIN-аутентификация, `system.info`, `net.status`, `net.scan`, граница отказов (`robot.move`, `system.pairingPin`, `update.select` отклонялись самим `btd` с кодом 14), передача `update.check` в `updaterd`, `NotFound` для невидимой сети и **настройка через BLE неизвестной ранее сети, подключение и автоматическое повторное подключение после перезагрузки** — главный сценарий. Неверный пароль возвращает `BadKey` с причиной NM 7, позволяя телефону снова запросить пароль вместо общей ошибки.

`net.forget` удаляет все профили SSID: пять дубликатов `kek`, оставленных прежними бинарными файлами, удалены одним вызовом. Весь `net.*` теперь проверен с настоящим NetworkManager.

На плате всё ещё нет шифрования (§5.5). Это единственное, что отделяет путь от решения, которое можно передать пользователю.

<a id="6-testing-without-a-radio-measured"></a>
## 6. Тестирование без радио · **измерено**

<a id="6-testing-without-a-radio---measured"></a>
Набор тестов работает на ноутбуке без оборудования, сети, D-Bus и Docker; это требование сохраняется благодаря двум границам подмены:

- **Wi-Fi `configd` представлен trait** с имитацией в памяти, как `RobotIo` у `duck-control`. `--fake-net` обслуживает весь `net.*`, включая вызываемую по требованию ошибку неверного ключа, неудобную для воспроизведения с настоящей точкой доступа.
- **Радио `btd` — два канала, не trait.** `GattLink` потребовал бы async `recv` и `send`, одновременно ожидаемые циклом сеанса: associated types или борьбу с borrow checker внутри `select!`. Структура с двумя `mpsc` выражает то же проще; тест создаёт её, ничего не реализуя.

Тесты сеанса проводят полный BLE-разговор через настоящие Unix-сокеты: запрещённый вызов не достигает демона, `robot.*` идёт в `robotd`, не `updaterd`, каждое уведомление потока приходит через MTU 23 байта.

`board-test.sh` проверяет Linux-специфику: режимы сокетов, разрешение имени `--allow-user`, чтение членом группы, блокировку постороннего режимом сокета, отказ неназванному члену в изменении **с подтверждением отсутствия изменения**, код выхода 5 вместо 1 при неверном пароле, ведущий ноль PIN и отсутствие пароля в журнале. Также проверяется `btd --version` — настоящая проверка кросс-компоновки: только `btd` использует C помимо `zstd`, поскольку `bluer` связывает libdbus, собранную из включённых исходников через `zig cc`.

`duckctl` (`cargo run -p duckctl`) заменяет телефон и является единственным способом проверить радио. Это **пример, не бинарный файл поставки**, поэтому `btleplug` не попадает на робота. Выбран `btleplug`, не `bluer`, ради работы на Mac разработчика. Он использует `duck_ble::framing`: разбиение действительно является клиентской половиной кода робота, а не независимой реализацией, способной согласоваться лишь с собой.

<a id="61-what-is-not-tested"></a>
### 6.1 Что не протестировано

- Ни одна служба ещё не встречалась с **настоящим радио** или **настоящим NetworkManager**. Обе проходят проверку типов для aarch64; только это.
- **Переключение** `migrate-network.sh` выполняется лишь на свежепрошитой плате. Его один раз выполнили вручную по шагам, затем повторно запустили скрипт для проверки идемпотентности. Первый пользователь, прошивающий плату, станет настоящим тестом.
- **Около 73s до ответа BLE.** `hci0` появляется лишь после подключения UART AIC8800 службой `aic-bluetooth.service`; `bluetooth.service` 26s ждёт `dbus`. `btd` ждёт и повторяет вместо завершения, как `robotd` ждёт моторную шину, но приложение с ожиданием мгновенного обнаружения будет разочаровано.

<a id="7-costs-accepted"></a>
## 7. Принятые издержки

- **Два D-Bus-стека в артефакте.** `btd` связывает libdbus через `bluer`, `configd` использует `zbus`; несколько MB. `bluer` выбран именно для GATT-сервера, объявлений и агента сопряжения вместо примерно 700 строк ручной обвязки `org.bluez`. Стоит пересмотреть, если появится backend `zbus`.
- **Включённую libdbus** обновляем мы, не дистрибутив. Это допустимо для библиотеки, доступной только через локальный сокет из написанного нами демона.
- **`btd` намеренно исключён из перезапусков `on_apply`.** Он может быть *транспортом запроса обновления*: перезапуск оборвёт `update.subscribe`, и телефон не узнает результат. Поэтому же `updaterd` не перезапускается посреди обновления. Исключение ограничено: после отправки ответа механизм перезапускает `btd` через 5 s, а следующий старт `updaterd` проверяет выполнение (`restart-order.md`, §1 и §5).

<a id="8-next"></a>
## 8. Следующие шаги

Порядок определён зависимостями, а не объёмом.

<a id="81-encryption-the-blocker"></a>
### 8.1 Шифрование — блокирующий вопрос

<a id="81-encryption--the-blocker"></a>
Полностью описано в §5.5. Соединение **по умолчанию** не шифруется: `--require-pairing` выключен из-за зависания клиентов, поэтому PIN и все пароли Wi-Fi передаются открыто. Нужно и исправить защищённую конфигурацию, *и* сделать её стандартной; только первое оставит платы небезопасными.

Теперь три кандидата вместо одного предполагаемого ранее:

| | |
|---|---|
| **Исправить канальный уровень** | Исходное предположение страницы. При успехе защищает весь маршрутизируемый API без собственного криптокода. Ограничение: сопряжение остаётся just-works, поэтому `encrypt_authenticated_write` недостижим независимо от прочих изменений (§5.5) |
| **Шифровать на уровне приложения** | Решение Reachy Mini, работающее на обеих мобильных платформах и прошедшее App Review. Защищает пароль от пассивного прослушивания без сопряжения. Ограничение: защищено лишь то, что не забыли зашифровать; транспорт теперь также несёт код устройства, строки журнала и сам PIN (§3.1) |
| **Шифровать весь сеанс, не отдельный вызов** | Та же криптография устанавливается один раз после `hello` и защищает каждый последующий кадр. Работы больше, но только этот вариант защищает `system.authenticate` и не позволяет забыть новый метод |

Решающий для первого варианта факт неизвестен: существует ли сопряжение (`bluetoothctl info <mac>` на роботе). *Сопряжён, но не шифрует* и *никогда не сопрягался* требуют противоположных исправлений. Неверное решение оставит проблему, выглядящую исправленной. §5.5 фиксирует результат iPhone и точку продолжения.

<a id="82-telling-robots-apart-three-people-three-robots-one-room-built"></a>
### 8.2 Различение роботов: три человека, три робота, одна комната · **реализовано**

<a id="82-telling-robots-apart--three-people-three-robots-one-room---built"></a>
Трое друзей распаковали роботов, каждый должен выбрать своего. До изменения все платы из одного образа объявлялись как `radxa-zero3`.

Это прежде всего удобство. Есть и риск: выбравший не того робота телефон может авторизоваться и записать туда пароль владельца, поскольку у всех PIN `000000`. Но исправление оправдано и без этого: робот, которого нельзя выбрать в списке, непригоден к использованию. §8.1 отслеживается отдельно и не блокирует эту работу.

<a id="what-a-robot-is-called"></a>
#### Имя робота

**Идентичность берётся из серийного номера SoC**, читаемого из `/proc/device-tree/serial-number` и возвращаемого `system.info` (`configd::identity`). Он записан в чипе, передаётся загрузчиком, переживает перепрошивку и смену радиомодуля, не требует первичной подготовки. Поэтому работает и вручную прошитая плата. Это обычное чтение файла без root и D-Bus, доступное сразу, не через ~73 секунды появления `hci0`.

Идея уже есть в репозитории: §5.6 `updater-design.md` выбрал то же значение как стабильный ID журнала обновлений по той же причине — оно работает без подготовки. Повторное использование даёт роботу одну идентичность вместо двух.

Адрес Bluetooth казался лучшим, поскольку сосед уже видит его на канальном уровне и производное имя не раскрывает нового. Но измерения отвергли его; см. §8.6.

**Имя по умолчанию — `duck-` и четыре шестнадцатеричных символа SHA-256 серийного номера**, например `duck-c51b`. Хеш вместо среза нужен потому, что неизвестно, какая часть ID различается между чипами. SHA-256 вместо стандартного хешера Rust обеспечивает стабильность между версиями Rust; иначе обновление toolchain переименовало бы всех роботов без очевидной связи событий.

Четыре hex-символа дают 65 536 вариантов: для трёх роботов в комнате совпадение примерно раз на 22 000 случаев. Это *различимое* имя по умолчанию, не уникальный ключ.

Имя передаётся в **scan response**, не основном объявлении, и теперь так будет всегда: flags (3), UUID службы 128 бит (18) и поле адреса (8, ниже) занимают 29 из 31 байта legacy-объявления. До адреса занималось 21; имя до 8 символов поместилось бы, но `duck-c51b` имеет 9, поэтому фактически не помещалось. Scan response — отдельный обмен, который можно пропустить; устройство без имени и служб поэтому может оказаться роботом, его нельзя фильтровать. Поэтому `duckctl` после срока поиска несколько секунд ждёт имя уже услышанного робота (`NAME_GRACE`).

<a id="the-advertised-name-is-the-one-the-robot-was-given"></a>
#### Объявляется назначенное роботу имя

`btd` спрашивает имя у `configd` и каждые несколько секунд приводит объявление к этому ответу. Раньше объявлялся `/etc/hostname`, а `system.setName` писал в никем не читаемый файл. Переименование ничего видимого телефону не меняло даже после перезапуска, хотя три комментария описывали намерение как реализованное.

Сверка работает вместе с наблюдением адаптера в одном цикле запуска. Потеря радио завершает оба; новый запуск спрашивает снова, подхватывая переименование во время отсутствия Bluetooth.

**У робота два имени, устанавливаются оба.** Объявление несёт Local Name; адаптер отдельно предоставляет GAP Device Name (`0x2A00`), который BlueZ берёт из `Adapter.Alias`, по умолчанию hostname. При изменении только первого робот объявлял `duck-c51b`, но при чтении характеристики отвечал `radxa-zero3`, а central читает её при подключении. BlueZ затем кешировал ответ поверх объявленного имени: Linux видел `duck-c51b` до первого контакта и `radxa-zero3` после, и `--name duck-c51b` переставал находить его. CoreBluetooth хранит оба и показывает `radxa-zero3 [duck-c51b]`. Настройки Bluetooth телефона показывают GAP-имя — наиболее важный случай, не видимый инструментам репозитория. `advertise` теперь задаёт alias вместе с объявлением, поэтому все пути публикуют оба имени. Клиентский кеш старого имени сохраняется до забывания устройства; это исправляется на клиенте.

Сверка намеренно периодическая, не событийная. `btd` пересылает `system.setName`, не читая ответ: разбор ответов он избегает. Немедленный запрос имени соревновался бы с только что пересланной записью. Опрос проще и учитывает переименования через `robotctl`, вообще не проходящие через `btd`. `--name` закрепляет *имя* для стенда, но цикл остаётся активным, поскольку адрес меняется независимо. Если `configd` недоступен, используется hostname: `btd` нужен для восстановления и должен запуститься раньше остального робота.

<a id="the-advertisement-carries-the-robots-ipv4-address"></a>
#### Объявление содержит IPv4 робота

`duckctl scan` никуда не подключается, поэтому полезен при недоступном роботе, но может показать лишь содержимое объявления. Главный вопрос списка — *куда подключать SSH?* — оставался без ответа: адрес был в `net.status`, требовавшем для каждого робота соединения, сопряжения и PIN.

Четыре байта IPv4 помещаются в manufacturer-data с company id `0xFFFF`, зарезервированным Bluetooth SIG для внутренних и совместимых тестов: подходящий выбор для проекта без назначенного id. Его может использовать любой, поэтому **поле не подтверждает идентичность**. Оно читается лишь у устройства, также объявившего UUID нашей службы.

**SSID здесь нет и быть не может.** Он занимает до 32 байт, тогда как бюджет оставляет 6 байт нагрузки. Его узнают через `wifi status`, особенно если адрес списка неожиданен.

Без адреса робот объявляет `0.0.0.0`, а не убирает поле. Это различает три состояния: адрес есть, робот без сети, старый выпуск вообще без такого поля. Смешение последних заставило бы проверять Wi-Fi там, где нужно обновление.

Адрес сверяется вместе с именем каждые несколько секунд — быстрее смены DHCP-аренды. Главное другое: выполнивший `wifi connect` ждёт полученный адрес. Недоступность `configd` сохраняет последнее значение, иначе его перезапуск заставлял бы на каждом такте перерегистрировать объявление с мигающим адресом. Если BlueZ отвергает объявление с полем, `btd` повторяет без него: робот без адреса ещё доступен, а без объявления полностью исчезает.

<a id="provisioning-can-name-a-board-and-does-not-have-to"></a>
#### При подготовке плату можно назвать, но это необязательно

`provision.sh --name`, передаваемый из `provision-board.sh --name`, в конце вызывает `robotctl system set-name`. Необязательность намеренная: производное имя уже различает платы, поэтому подготовка *улучшает* рабочее имя, а не создаёт его. Так сохраняется работоспособность ручной прошивки, из-за которой отвергли назначение идентичности только при подготовке.

<a id="what-the-app-should-do"></a>
#### Что должно делать приложение

- **Хранить серийный номер как ключ.** Только он переживает переименование и смену Bluetooth-адреса; к нему привязываются избранное и пользовательские подписи.
- **Хранить и peripheral identifier** для быстрого пути: `retrievePeripherals(withIdentifiers:)` iOS пропускает сканирование. Это кеш, не идентичность: он теряется при смене адреса (§8.6), а серийный номер восстанавливает соответствие избранному.
- **RSSI — ключ сортировки, никогда не идентичность.** Он позволяет показывать ближайшего первым, но тело или стол свободно меняют порядок сигналов.

После первого подключения задача решена: приложение возвращается к тому же роботу и показывает назначенное владельцем имя.

<a id="still-open"></a>
#### Оставшиеся вопросы

- **Который из трёх мой при первом включении.** Различимые имена не объясняют, какое относится к утке в руках. Нужен физический признак: надпись, действие `identify` или близость. Самая дешёвая мера без кода — включать роботов по одному и подсказать это в приложении.
- **`identify`** — заставить конкретного робота кивнуть, мигнуть или пискнуть. В дереве ничто не управляет LED, динамиком или экраном, а моторные команды через BLE намеренно запрещены (§3.1). Это отсутствующий аппаратный путь, не просто разрешение. Когда он появится, нужно определить допустимые исполнительные механизмы и разрешить действие *до* аутентификации: PIN не может быть предварительным условием, если нужно сначала понять, кому его вводить.
- **Наклейка и индивидуальный PIN на ней.** PIN нужен по §5.3; оба ждут не выбранного ещё оборудования. PIN нельзя выводить из идентичности: она публикуется, значит производное значение тоже публично.
- **Действие заводского сброса.** Сейчас ничто не очищает конфигурацию `configd`: она намеренно переживает обновления и откаты, а `update.resetToGolden` возвращает выпуски, не настройки. Исходное и пользовательское имя неразличимы. Отдельный «заводской» слот нужен только когда появится очистка одного без другого.

<a id="what-the-tests-do-not-cover"></a>
#### Что не покрывают тесты

Идентичность и производное имя проверяются обычными unit-тестами. Исходный сценарий — три одновременных объявления и правильный выбор клиента — вне платы не проверить; нужны три платы или имитатор peripheral. Зелёный набор тестов этого не подразумевает.

<a id="84-pin-attempts-across-reconnects"></a>
### 8.4 Попытки PIN между переподключениями

См. §5.6. Три ошибки закрывают сеанс, но между переподключениями счётчика нет: клиент повторяет бесконечно, оплачивая сопряжением каждые три попытки. Нужно хранение состояния по адресу.

<a id="86-the-adapter-address-does-not-hold-still-not-investigated"></a>
### 8.6 Адрес адаптера нестабилен — **не исследовано**

<a id="86-the-adapter-address-does-not-hold-still--not-investigated"></a>
Записано, чтобы не обнаруживать заново. Причины не исследованы; вопрос намеренно отложен, не находится в активной работе.

На одной плате за шестнадцать загрузок строка старта `btd` (`serving BLE ... address=`) показала два адреса:

- `50:37:CD:16:2B:EC` — два запуска `btd` за одну загрузку, 10:04 и 10:05;
- `50:37:CD:16:1B:92` — все последующие пятнадцать загрузок, начиная с 10:18.

Перепрошивки между ними не было. Выполнялись лишь BLE-подключения `duckctl` и сопряжение геймпада. Верхние четыре байта сохранились, нижние два изменились: это похоже на драйвер, генерирующий адрес под префиксом производителя и кеширующий его вместо чтения из модуля. `configd` не выключает и включает адаптер, а только включает уже выключенный. Очевидного механизма влияния сопряжения геймпада нет; его следует проверить, а не обвинять.

Последствия шире странной строки журнала:

- **Каждое сопряжение хранится в `/var/lib/bluetooth/<address>/`**. Смена адреса делает все записи недоступными: перестают работать и геймпад, и телефон. Повторное сопряжение выглядит исправлением несвязанной ошибки.
- **iOS выводит peripheral identifier из адреса устройства**. Сохранённый «мой робот» ломается вместе с ним; поэтому §8.2 привязывает избранное к *серийному номеру*.

Это уже не проблема идентичности: §8.2 больше ни для чего не использует адрес. Поэтому исследование может ждать.

Простейшие следующие шаги: `sudo ls -la --time-style=long-iso /var/lib/bluetooth/` покажет момент первого появления второго адреса, поскольку BlueZ создаёт каталог на каждый виденный адаптер. Затем `bluetoothctl show | head -3` до и после `robotctl pad pair` проверит гипотезу геймпада без перезагрузки. Если адрес берётся из файла, его можно закрепить намеренно и сохранить при перепрошивке.
