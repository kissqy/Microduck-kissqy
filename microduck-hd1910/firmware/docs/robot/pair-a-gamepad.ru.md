# Сопряжение геймпада

Выполняется один раз для каждого геймпада. После этого `padd.service` с момента загрузки использует подключённый геймпад: ничего запускать вручную не нужно, и завершение SSH-сеанса ничего не останавливает.

<a id="put-the-pad-in-pairing-mode"></a>
## Переведите геймпад в режим сопряжения

На **Xbox** нужны два нажатия; ошибаются обычно на втором:

1. Включите контроллер **коротким** нажатием кнопки Xbox. Не удерживайте её: удержание выключает контроллер.
2. Нажмите маленькую кнопку **Sync** на верхнем торце рядом с USB-C и удерживайте, пока индикатор Xbox не начнёт **быстро мигать**. Медленное мигание означает, что геймпад включён, но не в режиме сопряжения.

На **DualSense**: удерживайте Create и PS одновременно до мигания световой полосы.

На **Pro Controller** — безымянных геймпадах в стиле Switch, которые bluetoothctl показывает как `Pro Controller`, — удерживайте маленькую **Sync** на верхнем торце рядом с USB-C, пока индикаторы игроков не начнут пробегать туда и обратно. Это геймпад классического Bluetooth (BR/EDR), тогда как Xbox использует LE. Робот сопрягает их в противоположной последовательности; `pad pair` сам выбирает нужную. Если приходится работать вручную, порядок указан в [соответствующем разделе](#pairing-a-pro-controller-by-hand).

<a id="pair-it"></a>
## Выполните сопряжение

```bash
sudo robotctl pad pair
```

```
looking for a gamepad in pairing mode — on an Xbox pad, press the small Sync button on the
top edge (not the Xbox button, which switches it off)
paired  Xbox Wireless Controller 78:86:2E:BB:13:28
padd is driving from it now.
```

MAC-адрес не нужен: робот ищет геймпад в режиме сопряжения и выбирает найденный. Геймпад не только сопрягается, но и становится *доверенным*, благодаря чему сам подключается после перезагрузки, даже когда никто не вошёл в систему.

Если в режиме сопряжения находятся два геймпада, робот не угадывает, а отказывается и выводит их адреса. Указание адреса также позволяет сопрячь устройство, которое робот не распознал как геймпад:

```bash
sudo robotctl pad pair 78:86:2E:BB:13:28
```

**Перед добавлением второго геймпада забывать первый не нужно.** Уже сопряжённый геймпад находится поблизости и виден при каждом поиске, поэтому робот предпочитает тот, который в режиме сопряжения. После процедуры оба остаются сопряжёнными, а `padd` использует подключившийся. Обратная сторона: повторный запуск без нового геймпада в режиме сопряжения ждёт всё окно поиска, прежде чем сообщить об уже имеющемся. Если нужно лишь восстановить доверие, задайте `--timeout 5`.

<a id="check-it"></a>
## Проверка

```bash
robotctl pad status
```

```
pad     Xbox Wireless Controller 78:86:2E:BB:13:28  connected
padd    active — driving whatever pad connects
```

Две команды нужны потому, что ошибки независимы: подключённый геймпад с неработающим драйвером выглядит как исправный робот, который вас игнорирует.

У Pro Controller есть шестикоординатный IMU, который ядро показывает как второе устройство ввода рядом с управляющим. В `robotctl monitor` клавиша `p` открывает блок геймпада. Панель IMU появляется только при его наличии: каркасный геймпад повторяет положение настоящего; тангаж и крен определяются по гравитации, рыскание — только по гироскопу (оно дрейфует, поскольку ничто не измеряет курс); также отображается смещение гироскопа в покое. У клона это смещение нужно изучить, прежде чем изображение перестанет самопроизвольно поворачиваться. Положите геймпад на полсекунды, и появится `settled`. При закрытом мониторе поток не требует работы: `padd` читает узел IMU только при подписчике диагностического потока либо при управлении головой через IMU, описанном ниже.

Та же ориентация может управлять головой робота. В `sudo robotctl configure`, разделе *Controller-IMU head control*, включите `enabled`: Y передаёт голову под управление наклоном геймпада, пока стики продолжают вести робота; следующее Y фиксирует голову; третье Y заново центрирует по текущей ориентации геймпада и возобновляет слежение. Полный цикл — в [шпаргалке](cheatsheet.ru.md#gamepad-configd). Монитор и голова используют один фильтр, поэтому голова направляется туда же, куда нарисованный геймпад.

Важно состояние `paired but NOT trusted`: сейчас всё работает, но после перезагрузки геймпад не подключится, поскольку подтверждение повторного подключения требует агента, которого при загрузке нет. Для исправления повторите `pad pair`.

<a id="forget-one"></a>
## Забыть геймпад

```bash
sudo robotctl pad forget 78:86:2E:BB:13:28
```

Удаляется **половина сопряжения на роботе** — только её робот и может удалить. Геймпад сохраняет свою половину, поэтому повторное сопряжение требует снова включить режим сопряжения. Иначе он предъявляет ключ, которого у робота уже нет, и получает отказ.

Xbox хранит **одно** сопряжение с хостом. Незавершённая попытка может оставить у него ключ, которого у этой платы уже нет; ошибка будет выглядеть точно как неисправная плата. Если сопряжение продолжает срываться, один раз сопрягите геймпад с ноутбуком и удалите его там. Это занимает и освобождает слот сопряжения; одного перехода в режим сопряжения для этого не всегда достаточно.

<a id="when-a-pad-will-not-bond-at-all"></a>
## Геймпад вообще не создаёт сопряжение

На aic8800 геймпад не может создать **новую** пару, пока `btd` передаёт рекламные объявления. Повторно подготовьте такую плату с `--pause-btd-on-pair`:

```bash
./scripts/provision-board.sh --pause-btd-on-pair pierre@192.168.1.42
```

Это создаёт маркер `/var/lib/robot/weird-ble` и больше ничего не меняет. При наличии маркера `sudo robotctl pad pair` сам останавливает `btd`, выключает и включает адаптер, выполняет сопряжение и снова запускает `btd`, сообщая шаги. Существующая пара от этого не страдает: сопряжённый геймпад подключается и управляет при работающем полном стеке.

Некоторые экземпляры дополнительно вообще не сопрягаются при стандартном BlueZ `Privacy = off`, даже с остановленным `btd`. Им нужен `--weird-ble`, который включает паузу и устанавливает `Privacy = device`.

**Сначала попробуйте только паузу.** На плате, которой нужна лишь она, `Privacy = device` вызывает более сложный сбой, чем отсутствие флага: геймпад сопрягается, затем постоянно переподключается с `Encryption Change: PIN or Key Missing (0x06)`, так и не создавая устройство ввода. При таком симптоме уберите `--weird-ble`, оставив паузу. Таблица и команды перехода между вариантами находятся в [`install-dev.md`](install-dev.ru.md#the-three-configurations-and-how-to-tell-which-you-have).

Ручное сопряжение на такой плате требует тех же двух шагов:

```bash
sudo systemctl stop btd
```

```bash
sudo bluetoothctl power off && sudo bluetoothctl power on
```

Выполните сопряжение, затем:

```bash
sudo systemctl start btd
```

Выключение и включение адаптера обязательно. После остановки `btd` остаются его объявление и возможности ввода-вывода, назначенные контроллеру агентом сопряжения, поэтому геймпад всё ещё отказывается сопрягаться. Перезагрузка действует так же; именно так обходной путь был найден. Не заменяйте это на `systemctl restart bluetooth`: на этой плате после такой команды адаптер полностью исчезает до перезагрузки.

`--weird-ble` указан как вариант по умолчанию в [`install-dev.md`](install-dev.ru.md), поскольку он нужен примерно половине этих плат, а измеримого способа заранее отличить их нет. Но плате, которой он не нужен, оставлять его не следует: флаг требует остановки `btd` и перезапуска питания адаптера при каждом сопряжении. Поэтому та страница также объясняет проверку и отключение.

Оба механизма — обходы особенностей aic8800, а не свойства архитектуры. После смены радиомодуля они больше не нужны.

<a id="a-classic-pad-and-bluetoothds-cpu"></a>
### Классический геймпад и нагрузка bluetoothd

Pro Controller передаёт IMU в каждом пакете — около 200 пакетов в секунду, даже когда его не трогают. При стандартном BlueZ `UserspaceHID=true` каждый пакет пересылается bluetoothd через uhid; на graphite это занимало 16% одного ядра при бездействующем геймпаде. `scripts/setup-board.sh` устанавливает `UserspaceHID=false` в `/etc/bluetooth/input.conf` на каждой плате, передавая канал ядерному `hidp` и исключая bluetoothd из пути данных. После этого измерено 0.0% при том же драйвере, узлах ввода и сопряжении. Изменение действует со следующей загрузки. LE-геймпад вроде Xbox настройка не затрагивает: HID over GATT никогда не использовал `input.conf`. На ранее подготовленной плате настройка добавляется повторным запуском скрипта:

```bash
sudo sh scripts/setup-board.sh && sudo reboot
```

<a id="pairing-a-pro-controller-by-hand"></a>
## Ручное сопряжение Pro Controller

Только если недоступен `pad pair`. Порядок важен и **обратен** порядку для Xbox:

```bash
bluetoothctl pair 98:B6:E9:28:06:09
```

```bash
bluetoothctl connect 98:B6:E9:28:06:09
```

```bash
bluetoothctl trust 98:B6:E9:28:06:09
```

Если начать с `connect`, который побочно создаёт пару, возникает трудное для понимания состояние: индикатор геймпада горит постоянно, `pad status` показывает `connected`, `bluetoothctl info` — `Paired: yes` и `Connected: yes`, но **устройства ввода нет**. Поэтому `padd` остаётся на «waiting for padd to open a pad», и управления нет. Для восстановления выполните `sudo robotctl pad forget <address>`, снова включите режим сопряжения и повторите процедуру. `pad pair` никогда не создаёт это состояние: по классу BlueZ он определяет классический геймпад и сначала сопрягает, затем подключает.

<a id="when-pairing-fails-every-time"></a>
## Сопряжение срывается каждый раз

Проверьте `Privacy` в `/etc/bluetooth/main.conf`. Там должно быть `Privacy = device`. При `Privacy = off` плата может вообще не сопрягать геймпад: соединение прекращается с `le-connection-abort-by-local`, до `Paired: yes` дело не доходит.

Если же запись обмена доходит до `DHKey check failed (0x0b)`, это противоположная неисправность: на этой плате нужно попробовать `Privacy = off`. Перед изменением снимите `btmon`, поскольку встречались оба случая и решения у них разные.

```bash
sudo sh scripts/setup-board.sh
```

```bash
sudo reboot
```

`setup-board.sh` исправляет значение; оно вступает в силу после перезагрузки.

В остальных случаях обычная причина — геймпад вышел из режима сопряжения до начала обмена. Нажмите Sync снова и повторите, пока индикатор быстро мигает. Чтобы увидеть сам обмен:

```bash
sudo btmon -t > /tmp/btmon.log 2>&1 &
```

Выполните сопряжение, затем `sudo pkill btmon` и найдите `SMP: Pairing Failed` с указанной рядом причиной. Это инструмент, позволяющий отличить настройку платы от геймпада, который не слушает.

<a id="when-it-drops-while-you-are-driving"></a>
## Связь пропадает во время управления

Наблюдайте собственный поток ввода геймпада, уже доступный на плате:

```bash
robotctl monitor
```

Нажмите `p`. Откроется сырой поток evdev от геймпада, который использует `padd`: каждый отчёт с временной меткой ядра.

```
┌ pad Xbox Wireless Controller · /dev/input/event5 · 78:86:2e:bb:13:28 ─────────────┐
│ cadence  124/s while driving · last 8 ms ago · worst 84 ms · over 100 ms 0 · …    │
│ gap ms                                       ▁▁▁▁▂▁▁▁▁▃▁▁▁▁▁▁▂▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁ │
│ X     ····│██··   -8734 Y     ····│····       0 Z     ·········       0 …         │
│ held     BTN_START                                                                │
└ 4213 reports · gap ≤100 ms ───────────────────────────────── reports intact ──────┘
```

Двигайте стики, и полосы будут следовать за ними. Для диагностики нужна верхняя строка: одна полоса на отчёт, поэтому задержка выглядит как всплеск и остаётся на экране даже после восстановления. Полная высота означает 100 ms — порог, который начинает ощущать оператор; после 500 ms `robotd` обнуляет скорость.

**Ни один другой показатель робота этого не покажет.** `padd` повторяет последнее значение стика на 50 Hz, поэтому переставшее доставлять данные радио ниже по цепочке выглядит как живой водитель: `robot.state` содержит свежие намерения, аварийный таймер не срабатывает, робот продолжает идти по уже никем не подаваемой команде. Столбец `asked` в блоке выше будет выглядеть идеально, пока этот поток замер.

Неподвижный геймпад ничего не отправляет, поэтому тишина показательна только при управлении. После пяти секунд блок пишет `the sticks are still`, а не обвиняет связь, и считает такие промежутки отдельно.

Для заключения за интервал времени вместо текущей картинки скопируйте измерительный скрипт на плату из клона репозитория:

```bash
scp scripts/pad-link-test.sh microduck@<board>:/tmp/
```

Что уже происходило по журналу `padd`: геймпад не нужен, ответ сразу.

```bash
sudo sh /tmp/pad-link-test.sh --history
```

Для текущего измерения включите геймпад и запустите `padd`. **Двигайте стики все две минуты**: в покое геймпад молчит, и эта тишина неотличима от зависшего канала.

```bash
sudo sh /tmp/pad-link-test.sh
```

Считаются разрывы и промежутки между отчётами подключённого геймпада. Промежуток более 500 ms означает остановку робота: `robotd` обнуляет скорость. После каждого разрыва приводится причина ядра: `0x08` — supervision timeout, то есть дальность или помехи; `0x13` — кто-то выключил геймпад.

Положенный на стол геймпад не считается зависанием, но это время ничего не говорит о качестве связи. Поэтому отчёт указывает, какую часть интервала вы действительно управляли, и отказывается оценивать почти не наблюдавшийся канал.

Чтобы определить дальность, отходите от робота во время измерения.

<a id="is-this-board-running-the-same-stack-as-that-one"></a>
## Одинаков ли программный стек на двух платах?

Если один и тот же геймпад зависает на одном роботе, но не на его близнеце, причина обычно не в геймпаде. Платы, подготовленные с разницей в недели, могут иметь разные ядра, BlueZ, прошивки контроллеров и геймпадов. Ничего из этого не видно в `pad status`.

Скопируйте отчётный скрипт на каждую плату из клона репозитория:

```bash
scp scripts/pad-stack-report.sh microduck@<board>:/tmp/
```

```bash
sudo sh /tmp/pad-stack-report.sh
```

Он выводит весь стек и сохраняет тот же текст в `/tmp/pad-stack-<host>-<when>.log`: ядро, BlueZ, HCI-версию адаптера, модель радио и загруженную ядром при старте прошивку, обработчик HID, ключи пары, текущий транспорт и версию прошивки самого геймпада. Работает без root; для трёх требующих его пунктов пишет `unreadable`.

Для сравнения двух плат запросите только значения, которые должны совпадать:

```bash
ssh microduck@<board-a> sudo sh /tmp/pad-stack-report.sh --fingerprint > /tmp/a.fp
```

```bash
ssh microduck@<board-b> sudo sh /tmp/pad-stack-report.sh --fingerprint > /tmp/b.fp
```

```bash
diff /tmp/a.fp /tmp/b.fp
```

Пустой вывод означает одинаковый стек. Отпечаток не содержит временных меток и адресов, поэтому каждая строка `diff` — настоящее различие.

Сначала прочитайте две строки. `transport` у всех проверенных на момент записи геймпадов был `LE`; `BR/EDR` означает, что плата использует классический HID-путь ядра вместо BlueZ: другой драйвер и другая нумерация кнопок. `input` — четвёрка `Bus`/`Vendor`/`Product`/`Version`, из которой SDL и `gilrs` вычисляют GUID раскладки. Если она различается, у плат разные раскладки осей и кнопок, даже при совпадении всего остального.
