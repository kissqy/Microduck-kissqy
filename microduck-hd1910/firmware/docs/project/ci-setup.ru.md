# Настройка CI

Статус: черновик · Дата: 2026-07-28 · Ответственный: pierre

Однократная настройка конвейера выпуска. Хранение ключей описано в [`updater-design.md`](../design/updater-design.ru.md), §5.4, а модель staging → stable — в §16.3.

<a id="decision-two-keys-two-triggers-and-no-gate-on-this-plan"></a>
## Решение: два ключа, два триггера и отсутствие барьера на этом тарифе

**Решено 2026-07-29.** Push в ветки подписываются `team.dev`; выпуски по тегам и продвижения — `release-1`. Оба ключа находятся в CI.

| Триггер | Workflow | Ключ | Попадает на робот заказчика |
|---|---|---|---|
| Push в любую ветку | `dev.yml` | `team.dev` (секрет репозитория) | **Нет** — там `allow_dev_keys = false`, а имя доверенного файла должно оканчиваться на `.dev.pub` |
| Тег `daemon-staging-v*` | `release.yml` | `release-1` (секрет окружения `release`) | Только после продвижения — публикуется как предварительный выпуск |
| Продвижение вручную | `promote.yml` | `release-1` | **Да** |

В отличие от предыдущего предложения, это разделение не смешивает ключи *внутри* пути staging → stable: продвижение по-прежнему повторно подписывает манифест для тех же байтов (§16.3). Артефакт, подписанный `team.dev`, продвинуть было бы нельзя: `promote` направляет `sig_url` на существующую подпись staging-артефакта. Поэтому сборки разработки остаются сборками разработки, а не становятся кандидатами выпуска.

<a id="what-was-intended-and-why-it-is-not-there"></a>
### Что планировалось и почему этого нет

Планировалось закрыть доступ к `release-1` правилом обязательных проверяющих в окружении `release`. Создать его нельзя:

```
HTTP 422: Failed to create the environment protection rule.
Please ensure the billing plan supports the required reviewers protection rule.
```

В качестве замены проверили защиту тегов — она также недоступна:

```
403: Upgrade to GitHub Pro or make this repository public to enable this feature.
```

Обязательные проверяющие, правила веток развёртывания, защита веток и rulesets для *закрытого* репозитория требуют Team/Pro, а `pollen-robotics` использует бесплатный тариф. Окружение `release` существует без правил защиты.

<a id="the-accepted-risk-stated-plainly"></a>
### Явно принятый риск

**Любой участник с правом push может прочитать `release-1`.** Привязка к окружению `release` скрывает его от workflow, не объявляющего это окружение, но любой соавтор может написать workflow с таким объявлением. Поэтому «только для выпусков» — договорённость между уже доверяющими друг другу людьми, а не контроль доступа; файл workflow не является границей защиты.

Это принято осознанно: команда небольшая и взаимно доверяет участникам, ни один робот ещё не покинул помещение, а альтернатива — ручная подпись каждого выпуска — сегодня не даёт преимущества против ещё не существующей угрозы.

**Пересмотрите решение, когда исполнится хотя бы одно условие ниже.** Цена ошибки резко меняется, а исправить её полностью эта схема не позволяет: утечка ключа требует доставить обновление с подписью `release-2` на каждый робот; пропустивший его робот навсегда доверяет скомпрометированному ключу:

- робот находится у кого-то дома;
- кто-то с правом push не относится к людям, которым вы передали бы ключ подписи напрямую.

Тогда решение — переход организации на GitHub Team, сохраняющий это разделение и добавляющий обязательное одобрение, либо возврат подписи `release-1` на ноутбук.

<a id="the-tiering-unchanged-and-still-the-thing-that-bounds-damage"></a>
## Уровни ключей: без изменений и по-прежнему ограничивают ущерб

Независимо от решения выше, масштаб последствий компрометации ограничивает доступность каждого ключа:

| Ключ | В CI | Роль |
|---|---|---|
| `release-1` | **Сейчас нет** — см. выше | Подписывает все выпуски и продвижения |
| `release-2` | Нет | Первая замена при компрометации CI или `release-1` |
| `release-3` | Нет; в идеале никогда не хранится на машине с сетью | Последний резерв |
| `team.dev` | Планируется, только workflow разработки | Сборки веток; не затрагивает робот заказчика, поскольку там `allow_dev_keys` равен false |

> Примечание переводчика: исторический черновик содержит несогласованность. В решении от 2026-07-29 оба рабочих ключа уже находятся в CI, а таблица выше сохраняет более ранние формулировки. Перевод не утверждает текущее состояние секретов организации.

Все **открытые** ключи включаются в каждый образ робота с самого начала: робот проверяет подписи только набором, встроенным в образ. Это единственная возможность обеспечить смену ключа без физической перепрошивки.

<a id="secrets-and-variables"></a>
## Секреты и переменные

GitHub Secrets доступны **только для записи**: после установки никто, включая вас, не может прочитать их обратно. Это *копия для развёртывания*, а не хранилище. Основной экземпляр остаётся в менеджере паролей; его утрата означает потерю ключа и невозможность снова подписывать обновления для доверяющих ему роботов.

**Привязывайте их к окружению `release`, а не к репозиторию.** Секрет репозитория доступен всем заданиям workflow в репозитории; секрет окружения — только заданию, объявившему это окружение. На этом тарифе такое различие лишь скрывает ключ от несвязанного workflow, как описано выше, но это всё же лучше и ничего не стоит:

```bash
gh secret set MINISIGN_SECRET_KEY --env release < ~/.duck-keys/release-1.key
```

```bash
gh secret set MINISIGN_PASSWORD --env release
```

Вторая команда запрашивает ввод интерактивно, поэтому парольная фраза не попадает в историю оболочки или запись сессии.

**Секреты** (зашифрованы, прочитать обратно нельзя). Состояние на момент записи:

| Имя | Область | Значение | Установлено |
|---|---|---|---|
| `MINISIGN_SECRET_KEY` | Окружение `release` | Обе строки `~/.duck-keys/release-1.key` | ✅ |
| `MINISIGN_PASSWORD` | Окружение `release` | Парольная фраза `release-1` | ✅ |
| `MINISIGN_DEV_SECRET_KEY` | **Репозиторий** | `~/.duck-keys/team.dev.key` | ✅ |

`MINISIGN_DEV_SECRET_KEY` намеренно принадлежит репозиторию: им подписывается каждый push в ветку. Привязка к окружению заставила бы workflow разработки объявлять окружение для `release-1`. Отдельный секрет парольной фразы ему не нужен: ключ разработки не зашифрован для неинтерактивной подписи CI. `xtask keycheck` проверяет это, считая такое состояние правильным для ключа разработки и неправильным для ключа выпуска.

**Переменные** (открыты и доступны для чтения; открытый ключ не является секретом):

| Имя | Значение |
|---|---|
| `MINISIGN_PUBLIC_KEY` | Строка ключа из `~/.duck-keys/release-1.pub` |

Открытый ключ используется `release.yml` для проверки выпуска по тому же пути кода, что и на роботе, перед публикацией. Он намеренно хранится как *переменная*, а не секрет: секретность открытого ключа провоцирует путаницу между двумя частями пары.

**Не** добавляйте `release-2` и `release-3`. Их ценность состоит именно в отсутствии здесь.

<a id="the-release-environment"></a>
## Окружение `release`

И `release.yml`, и `promote.yml` объявляют `environment: release`. Создайте его в Settings → Environments и добавьте **required reviewers** — обязательных проверяющих.

Без этого любой, кто может отправить тег `daemon-staging-v*`, может подписать обновление для всего парка. С этим доступ к ключу требует одобрения второго человека: большая часть преимуществ локальной подписи возвращается ценой одного нажатия на выпуск.

Pull request из форков в любом случае не получают секреты, поэтому из таких PR ключ недоступен.

<a id="where-the-key-is-handled"></a>
## Где обрабатывается ключ

Ровно один шаг каждого workflow записывает ключ на диск, после чего он немедленно удаляется:

```
umask 077
printf '%s' "$MINISIGN_SECRET_KEY" > "$RUNNER_TEMP/secret.key"
cargo run -p xtask -- sign --dir dist --key "$RUNNER_TEMP/secret.key"
shred -u "$RUNNER_TEMP/secret.key" || rm -f "$RUNNER_TEMP/secret.key"
```

Ключ записывается в файл, а не передаётся аргументом, поскольку ключ в командной строке виден другим процессам runner через список процессов.

Шаг проверки `release.yml` намеренно **не требует** ключа: `xtask package` создаёт второй манифест с URL в виде одного имени файла для `LocalDir`, а `xtask sign` подписывает оба за один проход. Повторная подпись для проверки означала бы вторую обработку ключа в одном задании без пользы.

<a id="cutting-a-release"></a>
## Создание выпуска

**Точка входа — страница выпусков GitHub.** Результат зависит от того, что вы создаёте; `release.yml` определяет режим по тегу:

| Что создаётся | Режим | Действия CI |
|---|---|---|
| Предварительный выпуск, тег `daemon-staging-v0.4.0` | `staging` | Кросс-компиляция aarch64, упаковка, подпись `release-1`, проверка настоящим механизмом обновления, публикация **prerelease** |
| Выпуск, тег `daemon-v0.4.0`, staging 0.4.0 существует | `promote` | Подпись stable-манифеста для **тех же байтов артефакта**, проверенных staging; без пересборки; вывод staging-выпуска из использования |
| Выпуск, тег `daemon-v0.4.0`, staging 0.4.0 отсутствует | `stable` | Сборка 0.4.0 и немедленная публикация в stable с примечанием об отсутствии предварительной проверки на ограниченной группе |

В сводке запуска указан выбранный режим: если выпуск выглядит неправильно, это первый вопрос.

Отправка тега из терминала даёт тот же результат — объект выпуска создаётся автоматически:

```
git tag daemon-staging-v0.4.0 && git push --tags
```

Сначала увеличьте версию workspace: `xtask package` отклоняет тег, не совпадающий с `Cargo.toml`.

Два свойства, ради которых и нужно разделение:

- Обычный `update apply` пропускает prerelease, поэтому непродвинутая сборка не попадёт на робот, не запросивший её через `--staging`. Оба шага публикации повторно устанавливают флаг существующего выпуска: иначе staging, созданный кем-то без галочки prerelease, стал бы доступен всему парку, а stable с этой галочкой не получил бы никто.
- Продвижение никогда не пересобирает. Stable-выпуск становится самостоятельным: манифест, подпись, артефакт и bootstrap-бинарник. Поэтому staging можно затем удалить. Более старые stable-выпуски, например `daemon-v0.3.0`, всё ещё направляют `url` на staging, поэтому **эти staging-выпуски удалять нельзя.**

Ручное продвижение выполняет тот же процесс без предварительного создания выпуска; здесь задаётся `min_supported` (§8.1), принуждающий роботов со старой версией обновиться без ожидания клиента:

```
gh workflow run promote --field version=0.4.0
```

<a id="the-workflows"></a>
### Workflow

```
release.yml            the entry point: decides staging / promote / stable
_build-release.yml     build · package · sign · verify · publish        (called)
_promote-release.yml   copy bytes · verify sha · re-sign · retire staging (called)
promote.yml            workflow_dispatch → _promote-release.yml
dev.yml                every push: an unsigned-for-customers dev build, `team.dev` key
```

Процедура находится в двух вызываемых workflow, чтобы состав staging и stable не расходился. Проверки упаковки `xtask` читают список `--include` из `_build-release.yml` и `dev.yml`: если unit, hook или sysusers-файл не упакован, падает тест, а не робот.

Оба шага публикации создают выпуск только при его отсутствии и загружают файлы с `--clobber`, поэтому оборвавшееся задание можно повторить. Раньше задание, упавшее после создания выпуска, требовало ручного удаления выпуска и тега перед повтором.

<a id="rotating-a-key"></a>
## Смена ключа

При компрометации `release-1` или CI:

1. Замените `MINISIGN_SECRET_KEY` / `MINISIGN_PASSWORD` на значения `release-2`.
2. Опубликуйте выпуск с подписью `release-2`. Роботы уже доверяют ему — именно поэтому оба открытых ключа включены с первого образа.
3. В следующем выпуске удалите `release-1.pub` из `trusted_keys_dir`, чтобы скомпрометированный ключ больше не принимался.
4. Создайте новый третий ключ, чтобы сохранить резерв:
   `cargo xtask keygen --kind release --name release-4 --out ~/.duck-keys`

Шаг 3 намеренно следует после шага 2: отзыв старого ключа до получения нового выпуска всеми роботами оставил бы пропустивших его без пути обновления.
