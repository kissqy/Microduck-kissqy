# Развёртывание: конфигурация уровня ОС

Статус: черновик · Дата: 2026-07-28 · Ответственный: pierre

Настройки *образа робота*, а не отдельной службы. Unit находятся рядом со службами (`updater/systemd/`, `robotd/systemd/`); общие настройки робота — здесь.

| | |
|---|---|
| `updater.toml` | Конфигурация клиентского робота, устанавливается в `/etc/robot/updater.toml` |
| `trusted_keys/` | Открытые ключи выпусков — корень доверия, устанавливаются в `/etc/robot/trusted_keys/` |
| `journald.conf.d/10-robot.conf` | Сохранение журнала и ограничения размера |

Последнее теперь **измерено**, а не предположено: `/var/log` образа — zram, поэтому `Storage=persistent` создаёт каталог в памяти. Он переживает штатный reboot и теряет недавние записи при обрыве питания, которым робот обычно выключается. История обновлений в `/var/lib` — единственная устойчивая запись, как и задумано в `architecture.md`, §8.2.

> Короткая процедура запуска платы разработки: [`docs/robot/install-dev.md`](../docs/robot/install-dev.ru.md). Ниже — цепочка доверия, расположение файлов и журналов.

<a id="quickstart"></a>
## Быстрый старт

Три способа в порядке объёма набираемых команд. Остаток страницы описывает то же с обоснованиями; читайте его при несоответствии ожиданиям, а не обязательно заранее.

<a id="dev-board-repository-private-this-is-today"></a>
### Плата разработки, закрытый репозиторий — состояние на момент записи

<a id="dev-board-repository-private--this-is-today"></a>
Одна команда из клона, пошагово описанная в [`docs/robot/install-dev.md`](../docs/robot/install-dev.ru.md):

```bash
export DUCK_TOKEN=github_pat_replace_with_your_token
```

```bash
./scripts/provision-board.sh microduck@192.168.1.42
```

`--no-dev-key` — для платы только с выпусками; `--ref BRANCH` — подготовка из ветки; `--local` — отправить `provision.sh` этого клона вместо скачивания, чтобы проверить ещё не отправленную правку.

`team.dev.pub` закоммичен в [`dev-key/`](dev-key/README.ru.md), не `trusted_keys/`: его перенос *является* явным включением разработки, поэтому он не должен поставляться всем роботам. Скрипт отправляет эту копию; `--dev-key PATH` переопределяет её.

<a id="on-the-board-without-a-clone"></a>
### На плате без клона

Три команды, первая — с вашего компьютера. Именно это выше делает `provision-board.sh`:

```bash
scp deploy/dev-key/team.dev.pub microduck@192.168.1.42:/tmp/
```

```bash
export DUCK_TOKEN=github_pat_replace_with_your_token
```

```bash
curl -fsSL -H "Authorization: Bearer $DUCK_TOKEN" https://raw.githubusercontent.com/pollen-robotics/microduck/main/scripts/provision.sh -o /tmp/provision.sh && sudo DUCK_TOKEN="$DUCK_TOKEN" DUCK_DEV_KEY=/tmp/team.dev.pub sh /tmp/provision.sh
```

`provision.sh` последовательно запускает `setup-board.sh`, `migrate-network.sh`, `install.sh`, предупреждает десять секунд и перезагружает плату. SSH завершается; процесс заканчивается самостоятельно. Ключ разработки заранее копируется из `/tmp`, не переживающего reboot. Иначе плата подготовится без ошибки, но тихо *не* станет платой разработки; через недели отказ `--ref` будет похож на плохой выпуск.

Войдите снова:

```bash
robotctl health
```

Если работа продолжается, наблюдайте:

```bash
sudo tail -f /var/lib/robot/provision.log
```

Этот файл — запись ненаблюдавшейся половины; он намеренно не в journal, поскольку persistent journald настраивается drop-in внутри устанавливаемого выпуска и пока может быть только в RAM. Итог `DEV BOARD` появляется лишь при фактической установке ключа: тип платы можно проверить, не запоминать:

```bash
grep -c 'DEV BOARD' /var/lib/robot/provision.log
```

На обоих путях нет `newgrp robot` намеренно: группа `robot` создаётся до reboot, новая сессия уже входит в неё.

<a id="regular-user-repository-public"></a>
### Обычный пользователь, открытый репозиторий

Без токена и ключа разработки.

```bash
curl -fsSL https://raw.githubusercontent.com/pollen-robotics/microduck/main/scripts/provision.sh -o /tmp/provision.sh && sudo sh /tmp/provision.sh
```

```bash
robotctl health
```

Даже здесь файл скачивается, а не передаётся pipe: вторая половина работает после reboot и требует файл на диске. Pipe отклоняется, чтобы не оставить установку наполовину.

<a id="doing-it-by-hand"></a>
### Ручное выполнение

`DUCK_NO_REBOOT=1` останавливает `provision.sh` перед reboot и показывает дальнейшие команды. Так можно видеть отчёт каждого шага:

```bash
sudo DUCK_NO_REBOOT=1 DUCK_TOKEN="$DUCK_TOKEN" sh /tmp/provision.sh
```

```bash
sudo reboot
```

```bash
sudo /usr/local/sbin/robot-provision
```

Все три скрипта запускаются независимо; `provision.sh` — тонкий оркестратор без собственной логики. По одному: `setup-board.sh`, `migrate-network.sh`, reboot, оба снова, `install.sh`, затем `newgrp robot`, поскольку на этом пути группа не создана до reboot.

<a id="what-those-commands-actually-do"></a>
## Что команды действительно делают

Три скрипта разделены из-за разных задач. `setup-board.sh` — редкая подготовка ОС с device-tree overlays и ONNX Runtime, требующая reboot. `install.sh` ставит подписанный выпуск служб при каждом обновлении; объединение заставило бы заново решать загрузочную конфигурацию при каждом обновлении. `migrate-network.sh` временный: он нужен лишь из-за netplan стандартного Armbian и должен исчезнуть после образа с NetworkManager, а не поддерживаться вечно.

**NetworkManager на новой плате отсутствует**, поэтому средний шаг обязателен. Headless Armbian использует netplan + `systemd-networkd` + `wpa_supplicant`; `configd` управляет NM по D-Bus. До миграции `robotctl net status` сообщает `Unavailable`, настройка Wi-Fi по Bluetooth невозможна. Почему NM — [`../docs/design/app-path-design.md`](../docs/design/app-path-design.ru.md), §2.

`provision.sh` хранит пересекающее reboot состояние: токен, путь dev-ключа, boot id для проверки действительного reboot. Собственной логики подготовки нет намеренно: три скрипта с разным сроком жизни не должны превращаться в один с неотделимыми частями.

`provision-board.sh` — внешний слой, работающий на компьютере, не роботе. Он закрывает разрыв: правильный reboot с самостоятельным продолжением снаружи выглядит как умершая SSH-сессия и угадывание времени входа. Скрипт ждёт плату, передаёт журнал, заканчивает отчётом здоровья: одна команда с непрерывным выводом вместо трёх с пробелом.

Он действительно перезагружает, хотя вызываемые скрипты намеренно этого не делают. Противоречия нет: одноцелевые скрипты могут выполняться на занятом роботе и не знают, чему помешает reboot; оркестратор выполняется лишь при подготовке, где reboot — следующий шаг.

Цена — необслуживаемая вторая половина; опасен цикл, не просто отказ. Поэтому две защиты. Resume-unit отключает себя *до* работы: одна автоматическая попытка, а не вечное повторение. `migrate-network.sh` повторяется только когда Wi-Fi уже у NetworkManager: переход состоялся, осталось снять страховку. Если страховка вернула netplan, повторный автоматический переход снова включил бы её, упал, перезагрузился и повторился. Вместо этого журнал сообщает ситуацию, Wi-Fi не трогается. Выключенный unit остаётся на диске записью произошедшего.

Токен нужен трижды; только первые два раза относятся к подготовке: скачивание скриптов, выпуска, затем постоянно — `updaterd` читает `GITHUB_TOKEN` из drop-in systemd при последующих проверках. Передача `DUCK_TOKEN` обеспечивает обновления *после* подготовки. `provision.sh` в конце говорит, какую копию удалил, какую сохранил. Без токена закрытого репозитория установка проходит, но последующие загрузки невозможны — главная функция `updaterd` теряется.

Группа `robot` создаётся в первой фазе, поэтому выше нет `newgrp robot`. `install.sh` тоже делает это правильно, но поздно: его оболочка запущена до группы, а группы процесса фиксируются при старте. Создание до reboot включает группу в новую сессию.

**Токен: неверный URL — неверный диагноз.** `raw.githubusercontent.com` без учётных данных для закрытого пути отвечает **404**, не 401. Нет заголовка — будто опечатка. Токенов две копии: оболочки для скриптов и [службы для артефактов](#-while-the-repository-is-private-a-robot-needs-a-token), drop-in systemd, живущий дольше оболочки. Они соединяются при вызове `install.sh` из `provision.sh`: `DUCK_TOKEN` записывается в drop-in.

**`setup-board.sh`** идемпотентен, сам не перезагружает. Он исправляет труднодиагностируемое: Armbian задаёт `overlay_prefix=rk35xx`, а общие с RK3568 overlays RK3566 называются `rk3568-*.dtbo`. Неверный префикс даёт спокойную загрузку без `/dev/ttyS2`. Редактор overlays `armbian-config` падает по той же причине, поэтому файл правится напрямую.

⚠ Обновление ядра, меняющее `/boot/{Image,dtb,uInitrd}`, может отменить исправление. Если после `apt upgrade` моторы исчезли, выполните скрипт снова.

⚠ Строка `kernel console` показывает `until the reboot`, когда файл уже исправлен, но текущее ядро ещё старое: `/proc/cmdline` не меняется без reboot. Другой результат — реальная находка.

**`migrate-network.sh`** выполняется **дважды**, до и после reboot; `provision.sh` делает оба запуска. Первый включает загрузочную страховку возврата netplan, если `wlan0` не получил IPv4: плохой переход стоит reboot, не последовательного кабеля. Второй снимает её. Иначе более поздняя загрузка с просто медленным Wi-Fi откатила бы плату. SSID и ключ берутся из netplan: `/run/netplan/wpa-wlan0.conf`, если создан, иначе `access-points:` в `/etc/netplan/*.yaml`. SSH по той же сети переживает переход. Если оба источника недоступны, скрипт **ничего** не меняет и печатает команды `nmcli` для ручного профиля.

**`install.sh`** требует только `curl` и coreutils; `tar`, `zstd` встроены в `updaterd`. Идемпотентен, не перезаписывает `/etc/robot/updater.toml`. Пока репозиторий закрыт, это две команды вместо `curl … | sudo sh`: заголовок нужен загрузке, `sudo` сам не передаёт переменную, pipe не передаёт ничего из этого. Все настройки — переменные окружения, поскольку обычный запуск через pipe затрудняет флаги:

| | |
|---|---|
| `DUCK_TOKEN` | Токен закрытого репозитория для скриптов *и* артефактов |
| `DUCK_REPO` | Репозиторий форка или тестов |
| `DUCK_REF` | Ветка скриптов и доверенных ключей; закрепите тег для воспроизводимости |
| `DUCK_CONFIG_REF` | Источник `updater.toml`, по умолчанию тег устанавливаемого выпуска; `DUCK_REF` его не меняет. Поле конфигурации понимается лишь начиная со своей версии бинарника; конфигурация ветки с последним stable может запретить запуск `updaterd`. Задавать лишь для проверки изменения с понимающей его сборкой |
| `DUCK_DEV_KEY` | Путь к `team.dev.pub`, включающий плату разработки, см. ниже |
| `DUCK_FORCE_REINSTALL` | Переустановка поверх рабочего выпуска его собственным `updaterd` |

**Самоустановка.** Обновлению нужен обновлятор, поступающий в обновлении. Выход — отдельный бинарник `updaterd-bootstrap-aarch64`, поскольку на новой плате нет `zstd` для `.tar.zst`. Он запускает *обычный* механизм: проверка, распаковка, атомарное переключение, запись журнала. Хранилище точно соответствует ожидаемому resident-службой; отдельный bootstrap-путь не расходится с дальнейшими обновлениями. `on_apply` и `health` временно выключены: unit ещё внутри устанавливаемого выпуска. `updaterd install` отказывается работать при уже активном выпуске, поэтому не может тихо отключить автооткат работающего робота. `--from <dir>` устанавливает из локальных файлов — офлайн/заводской путь и проверка выпуска CI до публикации.

<a id="making-it-a-dev-board-so---ref-works"></a>
### Плата разработки для работы `--ref <branch>`

<a id="making-it-a-dev-board-so---ref--works"></a>
Те же два условия применимы к сборке ноутбука из `scripts/dev-push.sh`: тот же dev-ключ, те же отказы.

Плата дважды запрещает сборки веток: `allow_dev_keys` выключен, dev-ключом считается только доверенный файл с `.dev.pub`. Проверки независимы, нужны обе; одна без другой оставляет отказ с подписью, похожий на повреждённый выпуск. `DUCK_DEV_KEY` обеспечивает обе.

До изменений проверяются наличие файла, формат minisign public key и существующая строка `allow_dev_keys` в `updater.toml`. Ключ верхнего уровня нельзя просто дописать в конец последней `[table]`. При установке имя всегда `team.dev.pub`: вставка `.dev.` определяет тип. Иное имя доверяло бы ему как *ключу выпуска*, принимая ветки за проверенные выпуски.

`team.dev.pub` находится в [`dev-key/`](dev-key/README.ru.md) вне `trusted_keys/`; [`dev-key/README.md`](dev-key/README.ru.md) объясняет безопасность.

Итог сообщает `DEV BOARD` и две команды отмены. Никогда не включайте это на поставляемом роботе.

<a id="-while-the-repository-is-private-a-robot-needs-a-token"></a>
### ⚠ Пока репозиторий закрыт, роботу нужен токен

Артефакты закрытого репозитория недоступны без учётных данных; `releases/download/...` отвечает 404 даже с ними, поэтому механизм получает файлы через release API. `updaterd` читает `GITHUB_TOKEN` окружения — на плате это drop-in systemd, не export оболочки.

На плате разработчика допустимо, на клиентской **нет**: общий секрет парка в образе утечёт, а сменить его без перепрошивки нельзя. Именно такого отказа избегают уровни ключей подписи.

Поэтому `install.sh` пишет drop-in **только при переданном `DUCK_TOKEN`**, с режимом 600 и явным сообщением. Клиентский робот использует открытый репозиторий артефактов без токена и не попадает в этот путь. Иначе служба была бы установлена, запущена, но неспособна скачать ни одного обновления.

Хостинг артефактов поэтому ещё открыт как решение; [`../docs/design/updater-design.md`](../docs/design/updater-design.ru.md), §6.1, содержит варианты. Дешёвый — второй открытый репозиторий только с подписанными артефактами: безопасность задаёт подпись, не скрытость, исходники остаются закрыты.

> Примечание переводчика: это исторический черновик. Более поздняя [дорожная карта](../docs/project/roadmap.ru.md) фиксирует решение от 2026-08-26 открыть исходный репозиторий. Абзацы о закрытом хостинге описывают прежнюю конфигурацию.

<a id="the-trust-chain"></a>
### Цепочка доверия

1. TLS к `raw.githubusercontent.com` для `install.sh`, `updater.toml`, открытых ключей. Они не могут прийти из выпуска: до ключей нечего проверять.
2. TLS к `github.com` для bootstrap `updaterd`. **Пока не проверен.**
3. Бинарник проверяет манифест и артефакт ключами шага 1, отклоняя неподписанное ими.
4. Установщик сравнивает `sha256` bootstrap с `current/bin/updaterd` из проверенного артефакта. Совпадение подтверждает подлинность шага 2; `release.yml` утверждает одинаковые байты, поэтому расхождение — реальная находка, не особенность упаковки.

Все остальные файлы — оба unit, journald drop-in, `robot.conf` — берутся из *установленного* проверенного выпуска, не отдельно из репозитория.

Остаточное доверие — самому GitHub, откуда пришёл и скрипт. Шаг 4 сужает окно, не устраняет его. Полностью локальная установка использует `--from` с вручную доставленными файлами.

<a id="unattended-updates"></a>
### Необслуживаемые обновления

`updaterd` уже резидентен и имеет таймер `check_interval` в `updater.toml`; cron не нужен. Разрешённое таймеру определяется `auto_apply`:

| | |
|---|---|
| `off` | Никогда; доступность журналируется, обязательный выпуск — заметно |
| `mandatory` | **Поставляемое умолчание**: только выпуск с `min_supported`, запрещающим текущую версию |
| `all` | Каждый доступный выпуск |

Canary/стендовый робот, отслеживающий `staging` и устанавливающий каждого кандидата:

```bash
sudo sed -i 's/^auto_apply = .*/auto_apply = "all"/' /etc/robot/updater.toml
```

```bash
sudo sed -i 's/^tag_prefix     = .*/tag_prefix     = "daemon-staging-v"/' /etc/robot/updater.toml
```

```bash
sudo systemctl restart updaterd && journalctl -u updaterd -b | tail -20
```

Первая проверка через 60 с, затем каждые `check_interval`. `auto_apply = "all"` журналируется на `warn` при старте, позволяя ответить, почему робот перезапустился без запроса.

Не заменяйте это cron или systemd timer: `robotctl update apply` намеренно обходит known-bad, поскольку оператор мог исправить причину. Таймер унаследует обход, потеряет защиту и превратит плохой выпуск в вечный цикл скачивания, записи eMMC и отката. Подробнее `updater-design.md`, §8.1.1.

Окно обслуживания намеренно не нужно. Автоматический apply обычен: preflight до сети спрашивает `robotd`, безопасен ли перезапуск и есть ли удалённая сессия. Идущий или передающий видео робот отказывает до следующего интервала. `safeToRestart` лучше часов определяет неподходящий момент.

<a id="what-ends-up-where"></a>
### Расположение файлов

```
/etc/robot/updater.toml                 config; never touched by an update
/etc/robot/trusted_keys/release-*.pub   trust anchor
/opt/robot/daemon/releases/<version>/   the release tree
/opt/robot/daemon/current -> releases/<version>
/etc/systemd/system/*.service           every unit the release ships, copied out of it
/usr/lib/sysusers.d/robot.conf          creates the `robot` group
/var/lib/robot/updater/                 lock, update log, boot counter
/usr/local/bin/robotctl -> current/bin/robotctl
/usr/local/sbin/robot-provision         provisioning, resumed after its reboot
/var/lib/robot/provision.log            what the unattended half did
/etc/systemd/system/robot-provision.service   disabled once provisioning finished
```

Unit **копируются**, а не связаны через `current`: ссылка меняла бы содержимое под systemd при каждом обновлении, а после отката его вид зависел бы от последнего `daemon-reload`. `robotctl` *является* ссылкой: это вызываемый оператором инструмент, не кэшируемый systemd файл.

Изменяющие операции только для root: `allow_uids`/`allow_gids` намеренно пусты в `updater.toml`. Группа `robot` позволяет лишь *говорить* с `updaterd`, читать статус и журналы. При появлении `btd` его uid включается в allow-list: «может передать обновление приложения» уже, чем «входит в robot».

⚠ **После прямого `install.sh` первый `robotctl health` падает, хотя установка исправна.** Оба сокета `root:robot` 0660, установщик включает оператора в `robot`, но группы уже работающей оболочки фиксированы. В той же оболочке нужна команда:

```bash
newgrp robot
```

Нет API добавления группы работающему процессу даже у root; установщик не исправит запустившую его оболочку. Поэтому `provision.sh` создаёт группу заранее, а reboot обновляет сессию. При прямом запуске команда выводится в конце, `robotctl` называет её при ошибке вместо бесполезного `systemctl status` двух здоровых служб.

<a id="where-logs-go-and-what-survives-a-reboot"></a>
## Журналы и сохранение после перезагрузки

Все службы пишут в **stderr**, который systemd собирает в journal.

| | Где | Переживает reboot | Переживает обрыв питания | Ограничение |
|---|---|---|---|---|
| Журналы служб | journald | Только при настройке ниже | **Нет**: `/var/log` — zram | `SystemMaxUse=200M` |
| **История обновлений** | `/var/lib/robot/updater/update-log.jsonl` | **Да** | **Да** | 200 записей |

История обновлений намеренно не в journal. Она в `state_dir` механизма под `/var/lib`; каждая добавляемая запись проходит `fsync`. Перезапись — атомарный временный файл с rename и `fsync` родительского каталога (`updater/src/journal.rs`, `updater/src/fsutil.rs`). Поэтому «что установили и что случилось» сохраняется даже при непостоянном journal и читается через `robotctl update log` либо JSON lines с диска. Свойство проверено тестами, не предположено.

Для журналов служб установите drop-in из этого каталога, затем:

```bash
sudo systemctl restart systemd-journald
```

Подтвердите сохранение более одной загрузки: настоящая приёмочная проверка имеет смысл лишь *после* реального reboot:

```bash
journalctl --list-boots
```

Две и более строки означают доступность предыдущей загрузки. Одна строка или `no persistent journal was found` — журнал всё ещё только в RAM.

Чтение отдельной службы предыдущей загрузки:

```bash
journalctl -u robotd -b -1
```

<a id="the-ram-log-caveat-measured-and-decided-against-durability"></a>
### Ограничение RAM-журналов — измерено, устойчивость намеренно не выбрана

<a id="the-ram-log-caveat--measured-and-decided-against-durability"></a>
`/var/log` образа — **zram**, поэтому каталог `Storage=persistent` сам в памяти. Подтверждено на плате:

```bash
findmnt /var/log
```

Штатный `reboot` сохраняет его за счёт записи при выключении, обрыв питания теряет недавние записи. Поэтому журналы служб конструктивно best-effort; устойчивая запись — история обновлений `/var/lib` с `fsync` каждой записи, вообще не проходящая через `/var/log`.

Это намеренно, не пробел: `architecture.md`, §8.2, назначает выживающей записью журнал обновлений. Если конкретной плате нужны устойчивые журналы служб, альтернатива — одна команда с известной ценой:

```bash
sudo systemctl disable --now armbian-zram-config
```

Журналы попадут на eMMC и будут изнашивать её. Уровень `info` и ограничения размера удерживают объём небольшим — именно поэтому они выбраны. Но решение принимается на отдельной плате, не меняет умолчания всего парка.

<a id="versions-for-support"></a>
## Версии для поддержки

Вопрос — «что исполнялось?», и у робота **два ответа одновременно**. `updaterd` не может перезапустить себя посреди обновления (`updater-design.md`, §4.1); несколько секунд работающий бинарник законно отстаёт от установленного. Единственное число версии вводит в заблуждение. Более долгое отставание — неисправность, не замысел; см. `../docs/design/restart-order.md`, §7.

`robotctl version` показывает обе и отмечает различие. Намеренно работает при **остановленном** `updaterd`: сообщает это строкой, не завершает процесс, ведь именно тогда команда особенно нужна. `--json` предоставляет то же пакету поддержки.

Четыре независимых источника версии, чтобы потеря одного не стала фатальной:

1. **Строка запуска**, первая запись службы на `warn`, сохраняющаяся при `RUST_LOG=warn`: версия, ревизия, путь `exe`, pid. `exe` показывает каталог выпуска реально запущенного процесса.
2. **`robotctl version`**, по IPC.
3. **`--version`** каждого бинарника, когда ничего не работает.
4. **`version.toml`** внутри выпуска и `robotctl update list`.

`revision` встраивается из `DUCK_REVISION` при сборке: CI задаёт, ноутбук честно сообщает `rev unknown, not a CI build`. Только при компиляции, не git во время исполнения: у поставленного робота нет репозитория.
