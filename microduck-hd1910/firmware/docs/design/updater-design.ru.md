# Система обновления демонов робота — проект

<a id="robot-daemon-update-system--design"></a>
Статус: черновик · Дата: 2026-07-22 · Ответственный: pierre

<a id="1-context"></a>
## 1. Контекст

На плате класса Raspberry Pi (Raspberry Pi OS/Debian) работает демон Rust: управление моторами, кинематика, небольшая ML-модель походки, передача видео/аудио по HTTP/WebRTC. Служба Bluetooth BLE предоставляет конфигурацию и первичную настройку. Роботы поставляются пользователям без опыта разработки; обновление должно запускаться несколькими нажатиями в мобильном приложении.

Нужен безопасный способ обновления поставленного ПО на устройствах пользователей.

Порядок и этапы работы — в [`roadmap.md`](../project/roadmap.ru.md).

Разделение служб, IPC, владение состоянием, API робота и удалённый/WebRTC-доступ описаны в [`architecture.md`](architecture.ru.md). Здесь только система обновлений.

<a id="2-goals-non-goals"></a>
## 2. Цели и исключения

<a id="2-goals--non-goals"></a>
**Цели**
- *Независимо* обновлять **бинарный файл демона** и **ML-модель походки с конфигурацией**: они практически никогда не выпускаются вместе.
- Поддерживать **несколько моделей** (ходьба, прыжок, стояние…), **независимо** версионируемых и обновляемых, загруженных одновременно; каждую проверять на совместимость с демоном (§5.5).
- Запускать и отслеживать обновления из приложения.
- **Принудительно уводить с известных плохих выпусков** минимальной допустимой версией.
- Не выводить робота безвозвратно из строя: атомарная установка, автооткат, подписанные артефакты.
- Простота, без серверной системы управления парком.
- **Повторное использование на других роботах команды** с минимальной адаптацией.
- Хук после установки каждого компонента для миграций и разовых действий.

**Пока вне целей**
- OTA ОС, ядра, драйверов; отдельный путь, см. §11.
- Управление парком: поэтапная раскатка, телеметрия устройств, панели. Модель — «последняя версия всем».
- Дельта-обновления: полные артефакты достаточно малы для нашего темпа.

<a id="3-key-decisions-rationale"></a>
## 3. Основные решения и причины

<a id="3-key-decisions--rationale"></a>
| Решение | Выбор | Почему |
|---|---|---|
| Гранулярность | Уровень приложения, не образ A/B | Меняются лишь демон и модель, ОС статична; RAUC/Mender избыточны |
| Транспорт | Робот **загружает** из CDN через собственный Wi-Fi | У робота интернет; телефон только запускает и показывает прогресс; большие данные не идут через BLE |
| Хостинг | **GitHub Releases** для демона, **HF Hub** для модели | Без backend, естественные места артефактов; источник заменяем |
| Подпись | **minisign**, CI подписывает, робот проверяет | Проверенный формат, маленький crate проверки, простые ключи |
| Каналы | Один на независимо версионируемую сущность: `daemon` и по одному на модель | Разный темп; модели перезагружаются без полного перезапуска |
| Откат | Каталоги версий, атомарная замена symlink, проверка health | Просто и надёжно, без разделов диска |
| Повторное использование | Универсальный механизм из конфигурации | Каждый робот объявляет компоненты, механизм общий |

Ожидаемый темп *публичных* выпусков демона: каждые ~2–3 недели в первые месяцы, затем ~2–3 месяца. У моделей собственный ритм.

**Внутренняя** разработка быстрее: у прототипа ~8 тегов за 3 дня. Нужны быстрый внутренний поток `staging` и медленный отобранный `stable` (§16.3). Поэтому staging и автоматизированный откат — необходимые элементы, не украшения.

<a id="31-prerequisite-the-robot-needs-its-own-internet-access"></a>
### 3.1 Предварительное условие: собственный интернет робота

**Для обновления роботу нужен работающий интернет через собственный интерфейс.** Настройка Wi-Fi — условие обновления, не независимая возможность. Порядок: *сопряжение BLE → настройка Wi-Fi → обновление*. Никогда не настроенный робот не обновляется.

Связь телефона не заменяет её. Реальная устойчивая прикладная скорость BLE с интервалами и ограничениями iOS — порядка 10–30 kB/s: артефакт демона идёт десятки минут, модели — часы. Поэтому payload не передаётся по BLE (§13). Это ограничение канала, не кадрирования протокола.

Без сети работают `rollback` и `reset-to-golden` (§8.2) по уже имеющимся на диске выпускам, без манифеста, источника и передачи байтов. Они легко помещаются в BLE; `btd` обслуживает их даже при мёртвом `robotd` (§4.1). **Ненастроенный или отключённый робот восстанавливается, хотя не обновляется** — правильная сторона компромисса.

Доставка артефакта телефоном возможна как запасной путь, но требует полноценного Wi-Fi или USB, никогда BLE. См. §17.

<a id="4-architecture"></a>
## 4. Архитектура

`systemd` управляет жизненным циклом, перезапуском после сбоя, порядком и watchdog.

```
systemd
├── robotd     motor control · kinematics · gait ML · sensor loop   [RT-ish core]
├── mediad     video/audio capture · WebRTC/HTTP                     [isolated: media crash ≠ dead motors]
├── btd        BLE GATT server (bluer): wifi provisioning, naming, update trigger/progress
└── updaterd   the update engine (this document)
                    ↕ local IPC (unix socket) with robotd + btd
```

**Структурное правило:** обновляющая служба — *отдельный юнит* от обновляемой. Процесс не может чисто заменить собственный исполняемый файл; служба должна переживать отказ демона для отката.

**Следствие: `updaterd` постоянно работает и исключает себя из набора перезапуска.** `updaterd` и `btd` входят *внутрь* артефакта демона; наивный перезапуск всех убил бы исполнителя во время замены или health gate. `on_apply` перезапускает всё, **кроме** этих двух.

**Исключение во время операции не означает пропуск.** Именно такое прочтение стало ошибкой: перенос на «следующую загрузку или ручной рестарт» оставлял старые бинарные файлы навсегда. Резидентный `updaterd` отклонял новый `robotctl` с «client speaks API v4, daemon speaks v3»; отказ удалён, проблема была в старом процессе. Исправления `btd` проверяли на никогда не запускавшихся файлах. Теперь `RESTART_AFTER_REPLYING` назначает каждому transient-таймер systemd через 5 s после отправки результата. Причина исключения к этому моменту исчезает: операция окончена, ответ доставлен.

Перезагрузка платы не требуется. Блок юнитов `robotctl health` показывает, из какого выпуска процесс *фактически исполняется*, позволяя увидеть неудачный отложенный перезапуск.

Набор выводится из собственных `systemd/*.service` выпуска, не конфигурации платы. Исключения `NEVER_RESTART` заданы кодом как свойства служб, а не выбор оператора. Раньше список был в сохраняемом `install.sh` файле `/etc/robot/updater.toml`, поэтому плата, подготовленная до появления нового демона, никогда его не перезапускала, но обновление считалось успешным (`install-path-gap.md`, §4).

**Чего это не покрывает.** Сохранение `updaterd` защищает текущую операцию, но не проверяет новый `updaterd`. Если обнаружить ошибку только при следующей загрузке, операция уже завершена, наблюдателей нет, а восстановление `Engine::recover_on_start` находится **в не запускающемся процессе**. `Restart=on-failure` несколько раз падает и сдаётся, оставляя робота без способа обновиться. Это противоречит восстановлению уже сломанного робота.

Два слоя ловят разные ошибки. **Первый реализован**, второй — отдельный PR.

1. **Самопроверка нового файла до подтверждения**, затем перезапуск `updaterd` после ответа. Режим только чтения загружает конфигурацию, создаёт engine и выходит *до* восстановления. Он выявляет неверную архитектуру, библиотеку, немедленную панику и наиболее вероятное — отказ нового `updaterd` читать сохранённый пользовательский `updater.toml`. Ошибка даёт дешёвый откат без reboot. Перезапуск **отделён** от RPC `update.apply`, иначе клиент получит broken pipe вместо результата. То же относится к `btd`.

   Существующий `--check-only` для этого непригоден: сначала реально выполняет `recover_on_start`, увеличивает счётчик активных испытаний и может откатить. Это инструмент оператора, не проба; второй engine посреди установки изменил бы хранилище первого.

   Реализация: `self_test_updaterd` запускается после перезапуска поставленных юнитов, перед health gate, только при restart-варианте `on_apply`. У модели нет `updaterd`, начальная установка задаёт `on_apply=none`, поскольку ещё ничего не установлено. `Error::SelfTest` несёт последнюю stderr-строку бинарного файла, например «config error: unknown field `foo`», вместо общего «unreachable».

   Перезапуск идёт через `systemd-run --on-active=5s`. Дочерний процесс остался бы в cgroup `updaterd` и был убит при перезапуске родителя; transient-юнит независим. Блокировка обновления освобождается **до** создания процессов: fork копирует все дескрипторы, включая блокировки других engine того же процесса, что в тестах приводило к посторонним `Busy`.

2. **Защита загрузки вне `updaterd`** ловит пропущенное: через три минуты после каждой загрузки таймер проверяет старт служб, а `/bin/sh`-спасатель из установленной основы переводит `current` на golden при неуспехе. Он должен находиться вне процесса и выпуска: при неработающем `updaterd` недоступны и `recover_on_start`, и счётчик. Железо он не чинит: отсутствие питания приводов одинаково ломает `robotd` и в golden, как различие unhealthy/degraded в health gate. Механизм описывает [`boot-recovery-net.md`](boot-recovery-net.ru.md).

По той же причине логика обновления не может жить в `btd`: транспорт-клиент убил бы себя посреди операции. Он остаётся тонким каналом, а резидентный `updaterd` владеет автоматом, блокировкой одной операции, восстановлением старта и периодическими/обязательными проверками без клиента (§8.1).

`btd` пересылает check/apply в `updaterd` и возвращает прогресс телефону, никогда сам не передавая payload.

<a id="41-invariant-btd-and-updaterd-survive-a-dead-robotd"></a>
### 4.1 Инвариант: `btd` и `updaterd` переживают отказ `robotd`

**Обе службы должны запускаться, работать и оставаться полностью доступны при аварии, цикле падений или отсутствии `robotd`.** Это путь восстановления; зависимость от исправного робота сделала бы его бесполезным именно когда нужен. Главный структурный принцип защиты от необратимого отказа у пользователя.

Конкретно:
- **Нет systemd-зависимости от `robotd`.** Без `Requires=`/`After=robotd` и общей судьбы; обе службы запускаются независимо.
- **Нет обязательной IPC-зависимости.** Проверка безопасного рестарта, health и reload модели *необязательны и ограничены тайм-аутом*. Мёртвый сокет — обычный ответ, не зависание, паника или отказ телефону.
- **Семантика degraded.** При выключенном `robotd` рестарт безопасен: ничего не двигается. Gate проверяет, запускается ли новый демон и сообщает ли healthy, что и важно при восстановлении.
- **`btd` сообщает правду.** Приложение должно видеть «демон неисправен, версия X, последнее обновление неудачно» и предлагать обновление, откат, golden (§8.2). Не ходящий робот всё ещё объясняет состояние и принимает исправление.
- **Минимум зависимостей.** Последний рубеж защиты: мало библиотек, без ML runtime, медиа, GPU и камеры. Ошибка сложного кода не должна убивать восстановление.
- **Осторожное обновление этих служб.** Они входят в артефакт и тоже могут сломаться; для этого golden (§8.2) и откат счётчиком загрузок (§8). Их изменения рискованнее изменений `robotd`.

`updaterd` также не должен *требовать* `btd`: локальный `robotctl` (§15) через Unix-сокет обязан восстанавливать при неисправном BLE.

<a id="5-update-model"></a>
## 5. Модель обновлений

<a id="51-channels"></a>
### 5.1 Каналы

Два логических канала со своими манифестами и версиями:

- `daemon` — бинарные `robotd`/`mediad`/`btd` и вспомогательные файлы;
- `model` — веса походки и комплект поведения/конфигурации.

Хосты **разные**, engine выбирает заменяемый `source` компонента:
- `daemon` → **GitHub Releases**, тег `daemon-v1.4.2`, assets: артефакт, `.minisig`, манифест;
- `model` → репозиторий **HF Hub**, версии по git revision/tag, файлы `https://huggingface.co/ORG/MODEL/resolve/<rev>/<file>`. Latest — движущийся тег/ветка либо новейший тег. Модель мы также подписываем `minisign`, храним `.minisig` рядом; HF не подписывает за нас.

<a id="52-artifact"></a>
### 5.2 Артефакт

Один сжатый tar на выпуск, например `daemon-1.4.2.tar.zst`, содержащий:

```
bin/robotd  bin/mediad  bin/btd        # (daemon channel)
model/gait.onnx  config/…              # (model channel)
version.toml                           # semver, min_hw_rev, schema_version
hooks/postinstall                      # optional, executable, versioned+signed
```

<a id="53-manifest"></a>
### 5.3 Манифест

Небольшой JSON как release asset, доступный по стабильному URL (§6), подписанный minisign.

```json
{
  "channel": "daemon",
  "version": "1.4.2",
  "url": "https://github.com/ORG/REPO/releases/download/daemon-v1.4.2/daemon-1.4.2.tar.zst",
  "sha256": "…",
  "sig_url": "https://github.com/ORG/REPO/releases/download/daemon-v1.4.2/daemon-1.4.2.tar.zst.minisig",
  "min_hw_rev": 3,
  "schema_version": 2,
  "min_supported": "1.5.1",
  "changelog": "…"
}
```

`schema_version` — **контекст миграции, не условие совместимости**. Манифест всегда оценивает engine *предыдущего* выпуска; отказ при `schema_version > supported` сделал бы любое повышение схемы недоставляемым, включая содержащий поддержку новый engine. Миграцию выполняет post-install, а engine передаёт числа (§9).

`min_supported` — **нижний порог допустимой версии** (§8.1), включённый в схему с v1 даже до использования. Его нельзя задним числом добавить роботам, не умеющим искать поле.

Поля `not_valid_after` пока намеренно **нет**. Истечение манифеста защищает от замораживания обновлений, но эксплуатационная цена решения отложена в §8.4.2. Позднее добавление совместимо: отсутствие означает отсутствие срока, поэтому резервировать его, в отличие от `min_supported`, не нужно. Манифесты `model` также несут `model_api` (§5.5).

<a id="54-signing-trust"></a>
### 5.4 Подпись и доверие

<a id="54-signing--trust"></a>
- CI подписывает **артефакт** и **манифест** закрытым minisign-ключом из CI secrets; основной ключ желательно держать офлайн.
- Робот получает **набор доверенных открытых ключей** `/etc/robot/trusted_keys/`, не один. Достаточно проверки любым из них: это корень доверия без PKI.
- **Ротация:** набор с первого дня позволяет пережить потерю/компрометацию. Обновление подписывается существующим ключом, добавляет новый, позднее удаляет старый. Один встроенный потерянный ключ навсегда закрыл бы обновления.
- Можно выделить отдельный **dev-ключ**, разрешаемый флагом для локальной установки команды (§15).
- Порядок: подпись манифеста → загрузка артефакта → sha256 → подпись артефакта. **Неподписанные байты никогда не исполняются и не извлекаются в рабочий путь.**

<a id="key-custody"></a>
#### Хранение ключей

`cargo xtask keygen` отказывается писать ключи в репозиторий и создаёт секретные файлы с режимом `0600`.

| ключ | зашифрован | где закрытая часть | кто доверяет |
|---|---|---|---|
| `release-1.pub/.key` | да | менеджер паролей **и** CI secrets | все роботы |
| `release-2.pub/.key` | да, **другой пароль** | только менеджер паролей, **никогда CI** | все роботы |
| `release-3.pub/.key` | да, **другой пароль** | офлайн, желательно никогда не на сетевой машине | все роботы |
| `team.dev.pub/.key` | нет | хранилище команды и CI | только платы разработки |

Три легко нарушаемых условия:

1. **Резерв должен входить в первый образ.** Проверка использует встроенный набор, новый ключ нельзя доставить после потери единственного: придётся вручную перепрошить всех.
2. **Резерв отличается и паролем, и доступностью.** Он нужен при компрометации первого; `release.key` неизбежно находится в CI, а `release-2.key` там быть не должно. Общий пароль сводит их к одному.
3. **Пароли генерируются, не придумываются.** Их не вводят вручную, они живут в менеджере/секретах, поэтому запоминаемость бесполезна. scrypt minisign (32 MiB, opslimit 2²⁰) лишь умеренно замедляет офлайн-взлом утёкшего файла. Нужно ≥128 бит, например `openssl rand -base64 24`.

Выпуски подписываются **в CI**, не локально. Компенсирующее одобрение описано в [`ci-setup.md`](../project/ci-setup.ru.md).

Dev-ключ намеренно без шифрования: CI неинтерактивен, а пароль рядом с ключом мало помогает. Реальная защита структурная: ключ отсутствует у клиентских роботов и ограничен `allow_dev_keys = false`.

<a id="55-models-one-component-each"></a>
### 5.5 Модели: отдельный компонент каждой

Есть walk, jump, stand, ground-pick — **независимые версии**, все загружены одновременно, не выбор одной из многих.

**Политики управления пошли другим путём; здесь общее правило, не их реализация.** Они обучаются семейством, а слот→файл зависит от режима, поэтому поставляются одним `policies`; прочее решают переопределения слотов. См. §9 [`policy-channel-design.md`](policy-channel-design.ru.md). Общая идея сохраняется: компонент — сущность со своей линией версий, и их может быть сколько нужно.

Каждая модель имеет запись в `updater.toml`, специальное хранилище не требуется:

```toml
[component.model-walk]
install_dir = "/opt/robot/model/walk"
source      = { type = "hf_hub", repo = "ORG/gait-walk", revision = "main" }
on_apply    = { action = "reload", unit = "robotd", signal = "SIGHUP" }

[component.model-jump]
install_dir = "/opt/robot/model/jump"
source      = { type = "hf_hub", repo = "ORG/gait-jump", revision = "main" }
on_apply    = { action = "reload", unit = "robotd", signal = "SIGHUP" }
```

Каждая независимо получает цель отката, golden, закрепление, пробный запуск со счётчиком и историю плохих версий. `robotctl update apply model-walk` меняет только эту модель; `robotctl update select model-walk 1.1.0` выбирает любую установленную без загрузки.

Модели используют `reload` (SIGHUP → повторный `mmap` весов), не `restart`, чтобы не прерывать моторное управление. Это естественно задаётся `on_apply` компонента и объясняет разделение моделей и демона.

**«Библиотечная раскладка» была опробована и удалена.** `Layout::Library` с `library/<ver>/` и `active` должна была хранить несколько именованных комплектов с выбором одного, но меняла лишь два имени каталогов и имела те же возможности, только *выглядела* новой функцией. Кроме того, модели активны одновременно, а не «много установлено, одна активна».

Если одному слоту понадобятся альтернативы, например две walk, это настоящий ключ `(name, version)` и реальное изменение (§17). Сейчас поддержки не заявляется.

**Лёгкая совместимость.** Демон сообщает **версию API модели** `model_api`, например `1`, описывающую контракт датчиков/исполнительных выходов. Манифест модели задаёт требуемую. Загрузка разрешена при `model.model_api <= daemon.model_api`.

Версия повышается при новом входе датчика или выходе:
- модель API `2` отклоняется демоном `1`, приложение предлагает сначала обновить демон;
- старые модели работают с новыми демонами, обновление не ломает их.

Недоступный `robotd` означает *неизвестную*, не несовместимую версию: повод ждать для модели, но не демона. См. замечание `Compatibility` в §5.4.

<a id="56-hardware-single-target"></a>
### 5.6 Оборудование: одна цель

**Сейчас Radxa Zero 3** (RK3566, Cortex-A55, `aarch64`), **Armbian 26.2.x**, userspace **Debian 13 Trixie**, BSP-ядро Rockchip 6.1.115. Предварительный выбор ближайшей доступной платы, но именно на него рассчитаны сборка и тесты.

`scripts/board-test.sh` кросс-компилирует через `cargo-zigbuild`; `zig cc` даёт sysroot и C-компилятор для `zstd`. Затем файлы запускаются на настоящем ARM64 Linux в контейнерах.

Порог glibc закреплён на **2.31**, фактически получается 2.30, а не Trixie 2.41. Тесты идут **только на Trixie**, поставляемом userspace. Другие варианты Armbian не проверяются ради ненужных обещаний; `BOARD_IMAGES=` позволяет разовую проверку.

Закрепление защищает не от альтернативных ОС, а от *хоста сборки*. Без него glibc машины разработчика или CI может быть новее платы: компоновка успешна, загрузка на роботе нет, вывод сборки причину не объясняет. 2.31 просто достаточно ниже цели без издержек.

Ядро не ограничивает: `flock`, `SO_PEERCRED`, `statvfs` намного старше 6.1.

Контейнер не проверит настоящий `systemctl restart` (`on_apply` ещё не запускался с systemd), запись и тайминги eMMC, `statvfs` реальной ФС и пригодность health-тайм-аутов роботу, встающему десятки секунд. Это задача оборудования.

**v1 рассчитана на одну точно определённую конфигурацию.** Нет матрицы плат/вариантов/IMU/камер, профилей устройств и выбора артефакта. Разнообразие прототипа — след исследования, не требование будущего.

Оставлены только:
- `min_hw_rev` манифеста (§5.3) — одно число для отказа будущей несовместимой платы, без матрицы;
- **стабильный ID устройства** для журнала (§8.3) и будущей отправки данных: серийный SoC `/proc/device-tree/serial-number`, переживающий прошивку без подготовки.

Вторая аппаратная цель потребует ограничений манифеста и шага сопоставления; не раньше, чтобы не создавать спекулятивную сложность.

<a id="57-robot-specific-state-must-survive-updates"></a>
### 5.7 Индивидуальное состояние переживает обновления

Некоторые файлы принадлежат **этому** роботу, обновление и откат не должны уничтожать их. Три класса:

| класс | примеры | жизненный цикл |
|---|---|---|
| **Поставляемое**, заменяемое | бинарные файлы, политики, стандартные настройки, статические юниты | `releases/<ver>/`, атомарная замена |
| **Индивидуальное**, неприкосновенное | калибровка, созданные для устройства ресурсы, выученное состояние: карты, характер, привычки | вне выпусков; **сохраняется при обновлении и откате** |
| **Пользовательские предпочтения**, сохраняемые с миграцией | имя, Wi-Fi, активная модель, настройки приложения | собственный файл; миграция хуками при `schema_version` (§9) |

Правила:
1. Каталоги выпусков **расходные**. Сохраняемое лежит в `/etc/robot/` или `/var/lib/robot/`. Откат не теряет данные и не требует перекалибровки.
2. **Рабочая конфигурация — в файле, не systemd-юните.** Юниты статичны и читают неперезаписываемые настройки. Прототип встраивает CLI-флаги в генерируемый юнит, из-за чего переустановка молча сбрасывает параметры.

Следствие: индивидуальные ресурсы создаются со стабильным seed и лишь при реальной необходимости, не при каждом обновлении.

<a id="6-hosting-on-github-releases"></a>
## 6. Размещение в GitHub Releases

- Артефакт, `.minisig`, `manifest.json` — assets каждого выпуска.
- Latest определяется одним из способов:
  - **Стабильный redirect** `…/releases/latest/download/<asset>`: latest относится ко всему репозиторию, поэтому чисто работает при **одном канале на репозиторий**.
  - **GitHub API** ищет новейший тег префикса `daemon-v*`; подходит общему репозиторию и предпочтителен при обоих каналах в нём.
- CI может использовать `cargo-dist` для сборки и публикации подписанных артефактов; манифесты добавляются assets.

<a id="61-a-private-repository-cannot-serve-the-fleet-so-this-one-does-not-stay-private"></a>
### 6.1 Закрытый репозиторий не обслужит парк — поэтому этот станет публичным

<a id="61-a-private-repository-cannot-serve-the-fleet--so-this-one-does-not-stay-private"></a>
**Решено 2026-08-26: открыть `pollen-robotics/microduck`.** Пока он закрыт, робот пользователя ничего не скачает. Неочевидная причина: URL `releases/download/<tag>/<asset>` закрытого репозитория отвечает **404 с токеном и без**. Проверено напрямую:

| URL | закрытый репозиторий |
|---|---|
| `https://github.com/<repo>/releases/download/<tag>/<asset>` | 404 независимо от авторизации |
| `https://api.github.com/repos/<repo>/releases/assets/<id>` + `Accept: application/octet-stream` | 200 с токеном |

Engine разрешает assets через API, что работает на **плате разработчика** с `GITHUB_TOKEN` и установкой ветки `--ref`, а также публично. У клиентского робота токена нет и быть не должно: общий секрет образа утечёт и не сменится без перепрошивки, как проблема, ради которой разделены ключи подписи.

Если исходники понадобится снова закрыть, остаются варианты:

| вариант | без backend | замечание |
|---|---|---|
| **Публичный репозиторий только артефактов** | да | Безопасность даёт подпись, не сокрытие; раскрываются лишь метаданные сборки, исходники закрыты. Запасной путь |
| Object store/CDN с обычным HTTP-source | в основном | Ещё один оплачиваемый и обслуживаемый ресурс; trait источника уже позволяет |
| Read-only токен в образе | да | отвергнут: несменяемый секрет парка |

**Публичность не требует изменения кода.** API-путь корректен для обоих типов, ради чего и выбран.

**Меняется бюджет запросов.** Без токена GitHub допускает 60 API-запросов в час *на IP*. Домашний робот делит анонимный пул со всеми за адресом. При `check_interval = "6h"` и нескольких вызовах одна утка далеко от лимита, двадцать в одной сети при совместном обновлении могут упереться. Корректность не страдает: `http.rs` понимает 403/429 как «повторить позже» и объясняет. После открытия стоит получать байты через `browser_download_url`: `objects.githubusercontent.com` не расходует API-пул; API оставить закрытым репозиториям и dev-платам. Это нужно до комнаты уток, не до первой поставки.

<a id="7-updaterd-state-machine"></a>
## 7. Автомат состояний `updaterd`

```
receive trigger (from btd)  ── check | apply(version)
        │
        ▼
PREFLIGHT (§7.2):  single-flight lock · clock/NTP sane · robot stopped · disk space free
        │  (any fail → report + exit, no changes)
        ▼
fetch manifest ──► verify manifest signature ──► compare version, check min_hw_rev / model_api / pin / downgrade
        │                                                    │ (nothing to do / incompatible)
        ▼                                                    └─► report + exit
download artifact ──► verify sha256 ──► verify artifact signature
        │
        ▼
extract to releases/<ver>.tmp/  ──► orphaned-unit check (§7.3) ──► [pre_install hook]
        │                                    │ (an installed unit execs a binary this release lacks)
        │                                    └─► report + exit, nothing swapped
        ▼
atomic symlink swap:  current → releases/<ver>        (rename(2), same fs)
        │
        ▼
[post_install hook]  ──► apply: restart (daemon) | reload+SIGHUP (model)
        │
        ▼
HEALTH GATE (poll robotd over unix socket, timeout per component)
        │
   ┌────┴─────────────────────────┐
 healthy                        not healthy / hook failed / timeout
   │                                │
 prune old (keep_previous)      ROLLBACK: swap symlink back, re-apply, mark failed
   │                                │
 report success                 report failure
```

Ненулевой выход хука, провал health или тайм-аут обрабатываются одинаково: **прервать и откатить**.

<a id="71-on-disk-layout"></a>
### 7.1 Структура на диске

```
/opt/robot/daemon/
├── releases/1.4.1/     ← previous (kept for rollback)
├── releases/1.4.2/     ← new
├── current → releases/1.4.2     ← systemd units point at current/
└── golden  → releases/1.4.1     ← never pruned; what the rescue reads
```

Атомарность — один `rename(2)` символической ссылки в той же ФС. Частично записанное состояние никогда не становится активным.

`Engine::refresh_golden_links` при каждом старте записывает `golden` из `ComponentConfig::golden`. Внешнему восстановлению не нужен парсер; см. [`boot-recovery-net.md`](boot-recovery-net.ru.md).

<a id="72-preflight-preconditions"></a>
### 7.2 Предварительные условия

Проверяются до загрузки и изменений; отказ не имеет побочных эффектов:

- **Блокировка одной операции.** `updaterd` держит lock-файл/сокет, предотвращая столкновение двух запросов или повтора. Вторая операция получает busy.
- **Независимость от телефона.** Робот сам загружает и завершает работу при потере BLE. Статус сохраняется и повторяется после подключения; телефон не обязан оставаться.
- **Корректные часы.** У Pi/eMMC нет RTC с батарейкой; неверное время ломает HTTPS-проверку сертификата. Требуется NTP либо проверка разумности часов с ограниченными повторами. minisign от времени не зависит.
- **Робот остановлен.** Приложение предлагает обновление только припаркованному роботу с безопасными моторами. `updaterd` всё равно спрашивает `robotd`, безопасен ли рестарт, и отказывает при движении.
- **Нет удалённого сеанса.** Перезапуск `robotd`/`mediad` во время телеприсутствия неожиданен: отказ либо предупреждение с явным подтверждением. См. §5 [`architecture.md`](architecture.ru.md).
- **Место на диске.** eMMC конечна; износ менее важен, чем SD, но место ограничено. До старта проверяется объём загрузки, извлечения и `keep_previous`.

<a id="73-would-this-release-orphan-an-installed-unit"></a>
### 7.3 Оставит ли выпуск установленный юнит без исполняемого файла?

`hooks/postinstall` ставит юниты выпуска и оставляет их после отката (§9). Для отката это нормально: следующее успешное обновление поставит свои. Но **понижение ниже версии, добавившей демон**, оставляет юнит с `ExecStart`, указывающим отсутствующий файл. systemd выдаёт `203/EXEC`; демон входит в выведенный набор перезапуска, его отказ проваливает обновление и вызывает возврат. Это наблюдалось при выборе stable `0.2.0`, выпущенной до `configd`.

Кандидат без бинарного файла установленного юнита поэтому отклоняется `updater/src/orphan.rs`, `Error::WouldOrphanUnit`. Читаются `/etc/systemd/system/*.service`, отбираются юниты с `Exec*=` внутри `current` компонента. Именно живой каталог переживает породивший юнит выпуск; фильтр исключает чужие юниты. Неразбираемый файл не даёт находки: отказ только из-за непонимания парсером был бы хуже.

Три решения о расположении проверки:

- **Не preflight (§7.2)**: обе его проверки выполняются до загрузки, когда списка файлов кандидата ещё нет. Здесь проверка после извлечения, до swap: staging расходный, счётчик не включён, `current` прежний, побочных эффектов нет. Цена знания — загрузка.
- **До выхода dry run**: он и отвечает, сработает ли понижение.
- **Без исключений по цели**, в отличие от `WouldDowngrade` только для `Latest`. Та защита от устаревшего зеркала; эта — от неработающего юнита независимо от имени цели. Случай найден через `Ref`.

При rollback, golden и `select` проверки нет: это намеренное движение назад для спасения, где не должно быть препятствий ([`architecture.md`](architecture.ru.md), §1.1).

Отказ называет юнит, файл и решение — удалить юнит:

```
systemctl disable --now configd.service && rm /etc/systemd/system/configd.service
```

Флага `--force` намеренно нет. Ниже версии появления демона он и не должен работать; удаление делает состояние правильным, а не игнорирует проверку. Следующее содержащее юнит обновление восстановит его.

<a id="8-health-gate-rollback"></a>
## 8. Проверка работоспособности и откат

<a id="8-health-gate--rollback"></a>
- После установки новый `robotd` должен подтвердить **healthy** в тайм-аут компонента: подтверждения моторов, загрузка модели, запуск медиа.
- Дополнительная защита от жёсткого зависания:
  - `WatchdogSec` systemd у `robotd` запускает восстановление;
  - **счётчик загрузок**, проверяемый `updaterd`: если обновление не достигло healthy за 2 загрузки, спросить робота и решить. Покрывает и нездоровый старт, и отсутствие старта.

    **Бюджет определяет момент проверки, робот — необходимость отката.** Исчерпание означает, что apply не подтвердил trial. Частая причина — прерванный до gate apply, например из-за рестарта `updaterd` собственным `hooks/postinstall`. Поэтому тот же трёхсторонний ответ: *healthy* подтверждает, *degraded* подтверждает, остальное откатывает.

    Degraded подтверждается по причине из §4: без питания приводов golden не лучше. Откат скрыл бы аппаратную проблему программным изменением, откатывал бы последующие выпуски и молча заменял код под руками человека. На реальной плате установленная ветка с сопряжённым геймпадом через две загрузки превратилась в stable, и дальнейшие команды шли к никем не выбранному коду.

    Откат остаётся для unhealthy, недоступного `robotd` или неразбираемого ответа.

    **Проверка повторяется в течение `health.timeout` компонента**, не одним вопросом. Между открытием сокета и первым тактом `robotd` сообщает «control loop has not completed a cycle yet»; порядок запуска `robotd.service` и `updaterd.service` не задан. Однократная проверка часто попадает туда, принимая задержку за плохой выпуск. Недоступный сокет так же неотличим от ещё не созданного без ожидания. Цена платится на откатывающей загрузке: восстановление идёт до публикации сокета (§4 `restart-order.md`), поэтому не отвечающий `robotd` задерживает `/run/updaterd.sock` на весь тайм-аут, 30s в поставляемой конфигурации, вместо двух секунд одиночного вопроса.
- `keep_previous`, по умолчанию 1, ограничивает каталоги, всегда сохраняя заведомо рабочую цель.

<a id="81-minimum-version-floor-kill-switch"></a>
### 8.1 Минимальная версия и аварийное отключение

<a id="81-minimum-version-floor--kill-switch"></a>
**Реализовано**, включая необходимую часть: `check_interval` заставляет резидентный `updaterd` опрашивать источники, `auto_apply` определяет установку **без клиента**. Проход полностью пропускается во время другого обновления; первая проверка после загрузки задержана, поскольку сети часто ещё нет и парк не должен приходить одновременно.

Отсутствие `check_interval` выключает опрос и действие порога: робот без ручной проверки никогда о нём не узнает. `updaterd` предупреждает об этом при старте, отдельно — о `auto_apply` без запускающего таймера.

<a id="811-autoapply-unattended-update-policy"></a>
### 8.1.1 `auto_apply` — политика обновления без оператора

<a id="811-autoapply--unattended-update-policy"></a>
| | |
|---|---|
| `off` | никогда; доступность журналируется, обязательность подчёркивается |
| `mandatory` | **по умолчанию**: только выпуск, обязательный по порогу; обычный ждёт клиента |
| `all` | каждый доступный выпуск |

Одна упорядоченная настройка вместо флага на срочность не позволяет выразить «автоматически обычные, но не обязательные», исключив именно спасающие парк версии.

`mandatory` стандартен, чтобы парк не застрял на отозванной версии. Обычные ждут, потому что *момент перезапуска выбирает владелец* — ради этого нужен поток обновления через приложение.

`all` предназначен для canary и стендов, реализует Tier 2 §16.2: лабораторные роботы следуют staging и ставят кандидатов. У пользователей он отнял бы выбор момента.

Автоматический apply — **обычный** apply с тем же preflight и health gate. Идущий робот или активный удалённый сеанс отказывают до следующего интервала; не стартовавший выпуск откатывается. Окно обслуживания не нужно: `safeToRestart` лучше часов определяет неподходящий момент и проверяется *до* сети, поэтому пропуск занятого робота бесплатен.

**Это принадлежит демону, не cron.** Таймер, вызывающий `robotctl update apply`, не эквивалентен: явные установки обходят защиту known-bad, ведь оператор мог исправить причину. Внешний таймер унаследовал бы обход, восстановив бесконечный цикл ниже.

**Автоматический путь отклоняет версию, с которой этот робот уже откатился**, даже обязательную. Иначе: проверка → apply → провал gate → откат → интервал → повтор. Каждый круг снова качает, пишет eMMC, перезапускает `robotd`, расходует батарею и износ без наблюдающего клиента; сходимости нет.

`known_bad` выводится из *последнего* исхода версии в журнале и самоочищается после успеха. Только автоматический путь: явный `robotctl update apply` разрешает повтор после возможного исправления причины. Срабатывание пишется уровнем error: ниже обязательного порога нужен исправленный выпуск, это должно быть заметно.

Тест считает попытки в журнале, не активную версию: после каждого круга ссылка снова указывает на хорошую, и состояние выглядело бы правильным даже при цикле.

`min_supported` принудительно выводит с плохого выпуска даже при модели latest-for-all:

- Если при проверке/старте текущая версия `< min_supported`, обновление **обязательно** и применяется без нажатия; работа на плохой версии может запрещаться.
- Более прямой **kill switch**, подписанное «версия X отозвана», — усиление того же механизма. Подпись не позволяет подделку, но подтверждает **наше**, не **актуальное**; повтор старого настоящего манифеста остаётся возможен (§8.4).
- Поле нужно в схеме сейчас (§5.3), позднее внедрить задним числом нельзя.
- Порог действует только после успешного получения содержащего его манифеста. Это *исправление*, не защита: отрезанный от обновлений робот о нём не узнает.

<a id="82-golden-release-recovery"></a>
### 8.2 Golden и восстановление

<a id="82-golden-release--recovery"></a>
- Сохраняется известный рабочий **golden**, который **никогда не удаляется**, отдельно от `keep_previous`.
- Если текущий и предыдущий не становятся healthy, перейти к golden, затем при неуспехе в минимальный **режим восстановления** с сетью и повторной загрузкой. Робот должен восстанавливаться удалённо без возврата в сервис или выезда специалиста.

<a id="83-on-device-update-log-and-the-run-transcript"></a>
### 8.3 Журнал обновлений устройства и протокол выполнения

Последние N попыток сохраняются на диск: время, канал, from→to, исход, ошибка. Доступны через BLE/HTTP — первое, что нужно поддержке при «обновление не удалось».

Журнал говорит, *что* попытка была и чем закончилась, но не **что делала**. У подробностей тоже должно быть одно достоверное место.

**Почему не системный журнал.** `journalctl -f` хорош для наблюдения без дополнительного механизма, но не хранения. `/var/log` платы находится на zram: `Storage=persistent` переживает корректный reboot, не потерю питания, а именно такие обновления особенно нужны для диагностики. Это та же причина, что вынесла основной журнал наружу.

Хуже: фазы вообще были только в уведомлениях `update.progress`. Описание автомата существовало лишь пока клиент держал сокет; ненаблюдаемый `robotctl update apply` оставлял запись без середины.

**Содержание запуска.** Один `runs/<id>.jsonl` в `state_dir`, `fsync` каждой строки, вне любого `install_dir`: swap/откат не уничтожают собственную историю (§5.7). Записываются:

- начало: цель в формулировке клиента, источник, активное состояние, инициатор из `SO_PEERCRED`;
- прошедший подпись манифест: версия, хеш, размер, URL, **какой** доверенный ключ принят, исходная ревизия;
- каждая граница фазы с подробностью и длительностью;
- точный вывод хуков и код выхода при успехе и ошибке;
- каждый перезапущенный, перечитанный или отложенный юнит и ответ systemd;
- вердикт gate, определяющий подтверждение или откат;
- завершение.

Основная запись содержит номер запуска: `robotctl update log` — индекс, `robotctl update show` — подробности, как `git log`/`git show`.

**Запись никогда не проваливает обновление.** Всё best effort, ошибки сообщаются в systemd-журнал. Успешная установка с потерянным дневником лучше отменённой ради дневника.

**Завершение в другом процессе.** Обновление демона перезапускает сам `updaterd`, поэтому протокол может оборваться посреди работы, а вердикт прийти спустя минуты и перезагрузку через trial-счётчик. Откат открывает **собственный запуск**, не дописывает умерший процесс. Отсутствие `ended` означает внешний вердикт; `show` объясняет это, следующий запуск содержит результат. Shell-восстановление golden до старта `updaterd` оставляет след, по которому реконструируется короткий, помеченный косвенным протокол.

**Ограничения.** 20 запусков, 4000 событий и 2 MiB на запуск, 64 KiB на событие. После лимита запись прекращается с числом пропусков, но завершение пишется всегда, чтобы усечённый хвост не выглядел остановкой процесса. `hooks::MAX_OUTPUT` ограничивает крупнейший источник 8 KiB на хук; обычный запуск — несколько килобайт.

**Системный журнал добавляет клиент, не демон.** `robotctl update show` вызывает `journalctl --utc` за окно запуска и только его затронутые юниты. Привилегию чтения журнала `updaterd` не должен раздавать через намеренно открытый для чтения сокет. Журнал покрывает *остальные* службы, которых протокол не видит. Оператор без доступа получает протокол и команду для остального.

<a id="84-what-signatures-do-and-dont-buy-downgrade-and-freeze"></a>
### 8.4 Что дают подписи: понижение и замораживание

Подпись minisign доказывает **наше происхождение и неизменность**, не дату и актуальность. Две стандартные атаки сохраняются при корректной подписи:

| | суть | состояние |
|---|---|---|
| **Downgrade/rollback** | старый подлинный манифест возвращает к отозванной версии | **исправлено** |
| **Freeze** | текущий манифест выдаётся вечно, скрывая исправление | **открыто**, §8.4.2 |

Достаточно контролировать получаемое: устаревший CDN/зеркало, кеш-прокси, DNS-перехват, враждебная LAN. Ключ красть не нужно.

<a id="841-downgrade-closed"></a>
#### 8.4.1 Понижение — закрыто

<a id="841-downgrade--closed"></a>
`updaterd` запрещает более старого кандидата при цели «последняя»:

- `Target::Latest` → `WOULD_DOWNGRADE`; check показывает несовместимость, не доступное обновление;
- `Target::Exact` → **разрешено** как намеренный возврат оператора, не навязанный зеркалом;
- rollback/golden намеренно возвращаются к установленным версиям и вообще не читают манифест.

Асимметрия блокирует действия *атакующего*, сохраняя выбор *оператора*.

<a id="842-freeze-open-needs-a-decision"></a>
#### 8.4.2 Замораживание — открытый вопрос

<a id="842-freeze--open-needs-a-decision"></a>
Сейчас «обновления нет» неотличимо от «его скрывают». Реальный ущерб — бесконечное удержание уязвимой текущей версии без нарушения целостности.

Варианты от простого:

1. **Срок подписанного манифеста.** `not_valid_after` задаёт время, после которого приложение сообщает устаревшие метаданные и манифест отклоняется. Цена: CI должен регулярно переподписывать stable даже без выпуска, иначе предупреждают все роботы. Также нужны часы, которым проверка §7.2 не доверяет безусловно.
2. **Монотонный счётчик манифеста.** `sequence` только растёт; робот запоминает наибольшее значение и отвергает меньшие. Надёжно обнаруживает *откат* метаданных независимо от часов, но **не** замораживание: повторно выданный текущий манифест имеет ожидаемый номер.
3. **Сообщать об устаревании, не запрещая работу.** Запоминать «последнее успешное получение манифеста» и показывать в `status`/приложении: «последняя проверка 47 дней назад». Криптографически ничего не обнаруживает, но делает замороженного робота *заметным* владельцу и поддержке. Нет нагрузки на публикацию и зависимости от часов.
4. **Связь с сервером** (§17). Если робот отправляет отчёты, *мы* видим, кто перестал проверять обновления. Это единственный вариант обнаружения замораживания централизованно, а не на каждом роботе. Нужен сервер.

**Рекомендация: (3) сейчас, (1) — когда появится регулярный выпуск релизов.** Сообщать об устаревании почти ничего не стоит; механизм не создаёт собственных отказов и делает скрытую атаку видимой. Срок действия — настоящая защита, но её эксплуатационная цена — график переподписания, пропуск которого вызывает предупреждения у всего парка, — не оправдана, пока публикация не станет обычной процедурой. (2) дёшево, но решает задачу, уже закрытую на уровне версий в §8.4.1.

**(3) реализован.** `update.status` содержит `last_checked` для каждого компонента, а `robotctl health` сообщает, когда источник обновлений отвечал последний раз, и предупреждает после недели молчания. Учитывается только latest от источника, подписанный и относящийся к нужному каналу; ошибка получения, неподтверждённая подпись и каталог `--from` оставляют запись прежней. Как и сказано в варианте, это делает заметным робота, не достигающего источника, но не того, которому выдают старый подписанный манифест: для этого по-прежнему нужен (1).

**Источник, который никогда не отвечал, — повод для предупреждения, а не для молчания.** У платы, заблокированной с момента первоначальной настройки, нет записи; то же самое присылает `updaterd` старше `API_LAST_CHECKED`. `robotctl health` различает случаи по версии API в уже полученном `hello` и предупреждает в первом: робот, ни разу не достигший источника, — худший случай, ради которого создан отчёт; трактовка «нет новостей» дала бы такой же вывод, как у здорового робота.

**Каждая проверка тоже записывается — с ответом или без, с причиной ошибки.** Отсутствие записи всё ещё означало два состояния: неудачные проверки и `updaterd`, ещё не выполнивший первую, — любая плата в первую минуту после старта, включая запуск сразу после обновления, добавившего запись; тогда предупреждение ошибочно говорило, что источник никогда не отвечал. `check-attempts.json` хранит последнюю проверку каждого компонента, а `update.status` передаёт её как `last_check_attempt` (`API_CHECK_ATTEMPT`). Отсутствие попытки — строка отчёта, не предупреждение; неудачная попытка — предупреждение, причём с ошибкой, а не отсылкой к журналу. Попытка записывается при любых часах, в отличие от ответа: именно плата с несинхронизированными часами получает ошибки TLS, и отбрасывание её попыток выглядело бы как отсутствие проверок.

`robotctl update check` выполняет проверку немедленно, а `robotctl health --check` проверяет каждый компонент перед отчётом. Это флаг, а не поведение по умолчанию: баннер входа запускает `health`, и иначе каждый вход по ssh ждал бы сеть.

**Зависимость от часов всё же есть**, вопреки приведённому выше описанию варианта: записанное время имеет смысл только относительно часов читающей стороны. Оба направления расхождения обрабатываются явно: время ниже минимального порога из §7.2 вообще не записывается — иначе плата без RTC с источником `local_dir`, отвечающим без TLS, после появления NTP сообщила бы о пятидесяти годах молчания. Время *впереди* часов читающей стороны показывается как неизвестное с предупреждением, а не округляется до «только что»: иначе плата, часы которой после проверки перевели назад, навсегда выглядела бы только что проверенной, поскольку запись заменяет лишь успешная проверка.

**Явно принято для v1:** враждебная сеть может помешать роботу обновиться. Она не может заставить его *понизить версию*, установить не подписанный нами артефакт или артефакт, не проходящий проверку работоспособности. Именно на эти свойства мы полагаемся.

<a id="9-post-install-hooks"></a>
## 9. Хуки после установки

Идея та же, что у dpkg `postinst`, но хук находится **внутри подписанного tar-архива**, поэтому неподписанный код никогда не выполняется. Бинарный файл Rust или shell-скрипт — движок просто вызывает `exec`.

**Контракт**
- Выполняется *после* переключения символьной ссылки, *до* `apply`. Хук `pre_install`, если он есть, выполняется до переключения.
- Для хука до установки лимит больше: десять минут против двух после установки. Он устанавливает то, что нужно релизу и может отсутствовать на плате: ONNX Runtime; стек GStreamer для `mediad`, составляющий около 100 MB пакетов apt на плате, где его никогда не было. Эти минуты допустимы именно потому, что переключения ещё не было: старый релиз продолжает работать и обслуживать запросы, поэтому долгий pre-install означает медленное обновление, а не неопределённое состояние робота.
- Ненулевой код выхода ⇒ неудачное обновление ⇒ откат.
- Предоставляемое окружение: отсутствующие значения **не задаются**, а не задаются пустыми, чтобы хук различал «первую установку» и «неизвестно»:
  - `UPDATE_COMPONENT` / `UPDATE_CHANNEL` — имя компонента; заданы оба с одинаковым значением;
  - `UPDATE_NEW_VERSION`, а при наличии предыдущего релиза — `UPDATE_OLD_VERSION`;
  - `UPDATE_RELEASE_DIR` — устанавливаемый релиз, `<install_dir>/releases/<ver>/`. **Именно это обычно нужно миграции**; это также рабочий каталог хука;
  - `UPDATE_INSTALL_DIR` — *корень* компонента, например `/opt/robot/daemon`;
  - `UPDATE_NEW_SCHEMA_VERSION`, а когда известно — `UPDATE_OLD_SCHEMA_VERSION`.
- Хуки запускаются с **очищенным окружением** и фиксированным `PATH`, чтобы поведение не зависело от того, как systemd запустил `updaterd`.
- Вывод перехватывается, ограничивается и в любом случае попадает в журнал обновления: при ошибке — внутрь ошибки, при успехе — построчно (`updater/src/hooks.rs`). Успешный вывод тоже журналируется, поскольку отчёт pre-install — какие плагины и runtime установлены, есть ли у платы NPU — отвечает на вопрос «что реально умеет этот робот на этом релизе». Однажды поиск в `journalctl -u updaterd` ничего не нашёл на плате, где хук явно выполнялся.
- Типичные задачи: установка необходимого релизу и отсутствующего на плате (§9.1), миграции схемы конфигурации, изменения `udev`/прав, преобразование данных при повышении `schema_version`.

<a id="91-if-a-fresh-install-does-it-the-hook-does-it"></a>
### 9.1 Что делает чистая установка, должен делать и хук

**Релиз не установлен, пока на плате нет всего необходимого.** Доставка файла в каталог релиза ещё не установка; доставка скрипта ещё не его запуск. Хук — единственное, что запускается на каждой плате при каждом обновлении, поэтому требование «для этого релиза на плате должен быть X» относится к хуку, а не к скрипту первоначальной настройки, однократно выполненному до появления X, и не к памяти человека.

**Вопрос не в том, нужен ли элемент релизу, а в том, выполняет ли это чистая установка.** «Нужен» — оценочное суждение, уже пропустившее ошибку: фрагмент, добавляющий имя робота в приглашение оболочки, релизу не *нужен*, поэтому попал только в `install.sh`, и ни одна плата, получавшая лишь обновления, его не имеет. Задавайте механический вопрос: **записывает ли `scripts/install.sh` этот файл или выполняет эту команду?** Ответ находится поиском в одном файле, а любая не новая плата получает ровно то, что делают хуки, и ничего больше.

Это уже делали неправильно четыре раза, четырьмя способами:

1. **Юниты.** Релиз с новым демоном помещал `.service` в артефакт, но не туда, где ищет systemd. `btd` завершался с `203/EXEC` на плате с полным и правильным релизом, а `on_apply` не мог перезапустить ещё не существующий юнит. Разбор — `docs/project/install-path-gap.md`, исправление — `hooks/postinstall`.
2. **Стек GStreamer и движок 3A.** Их устанавливала первоначальная настройка, поэтому на более старых платах их не было; то же происходило, если плагины на плате были старше тех, с которыми собирался релиз. `hooks/preinstall` при каждом обновлении выполняет собственные `setup-gstreamer.sh` и `setup-rkaiq.sh` релиза; это закрыло пробел.
3. **NPU.** Ветка с детектором уток добавила `setup-npu.sh`, упаковала его рядом с моделью — и ни разу не вызвала. Каждая плата получила бы детектор без доступа к NPU, пока кто-нибудь не вошёл бы по SSH; узнать об этом можно по числовой ошибке `rknn_init`.
4. **Оболочка входа.** В `install.sh` добавился фрагмент `/etc/profile.d`, показывающий имя робота рядом с hostname — `microduck@radxa-zero3 (coincoin):~$`, — чтобы три окна ssh к трём уткам не имели одинаковых приглашений. Ничто другое его не устанавливает, а `install.sh` не входит в релиз, так что хук даже не *мог* его вызвать. Плата, настроенная раньше, получила все последующие обновления, но не этот фрагмент; обнаруживается это сообщением `ls: cannot access '/etc/profile.d/robot-name-prompt.sh'` на плате, релиз которой содержит функцию.

Каждый раз картина одна: работа *сделана*, но пропущен механизм её доставки на плату. При ревью это незаметно: изменение, добавляющее скрипт, выглядит законченным.

Четвёртый случай показывает, как ошибка может выглядеть *правильно*. Два соседних участка `install.sh` — баннер входа и автодополнение `robotctl` — имеют тот же пробел и появились раньше, поэтому окружающий код выглядел образцом. Три функции подряд, выполняемые лишь при чистой установке, — не прецедент, а три случая одной ошибки.

**Следствия.**

- **Всё, что `install.sh` делает с платой, делает и хук.** Остальные три правила — частные случаи этого; направление соответствует реальной ошибке: шаг добавляют в `install.sh`, где его легко проверить на всё равно настраиваемой плате, а путь обновления о нём не узнаёт. `install.sh` не входит в артефакт, и хук не может его вызвать, поэтому общий шаг должен находиться в `scripts/setup-*.sh`, вызываемом обоими, как `setup-gstreamer.sh` и `setup-login.sh`.
  `every_install_sh_step_reaches_an_updated_board` читает места вызовов в `install.sh` и падает, если каждый шаг не выполняется также хуком или не задокументирован с причиной как предназначенный только для чистой установки. Это принуждение к явному решению, а не доказательство: лазейка — строка в таблице. Но все четыре случая потребовали бы обоснования этой строки, которого ни для одного нет.
- **Шаг хука должен быть идемпотентным и дешёвым, когда делать нечего.** Первое необходимо, потому что он выполняется на каждой плате при каждом обновлении, а не один раз: «уже сделано» — норма. Второе — потому что цена платится при каждом обновлении навсегда: десять секунд на уже настроенной плате добавляются ко всем будущим релизам. С каждой функцией в хуке появляется шаг, а бюджет не растёт. Лимиты: 600s до установки (`UPDATE_MAX_SILENCE_SECONDS`, контракт со всеми клиентами — максимальное молчание apply) и 120s после установки, общие с юнитами, учётными записями и перезапуском. Рабочий подход — файл-метка: `setup-npu.sh` записывает версию runtime в `/usr/lib/librknnrt.version` и сравнивает её; `setup-gstreamer.sh` сравнивает метку и результаты двух вызовов `dpkg -s`. На уже подготовленной плате оба не делают ничего заметного по времени.
- **Скрипт, вызываемый хуком, должен входить в пакет.** `every_script_the_hooks_run_is_packaged` читает присваивания `script=scripts/…` из обоих хуков и останавливает сборку, если хотя бы одно место упаковки пропускает скрипт.
- **Необходимые скрипту файлы должны поставляться вместе с ним.** `setup-rkaiq.sh` компилирует shim для LD_PRELOAD из соседнего C-файла; `setup-npu.sh` компилирует наложение device tree из соседнего `.dts`. У каждого есть тест этого требования, поскольку отказ незаметен: скрипт выполняется, не находит исходник, а обновление успешно завершается с одним предупреждением в журнале.
- **Необязательное оборудование никогда не вызывает фатальный отказ.** Ненулевой выход хука срывает обновление и вызывает откат, поэтому хук может завершаться ошибкой только если релиз невозможно установить. Плата без камеры, Bluetooth-адаптера или NPU остаётся роботом; такие шаги сообщают, чего не будет, указывают команду повтора и завершаются успешно.

**Именно для этого первоначальная настройка отделена от обновления.** `provision.sh` и `install.sh` однократно настраивают новую плату. Каждая плата, настроенная до появления функции, должна получать её обычным обновлением: релиз не может предполагать дату настройки платы, а шаг, выполняемый только при первоначальной настройке, половина парка никогда не получит.

<a id="10-reusable-config-driven-engine"></a>
## 10. Повторно используемый движок, управляемый конфигурацией

Движок одинаков для всех роботов; конфигурация каждого перечисляет его компоненты. Адаптация к новому роботу = новая конфигурация + новый ключ подписи +, возможно, новая проверка работоспособности.

Эталонный пример, проверяемый парсером, — [`updater/updater.example.toml`](../../updater/updater.example.toml): модульный тест разбирает его, поэтому он не может разойтись с кодом. Сокращённая версия:

```toml
# /etc/robot/updater.toml
trusted_keys_dir = "/etc/robot/trusted_keys"   # a *set* of keys (§5.4)
hw_rev           = 1
state_dir        = "/var/lib/robot/updater"    # must be outside every install_dir

[component.daemon]
install_dir   = "/opt/robot/daemon"
keep_previous = 1
golden        = "1.0.0"

[component.daemon.source]
type       = "github_releases"
repo       = "ORG/robot-daemon"
tag_prefix = "daemon-v"

[component.daemon.on_apply]
action = "restart"
units  = ["robotd", "mediad"]                  # never updaterd or btd — see §4

[component.daemon.health]
probe   = "socket"
path    = "/run/robotd.sock"
timeout = "30s"

# One component per model — each versions independently (§5.5).
[component.model-walk]
install_dir   = "/opt/robot/model/walk"
keep_previous = 3

[component.model-walk.source]
type     = "hf_hub"
repo     = "ORG/gait-walk"
revision = "main"

[component.model-walk.on_apply]
action = "reload"                              # never drops motor control
unit   = "robotd"
signal = "SIGHUP"
```

Конфигурация проверяется при загрузке; включён `deny_unknown_fields`, поэтому опечатка вызывает явную ошибку, а не молча отключает настройку. В частности, запрещены: `state_dir` внутри `install_dir` (переключение уничтожило бы журнал обновления), общий `install_dir` у двух компонентов, относительные пути и `keep_previous = 0` без golden (нет цели отката).

Две необязательные защиты компонента отклоняют подписанный, но неподходящий артефакт:

```toml
[component.daemon]
# Alongside source, install_dir and on_apply:
required_files = ["bin/robotd", "bin/mediad"]
max_artifact_bytes = 134217728 # compressed bytes, inclusive
```

`max_artifact_bytes` требует объявленного `size` в подписанном манифесте. И `check`, и `apply` отклоняют отсутствующий или превышающий лимит размер до получения нового артефакта; уже установленная версия не требует скачивания и обходит этот лимит. `apply` также проверяет фактический размер скачанного файла перед распаковкой. Это бюджет установки, а не потоковый лимит отдельной передачи: артефакт с заниженным размером отклоняется после скачивания. Лимит передачи HTTP-источника и общие ограничения распаковки `max_uncompressed_bytes` / `max_archive_entries` продолжают действовать.

`required_files` проверяется после подтверждённой распаковки, до любого хука и переключения рабочего релиза, в том числе при пробном запуске. Элементы — непустые относительные пути к файлам без `..`; каталоги и ссылки за пределы распакованного дерева не подходят. `check` не скачивает и не изучает архив, поэтому не может проверить этот список. Отказ оставляет установленный релиз на месте и удаляет staging.

Отсутствие настройки отключает соответствующую защиту. Поставляемый `deploy/updater.toml` включает `required_files` для каждого бинарного файла релиза демона, включая инструменты, которые не запускает ни один юнит systemd; тесты `xtask` согласуют список со всеми рецептами упаковки. `max_artifact_bytes` остаётся незаданным. Установщик связывает конфигурацию с её релизом через `DUCK_CONFIG_REF`, чтобы updater понимал поставляемые ключи. При переопределении этой ссылки или добавлении ключей в существующую конфигурацию используйте понимающий их updater: старые версии отклоняют неизвестные поля.

Обратите внимание: модель использует `reload` (SIGHUP → повторный mmap весов), а не `restart`, поэтому замена модели не прерывает управление моторами. Отдельный `on_apply` каждого компонента естественно поддерживает это и служит одной из главных причин разделения каналов.

Общее для роботов: движок, процесс minisign, протокол запуска с телефона/BLE, логика отката. Специфично для робота: конфигурация, ключ подписи, проверки работоспособности, хуки. Это небольшой бинарный файл и схема, а не фреймворк.

<a id="11-os-updates-deliberately-out-of-scope-for-ota"></a>
## 11. Обновления ОС (намеренно вне OTA)

Отказ от A/B имеет одно настоящее ограничение: ядро и системные библиотеки не обновляются через OTA. Меры компенсации:
- Включить `unattended-upgrades` только для раздела Debian **security**, чтобы получать исправления CVE. Настроить один раз.
- Всё более крупное — новое ядро, новая системная библиотека для демона — требует **перепрошивки при обслуживании**.
- Сокращать зависимости от базовой ОС во время выполнения: преимущественно статическая линковка, упаковка всего возможного в tar-архив, чтобы штатная ОС не блокировала обновление демона.

<a id="111-peripheral-mcu-firmware-out-of-scope"></a>
### 11.1 Прошивки периферии / MCU — вне охвата

<a id="111-peripheral--mcu-firmware--out-of-scope"></a>
Прошивки дочерней платы и сервоприводов записываются **на производстве**, не у пользователя. Это не компонент OTA, поддержки для них не предусмотрено. Если это когда-нибудь изменится, такой компонент будет прошивать устройство через шину моторов в `on_apply`, что существенно рискованнее: откат означает перепрошивку, а не смену символьной ссылки.

<a id="12-alternative-considered-apt-dpkg-own-signed-repo"></a>
## 12. Рассмотренная альтернатива: apt / dpkg (свой подписанный репозиторий)

<a id="12-alternative-considered-apt--dpkg-own-signed-repo"></a>
Вариант стоит сохранять, особенно для канала **daemon** на Debian:

**Плюсы**
- Подпись GPG, атомарная установка, версии и **скрипты сопровождающего** (`preinst`/`postinst`/`prerm`/`postrm`) — нужный нам хук после установки — уже реализованы и проверены практикой.
- Стандартные инструменты Debian, понятное поведение; `apt` управляет зависимостями.

**Минусы в нашем случае**
- Нет готового отката по результатам проверки работоспособности и простого возврата к предыдущей версии: всё равно придётся писать надстройку.
- Неудобно поставлять ML-модель как обычный версионируемый файл.
- Нет запуска с телефона и IPC прогресса: снова нужна оболочка.
- **Переносимость:** отсутствует на будущих роботах без Debian, например Yocto, что противоречит цели общего инструмента для разных роботов.

**Когда apt был бы уместен:** если обозримое будущее парка ограничено Debian и мы согласны отказаться от автоматического отката по работоспособности либо управлять им через закрепление `apt install pkg=old`, собственный подписанный apt-репозиторий действительно проще для бинарного файла демона. Модели всё равно нужен отдельный канал. Рекомендация: начать с собственного движка Rust ради переносимости и отката; вернуться к apt, если цена сопровождения движка превысит пользу, а парк останется только на Debian.

<a id="13-phone-ble-trigger-protocol-sketch"></a>
## 13. Протокол запуска с телефона / BLE (набросок)

<a id="13-phone--ble-trigger-protocol-sketch"></a>
`btd` предоставляет две GATT-характеристики на канал либо одну с полем канала:
- **Trigger** (запись): `{ "cmd": "check" | "apply", "channel": "daemon", "version"?: "…" }`
- **Status** (чтение/уведомления): `{ "channel", "state": idle|checking|downloading|applying|healthy|failed|rolled_back, "progress": 0-100, "version", "error"? }`

`btd` пересылает запрос в `updaterd` через Unix-сокет и отражает его состояние обратно. Сами пакеты через BLE не передаются.

<a id="14-implementation-sketch"></a>
## 14. Набросок реализации

`updaterd` — небольшой бинарный файл Rust, примерно несколько сотен строк логики:
- `reqwest` — скачивание с возобновлением/повторами и GitHub API для поиска последнего тега.
- `minisign-verify` — проверка подписи.
- `tar` + `zstd` — распаковка.
- `serde` / `toml` — конфигурация; `serde_json` — манифесты.
- Атомарная смена символьной ссылки через `rename(2)`; опрос работоспособности через существующий IPC Unix-сокета.
- Интеграция с systemd: `Type=notify`, `WatchdogSec`, шаблоны юнитов.

CI для каждого канала:
1. Собрать артефакт, при необходимости через `cargo-dist`.
2. Подписать артефакт и манифест через `minisign -S`.
3. Создать GitHub Release с тегом `daemon-vX` / `model-vX` и вложениями: артефакт, `.minisig`, `manifest.json`.

<a id="15-good-neighbors-in-scope"></a>
## 15. Полезные соседние возможности (в охвате)

Недорогие дополнения к тому же IPC / движку с заметной пользой:

- **Общий модуль самопроверки.** Одна проверка — ответы моторов, загрузка модели, инициализация медиа — вызывается при старте и после обновления для допуска релиза. Единый источник ответа «робот исправен?».
- **Локальный CLI `robotctl`.** Тонкий клиент Unix-сокета `updaterd`: та же роль, что у `btd`, другой транспорт, собственной логики обновления нет. Для поддержки, восстановления на месте и CI.
  Команды имеют пространство имён (`robotctl update …`), чтобы последующие пространства добавлялись без конфликтов: `check`, `apply [--version|--dry-run]`, `rollback`, `reset-to-golden`, `select` (переключение набора модели), `pin`, `status`, `log`, `watch`. Реализовано только пространство `update`.
- **Локальная загрузка для разработки.** Принимать артефакты, подписанные отдельным **ключом разработки**, который входит в доверенный набор, но доступен через флаг / сборку разработки, чтобы команда могла устанавливать локальные сборки без производственного ключа (§5.4).
  **Реализовано.** `robotctl update apply --from <dir>` подменяет источник на один вызов: релиз читается из каталога на плате, а остальной apply остаётся прежним — предварительные проверки, подпись, хеш, совместимость, проверка работоспособности, автоматический откат. `scripts/dev-push.sh` выполняет весь путь: кросс-компиляцию, упаковку, подпись, копирование, применение. Две вещи намеренно отсутствуют: это не `updaterd install --from`, принудительно отключающий `on_apply` и проверку и потому непригодный для рабочего релиза; проверки также не ослабляются, поэтому на плате нужен ключ разработки, а не флаг пропуска проверки. Защита от понижения отступает для `--from` по той же причине, что для `--version`: оператор с явно заданным каталогом — не зеркало, вернувшееся назад; локальная сборка является prerelease и сортируется ниже установленной, поэтому защита отклонила бы любую отправку.
  Единственное ограничение каталога связано с systemd, а не с движком: `updaterd.service` задаёт `PrivateTmp=yes`, выделяя юниту собственные `/tmp` **и** `/var/tmp`; релиз, скопированный туда из оболочки, — не тот, который читает демон. Поэтому каталог локальной загрузки находится в домашнем каталоге пользователя платы и существует `Check::SideloadDir`: без этой проверки ошибка говорит об отсутствующем манифесте в каталоге, где `ls` его показывает, и снаружи опровергнуть это невозможно.
- **Безопасность первоначальной настройки по BLE.** Смежный, но важный вопрос: учётные данные wifi при настройке проходят по BLE. Эта характеристика должна требовать сопряжения и шифрования, иначе данные утекут. Артефакты подписаны, поэтому поддельный *запуск* обновления малорискован, но записи *настройки* должны быть аутентифицированы. Убедиться, что `btd` уже это обеспечивает.

<a id="16-release-testing-confidence"></a>
## 16. Тестирование релизов и уверенность в результате

<a id="16-release-testing--confidence"></a>
**Мотивация.** На предыдущем роботе релизы проверяли вручную: вручную возвращали известную версию, применяли новую и проверяли результат. Слишком много места для человеческой ошибки. Цель: **сделать путь обновления доступным скриптам и автоматическим тестам, чтобы поставка клиентам стала решением, а не ручной процедурой.**

Главное: основная часть этого риска — возврат → применение → проверка — лежит в *механизме* обновления, то есть чистом ПО, тестируемом в CI **без оборудования**. Реальная плата нужна лишь поведению, действительно зависящему от оборудования.

<a id="161-design-for-testability"></a>
### 16.1 Проектирование с учётом тестируемости

- **Настоящий путь кода на тестовых артефактах.** `updaterd` берёт источник/манифест из конфигурации, поэтому тесты направляют его в локальный каталог или канал `staging` и выполняют *тот же производственный код*, а не фиктивный updater, расходящийся с реальностью.
- **Идемпотентные операции, доступные скриптам** через `robotctl` (§15): `apply --version X`, `rollback`, `pin <version>` / `unpin`, `model select`, **`reset-to-golden`**. Раньше не хватало простой команды «перейти ровно на эту версию» — теперь это они. Все **неинтерактивные**: нет приглашений и вопросов, на которые оператор может ответить неправильно.
- **`--dry-run`:** получить, проверить подпись, совместимость и место, остановиться перед переключением.
- **Средства внесения отказов:** флаги принудительно неудачной проверки, повреждённого артефакта, ненулевого выхода хука или завершения процесса посреди переключения — чтобы откат *проверялся*, а не предполагался.

<a id="162-two-test-tiers"></a>
### 16.2 Два уровня тестов

**Уровень 1 — механизм (CI, без оборудования, быстро).** Запуск на каждом PR; уже этого достаточно для снятия большей части риска ручного возврата. Автоматически покрыть:

- верная / неверная подпись / другой ключ → принять / отклонить;
- несовпадение хеша → отклонить;
- несовместимые `min_hw_rev` / `model_api` → отказ с понятным статусом;
- старый правильно подписанный манифест как latest → отказ из-за понижения (§8.4.1), при этом явное понижение через `--version` разрешено;
- `rollback` никогда не выбирает только что отказавший релиз или релиз, уже отмеченный в журнале как отменённый;
- счётчики пробных загрузок отдельны для компонентов: переход одного не расходует бюджет другого;
- **индивидуальное состояние робота сохраняется** при обновлении *и* откате: калибровка, генерируемые ресурсы, обученное состояние, пользовательские настройки (§5.7);
- исправное обновление → фиксация + очистка старых версий;
- неудачная проверка работоспособности → автоматический откат; робот исправен на *старой* версии;
- ненулевой выход хука → откат;
- **kill -9 посреди переключения / имитация потери питания** → согласованное состояние после запуска, никаких наполовину активных релизов;
- заполненный диск → отказ до любых изменений;
- параллельные запросы → одна операция; второй сообщает о занятости;
- **`robotd` отсутствует / постоянно падает** → `btd` и `updaterd` продолжают обслуживать запросы; обновление, откат и reset-to-golden завершаются (§4.1). Добавить сценарий «восстановление после плохого релиза»:
  намеренно неисправный релиз проверяет самый важный путь;
- зависание IPC `robotd` (сокет открыт, ответа нет) → тайм-аут, а не остановка навсегда;
- матрица версий: обновление A→B, пропуск A→C, откат B→A, миграция при повышении `schema_version`.

Уровень 1 запускает движок с внутрипроцессным `FakeRobot`, реализующим `RobotClient`. Это правильный способ проверять *решения* движка: поддельный робот по требованию неисправен, зависает или отсутствует, что трудно устроить в реальности. Но он ничего не сериализует, поэтому вообще не видит протокол передачи.

**Уровень 1b — настоящий процесс `robotd`** (`robotd/tests/updater_gate.rs`, всё ещё CI и без оборудования) закрывает этот пробел. Он запускает настоящий бинарный файл, а реальный `SocketRobotClient` общается с ним через настоящий Unix-сокет: каждый вызываемый движком метод должен вернуть данные в ожидаемом формате, обновление — пройти проверку и зафиксироваться, а `robotd --unhealthy` — вернуть *содержимое* за `current`, не только символьную ссылку.

Больше это ничем не покрыто. Собственные round-trip-тесты крейта протокола не обнаруживают расхождение, поскольку обе стороны используют одну структуру; модульный тест уровня `dispatch` в `robotd` дёшево ловит смену формы ответа, но сам сокет проверяет только настоящий процесс.

**Уровень 2 — приёмка на устройстве (контрольные роботы).** Поведение, зависящее от оборудования — походка, моторы, медиа, — требует настоящих плат. Держать несколько **лабораторных/контрольных роботов**, следующих `staging`, автоматически устанавливающих каждого кандидата, выполняющих сценарий приёмки — проход моторов, базовую проверку походки, инициализацию медиа, самопроверку — и отправляющих результат и журнал обновления. Повторяемость обеспечивают доступные скриптам reset-to-golden и `apply --version`.

<a id="163-channels-promotion"></a>
### 16.3 Каналы и продвижение

<a id="163-channels--promotion"></a>
**Реализовано** тремя workflow GitHub Actions и издателем `cargo xtask` (`.github/workflows/`, `xtask/`):

| | |
|---|---|
| `ci.yml` | fmt, clippy, тесты и `board-test.sh` — единственная задача, доказывающая запуск бинарных файлов на aarch64 Linux |
| `release.yml` | по тегу `daemon-staging-v*`: кросс-сборка, упаковка, подпись, **проверка тем же кодом, что использует робот**, публикация prerelease |
| `promote.yml` | вручную: переподписать манифест *stable*, скопировать проверенный артефакт в стабильный релиз, удалить staging |

Издатель написан как Rust `xtask`, а не shell-скрипт, по одной причине: он использует ровно те же крейты `minisign`, `tar`, `zstd` и `sha2`, которыми проверяет updater. Shell-версия зависела бы от отдельно установленных программ, поведение которых могло бы отличаться от принимаемого роботом, а здесь различия недопустимы. Кроме того, он линкует *полный* крейт `minisign`, способный подписывать, тогда как демон — только `minisign-verify`, не способный на это.

Три свойства стоит назвать явно: каждое проверяется утверждением теста, а не принимается на веру.

- **Продвижение никогда не пересобирает.** Стабильный манифест содержит `sha256` из staging, а продвижение после проверки хеша копирует артефакт staging в стабильный релиз: клиенты получают байты, проверенные контрольным роботом. Тест утверждает неизменность хеша.

  Раньше манифест ссылался на релиз *staging* вместо копирования: рассуждали, что один набор байтов не может разойтись сам с собой, а две копии — могут. При этом упустили, что робот проверяет `sha256` до установки, поэтому изменившаяся копия никогда не установится незаметно, а стабильный канал, артефакты которого лежат под похожим на временную заготовку тегом, может сломаться при первой очистке. Так и произошло: удаление релизов `daemon-staging-v0.1.x` оставило `daemon-v0.1.0`, `v0.1.1` и `v0.1.4` с правильными подписями и ссылками на 404. Теперь стабильные релизы самодостаточны, а staging удаляет сам `promote.yml`.
- **Артефакты воспроизводимы.** Фиксированные mtime в tar обеспечивают одинаковый архив из одинаковых входных данных, позволяя сравнить повторную сборку с опубликованной. Тест утверждает одинаковые хеши двух упаковок одинаковых данных.
- **`release.yml` проверяет до публикации.** Он устанавливает релиз настоящим движком (`updaterd install --from`, источник `LocalDir`) и проверяет исполняемость установленных бинарных файлов. Если updater не принимает релиз, его никто не сможет скачать.

Есть две защиты от простых ошибок: `package` отвергает `--version`, не совпадающую с `Cargo.toml` (тег без повышения версии), а `promote` — версию, не совпадающую с манифестом staging.

- Каналы: `staging` → `stable`. CI публикует кандидатов в `staging`.
- Контрольный робот получает кандидата **одним флагом для каждой команды**:

  ```
  sudo robotctl update apply daemon --staging
  ```

  Ранний проект говорил, что контрольные роботы «автоматически получают staging», но в таком виде это было нереализуемо: `newest_version` пропускает всё, что GitHub помечает prerelease, *и* всё с prerelease-компонентом semver. Именно этот фильтр удерживает клиентских роботов от кандидатов, поэтому он остаётся, а единственное явное включение — `--staging`: второй поиск с `staging_tag_prefix`, разрешающий флаг *GitHub*, но по-прежнему исключающий prerelease semver, чтобы сборку ветки нельзя было принять за кандидата. `latest_manifest` не изменён; `auto_apply` и периодическая проверка продолжают выбирать stable: без человека и root на кандидата ничто не перейдёт.

  Первая попытка состояла в изменении `tag_prefix` на плате: она отвечала `no releases in … with tag prefix "daemon-staging-v"`, хотя кандидат находился там. Префикс указывал место поиска, а фильтр prerelease отказывался смотреть.

  **`--staging` отказывает, если канал отстаёт от платы.** Продвижение прямо в stable не публикует кандидата — поддерживаемый путь, отмеченный в `release.yml` как «NOT canaried», — поэтому поиск staging продолжает возвращать последнюю версию, для которой кандидат был. Раньше на уже более новой плате `--staging` устанавливал её: проверял, переключал, затем откатывал, когда не запускался демон, отсутствующий в старом релизе. Откат был правильным, но ничего не говорил о причине. Теперь найденный кандидат сравнивается с установленным, а отказ называет обе версии. `--staging --version X` обходит защиту: оператор, называющий кандидата, явно выражает намерение; так же переустанавливается версия, с которой плата только что откатилась.
- При успехе **продвинуть**: направить `stable` на *те же проверенные байты*, переподписав манифест `stable` со ссылкой на тот же tar-архив и хеш. Никакой пересборки, перепрошивки или ручного копирования. Продвижение — одна команда / одно нажатие, поставляющее ровно проверенное.
- Плохой `stable` → то же в обратную сторону: направить `stable` на предыдущий заведомо исправный манифест; после появления исправления `min_supported` (§8.1) подтянет роботов вперёд.

<a id="164-provenance"></a>
### 16.4 Происхождение

`version.toml` и журнал обновлений записывают git SHA и хеш каждого артефакта, поэтому «точную версию клиента» всегда можно воспроизвести в лаборатории.

Это закрывает прежнюю проблему: **люди решают, продвигать ли релиз; машина каждый раз одинаково возвращает, применяет и проверяет.**

<a id="165-bootstrap-state-over-for-the-health-gate-not-for-the-payload"></a>
### 16.5 Начальное состояние — проверка работоспособности уже работает, комплект поставки ещё неполон

<a id="165-bootstrap-state--over-for-the-health-gate-not-for-the-payload"></a>
Артефакт `daemon` пока содержит меньше, чем будет в итоге: `bin/updaterd`, `bin/robotctl`, `bin/robotd`, `version.toml`. `mediad` и `btd` ещё нет.

Здесь нет замкнутого круга: §4.1 устанавливает, что `updaterd` и `btd` входят *внутрь* артефакта daemon, поэтому обновление updater самим собой — настоящий будущий путь и самый рискованный. Проверить его первым — смысл порядка сборки из §9.

Две настройки в `updater.example.toml` намеренно оставались неактивными, пока не появилось то, что можно проверять. Теперь обе работают:

| | было | сейчас | ещё предстоит |
|---|---|---|---|
| `on_apply` | `none` | `restart` с `["robotd", "configd"]` | — |
| `health` | `none` | `socket`, 30s | тайм-аут предварительный, пока M4 не измерит настоящую загрузку |

Раньше `mediad` требовал записи в авторитетном списке, теперь нет: набор перезапуска выводится из юнитов релиза с пропуском не имеющих раздела `[Install]`, а `mediad.service` его имеет. Поэтому apply перезапускает его, а робот, никогда его не запускавший, включает его при следующей установке: правило — файл юнита, а не поддерживаемое кем-то имя.

**`health = none` было самым слабым состоянием проекта:** оно фиксирует обновление сразу после успешного переключения, поэтому автоматического отката не было вообще, и единственным механизмом восстановления оставался счётчик загрузок. Выход из этого состояния был целью M1.

Модульный тест, закреплявший неактивные значения примера, теперь проверяет обратное: `on_apply` должен перезапускать `robotd` и **не должен** перезапускать `updaterd` или `btd` (§4.1), а `health` должен быть проверкой сокета. Возврат к `probe = "none"` незаметно отключил бы автоматический откат изменением одного слова — именно таким изменениям нужен преграждающий путь тест.

**Что ещё не проверено:** `systemctl restart` из `on_apply` ни разу не запускался с настоящим systemd — на ноутбуке разработчика его нет, а заглушка проверяла бы саму себя. Сама проверка работоспособности *проверена* с настоящим процессом `robotd` и сокетом (`robotd/tests/updater_gate.rs`); неподтверждёнными остаются именно перезапуск и тайм-аут 30s. Оба относятся к M4 на Radxa.

<a id="17-open-questions-future"></a>
## 17. Открытые вопросы / будущее

<a id="17-open-questions--future"></a>
- **Принадлежность конфигурации.** Сейчас конфигурация идёт с набором модели. Должна ли часть относиться к каналу daemon или стать отдельным маленьким каналом? Миграции схемы в любом случае выполняют хуки (§9).
- **Минимальный отчёт серверу «получилось ли».** Управление парком отложено, но один сигнал успеха/ошибки на обновление помог бы рано обнаружить плохой релиз и сделать `min_supported` (§8.1) практически полезным. Стоит ли?
- Поэтапные развёртывания / телеметрия / панели: явно отложены; вернуться при росте парка.
- Дельта-обновления отложены: при нынешнем темпе артефакты малы.

Известные и намеренно открытые расхождения между документом и реализацией:

- **Конкурирующие варианты внутри одного слота модели не поддерживаются.** Каждая модель — компонент с одной линией версий (§5.5), что покрывает «ходьба, прыжок и стойка обновляются независимо», но *не* «установлены две разные модели ходьбы, пользователь выбирает». Нужен ключ хранилища `(name, version)`, затрагивающий около 14 файлов: методы `Store` с ключами, `known_bad`, `PendingUpdate`, `Pins`, `golden`, `pinned` и типы протокола, то есть повышение `API_VERSION`. Кроме того, четыре понятия становятся отдельными для набора, а не общими: число сохраняемых версий, цели отката, latest и golden. Отложено до подтверждения необходимости: догадки об этих четырёх вещах и породили удалённый `Layout::Library`.
- **Нельзя обнаружить доступные для установки модели.** Приложение перечисляет *установленное*, но ни один `Source` не отвечает «что можно установить»: сейчас добавление модели требует редактирования конфигурации. Нужна операция `Source::list_*`.
- **Нет режима восстановления.** Цепочка §8.2 — `current → previous → golden`; все три реализованы, включая переход дальше отсутствующего или заведомо плохого previous. Последнего «минимального режима восстановления, способного скачать заново» нет.
- **Один `RobotClient` обслуживает все компоненты.** `HealthCheck::Socket { path }` учитывается при выборе *проверки*, но сам путь сокета берётся из клиента, созданного `main`. Пока оба компонента проверяют `robotd`, это нормально; если потребуется другой собеседник — ловушка. Нужен клиент на компонент.

Ещё открыто:
- **Передача артефактов телефоном как запасной путь** для робота без пригодного интернета: ещё не настроен, captive portal, заблокированный CDN, автономная демонстрационная площадка. На стороне движка почти всё бесплатно: `LocalDir` (§15, §16.1) уже применяет каталог с манифестом, артефактом и обеими `.minisig` через настоящую проверку, а подписи изначально позволяют не доверять транспорту. Вся цена — в связи, которая должна быть wifi или USB (§3.1). Два варианта решают разные задачи: робот создаёт AP, к которой подключается телефон — учётные данные робота не нужны, но телефон должен скачать релиз через мобильную сеть *до* подключения, а обе мобильные ОС сопротивляются сети без интернета; либо, когда wifi работает, а CDN нет, телефон отправляет по LAN — гораздо дешевле, но появляется сетевой приёмник загрузок. Последствия его компрометации ограничены проверкой подписи: неподписанное не установится, худший случай — заполнение диска. Однако токен и явно выбранный адрес привязки всё равно нужны (`architecture.md` §2.2). Запасной план, не v1.
- ~~**Сообщение об устаревании манифеста**~~ (§8.4.2) **реализовано**: `update.status` содержит `last_checked`, а `robotctl health` предупреждает после недели молчания источника. Срок действия подписанного манифеста остаётся настоящей защитой, отложенной до отлаженной публикации.
- **Принадлежность конфигурации** — набор модели, daemon или отдельный маленький канал? Хуки выполняют миграции в любом случае (§9).
- **Минимальный отчёт серверу об успехе/ошибке** — один сигнал на обновление поможет рано обнаружить плохой релиз и сделать `min_supported` (§8.1) полезным на практике. Стоит ли, или слишком много для v1?
- **Слой поведения/мышления** — если верхний слой поведения (побуждения, настроение, привычки) когда-нибудь станет самостоятельным артефактом, это будет третий канал со своим ограничением совместимости. Его обученное состояние также прямо относится к §5.7.

Явно **не делаем**: матрицу аппаратных вариантов (§5.6), OTA периферийных прошивок (§11.1), поэтапное развёртывание / телеметрию, дельта-обновления.

Решено после первого проекта: раздельный хостинг GitHub + HF Hub; порог `min_supported` в схеме; *наборы моделей с именованными слотами* и совместимость `model_api`; несколько доверенных ключей подписи; одна аппаратная цель; сохранение индивидуального состояния робота (§5.7); конфигурация в файле, а не в юните systemd.
