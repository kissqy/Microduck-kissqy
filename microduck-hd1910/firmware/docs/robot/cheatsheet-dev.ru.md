# Шпаргалка для платы разработчика

<a id="cheat-sheet--dev-board"></a>
Команды, имеющие смысл только на плате, подготовленной по [`install-dev.md`](install-dev.ru.md). Повседневные команды робота находятся в [`cheatsheet.md`](cheatsheet.ru.md).

<a id="the-dev-channel"></a>
## Канал разработки

Установить последнюю сборку ветки, созданную CI:

```
sudo robotctl update apply --ref <branch> daemon
```

```
sudo robotctl update apply --ref main daemon
```

`--version` вместо этого закрепляет конкретный выпуск. Указывайте один из параметров, если только действительно не хотите «перейти на стабильный канал».

**`apply daemon` без `--ref` устанавливает последний *стабильный* выпуск, что на плате разработчика обычно означает понижение версии.** Это не «установить самое новое», а «установить предлагаемое стабильным каналом». Сразу после слияния ветки стабильный выпуск всё ещё старее всех проверяемых вами сборок. Если он предшествует службе, unit-файл которой уже находится на плате, `ExecStart` указывает на отсутствующий в старом выпуске исполняемый файл; перезапуск завершается ошибкой, и обновление откатывается. Защита работает правильно, но вызвавшая её команда выглядела очевидным выбором.

Тег `daemon-dev-<branch>` перемещается вместе с веткой, поэтому копировать номер версии не нужно. Версия *внутри* уникальна для каждой сборки — `0.1.0-dev.42.c719ec8`, — и две сборки одной ветки не перепутать. `--ref main` возвращает плату на основную ветку, сохраняя канал разработки. Простой `apply daemon` покидает этот канал, поскольку предварительный выпуск сортируется ниже соответствующего релиза; отдельного шага отключения канала нет.

Слияние не публикует сборку мгновенно: CI должен собрать `main`, прежде чем `--ref main` начнёт указывать на результат.

```
gh run list --branch main
```

<a id="release-candidates"></a>
## Кандидаты в релиз

Сборки, опубликованные `release.yml` в staging, но ещё не переведённые в стабильный канал. Именно их должен запускать пробный робот перед продвижением:

```
sudo robotctl update apply --staging daemon
```

```
sudo robotctl update apply --staging --version 0.3.0 daemon
```

Кандидат подписан ключом выпуска, как обычный релиз, и уже имеет версию, с которой будет продвинут. Без флага он недоступен потому, что помечен как предварительный выпуск, а обычный `apply` их пропускает, чтобы робот не получил непроверенную сборку самопроизвольно. `--staging` — единственный способ обойти этот фильтр; он действует только на конкретную команду и не оставляет постоянной настройки.

<a id="after-an-update-the-part-that-bites"></a>
## После обновления: типичные ловушки

<a id="after-an-update--the-part-that-bites"></a>
- **`robotd`, `configd` и `padd` перезапускаются во время обновления. `updaterd` и `btd` — через 5 секунд после ответа.** Первый не может перезапустить себя посреди обновления, а второй может передавать сам ответ. Поэтому исправление `btd` начинает работать через несколько секунд без ручных действий. Переподключитесь — и оно уже действует.
- **Если один из этих двух перезапусков не состоялся, следующий запуск `updaterd` исправляет ситуацию.** Исключение — сам `updaterd`: он сообщает о несовпадении, но не перезапускает себя. Для него повторите apply: ответ будет `already_current`, в нём будет названа служба, не использующая установленный выпуск, и запланирован её перезапуск. `sudo systemctl restart updaterd` делает то же вручную.
- **На плате с `updaterd` старше 0.4.0 этих механизмов нет**: обе службы остаются на старом исполняемом файле до ручного перезапуска. Одно обновление устанавливает исправление, но правильно ведёт себя только следующее обновление.
- **`robotctl update apply` отвечает `already_current` и ничего не устанавливает**, если запрошенная версия уже есть на плате, но теперь это не пустое действие. Команда проверяет, какие службы работают из этого выпуска, перезапускает остальные и перечисляет их в `stale`. Поэтому именно её следует использовать, если исправление кажется отсутствующим: она либо устранит проблему, либо `stale` окажется пустым и исправления в данном выпуске вообще не было.

Симптом: исправление точно установлено, но точно не действует. Узнайте, какой выпуск использует каждая служба:

```
robotctl health
```

Блок `units` выводит строку для каждой службы с выпуском, из которого запущен процесс, и предупреждение с нужным перезапуском, если он отличается от установленного. `build unknown` означает, что служба работает, но не опубликовала идентификатор, скорее всего из-за старой сборки; перезапустите её, и она ответит. `restarting` означает, что процесс завершился и systemd запускает его снова: несколько секунд после обновления это нормально; постоянное состояние означает, что служба вообще не может запуститься.

Если служба действительно осталась старой, перезапустите её. Обычно этого не требуется, поэтому стоит прочитать журнал и понять причину:

```
sudo systemctl restart configd
```

`updaterd` никогда не исправляет сам себя:

```
sudo systemctl restart updaterd
```

Редактировать `updater.toml` на плате не нужно: набор перезапуска определяется unit-файлами, поставляемыми выпуском. Полная последовательность по шагам находится в `../design/restart-order.md`.

<a id="from-a-laptop-build-here-install-on-the-board"></a>
## С ноутбука: собрать здесь, установить на плату

<a id="from-a-laptop--build-here-install-on-the-board"></a>
Полностью минуя CI: сборка на своём компьютере и установка по SSH примерно за минуту.

```bash
scripts/dev-push.sh microduck@<board>
```

Результат — обычное обновление с проверкой допуска, поэтому описанные выше ловушки перезапуска остаются актуальны. В [`dev-push.md`](dev-push.ru.md) описаны подготовка, сборка в контейнере, `--dry-run`, первая отправка на плату с версией ниже 0.5.0 и действия при ошибке.

<a id="from-a-laptop-drive-with-a-pad-in-your-hands"></a>
## С ноутбука: управление геймпадом в руках

<a id="from-a-laptop--drive-with-a-pad-in-your-hands"></a>
Геймпад у вас в руках, робот на стенде, установка на обе стороны не нужна: `padd` — обычный клиент, который можно запустить из клона репозитория через проброшенный сокет.

Сначала остановите экземпляр на роботе, иначе два процесса будут бороться за управление стиками:

```bash
sudo systemctl stop padd
```

Пробросьте сокет и оставьте соединение открытым:

```bash
ssh -L /tmp/robotd.sock:/run/robotd.sock microduck@192.168.1.42
```

Затем из этого клона в другом терминале:

```bash
cargo run -p padd -- --socket /tmp/robotd.sock
```

`systemctl start padd` возвращает собственный экземпляр робота. Здесь полезны флаги `padd`: `--max-linear` (m/s), `--max-angular` (rad/s), `--max-head` (радианы) и `--deadzone`. Последний нужен потому, что аналоговые стики редко возвращаются точно в ноль и без мёртвой зоны робот ползёт. Служба запускается со значениями по умолчанию, поэтому для других значений нужно запустить исполняемый файл вручную — здесь или на плате:

```bash
sudo -u padd /opt/robot/daemon/current/bin/padd --max-linear 0.25
```
