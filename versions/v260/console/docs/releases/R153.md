# Microduck R17 v1.0.153

本版修正 v152 固件包损坏及中控连接状态判断。配套原生固件仍为 `1fa8438-feetech-ft6-control.32`。停用 v152，完整解压本版中控，通过“系统维护 → 随包固件”安装一次；无需重装 Linux 或清空标定。

## 已确认的启动崩溃

09:31 的录制中，安装前旧 control.31 的 IMU 正常，控制循环约 50 Hz；新进程启动后收到 `SIGBUS`。v152 中的 ONNX Runtime 动态库只有 14,073,856 字节，完整原件应为 20,591,712 字节。部分 ELF 加载段超出实际文件结尾。

相同 ARM 程序和模型使用截断库时复现 SIGBUS，换回完整原件后新旧程序各五个模型均通过加载和首次推理。这次崩溃的根因是运行库文件不完整，不能据此判定 IMU 损坏。

v153 从原始固件归档恢复运行库，先核对原始 SHA，再打包；对五个程序、两个运行库执行 ELF 范围检查。安装在停止现有服务前检查 ELF，并校验复制前后文件哈希，避免将损坏包或短复制文件替换到运行目录。

## 中控连接与诊断

新录制中 robotd 数据通道报 WinError 10054，但测距连接仍在更新；用户也确认 ping 和 CMD 的 SSH 登录正常。v152 把 robotd 转发断开统一改写为“SSH 连接失败”，并仅凭 robotd 的 system 遥测判断 SSH 是否连接，造成误报。

v153 使用现有 SSH 转发的认证成功事件判断连接，单独显示 robotd 数据连接错误并保留原文；两个机器人服务都未运行时仍能进行维护。真实 SSH 端口或认证错误继续显示，新连接不继承旧连接状态。没有新增线程、定时器或重试循环。运动入口仍按总线和 IMU 就绪状态放行。

“导出启动诊断”增加 SSH 服务状态、监听端口和本次 SSH 日志；现有内核、网络、UART 和 robotd 日志继续保留。诊断每次点击只执行一次，不打开串口、不重启服务。真正 SSH 离线时，需恢复连接后才能读取设备日志。

## 保留的启动方案

control.32 原生代码与已验证二进制保持一致：旧同一 UART 五次重试已删除；首次通信超时后释放旧串口，等待一次 400 ms，再新开串口一次。两个串口代次分别验证 FIFO/IRQ，仍失败则明确结束，无自动重启。

启动先确认全部 15 个舵机卸力，再读取 IMU；未就绪时拒绝 HOME、策略与技能，失败请求不排队。正常 50 Hz 循环不增加后台重试、采集或推理。模型、标定、手柄映射和 v151 手柄修复按钮继续保留。

## 使用与验证范围

安装前支撑机器人。新包安装后核对中控 `1.0.153`、运行固件 `control.32`，等待总线与 IMU 就绪再按 HOME。若仍失败，导出启动诊断 JSON。

验证包括 ARM 仿真的五模型加载与推理、截断库崩溃对照、安装完整性和中控回归测试。准确记录见随包 `BUILD_MANIFEST.json` 和源码 `verification/recovery153.json`。本次未连接真机，断电重启、实际行走和温度尚待真机确认。
