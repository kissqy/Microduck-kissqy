# Симуляция: те же службы, тело в MuJoCo

**Состояние:** реализовано и используется. Здесь есть `robotd --sim`, `tofd --sim` и `mediad --sim-camera`, вторую половину обслуживает `duck-body` из `microduck_rl`; контейнеры (§8), эфир (§5) и отдельные камеры роботов запускаются через `scripts/duck-sim`. Измерено: с телом MuJoCo служба держит `50.0 of 50.0 Hz · 0 missed`, обнаруживает загрузку в сидячей позе по собственным углам суставов симулятора, а `robotctl robot init` выполняет sitstand до подъёма и удержания вертикального положения. Четыре робота в контейнерах поют полный хорал через эфир. Использование описано в [`docs/robot/simulation.md`](../robot/simulation.ru.md); здесь — проектирование.

Цель — робот, с которым разрабатывают точно так же, как с настоящим: те же исполняемые файлы, службы, `robotctl`, `duckctl open`, но тело находится в MuJoCo, а не на столе. Это не имитация ответов и не тестовая обвязка, а двойник с явно описанной границей.

<a id="1-what-using-it-looks-like"></a>
## 1. Как выглядит использование

Одна команда создаёт робота. Дальше это обычный робот, команды которого вы уже знаете.

**Что работает сейчас** (`scripts/duck-sim`, один робот, без контейнера):

```
scripts/duck-sim               # a window opens, the duck stands up, and it is yours
scripts/duck-sim drive         # walk it forward, then stop
scripts/duck-sim ctl health    # or anything else robotctl does
scripts/duck-sim log
scripts/duck-sim down
```

Скрипт собирает недостающее, записывает параметры, находит ONNX Runtime в venv репозитория RL, запускает обе стороны и поднимает робота. Он избавляет от ручного ввода трёх неочевидных вещей: политики на роботе лежат в `/opt/robot/daemon/current`, а на ноутбуке — в этом репозитории; `ort` загружает через dlopen библиотеку libonnxruntime, которой нет на ноутбуке; путь Unix-сокета ограничен примерно 108 байтами, поэтому каталог состояния должен быть коротким.

**К чему это ведёт**, после появления контейнеров:

```
duck-sim up 4                  # four ducks, sharing one MuJoCo window
duck-sim shell duck-a          # you are on duck-a
```

Внутри всё обычно:

```
duck-a # robotctl health
duck-a # robotctl configure
duck-a # robotctl chorale
duck-a # journalctl -u robotd -f
```

А из своей оболочки — точно как с роботом на столе:

```
duckctl open duck-a
scripts/dev-push.sh microduck@duck-a
```

Четыре правила среды запуска: инструмент разработки, которому нужен отдельный регламент эксплуатации, не будут использовать.

**Никакой подготовки, которую нужно помнить.** `duck-sim up` на ещё не использовавшей его машине собирает rootfs, получает недостающее и сообщает об этом один раз. То, чего он действительно не может сделать сам, выводится точной командой для вставки, в стиле остальных `scripts/`.

**По умолчанию — обычный случай.** Без количества — один робот. Без сцены — квартира. Без `--cameras` — никаких камер: большинству сеансов они не нужны, а основная цена вычислений приходится на них.

**Всё можно остановить.** Каждый робот работает как служба systemd, поэтому `duck-sim down` — это `systemctl stop`, а не комбинация клавиш. Правило появилось после контейнера, который пришлось убивать из второго терминала: `Ctrl-]` на французской клавиатуре требует `AltGr + )`.

**Робот доступен по имени.** `duck-a`, `duck-b`, каждому — собственный machine-id. Поэтому `robotctl quack` у каждого звучит иначе: голос строится из серийного номера. Четыре робота в хорале не должны быть четырьмя копиями одного голоса.

<a id="2-where-the-seam-is"></a>
## 2. Где проходит граница

`duck_control::io::RobotIo` — шесть методов и единственное место, где разрешено существовать симулятору:

```rust
fn read(&mut self) -> Result<Sensors>;          // joints and IMU, one transaction
fn write(&mut self, targets: &JointTargets) -> Result<()>;
fn set_gain(&mut self, kp: u16) -> Result<()>;
fn set_torque(&mut self, on: bool) -> Result<()>;
fn slow_sensors(&mut self) -> Result<SlowSensors>;   // volts, per-joint temperature
```

Выше ничего не меняется: цикл 50 Hz, политики ONNX, `Safety`, обнаружение падения, одометрия, кинематика, maploc, все вызовы IPC, весь `robotctl` и `duckctl`. Ниже находится один компонент — `DynamixelIo`. IMU не отделён от него: на этом роботе он является узлом Dynamixel и читается тем же `sync_read`, что пятнадцать сервоприводов.

`FakeIo` уже полностью реализовывал этот trait, поэтому `cargo test` не требует оборудования. `RemoteIo` — третья реализация.

**Если служба датчика сама является его драйвером, не заменять ни службу, ни драйвер.** `tofd --fake` уже синтезирует кадры на уровне цикла; `tof/src/sensor.rs` прямо говорит, что внеплатный `Sensor` «не является фиктивным датчиком и никогда не должен им стать». Симулируемая глубина подаётся в существующий цикл. То же рассуждение применимо к любому драйверу, который нельзя отделить от оборудования.

<a id="3-the-body-protocol"></a>
## 3. Протокол тела

TCP, JSON с разделением переводами строк, один запрос и один ответ на вызов. Реализация и обоснование находятся в `duck_control::sim`; кратко:

* **TCP**, потому что Unix-путь ограничен `SUN_LEN` (около 108 байт), а симулятор должен быть доступен извне среды служб: из контейнера Linux или Linux VM с MuJoCo на хосте macOS.
* **JSON**, потому что такт — около 1 KB, то есть 50 KB/s, зато кадр можно прочитать через `nc`, а другую сторону написать двадцатью строками Python. Упакованная структура, разделяемая двумя репозиториями на двух языках, уже стоила проекту дней работы.
* **`TCP_NODELAY`** — не микрооптимизация: Nagle задерживает небольшую запись примерно до 40 ms, вдвое дольше такта; это выглядело бы как медленный симулятор.

Запросы: `{"op":"hello"|"read"|"write"|"gain"|"torque"|"slow", …}`. Рукопожатие содержит `protocol` (сейчас 1), проверяемый в обоих направлениях: стороны находятся в разных репозиториях, и иначе «старый симулятор» и «старая служба» давали бы одинаковый симптом.

**Симулятор сообщает данные в собственных единицах робота:** радианы, rad/s, mA и IMU, уже приведённый к системе корпуса. MuJoCo знает порядок, масштаб и системы координат своей модели; преобразование на этой стороне стало бы вторым местом, способным разойтись с первым.

**Упавший симулятор — один неудачный такт.** MuJoCo компилирует модель, поэтому смена количества роботов его перезапускает; роботы должны это переживать. Разорванное соединение возвращает вызывающему ошибку, а следующий вызов переподключается. Поток с задержками повторов не нужен: таймер повторных попыток — сам контур управления.

<a id="4-faking-the-radio-costs-nothing"></a>
## 4. Имитация радио не требует новой инфраструктуры

Присутствие уже выражено контрактом IPC на собственном сокете `robotd`: `chorale.subscribe`, `chorale.beacon` (что объявлять) и `chorale.heard` (что услышано, с *возрастом* вместо временной метки). `btd` — **клиент** robotd, а не сервер, поэтому симулируемый эфир никого не подменяет и не занимает чужой путь сокета. Один процесс держит соединение с каждым роботом, собирает объявления и доставляет остальным с RSSI, вычисленным по расстоянию между телами.

Изменений `robotd` и протокола нет, а для разработки появляются три преимущества перед настоящим радио: действительно проверяется синхронизация по возрасту; RSSI из истинных координат превращает границы дальности и асимметрию связи в параметры, а не задачу подготовки стенда; `from` определён только как идентификатор удаления дублей, поэтому его периодическая смена превращает стоившую дня ошибку ротации адреса в регрессионный тест.

<a id="5-the-radio-has-to-be-bad-or-the-bug-hides"></a>
## 5. Радио должно быть плохим, иначе ошибка скрывается

Идеальный эфир скрывает ошибки реального; это измерено, а не только предположено. Четыре робота-двойника всегда сходились к одной пьесе при одновременном и разнесённом запуске: каждый мгновенно и без потерь видел остальных. Единственное свойство, вызывающее ошибку на практике, симулятор как раз не моделировал.

`duck-ether --discovery <s> --loss <f> --seed <n>` делает радио плохим: чтобы робота *заметили*, требуется время, отдельно для каждой пары и с момента начала передачи; часть сообщений теряется. Раздельность по парам важна: стаю раскалывает асимметрия, а одна общая задержка её не воспроизведёт. Seed нужен, чтобы нестабильность повторялась и помогала отладке.

**Воспроизведение:** четыре робота, `a` и `b` начинают петь за двенадцать секунд до присоединения `c` и `d`:

```
duck-ether --discovery 90 --loss 0.3 --seed 3
```

Хорал ветки main:

| Робот | Партия | Такт | Состав |
|---|---|---|---|
| a | *Не поёт* | — | 1 в зоне действия |
| b | Бас | 4 | 3 голоса |
| c | Альт | 4 | 2 голоса |
| d | Бас | 2 | 2 голоса |

Это соответствует полевому сообщению «иногда ничего не происходит, иногда две разные песни», а также показывает разные составы и дублирующуюся партию.

**Чего это пока не доказывает.** После слияния `chorale-election` тот же сценарий всё ещё разделяется: такты 5, 12 и 8, три временные линии. Но при `--discovery 20 --loss 0.4` *оба* варианта сходятся. Девяносто секунд обнаружения жёстче условий, для которых писалась ветка; это не доказательство неработоспособности исправления на роботе. Полезный следующий эксперимент — перебор времени обнаружения, при котором каждая версия перестаёт сходиться. Теперь это цикл по числу, а не четыре робота в комнате.

<a id="6-architecture-follows-the-host"></a>
## 6. Архитектура следует за хостом

Все артефакты проекта — aarch64. Привлекательная идея: запускать собственные бинарники платы на x86-ноутбуке через `qemu-user`, сохраняя те же байты и безупречное происхождение. Два измерения дали противоположные результаты.

**Отдельная служба работает нормально.** Настоящий артефакт aarch64 из CI под эмуляцией на x86:

| | |
|---|---|
| `robotctl health` | `50.0 of 50.0 Hz · 3804 ticks · 0 missed` |
| CPU хоста | 4.7% одного ядра, загружены девять ONNX-сессий, политика управляет. |
| Инференс политики | 0.029 ms при такте 20 ms (измерено нативно). |

Пропускная способность не была риском; медленная часть настоящего такта — Dynamixel sync-read — здесь заменена локальным сокетом.

**Под systemd — нет.** В `systemd-nspawn` aarch64 systemd 257 запускается за 8.7 s, но затем не может запустить ничего:

```
robotd.service:            (code=exited, status=226/NAMESPACE)
systemd-journald.service:  (code=exited, status=243/CREDENTIALS)
systemd-logind, systemd-tmpfiles, console-getty: the same
```

qemu-user 8.2 не переводит новый mount API (`fsopen`, `move_mount`, `open_tree`), используемый systemd 257 для отдельных пространств имён и учётных данных служб. Именно защита каждой службы оправдывает загрузку контейнера вместо семи процессов в терминале; потеря её лишает подход смысла. Более новый qemu может исправить ситуацию, но в Debian 13 и Ubuntu 25.04 статические пакеты переходные, а настоящие бинарники динамически связаны: это вопрос сборки из исходников, а не команды apt.

Поэтому двойник использует **архитектуру хоста**:

* **Хост x86** — контейнер amd64 и нативная сборка. Настоящие службы, защита и журнал; всё, кроме точных байтов CI.
* **Хост arm64 (Apple Silicon)** — контейнер arm64 с собственным подписанным артефактом робота, нативно. Полное происхождение, без эмуляции, те же команды.

Последствие для обновлений небольшое, но его нужно назвать: `robotctl update apply` выполняется целиком — предварительная проверка, подпись, хеш артефакта, совместимость, проверка работоспособности и автооткат, — поскольку именно так устанавливает `dev-push.sh`. Двойник x86 не может установить *опубликованный* выпуск. Настоящий артефакт на реальной архитектуре уже проверяется `board-test.sh` в CI.

<a id="7-what-it-is-and-is-not-a-twin-of"></a>
## 7. Что двойник повторяет и чего не повторяет

Идентично, поскольку используется тот же код и путь: контур управления, политики, безопасность, обнаружение падения, кинематика, одометрия, maploc, весь IPC и клиенты, выбор лидера и ритм хорала, службы systemd с настоящими `User=`, группами, `RuntimeDirectory=` и защитой, а также обновлятор.

Моделируется — настоящий путь кода с синтетическим входом: отклик приводов (BAM, подогнанные к реальным XL330), IMU, глубина ToF, RSSI, изображение камеры и происхождение выпусков на x86.

Отсутствует и вообще не проверяется: драйвер Dynamixel, BLE-радио, ISP камеры и 3A rkaiq, NPU, аппаратный кодировщик и его путь RGA, тепловые процессы и батарея.

**Полезная проверка списка:** сопоставить его с неделей настоящих ошибок. `videoflip`, потерявший 22 fps из-за разрушения zero-copy пути кодировщика к RGA; движок 3A, пропустивший событие начала потока; автоэкспозиция, сходящаяся один раз и останавливающаяся; INT8-голова, чей канал оценок сводится к двум значениям; пропуски чтения шины сервоприводов. Двойник не нашёл бы **ни одной**. Это граница проекта, а не его недостаток: настоящие драйверы остаются только на оборудовании.

<a id="8-a-simulated-duck-is-a-duck-and-says-so-once"></a>
## 8. Симулируемый робот остаётся роботом и объявляет это один раз

Робот MuJoCo регистрируется в rendezvous и появляется рядом с настоящими в списке владельца Hugging Face. Это полезно: весь путь удалённого доступа проверяется без оборудования. Но симуляцию нужно явно отличать, иначе пользователь будет управлять ею и недоумевать, почему робот на полке неподвижен.

**Один факт, объявленный один раз.** Единственное место задания — `configd --simulated <serial>`. `system.info` передаёт факт; `mediad`, и так запрашивающий там имя при запуске, узнаёт его и добавляет `simulated: true` в регистрационные `meta`. `robotctl system info` его печатает. Ничто другое не делает вывод самостоятельно; в частности, клиент не распознаёт симуляцию по префиксу `sim-` серийного номера: пришлось бы согласовывать правило в трёх местах, и одно ошиблось бы.

`mediad --sim-camera` также задаёт признак. Это не второй источник истины, а защита конкретного случая: `configd` опрашивается один раз с таймаутом на машине, где службы стартуют одновременно; поздний ответ зарегистрировал бы симуляцию как оборудование. Два источника не могут противоречить: невозможно, чтобы кадры пришли из симулятора, а их робот был настоящим.

**Идентичность объясняет, почему флаг принимает значение.** У симулируемого робота нет SoC serial и отдельного `/etc/machine-id`. Четыре тела одной сцены разделяли бы идентификатор ноутбука и вытесняли друг друга из списка; в macOS файла вообще нет и не зарегистрировался бы никто. `sim-duck-a` стабилен для каждого робота и между запусками, как требует `hardware_id` (`remote-access-design.md` §3.7). Имя строится из него так же, как у реального робота: `duck-eb55`, а не hostname компьютера.

**Учётная запись подключается обычной процедурой робота, а не переданными заранее данными.** `updaterd` работает в симуляторе с `--token`, указывающим в каталог состояния; `robotctl account login` выполняет RFC 8628 с Hugging Face: код вводится на телефоне или в браузере, точно как на роботе. `mediad` опрашивает файл и регистрируется после его появления, поэтому вход посреди сеанса не требует перезапуска. Путь учётных данных не симулируется. В этом смысл: именно здесь проще всего допустить тонкую ошибку удалённого доступа и сложнее проверить её на плате.

Ограничение задаёт rendezvous, а не симулятор: участники идентифицируются по токену, поэтому одновременно в списке один робот на учётную запись. У каждого свой device flow; это правило учётных записей, не предел симулятора.

<a id="9-gstreamer-is-not-the-linux-part"></a>
## 9. GStreamer не является исключительно Linux-частью

Весь конвейер `mediad` был закрыт `#[cfg(target_os = "linux")]`. Это было верно, пока единственным источником была камера платы, и перестало быть верно после `Source::Sim`. Около 230 строк `pipeline.rs` действительно аппаратные: `v4l2src`, пул буферов драйвера, запрос выделения `GstVideoMeta`, режим сенсора из медиатопологии. Остальное — appsrc, tee, appsink, `webrtcsink`, сигнал encoder-setup — обычный GStreamer, работающий везде, где доступен GStreamer.

Поэтому условие — `any(target_os = "linux", feature = "gstreamer")`: подразумевается в ОС робота, включается явно в других системах. За две формулы Homebrew разработчик получает настоящие службу, консоль и WebRTC с симулируемой камерой; `Source::Camera` вне Linux даёт понятную ошибку, а не отсутствующую ветвь.

Формул две, не одна, и вторую ловушку стоит зафиксировать: Homebrew `gstreamer` ссылается на `libgstnice.dylib` из отдельной `libnice-gstreamer`, от которой не зависит. Без неё ссылка висячая, у `webrtcbin` нет ICE-агента, но всё остальное работает — конвейер, камера, регистрация rendezvous — до первого запроса pad потребителем. Затем сессия падает в потоке GStreamer с «libnice elements are not available». Проверка сборки этого не видит, поэтому `scripts/duck-sim` проверяет элементы, а не файл pkg-config. `exposure.rs` остаётся только для Linux не по причине упаковки: он записывает V4L2-контролы через `ioctl`, а за симулируемым источником нет сенсора для измерений.

Вне Linux возможность по умолчанию отключена намеренно: объединённая формула Homebrew `gstreamer` тянет gtk4 и ffmpeg, а разработчику `robotd` не следует требовать их ради `cargo check`. Цена — отсутствие CI-задачи, компилирующей эту комбинацию: все CI работают на `ubuntu-*`. Работоспособность поддерживают запускающие её разработчики. Это изменила бы задача `macos-latest` с `cargo check -p mediad --features gstreamer`, но она намеренно не добавлена: CI уже медленный, а runners macOS ещё медленнее.

<a id="10-the-harness"></a>
## 10. Среда запуска

Один процесс MuJoCo, одно окно, N тел роботов в одной сцене: они разделяют физику и могут сталкиваться. Эта половина принадлежит `microduck_rl`, где уже есть сцены, модели приводов BAM и mjlab; обслуживание тела для службы зеркально существующему sim2real.

Каждый робот — контейнер `systemd-nspawn`: без отдельной службы контейнеризации и формата образа, просто каталог. Он загружается из одного rootfs Debian 13 Trixie (`mmdebstrap`, без привилегий, 238 MB, менее трёх минут) с отдельным overlay. Каждый запускается как служба (`systemd-run --unit=duck-a …`), чтобы `duck-sim down` был `systemctl stop`: робот, которого нельзя остановить, мало полезен.

`machinectl shell duck-a` — вход внутрь, `duckctl open duck-a` — просмотр, `scripts/dev-push.sh microduck@duck-a` — установка сборки.

Два ограничения следуют из физики. **Роботы не добавляются на лету:** MuJoCo компилирует модель, поэтому смена количества перезапускает симулятор; потому `RemoteIo` и переподключается. **Предел масштабирования — камеры**, а не двуногие тела: N рендеров вне экрана на 30 fps дороже N тел с пятнадцатью степенями свободы. Камеры должны включаться отдельно для каждого робота. Порог здоровья 45 Hz делает предел жёстким: слишком много роботов не замедляются, а становятся *unhealthy*, и обновлятор начинает откатывать выпуски.

<a id="11-three-ways-to-pick-the-wrong-model"></a>
## 11. Три способа выбрать неправильную модель

Каждый выглядит как «робот лежит на спине» и каждый стоил часа.

**В `scene_walk.xml` нет столкновений.** Он включает модель обучения RL, чьи классы приводов по умолчанию имеют `contype="0" conaffinity="0"`. Робот проваливается сквозь действительно существующий пол: z корпуса меняется с 0.120 до -0.105 за секунду. Служба правильно сообщает лежащего робота. `scene.xml` включает `robot_allcollisions.xml` и подходит двойнику.

**`qpos0` — не поза.** Нули всех суставов дают конфигурацию, в которой этот робот никогда не находится. Служба измерила отклонение 0.41 rad от домашней системы и обоснованно попыталась поднять уже сложенного робота. В сценах есть `INIT`, `STAND`, `SIT`, `FOLD`; `STAND` соответствует `duck_control::DEFAULT_POSITION`, где правая нога *зеркальная*, а не симметричная. Это стоит прочитать, а не предполагать.

**Момент должен быть включён при старте.** `robotd` никогда не включает его при запуске: перезапущенная обновлением служба должна оставить стоящего робота стоять, его сервоприводы уже удерживают положение. Симулятор, начинающий с расслабленного тела, кладёт робота на пол до первого чтения.

Реально предусмотренная службой загрузка — `--keyframe SIT`: робот найден сложенным, распознаёт положение и поднимается политикой sitstand.

<a id="12-known-material-to-reuse"></a>
## 12. Известные материалы для повторного использования

В `~/MISC/microduck_maploc`, устаревшем во всём остальном, полезны две вещи: симулируемый VL53L5CX в `sim/tof_sensor.py` — зоны 8×8, квадратный угол 45°, дальность 4 m, растущий с расстоянием шум, 15 Hz — и `sim/assets/apartment.xml`, интерьерная сцена из 83 геометрических элементов. Для maploc, блуждания и всего, что прячется, комната намного полезнее плоскости пола.
