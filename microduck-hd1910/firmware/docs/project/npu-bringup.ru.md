# NPU и работающий на нём детектор утки

RK3566 имеет небольшой одноядерный INT8 NPU производительностью 0.8 TOPS. Это запись переноса обученного детектора утки на него: что запускать, чего ожидать и чего ещё не хватает, чтобы использовать его в поведении робота.

Модель обучается в [duck_detector](https://github.com/pollen-robotics/duck_detector) и поступает сюда в виде квантованного `.rknn`. Первая модель для справки: `yolo11n`, 320×320, один класс, 150 кадров из трёх сессий, mAP50 0.976 на отложенной сессии; после квантования INT8 — 3.9 MB. При настольной проверке сохранились 2 из 2 обнаружений с перекрытием рамок 95% относительно float-модели.

<a id="where-the-model-comes-from"></a>
## Откуда берётся модель

**Из Hub, как и политики управления.** `duck_detector` публикует каждый запуск в [`pollen-robotics/microduck-duck-detector`](https://huggingface.co/pollen-robotics/microduck-duck-detector): `duck_detect.rknn` для NPU и `duck_detect.onnx` для CPU-резерва, фиксированные имена в корне репозитория, отдельный тег для каждого запуска. Веса не хранятся в этом репозитории: `mediad` читает их из `/opt/robot/detector/current`, который наполняют:

| | |
|---|---|
| `scripts/seed-detector.sh` | Запускается postinstall-хуком выпуска; устанавливает версию из `[workspace.metadata.detector]` на пустую плату и не трогает набор, который установил не он |
| `robotctl duck-detector check` | Сравнивает установленное с доступным в репозитории |
| `sudo robotctl duck-detector update [--version <tag>]` | Устанавливает ревизию и перезапускает `mediad` с ней |

Это аналоги `seed-policies.sh` и `robotctl policy check/update` с другим корнем и фиксированным списком файлов, обслуживаемые теми же вызовами `updaterd` (`detector.check`, `detector.install`). Обоснование из `docs/design/policy-channel-design.md`, §9, применимо и здесь: закреплённая версия — нижняя граница, частичные наборы не становятся рабочими, переобучение публикуется тегом, а не выпуском службы.

Два уточнения. Репозиторий модели **называется так же, как репозиторий набора данных**; робот обращается только к модели (`…/resolve/<rev>/…`, `api/models/…`), а данные находятся под `datasets/`, поэтому случайно получить кадр вместо модели нельзя. «Самая новая» версия в `update` определяется **тегами версий** (`v2` выше `v1`, имя вроде `experimental` не учитывается). Запуску для роботов нужен тег `vN`: первый запуск имел тег `duck-v1`, на который ссылается закреплённая версия. Его можно установить по имени, но `check` не может ранжировать его как версию.

<a id="what-is-here"></a>
## Что находится здесь

| | |
|---|---|
| `duck-detect` | Letterbox-подготовка изображения, привязка среды выполнения и декодирование, а также `duck-bench`. |
| `scripts/setup-npu.sh` | Включает узел NPU, устанавливает `librknnrt.so` и сообщает сведения о драйвере. |

Два решения, которые полезно знать перед чтением:

**`dlopen` вместо линковки.** `librknnrt.so` — закрытая библиотека производителя, отсутствующая в Debian. Линковка с ней помешала бы кросс-компиляции crate в CI. `robotd` обращается к ONNX Runtime тем же способом. Цена — `duck-detect/src/rknn.rs`; преимущество — `cargo board --bins` продолжает работать на ноутбуке.

**Деквантование выполняет runtime.** Выходной тензор квантованной модели — int8 с масштабом и нулевой точкой. `rknn_outputs_get` по запросу преобразует его во float; такой запрос и используется. Альтернатива — передавать масштаб в декодер и однажды незаметно ошибиться.

<a id="running-the-benchmark"></a>
## Запуск измерений

Необходимое условие — драйвер: он входит в ядро производителя, в mainline его нет, и пользовательское ПО не может компенсировать отсутствие.

**Обычный `robotctl update` выполняет настройку.** `hooks/preinstall` запускает копию скрипта из выпуска рядом с `setup-gstreamer.sh` и `setup-rkaiq.sh`; ошибка не фатальна, отчёт попадает в журнал обновления. Поэтому плата, настроенная до появления поддержки NPU, исправляется обновлением, а не запоминанием ручной команды. Ручной запуск — повторная попытка:

```bash
sudo sh /opt/robot/daemon/current/scripts/setup-npu.sh
```

**Первое обновление с этой функцией, скорее всего, попросит перезагрузку.** Armbian поставляет `npu@fde40000` с `status = "disabled"` на каждой Radxa Zero 3. Поэтому стандартная плата имеет оборудование, ядро и драйвер, но NPU недоступен. Скрипт записывает исправляющий overlay и сообщает об этом; узел подключается при следующей загрузке. `--no-enable-node` устанавливает только runtime; затем состояние проверяют через `dmesg | grep rknpu`.

Запускайте копию из выпуска, а не `/usr/local/sbin/robot-setup-npu`: исходник overlay лежит рядом со скриптом, а у копии в `/usr/local/sbin` при первом запуске соседних файлов нет.

Затем из клона на своём компьютере:

```bash
cargo board --bins -p duck-detect
scp target/aarch64-unknown-linux-gnu/release/duck-bench microduck@<robot>:/var/tmp/
scp <the>.rknn microduck@<robot>:/var/tmp/duck.rknn
scp -r datasets/raw/<a-session> microduck@<robot>:/var/tmp/frames
```

`duck-bench` не входит в выпуск: это измерительный инструмент, и упаковка установила бы его каждому роботу ради двух человек. Его передают через `scp`, пока не появится поведение, использующее детектор; тогда поставляться будет детектор внутри `mediad`, а не этот инструмент.

```bash
/var/tmp/duck-bench --model /var/tmp/duck.rknn --frames /var/tmp/frames
```

Он отвечает на три вопроса в порядке важности:

1. **Запускается ли?** Незагружаемый runtime, модель для другой платформы или драйвер старше runtime обнаруживаются здесь, а не внутри службы.
2. **Продолжает ли видеть уток?** Выводится число обнаружений на кадр: модель, которая работает, но ничего не обнаруживает, внешне неотличима от исправной.
3. **Какова стоимость?** Перцентили задержки и CPU, затраченный *этим процессом*. Смысл NPU — не мешать циклу `robotd` на 50 Гц; это нужно измерять.

Сначала пробуйте флаг `--threshold`. **Оценки квантованной модели имеют собственную шкалу**: 0.5 float-модели не равно 0.5 этой модели. Поэтому отсутствие обнаружений вероятнее связано с порогом, чем с поломанным преобразованием. Попробуйте `0.2`, прежде чем предполагать худшее.

<a id="numbers"></a>
## Числа

Radxa Zero 3, `duck-bench` с ограничением 2 Гц, 30 кадров за 3 прохода:

| | Измерено | Примечания |
|---|---|---|
| Драйвер / runtime | 0.9.8 / 2.3.2 | `setup-npu.sh` выводит оба |
| Задержка p50 / p95 | 25.7 мс / 58.4 мс | Инференс и декодирование выходов, без декодирования JPEG |
| CPU на кадр | 20.7 мс | См. ниже: это не только инференс |
| Обнаружения | | По кадрам, уже размеченным человеком |
| Температура SoC | 63 °C | В конце запуска с ограничением частоты |

**Показатель CPU не равен стоимости NPU, хотя способ вывода подталкивает к такому прочтению.** Столбец задержки измеряет `infer` + `decode`; CPU — процессорное время всего цикла, делённое на число кадров. Он включает `letterbox_rgb`, пересчёт 1280×720 → 320×320 на CPU, вообще не входящий в задержку. Пока неизвестно, означает ли остаток активное ожидание в `rknn_run`, относящее ожидание NPU к CPU. При 2 Гц в любом случае это 4% ядра; прежде чем называть это ценой восприятия, части нужно измерить раздельно.

<a id="what-is-still-missing"></a>
## Чего ещё не хватает

У `mediad` есть сырая ветка tee именно для этой цели — `architecture.md`, §5.3. Два не исключающих друг друга пути:

- **`media.frame` — готово.** Вызов, возвращающий один кадр через собственный unix-сокет `mediad` (`/run/mediad/media.sock`), доступный группе на чтение, как другие сокеты наблюдений. Полезен не только для восприятия: снимок в консоли, изображение для отчёта об ошибке; сбор набора данных больше не требует останавливать `mediad` ради камеры. Ответ состоит из заголовка JSON-RPC с числом байтов и самих байтов: сырой кадр около 1.8 MiB не стоит кодировать base64 в ответе управления. Запрашивается *следующий* кадр tee, а не кэшированный, поэтому читатель не получает кадр, на котором остановилась камера.
- **Детектор внутри `mediad`:** подписаться на сырую ветку, исполнять модель с частотой несколько Гц и публиковать обнаружения в потоке состояния. Это конечное место: восприятие рядом с датчиком, передача признаков вместо пикселей. Именно это будет потреблять поведение робота.

Когда обнаружения станут состоянием, поведения из `docs/ideas/autonomous_behavior.md`, сейчас опирающиеся на Bluetooth («утка *поблизости*»), смогут опираться на зрение («утка *там*»): приближение, следование, поворот к другой утке и хор, в котором утки смотрят друг на друга во время пения.

<a id="taking-a-snapshot"></a>
### Получение снимка

На роботе `robotctl frame --output frame.uyvy` сохраняет один свежий упакованный кадр UYVY и выводит метаданные JSON в stderr: ширину, высоту, байты, время захвата и `rotate` — угол установки камеры по часовой стрелке относительно вертикали, тот же, что `media.video` сообщает WebRTC-партнёру. При преобразовании используйте эти размеры и поворот, например `ffmpeg -f rawvideo -pixel_format uyvy422 -video_size 1280x720 -i frame.uyvy -frames:v 1 -vf transpose=1 frame.png` для кадра 1280×720 с камеры, установленной на 90°. После смены режима или крепления нельзя предполагать прежние значения. Файл записывается только после получения полного ответа.

**Пиксели сохраняются как получены от датчика; `rotate` сообщается, но не применяется.** Конвейер перестал поворачивать кадры, поскольку `videoflip` лишал кодировщик zero-copy и стоил плате 22 кадра/с. Каждый потребитель поворачивает сам. Без `-vf` выше изображение будет боком без объясняющей причины — именно это предотвращает `rotate`. Он равен `0`, когда `--flip-in-pipeline` уже выполнил поворот.

В браузере локальной сети робота откройте `http://<robot>:8080/frame` либо сохраните через `curl --fail http://<robot>:8080/frame -o frame.png`. Возвращается **правильно ориентированный** PNG с `Cache-Control: no-store`. Этот маршрут — исключение из предыдущего абзаца: PNG негде передать угол. При повороте на четверть оборота ширина и высота меняются местами относительно геометрии захвата, а затрата — один поворот на запрос вместо каждого кадра. Остановленная или недоступная камера возвращает HTTP 503, а не последнее хорошее изображение. PNG сохраняет преобразование RGB без JPEG-сжатия; это не побайтовая замена сырым UYVY. Граница доступа та же локальная сеть, что у консоли и видеопотока; отдельной аутентификации маршрута нет.

Локальный endpoint поддерживает `hello`, затем `media.frame` в одном соединении. Сокет настраивается через `mediad --frame-socket <path>` и `robotctl --media-socket <path> frame`. Невозможность занять сокет останавливает запуск; существующий файл или активный слушатель сохраняется. Допускаются максимум 16 локальных соединений по пять секунд и четыре задания HTTP-снимков. HTTP-захват ограничен тремя секундами, метаданные ответа — 4 KiB. Оба клиента отклоняют неверную геометрию и данные свыше 16 MiB.

У `media.frame` намеренно нет маршрута `Call`/служебной линии: за JSON-заголовком идёт двоичный хвост. Ни канал управления WebRTC, ни текущий BLE-транспорт `duckctl` не передают снимки. Используйте локальный сокет или HTTP-маршрут консоли; удалённое видео — отдельный транспорт. Будущий общий помощник управления группой сокета может заменить дублирующийся код владельца, не связывая эту функцию с рефакторингом нескольких служб.
