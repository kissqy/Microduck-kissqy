# Удалённый доступ: учётная запись и посредник

Статус: черновик · Дата: 2026-09-02 · Ответственный: pierre

Как связаться с роботом из-за пределов локальной сети. В §7 [`remote-webrtc.md`](remote-webrtc.ru.md) верно описана общая схема: мост между службой-посредником и уже работающим на роботе сервером сигнализации. Здесь рассматриваются два недостающих элемента этой схемы: **учётные данные, обозначающие учётную запись**, и **служба, которой их предъявляют**.

**Что уже реализовано** (2026-09-02): §2 — учётная запись. Вызовы `account.login`, `account.status` и `account.logout` обслуживает `updaterd`; они доступны локально, через BLE и канал данных WebRTC. `robotctl account login` выводит код и ожидает, `duckctl account login` выводит код и завершает соединение. Учётные данные сохраняются в `/etc/robot/hf-token` и обновляются автоматически. Пока их ничто не использует — этим займётся §3, следующий этап.

Что **установлено** проверкой служб, от которых зависит решение, а не чтением их документации:

- **Hugging Face поддерживает OAuth Device Grant**, а `huggingface_hub` предоставляет для него **официальный публичный клиент** (`DEVICE_CODE_OAUTH_CLIENT_ID`). Регистрировать OAuth-приложение не нужно. См. §2.3.
- **Токен действует 30 дней**, выдаётся с refresh-токеном, который **меняется при каждом обновлении**. Последствия описаны в §2.7.
- **Токен получает все права, которые выдаёт Hugging Face**: `write-repos`, `manage-repos`, `jobs`, `read-billing`, поскольку официальный клиент не принимает параметр `scope`. См. §2.4: перед выпуском робота это следует изменить.
- **`/oauth/userinfo` возвращает идентификатор за один запрос**, так что декодировать JWT не требуется.
- **Посредник находится под нашим контролем**: это `pollen-robotics/reachy_mini_central`, приложение FastAPI в Space, код которого мы можем читать и изменять. Всё сказанное ниже в §3 и §4 основано на его серверном коде, а не на догадках по клиенту.
- **Его протокол — не протокол сигнализации gst через WebSocket.** Используются те же JSON-конверты, но поверх **HTTP**: входящие сообщения через SSE, исходящие через `POST`, заголовок `Authorization: Bearer` и идентификаторы участника и сеанса на каждом переходе. Это исправляет утверждение в §7 `remote-webrtc.md`; цена исправления рассмотрена в §3.2.

<a id="1-what-has-to-be-true-for-a-duck-to-be-reachable"></a>
## 1. Что нужно, чтобы робот стал доступен

Четыре вещи, которых у робота пока нет:

1. учётные данные, обозначающие учётную запись владельца (§2);
2. служба, к которой робот обращается **сам**, показывающая его только владельцу (§4);
3. мост от этой службы к `ws://127.0.0.1:8443` (§3);
4. клиент, работающий по протоколу службы и размещённый там, откуда он доступен (§5).

Дополнительно нужен обход NAT: это свойство медиапути, а не какого-либо из четырёх компонентов (§6).

Одно обязательное правило ограничивает все четыре: **локальный режим не должен зависеть ни от одного из них.** Первый инвариант `architecture.md` сохраняет независимым локальное восстановление; §7 `remote-webrtc.md` распространяет его на медиа: при недоступности службы клиент в LAN по-прежнему подключается. Ниже не раз выбирается более сложный вариант, чтобы не проводить через службу также локальные сеансы; конкретная цена видна в §3.1.

<a id="2-the-account-is-an-oauth-device-flow-against-hugging-face"></a>
## 2. Учётная запись: OAuth Device Flow Hugging Face

**Протокол входа реализован в отдельном репозитории [`hf-robot-account`](https://github.com/pollen-robotics/hf-robot-account)**, поскольку он не зависит от Microduck: любой робот без браузера выполняет вход одинаково. В `updater/src/account.rs` остаётся только относящееся *к этому* роботу: путь токена, группа `robot`, отображение на `proto` и код JSON-RPC для каждого отказа. Далее описание самого процесса относится к этому крейту; хранение и доступ к учётным данным — к данному репозиторию.

<a id="21-why-the-device-grant-which-is-also-where-reachymini-ended-up"></a>
### 2.1 Почему Device Grant, к которому пришёл и `reachy_mini`

У `reachy_mini` есть **оба** варианта. Изначально он использовал Authorization Code + PKCE с перенаправлением обратно на HTTP-сервер робота — `http://reachy-mini.local:8000/api/hf-auth/oauth/callback` либо `localhost` для подключённого кабелем варианта. Позднее добавили Device Code Flow, названный в исходниках «входом с обновляемым токеном без перенаправления»; теперь его использует мастер настройки мобильного приложения. Причины — две следующие. Это не спор двух подходов: к одному выводу пришли независимо.

Перенаправление несёт три издержки:

- **Зарегистрированный URI перенаправления для каждого имени хоста.** У приложения такой URI только один, поэтому мобильное приложение содержит локальный HTTP-мост: он принимает callback HF на `127.0.0.1:8000` и переправляет его ответом 302 на собственную схему `reachymini://`. Назначение целого компонента — избежать изменения настроек на стороне HF (`features/auth/oauthLoopback.ts`).
- **Браузер должен найти робота и соединиться с ним.** Callback указывает URL *на роботе*. Поэтому для входа нужно быть в его сети с работающим mDNS: это тот же класс проблемы, которому §2 `webrtc-console.md` посвящает целый раздел при открытии страницы.
- **Это браузерный процесс на устройстве без браузера.** Подлинность подтверждает не робот; он лишь предоставляет точку возврата.

Device Grant меняет направление: робот запрашивает у HF код, сообщает *«открой hf.co/oauth/device и введи M8HJ-FMGN»* и опрашивает сервер, пока кто-то не сделает это. Не нужны URI перенаправления, имя хоста и даже сетевая доступность робота для устройства подтверждения — подойдёт телефон в сотовой сети. Этот протокол создан для устройств без браузера и клавиатуры, к которым относится Microduck. Кроме того, только он из двух даёт **refresh-токен**, позволяющий роботу оставаться доступным дольше первого месяца (§2.7).

Цена проста: человек вводит восемь символов. Это меньше, чем зависимость от mDNS, которую такой способ устраняет.

**Три инварианта, перенятых из мастера `reachy_mini`**, не зависят от Python и извлечены из ошибок на практике:

- **Сначала показывать код. Открывать ли браузер — свойство интерфейса, а не общее правило.** Приложение Mini выяснило, что автоматическое переключение на Safari скрывает код до того, как его прочтут. Но это *телефон*: браузер заменяет единственный экран и уводит приложение в фон. В терминале код остаётся в истории вывода; поэтому ответы для трёх интерфейсов различны:

  - `robotctl account login` ничего не открывает: команда работает **на роботе** без дисплея. Она печатает код и ждёт.
  - `duckctl account login` печатает код и *затем* открывает страницу: команда работает на компьютере пользователя, где `duckctl open` уже запускает браузер. `--no-open` подавляет это действие; браузер также не открывается, если stderr не терминал, потому что скрипт не должен неожиданно показывать окно. Неудачный запуск браузера добавляет предупреждение после кода, а не подменяет код ошибкой.
  - Телефонное приложение сохраняет правило Mini по той же причине.

  **Открытие страницы помогает перейти к ней, а не автоматически ввести код.** Раньше этот раздел утверждал, что робот может передать URL с кодом: в документации настройки Mini было сказано, будто `huggingface_hub` создаёт форму `?user_code=`. На самом деле библиотека без изменений использует `verification_uri`, а страница HF игнорирует этот параметр; это проверили в браузере после реализации. Сейчас `verification_uri_complete` — обычный адрес страницы. Поле оставлено в ответе на случай, если сервер позже начнёт выдавать настоящий полный URL: протокол менять не придётся.
- **Исчезновение клиента посреди процесса — нормальное событие.** Когда на телефоне открывается страница HF, приложение уходит в фон, и iOS разрывает GATT-соединение. К тому моменту транспорт свою задачу выполнил: демон опрашивает HF, а вернувшийся клиент проверяет `status`. Поэтому `login` отвечает кодом, а не токеном; цикл ожидания `robotctl` тоже не должен быть критическим для завершения входа.
- **Появление робота у посредника — единственный настоящий признак успеха.** Сохранённый токен доказывает успешный *вход*, но не доступность робота. Мастер Mini считает задачу законченной, когда в списке появляется робот с его аппаратным идентификатором; прочие состояния считаются восстанавливаемыми. Проверку надо предоставить и здесь через §3; состояние релея должно войти в ответ `account.status`.

<a id="22-the-flow-and-the-transcript-it-was-built-from"></a>
### 2.2 Процесс и протокол наблюдений, на котором он основан

```
POST https://huggingface.co/oauth/device
     client_id=26be6b09-91c5-47da-9861-d2d2bb7a7e36

  → {"device_code":"41ad39ae-…","user_code":"A6MY-0314",
     "verification_uri":"https://hf.co/oauth/device","expires_in":300}

POST https://huggingface.co/oauth/token
     grant_type=urn:ietf:params:oauth:grant-type:device_code
     &client_id=26be6b09-…&device_code=41ad39ae-…

  → HTTP 400 {"error":"authorization_pending"}      until somebody approves it
  → {"access_token":"…","refresh_token":"…","expires_in":2591999,
     "token_type":"bearer","id_token":"…","scope":"manage-repos write-repos …"}

GET  https://huggingface.co/oauth/userinfo   Authorization: Bearer <access token>
  → {"name":"Rouanet","preferred_username":"PierreRouanet","orgs":[…], …}
```

Параметр `scope` не передаётся: официальный клиент его не принимает (§2.4). Этот протокол наблюдений отвечает на пять вопросов, которые больше не нужно решать предположениями:

- **Нет `verification_uri_complete`, и создать его искусственно нельзя.** URL с кодом не существует: страница HF игнорирует `?user_code=`. Человек обязан *прочитать код*, поэтому показывать его должен **клиент**, а не демон. Пока в соответствующем поле передаётся обычный `verification_uri`; если сервер позже выдаст полный адрес, изменений не потребуется.
- **Нет `interval`.** Применяются пять секунд по RFC 8628; `slow_down` прибавляет ещё пять.
- **`expires_in: 300`** относится к *коду*. Пять минут дают время без спешки, но клиенту полезно видеть остаток; поэтому `account.status` отсчитывает его, а не повторяет исходное число.
- **`expires_in: 2591999`** относится к *токену*; вместе с ним выдаётся `refresh_token`. См. §2.7.
- **`/oauth/userinfo` возвращает личность одним запросом**: `preferred_username` — имя учётной записи, а `name` — произвольное отображаемое имя. Сохраняется и показывается первое. Альтернативой было бы декодирование `id_token` с парсером JWT и загрузкой JWKS ради той же строки.

  **Это последний и наименее важный запрос, поэтому его неудача не должна обрывать вход.** К этому моменту человек уже ввёл код на телефоне. Удалять токен из-за ответа прокси 502 означало бы заставить его повторить весь процесс ради подписи. Запись сохраняется без имени; `account.status` отвечает `unknown`, а не «вышел», следующий цикл `maintain` заполняет поле. От сети, вызвавшей сбой, именно эта плата и зависит.

**Одновременно выполняется один вход; блокировка охватывает сетевой запрос, а не только предварительную проверку.** При одновременном обращении консоли и телефона, обычном во время настройки, иначе оба получили бы код, а хранилище оставило бы последнюю подтверждённую запись. Кто-то наблюдал бы за бесполезным первым кодом. Второму вызывающему возвращается `BUSY` со своим сообщением: в другом месте `BUSY` означает «уже идёт обновление», что направило бы пользователя искать не там. `account.status` содержит текущий код, и потерявший его клиент может присоединиться к процессу, а не начинать новый.

**Отказ должен указывать путь продолжения; здесь для этого тоже служит `force`.** Код, который никто не собирается подтверждать, иначе блокирует робот на пять минут. Раньше можно было только вызвать `logout`, удалив работающие учётные данные ради отмены незавершённой попытки. `force` уже означает «заменить владельца робота»; замена *попытки* сделать это — те же полномочия в меньшем масштабе.

**Издержка: у оставленного процесса сохраняется действующий код устройства**, который Hugging Face подтвердит, если кто-то всё-таки до него дойдёт. Процесс выполняется в задаче дольше вызова, запустившего его, поэтому то же верно для `logout`: выход с уже выданным кодом и подтверждение через минуту самопроизвольно вернули бы вход. Каждая попытка хранит номер поколения, с которым началась, и проверяет, что он всё ещё текущий, до доступа к хранилищу и ещё раз после него, потому что запись требует ожидания. Устаревшая попытка сохраняет выданный код, но отбрасывает результат. Это позволяет `logout` выполнять своё обещание.

<a id="23-the-oauth-client-is-hugging-faces-own--closed"></a>
### 2.3 OAuth-клиент принадлежит Hugging Face — **вопрос закрыт**

`huggingface_hub` содержит **официальный публичный клиент Device Code**, `DEVICE_CODE_OAUTH_CLIENT_ID` = `26be6b09-91c5-47da-9861-d2d2bb7a7e36`; его использует `hf auth login`. Клиент публичный — секрет не нужен, а в выпуск включается только публичный идентификатор. Регистрировать OAuth-приложение нигде не требуется. Константа `hf_robot_account::HUGGINGFACE_CLIENT_ID` и есть итог этого решения.

Зафиксированы две альтернативы; первая выглядит очевидной, но недоступна:

- **Собственное приложение `reachy_mini`** (`71146982-…`) — **конфиденциальный** клиент, поэтому endpoint устройства отказывает ему: *«если вы хотите использовать Device Code Flow без секрета клиента, удалите секрет из OAuth-приложения, сделав его публичным»*. Вшитый во всех роботов секрет перестал бы быть секретом, а перевод приложения в публичный режим изменил бы модель безопасности Mini ради нас.
- **Динамическая регистрация.** `POST /oauth/register` не требует авторизации и принимает `token_endpoint_auth_method: "none"`, поэтому робот мог бы создать своего публичного клиента при первом входе. Это работает, но пока бессмысленно: один клиент на робота создал бы парк идентификаторов, который нельзя перечислить или отозвать.

<a id="24-the-scopes-are-not-ours-to-choose-and-that-is-the-thing-to-fix-before-shipping"></a>
### 2.4 Права токена не выбираем мы; это нужно исправить до выпуска

Официальный клиент **не принимает параметр `scope`**, и выданный токен получает все права, предоставленные Hugging Face:

```
manage-repos write-repos read-repos gated-repos contribute-repos write-collections
read-collections openid write-discussions inference-api jobs webhooks read-billing read-mcp
```

Таким образом, робот хранит учётные данные, позволяющие **отправлять изменения в репозитории владельца, запускать Jobs и читать платежные данные**, хотя их цель — лишь подтвердить личность службе-посреднику. У всех установленных Reachy Mini та же ситуация; это контекст, а не оправдание.

Учётной записи действительно нужны `openid profile`, а также `read-repos` для одной реальной задачи: доступ `policy.install` к **приватному** репозиторию политики через тот же файл токена без нового механизма (§7 `policy-channel-design.md`).

**Поэтому ограниченный вариант — публичный Device Code-клиент, принадлежащий Pollen, с `openid profile read-repos`**. Понадобятся один `Config::client_id` и действие администратора организации HF. Это не блокирует нынешнюю работу: вход уже работает, а смена прав потребует повторного входа. Но изменить их следует до передачи робота пользователю: прежнее право записи, которым можно было воспользоваться, нельзя отменить задним числом, а если позже понадобятся более широкие права, робот просто запросит их.

<a id="25-where-the-token-lives-and-who-writes-it"></a>
### 2.5 Где находится токен и кто его записывает

`/etc/robot/hf-token`, `root:robot`, `0640`. Файл JSON содержит access-токен, refresh-токен, абсолютное время `expires_at` (ответ даёт относительную длительность, бесполезную после перезагрузки) и имя пользователя. Поэтому `account.status` отвечает без сети: робот и в офлайне знает, кому принадлежит.

**Сначала файл создаётся с `0600`; после установки группы права расширяются до `0640`**, в отличие от остальных записей этого демона через `fsutil::write_atomic`. Вспомогательная функция не выставляет режим, поэтому созданный с `0644` и мгновением позже исправленный файл какое-то время доступен всем. Такое окно незаметно при тестировании, но его последствия навсегда останутся после `ps` и `cat`. `account::write_private` использует то же атомарное переименование, открывая временный файл сразу с `0600`; тест проверяет отсутствие прав у «others». Если на плате нет группы `robot` — на ноутбуке разработчика или ещё не подготовленной плате — файл остаётся доступным только root, о чём выдаётся однократное сообщение, без догадок.

**Не в `robotd.toml`.** Каждый существующий способ работы с этим файлом неприемлем для секрета: `robotctl configure --list` печатает изменённые настройки; полноэкранный редактор из `policy-channel-design.md` показывает файл; теперь создаётся отчёт «что изменено на этом роботе». Bearer-токен попал бы во все три вывода. Отдельный файл с собственным режимом доступа — вся предусмотренная защита; §7 объясняет, почему её достаточно.

**Файлом владеет `updaterd`.** У него уже есть HTTP-клиент, он уже выходит в сеть от имени робота, работает как `root` и имеет вызовы, меняющие системное состояние (`policy.*`). `configd` владеет *конфигурацией*, не содержит HTTP-клиента; внешний сетевой доступ для демона, отвечающего на `system.info`, был бы новой ролью. `mediad` не должен владеть токеном: он работает от `User=mediad` под `ProtectHome=yes` и общается с удалённым участником.

**`mediad` будет читать файл** при каждой попытке подключения и при медленном опросе (30 s), пока токена нет; это же состояние `waiting for token`. Пока не реализовано: до появления §3 токен никто не использует. Междемонное уведомление не нужно. У `reachy_mini` роутер авторизации вызывает `notify_token_change` у релея, но здесь достаточно повторно прочитать файл при неизбежном переподключении. Новый вход сможет превратиться в активного производителя с задержкой до одного интервала опроса, незаметной пользователю.

<a id="26-the-calls-and-which-transports-may-reach-them"></a>
### 2.6 Вызовы и доступные для них транспорты

`account.login`, `account.status` и `account.logout` обслуживает `updaterd` по тем же причинам, что и `policy.*`: у демона есть сетевой стек, `robotctl` не должен его подключать (он нужен для восстановления), а сохранённый токен позволяет добраться и до приватного репозитория Hub — это уже задача `updaterd`. `configd` владеет *конфигурацией*, а не учётными данными, и не имеет HTTP-клиента. `mediad` не должен владеть токеном: это непривилегированный процесс с `ProtectHome=yes`, взаимодействующий с удалёнными участниками.

**`login` отвечает кодом и передаёт ожидание демону.** Нет уведомлений о прогрессе или долго открытого соединения; клиент опрашивает `status`. Это не упрощение, а требование второго инварианта §2.1.

**Все три вызова доступны через все три транспорта:** локальный, BLE и канал данных WebRTC. BLE особенно важен и очевиден: только он достигает робота сразу после распаковки, когда сети, консоли и LAN для её открытия ещё нет; в этом же месте находится мастер настройки. Локальный способ — `robotctl`, инструмент разработчика для остальных действий.

**Доступ через WebRTC требует отдельного обоснования.** Кнопка «войти» естественна для консоли, где робот уже показан на странице; альтернатива — SSH или телефон. Но это единственный вызов этого транспорта с **долговечным последствием**. Действия других клиентов LAN ограничены сеансом; `account.login` превращает *однократное присутствие в Wi-Fi-сети* в удалённый доступ даже после ухода из неё. §4 `remote-webrtc.md` допускает, что любой в этой сети получает доступ к роботу и камере, но не рассматривал возможность сохранить его на следующий месяц из другого континента.

Приемлемость этого решения обеспечивают три свойства:

- **Робот с существующим владельцем отказывает.** `account.login` без `force` возвращает `INVALID_PARAMS` с именем владельца. Клиент LAN не может незаметно забрать робота: он должен явно заявить об этом, а корректный клиент — сначала спросить человека.
- **Владение видно.** `account.status` сообщает имя учётной записи через любой транспорт без авторизации. На вопрос «чьей учётной записи принадлежит робот?» может ответить любой.
- **Доступ можно отозвать** через `account.logout` с любого транспорта или через отзыв разрешения в Hugging Face, чего роботская проверка сама обеспечить не могла бы.

  Первое действие имеет две части, и только одна принадлежит `updaterd`. `logout` удаляет токен, релей замечает это не позже следующего heartbeat — через десять секунд — и разрывает соединение, после чего служба сразу удаляет производителя из списка. Робот, вышедший из учётной записи, перестаёт показываться и быть доступным. Но **`logout` лишь удаляет копию токена на роботе и ничего не сообщает Hugging Face**. Робот перестаёт быть производителем — желаемый эффект выхода, однако прежний access-токен остаётся действительным в HF до истечения срока, вплоть до тридцати дней, для любого, кто уже прочитал файл. Права файла — `0640 root:robot`, то есть «любой» здесь означает root или `mediad` на этой плате. При краже платы ответ — страница подключённых приложений на hf.co, а не локальный вызов. Отправка запроса отзыва с робота остаётся кандидатом для §9: сначала нужно проверить endpoint с официальным клиентом, а не предполагать его работу. Кроме того, `logout` обязан удалить токен локально, даже когда сеть недоступна.

**Последствие в другом файле позволило найти ошибку.** `account.login` и `account.logout` помечены `Call::is_mutating`; `updaterd` сверяет такие вызовы с UID клиента. Поэтому `mediad` пришлось добавить в `allow_users` файла `deploy/updater.toml` рядом с `btd`.

**Следует точно понимать объём этих полномочий: он шире учётной записи.** `allow_users` ограничивает *вызывающего*, а не метод. Теперь `updaterd` выполнит любой изменяющий вызов `mediad`, включая `update.apply`. Удалённому участнику применить обновление не позволяет лишь таблица маршрутизации `mediad`, которая отказывается его пересылать. Это не одна из нескольких проверок, а единственная проверка процесса, наиболее открытого для стороннего трафика. С BLE ситуация такая же с момента, когда через него стало можно применить обновление. Защита там и здесь — явный список с тестом `mediad::route` `only_these_mutating_calls_are_reachable_over_webrtc`: чтобы провести новый изменяющий метод, список нужно сознательно изменить и объяснить причину. Пооперационная проверка в `updaterd` дала бы второй слой, но пока не реализована; этот документ фиксирует сознательное решение.

При описании обнаружились два ранее не замеченных неработающих метода: **`policy.install` и `policy.fetch` были доступны через WebRTC, но `mediad` не входил в `allow_users`**, поэтому `updaterd` отвечал `PERMISSION_DENIED`. Консоль могла показать каталог политик Hub, в котором кнопка установки не работала. Строка `allow_users`, добавленная для учётной записи, исправила и их. Вот зачем нужен список имён, а не простое число: именно он заставляет явно согласовать полномочия транспорта и настройки файла.

<a id="27-the-token-expires-in-30-days-and-the-refresh-token-rotates--closed"></a>
### 2.7 Токен действует 30 дней, refresh-токен меняется — **вопрос закрыт**

Device Code-токен выдаётся с `expires_in: 2591999` — тридцать дней — и с `refresh_token`. Обновление **заменяет** refresh-токен: ответ содержит *новый*, а прежний перестаёт действовать. Поэтому хранилищу нужны две строки и отметка времени; последствия три.

**Оставленный включённым робот должен обновлять токен самостоятельно.** `hf_robot_account::maintain` просыпается каждые шесть часов и обновляет токен, если до истечения меньше недели. Это примерно три четверти срока действия и ещё неделя на повторные попытки при нестабильной сети. Задача запускается безусловно, в отличие от планировщика обновлений: робот с отключёнными проверками обновлений всё равно имеет учётную запись, которая через месяц перестала бы работать.

**При замене остаётся окно, которое нельзя закрыть.** Между выдачей Hugging Face новой пары и записью её на диск старый refresh-токен уже недействителен. Отключение питания в этот момент оставит робот с учётными данными, которые HF не обновит. Порядок записи не поможет: замена произошла на стороне HF. Поэтому сбой обрабатывается, а не предотвращается: запись атомарна (читатель видит старую или новую пару целиком), ошибка доступна в поле `last_error` ответа `account.status`, исправление — повторный вход. Обновление за неделю до срока превращает проблему в неудобство, а не в немедленную потерю доступа.

**Робот, выключенный более чем на тридцать дней, после включения потребует входа**, и никакой запас срока здесь не поможет. `account.token_expires_in` становится отрицательным, позволяя клиенту прямо сообщить причину отсутствия робота.

<a id="3-the-bridge"></a>
## 3. Мост

<a id="31-a-listener-on-loopback-not-a-signaller-inside-webrtcsink"></a>
### 3.1 Слушатель на loopback, а не сигнализатор внутри `webrtcsink`

`webrtcsink` допускает собственный сигнализатор через интерфейс `Signallable`. Возникает соблазн реализовать прямое подключение к протоколу посредника: на один переход меньше, нет преобразования идентификаторов и локального клиента WebSocket. **Этот вариант отвергнут** по структурной, а не эстетической причине: у одного `webrtcsink` один сигнализатор. Направить его на внешнюю службу — значит заставить локальные сеансы проходить через неё и нарушить инвариант §1. Сохранить оба пути через второй `webrtcsink` после ответвления — значит дважды кодировать одни кадры на плате, где кодировщик уже ограничивает возможности.

Поэтому используется мост, описанный в §7 `remote-webrtc.md` и реализованный в `reachy_mini`:

```
  rendezvous  ──SSE──►  relay task  ──ws──►  127.0.0.1:8443  ◄──ws──  webrtcsink
  (HTTP)      ◄─POST──  (in mediad)  ◄──ws──  signalling server      (the producer)
```

Релей регистрируется у внешней службы как **`producer`**, а у локального сервера как **`listener`**. Роли на сторонах противоположны: для службы релей *представляет* робота, а для конвейера это участник, запрашивающий сеанс.

<a id="32-what-it-translates-and-the-correction-to-7"></a>
### 3.2 Что преобразуется и исправление §7

В §7 сказано: «мост ничего не разбирает; он пересылает протокол сигнализации gst, по которому говорит клиент LAN». Полезная нагрузка — SDP и ICE — действительно непрозрачна и такой остаётся. Обёртка отличается по трём направлениям:

| | Локальная сторона | Сторона посредника |
|---|---|---|
| транспорт | WebSocket | входящие SSE, исходящие `POST /send` |
| авторизация | отсутствует (§4 `remote-webrtc.md`) | `Authorization: Bearer <hf token>` |
| идентификаторы | свои `peerId` и `sessionId` | другие для каждого перехода |
| наша роль | `listener` | `producer` |
| где приходит ответ | всегда в сокете | **`sessionStarted` и `list` в теле ответа `POST`**; всё остальное — в потоке |

Последняя строка стоила половины рабочего дня и должна оставаться в таблице, а не в чьей-то памяти. В WebSocket ответы приходят в сокет, поэтому отправку естественно считать действием без отдельного результата. Здесь `handle_start_session` *возвращает* `{"type":"sessionStarted","sessionId":…}` вызывающему `POST /send`: производитель получает уведомление по SSE, потребитель — ответ HTTP. Страница, отбросившая тело ответа, получала от робота предложение сеанса, идентификатор которого ей не сообщили, и падала из-за пустого peer connection. `list` возвращается так же и *дополнительно* передаётся в поток после приветствия: список выглядел исправным, пока сеанс не работал.

Поэтому мост хранит двунаправленную таблицу сеансов и переписывает `sessionId` в каждом сообщении `peer`. Релей `reachy_mini` накопил больше всего обходных решений именно здесь (§3.4). Точное описание — **преобразователь с непрозрачной полезной нагрузкой**, а не простой релей. Довод §7 за `webrtcsink` вместо `webrtcbin` сохраняется: готовый протокол есть, его не нужно изобретать, а преобразование ограничено таблицей, не парсером. Но говорить «просто пересылает, ничего не разбирая» больше нельзя.

<a id="33-the-lease-and-why-the-heartbeat-is-not-optional"></a>
### 3.3 Аренда соединения и обязательный heartbeat

Служба удаляет производителя, от которого не приходят сообщения в течение `LEASE_SECONDS`, независимо от состояния его сокета. Это не излишняя перестраховка: полуоткрытое TCP-соединение после потери Wi-Fi, переназначения NAT или засыпания captive portal способно минутами молча поглощать отправляемые сервером keepalive. Робот считает себя доступным, хотя это не так.

Числа взяты из сервера: `PRODUCER_LEASE_SECONDS` равно **30**, а приветственное сообщение SSE объявляет `recommended_heartbeat_interval_seconds: 10.0`. Время аренды обновляет *только* входящий `POST /send`; внешне здоровый поток SSE ничего не продлевает.

Поэтому релей повторно отправляет `setPeerStatus` с частотой из приветствия. При отсутствии значения применяется 5 s; интервал ограничен диапазоном [1 s, 60 s], чтобы неверная настройка службы не вызвала лавину запросов и не заставила выбрать интервал длиннее собственного срока удаления. У `reachy_mini` есть промежуточная ступень — `lease_seconds / 3`, когда сервер сообщает срок аренды, но не частоту. **Этот сервер не сообщает `lease_seconds`**, поэтому здесь такая ступень недостижима; незачем воспроизводить согласование поля, которое никто не передаёт.

**`POST /send` до `GET /events` возвращает 400, поэтому порядок обязателен.** Пока нет потока, не существует и участника: личность устанавливается из bearer-токена, который привязывается к участнику соединением `/events`. В §3.4 регистрация перед объявлением доступности требовалась по другой причине; служба обеспечивает тот же порядок по собственным правилам.

**Ограничение частоты — 1200 запросов за 60 s на участника**, по скользящему окну. Heartbeat каждые 10 s и опрос каждые 30 s составляют девять запросов в минуту; здесь предел не срабатывает. Но его нужно знать, прежде чем кто-то укоротит интервал «для надёжности».

**Для входящего SSE есть собственный keepalive.** Через 30 s без сообщений сервер посылает `event: ping`; единственная цель — не позволить HTTP/2-прокси перед Space закрыть простаивающее соединение. Тайм-аут чтения у нас должен быть заметно больше 30 s. `reachy_mini` использует 60 s, то есть допускает две пропущенные отметки; следует взять это значение.

<a id="34-the-failure-modes-are-already-known-which-is-the-main-reason-to-read-their-relay"></a>
### 3.4 Режимы отказа уже известны; поэтому полезно читать их реализацию релея

Описанные случаи дешево учесть сейчас и дорого обнаруживать заново:

- **Раздвоение состояния.** Поток SSE работает, но служба больше не показывает робота: отменённый посреди отправки запрос `setPeerStatus` оставляет именно такую ситуацию. Соединение не замечает её. Решение Mini: проверять `/api/robot-status` каждые 30 s и принудительно переподключаться после двух последовательных пропусков.
- **Одновременные сеансы.** Сервер уже ограничивает их: `handle_start_session` возвращает `sessionRejected` с `reason: "robot_busy"` и именем `activeApp`, удерживающим сеанс; другим устройствам владельца посылается `sessionStateChanged`, чтобы интерфейс обновился в течение одного запроса. Проверка на роботе всё равно нужна для надёжности. Два удалённых участника, управляющих роботом, вызывают ту же ошибку чередования команд, что и сочетание геймпада с участником в §9 `remote-webrtc.md`; последствие достаточно серьёзно для двойной проверки.
- **Порядок регистрации.** Сначала зарегистрировать производителя, *потом* объявлять `connected`. Иначе каждый наблюдатель — запрос состояния, страница, человек — увидит «удалённый доступ включён», пока служба ещё не знает о роботе.
- **Ограниченная экспоненциальная задержка со случайным разбросом.** От 5 s до 60 s плюс около 10%. Одновременное переподключение всего парка после перезапуска службы само вызвало бы отказ.
- **Учётные данные изменились во время соединения.** Токен читается один раз на соединение; поэтому `logout` и `login --force` с переходом к другой учётной записи сами по себе не повлияют на работающий релей. Он продолжил бы продлевать аренду учётными данными, которые владелец удалил. Токен перечитывается на каждом heartbeat; отставание не больше одного интервала. Закрытие потока снимает регистрацию: при нормальном разрыве участник удаляется немедленно, а фоновая очистка нужна лишь для сокетов, которые никогда не сообщили о закрытии. Есть и явный отзыв `roles: []`, предназначенный для сохранения канала с возможностью последующей регистрации; здесь он не нужен.
- **Ответ 401 не требует повторов с нарастающей задержкой.** Отвергнутый службой токен повторами не исправить: нужен новый вход. Такой путь ожидает изменения файла токена с тем же интервалом 30 s, что и робот без владельца, вместо отправки заведомо бесполезных запросов каждые пять секунд в чужой Space.

Из серверного кода следуют ещё два факта. **Очистка распространяется лишь на производителей с `meta.hardware_id`**; без него упавший демон оставался бы в списке владельца до перезапуска Space. Поэтому «желательно» в §3.7 превращается в «обязательно». И **второе соединение `/events` с тем же токеном заменяет первое, не удаляя участника**. После перезапуска демона, когда прежний сокет полуоткрыт, повторное подключение проходит нормально; именно поэтому тайм-аут чтения 60 s безопасен, а не просто смел.

Мы **не копируем** их `RobotAppLock`: он распределяет доступ между локальным *приложением* и удалённым сеансом, а у Microduck такого приложения нет. Эквивалентный вопрос — геймпад и удалённый участник одновременно посылают намерения — принадлежит §9 `remote-webrtc.md` и сознательно отложен. Второй удалённый участник создаёт тот же пробел, а не новый.

<a id="35-it-is-a-task-in-mediad-in-a-module-with-no-gstreamer-in-it"></a>
### 3.5 Задача внутри `mediad`, в модуле без GStreamer

Отдельный unit-файл не нужен. `relayd` потребовал бы собственную копию идентификатора производителя, настройки, сценарий перезапуска и всё равно не работал бы без `mediad`: три новые подвижные части для изоляции задачи из WebSocket, HTTP-клиента и хеш-таблицы.

Модуль размещается там же, где `session.rs`, и по той же причине: **намеренно не зависит от транспорта**, чтобы его можно было тестировать на ноутбуке с поддельной службой и локальным сервером. Это позволило проверять канал управления без платы; здесь ценность ещё выше, потому что сбои §3.4 связаны со временем и ручное испытание оборудования не воспроизведёт их по требованию.

Унаследованное правило: обработчик сигнала GStreamer не должен вызывать panic (заголовок `pipeline.rs` и аварийное завершение процесса, после которого появилось правило). Сам релей обработчик не затрагивает, но когда-нибудь захочет *обратиться* к конвейеру — границу следует сохранить.

**Действия службы публикуются, а не только записываются в журнал.** Каждое состояние — вход не выполнен, подключение, регистрация, отказ, повторная попытка — сохраняется в `/run/mediad/remote.json` (тип `RemoteStatus` в `duck-ipc-proto`). Регистрация также сохраняет имя учётной записи, к которой служба отнесла токен, и каждый успешный heartbeat. `robotctl health` показывает это строкой `central` рядом с учётной записью из `updaterd`. Робота часто «нет в списке» потому, что он числится под чужой учётной записью; в этой строке встречаются оба имени.

<a id="36-what-a-bridged-peer-may-call-exactly-what-a-lan-peer-may"></a>
### 3.6 Права участника через мост совпадают с правами участника LAN

Сеанс тот же `webrtcsink`, таблица маршрутов та же `route.rs`. Это намеренно; после реализации решение нужно пересмотреть. §4 доказывает, что дополнительная проверка роботу не требуется, поскольку служба удостоверила обе стороны. Здесь довод даже *сильнее*: участник через мост доказал владение учётной записью, а участник LAN — лишь присутствие в Wi-Fi-сети. По адресу источника робот умеет их различить (§7), но пока ничего на этом основании не меняет. Важно сохранить именно это понимание.

<a id="37-what-a-duck-has-to-call-itself-and-it-is-not-free-form-after-all"></a>
### 3.7 Как робот должен представляться: поля не столь произвольны

Для *протокола* `meta` свободен, но сервер читает два ключа. Произвольное заполнение даст неверное поведение без явной ошибки:

- **`hardware_id`** (либо `install_id`) — **ключ устойчивой идентичности**. При `setPeerStatus` сервер ищет другого производителя *того же пользователя* с тем же значением и удаляет прежнего вместе с сеансом. Иначе повторная запись образа, дубликат SD-карты или забытый процесс постоянно показывали бы второго робота.

  Робот **обязан** поставить устойчивое значение. Очевидный источник уже есть: `producer.rs` читает серийный номер SoC для локального `meta`, то есть значение, которое неизменно для физического робота при переустановке и смене имени. Без ключа повторное соединение с новым токеном создаст вторую запись, а поскольку очистка опирается на поле, она вообще никогда не исчезнет. Использовать *имя* нельзя: переименование раздвоит личность робота.

  Если серийный номер недоступен — ноутбук разработчика или плата без него в device tree — используется `/etc/machine-id`, устойчивый для *установки*, а не для физического робота. Он слабее, но решает задачу: одна машина показывает одну запись, которую можно очищать. `sounds` уже делает ту же подстановку по той же причине.
- **`simulated`** — наше поле, сервер его не читает. Робот в MuJoCo регистрируется так же, как физический; без различия в списке человек мог бы управлять симуляцией и недоумевать, почему стоящий на полке робот неподвижен. Флаг объявляет `configd --simulated <serial>`, и §8 `docs/design/simulation.md` объясняет, почему только он. Серийный номер позволяет задать `hardware_id` симулированного робота: `/etc/machine-id` одинаков у всех роботов на *одной установке*, поэтому они удаляли бы друг друга; на macOS такого файла вообще нет.
- **`name`** — имя, показанное человеку в списке. Имя потребителя сервер возвращает как `activeApp` другим устройствам владельца. `transport` (`"wifi"` / `"usb"`) характерен для Mini; робот может его не использовать. `kind` со значением `microduck` позволит клиенту показать обе семьи роботов, не открывая сеанс.

**Ещё один важный факт протокола: участники определяются по токену.** В `get_or_create_peer` есть отображение `token -> peer_id`; второе соединение с тем же токеном вытесняет первое. Два устройства с общим токеном по очереди становились бы доступными и не выглядели бы сломанными. Каждый робот выполняет свой Device Flow, поэтому токены у них не совпадают; образы создаются заново, а не клонируются, и передать токен на вторую плату штатным путём нельзя.

  Ошибка проявится у **потребителя**: облачный сервер с *токеном робота* вытеснит участника самого робота из списка. Space-клиенту нужен отдельный токен той же учётной записи или токен посетителя. Клиент §5 использует токен посетителя, поэтому не сталкивается с этим.

<a id="38-a-control-lane-that-needs-no-candidate-pair"></a>
### 3.8 Канал управления без установления пары ICE-кандидатов

Мост передаёт *согласование*, а канал данных `control` — это SCTP поверх пары, выбранной ICE. Если релей с тарифицируемым трафиком исчерпан или временно не отвечает, вместе с видео перестаёт проходить и вызов JSON-RPC в несколько сотен байт.

Посредник уже переносит всё необходимое для вызова. `handle_peer_message` в их `app.py` пересылает партнёру сеанса **каждый ключ конверта `peer`, кроме `type` и `sessionId`**, без изменений. Поэтому конверт `peer` с ключом `rpc` станет непрозрачно пересланным управляющим вызовом; менять службу, от которой зависит парк Mini, не придётся:

```
  consumer ──POST /send {type:peer, sessionId, rpc:{…}}──► rendezvous ──SSE──► relay
           ◄─────────── SSE {type:peer, sessionId, rpc:{…}} ◄──POST /send───────┘
```

`mediad::relay` отвечает через `session::run`: та же таблица маршрутов, те же отдельные сокеты, те же права участника через мост из §3.6. Клиентская часть находится в `spaces/shared/wire.py`. Так **программа** управляет роботом из центра обработки данных: обе стороны удостоверены учётной записью (§7), а для связи достаточно HTTP.

Ограничения два, оба наложены службой:

- **Нет изображений.** Передавать видео означало бы вложить base64 в JSON с частотой ниже. Кадры получают через WebRTC или `media.stream` (§5.3).
- **Не подходит для телеуправления джойстиком.** Посредник допускает 1200 запросов за 60 s на участника; при превышении возвращает `429` для участника целиком, включая продление аренды робота. Поэтому робот ограничивает уведомления в этом канале (`relay::Budget`), а клиент посылает вызовы с частотой поведения, а не команд джойстика.

<a id="4-the-rendezvous-is-the-one-reachymini-uses--decided"></a>
## 4. Посредник — тот же, что использует `reachy_mini` — **решено**

`pollen-robotics-reachy-mini-central.hf.space`, Space, в котором уже регистрируется парк Mini. Это именно принятое решение, а не вынужденный вывод: не требуется создавать серверную часть, служба уже работает с настоящими роботами, и вся задача из этого документа становится клиентской.

Роботу нужны лишь `GET /events` (SSE, `Authorization: Bearer <hf token>`), `POST /send` (то же) и `GET /api/robot-status`, чтобы проверить своё присутствие в списке. Поле `meta` свободно для подходящего идентификатора; `producer.rs` уже собирает имя, серийный номер, выпуск и `api_version`, нужные списку. Это именно те поля, которые §5 `webrtc-console.md` предвидел для посредника. В ту же структуру добавляется `kind: microduck`, чтобы клиент списка мог отличить Microduck от Mini, не открывая сеанс.

**Служба принадлежит нам**, поэтому это повторное использование, а не слепая зависимость: `pollen-robotics/reachy_mini_central` — приложение FastAPI в Space, код которого можно читать и менять. Следствия два:

- **Протокол известен, а не угадан.** Все числа §3 — аренда 30 s, которую продлевает `POST /send`, объявленный интервал 10 s, ping SSE через 30 s, ограничение `sessionRejected` и очистка по `hardware_id` — взяты из `app.py`. Ранняя версия этой страницы ошибочно называла репозиторий приватным: ответ 401 из-за неверного имени приняли за ошибку прав и без нужды восстанавливали протокол по клиентскому коду.
- **Потребность Microduck оформляется как pull request, а не форк.** Если потребуется другая аренда, фильтр списка по `kind` или очистка без предположения «один робот на токен», мы можем изменить поддерживаемый нами сервер. Верно и обратное: изменение ради Mini может сломать Microduck; теперь в службе две семьи роботов.

Единственное, что не переносится, — их **модель блокировки** `RobotAppLock` между локальным приложением и удалённым сеансом. У Microduck приложения нет; §3.4 заимствует поведение переподключения, но оставляет эту часть.

<a id="5-the-client-is-a-space-with-a-hugging-face-sign-in--decided"></a>
## 5. Клиент — Space со входом через Hugging Face — **решено**

Консоль включается в `mediad` через `include_str!` и отдаётся самим роботом (§1 `webrtc-console.md`). Это работает в LAN. **Удалённый клиент не может получить страницу от недоступного ему робота**, поэтому страницу надо разместить вне робота и дать ей второй способ сигнализации.

**Решение: Space в организации `pollen-robotics` с `hf_oauth: true`** — `microduck-console` — отдаёт ту же страницу, что и робот; способ связи определяется тем, откуда страница открыта. Главный довод не хостинг, а **токен**.

Удалённый потребитель удостоверяется у посредника так же, как робот: bearer-токен; служба проверяет его через `whoami-v2` и читает `name` из ответа. Тип и права токена не проверяются, поэтому OAuth-токен браузера подходит наравне с Device Flow-токеном робота. Вопрос сводится к тому, откуда страница получает токен HF. Space решает его: `hf_oauth: true` в README создаёт OAuth-приложение и регистрирует URI перенаправления в Space; `oauthLoginUrl` / `oauthHandleRedirectIfPresent` из `@huggingface/hub` выполняют остальную часть **на клиенте**, с PKCE и без секрета на странице.

<a id="50-it-is-a-docker-space-and-that-cost-an-afternoon"></a>
### 5.0 Это Docker Space; выяснение заняло половину дня

Документированы два способа передать странице client ID, и более аккуратный не сработал. **Статический** Space должен внедрять `window.huggingface.variables.OAUTH_CLIENT_ID`: именно это читает `huggingface.js` (`oauth-login-url.ts`), `reachy_mini_website` и официальный пример HF `huggingfacejs/client-side-oauth`. В `microduck-console` переменная так и не появилась: ни после изменения метаданных, ни после открытия Space, ни после удаления и повторного создания, ни после добавления странице настоящих `<html><head>` для внедрения переменной. До этого страница всю жизнь была только doctype без остальной оболочки. API Hugging Face показывал наш Space и работающий пример одинаковыми: оба `sdk: static`, публичные, с `hf_oauth: true`, в состоянии `RUNNING`.

Поэтому консоль размещена в **Docker** Space. `hf_oauth: true` помещает `OAUTH_CLIENT_ID` в окружение контейнера — документированный путь для нестатического SDK, используемый Space `grabette-*`. Восемь строк `sh` подставляют его в отдаваемую страницу. Страница, не нуждающаяся в сервере по иным причинам, получает сервер только ради этого. `OAUTH_CLIENT_SECRET` находится в том же окружении и никогда не передаётся странице.

Из поиска проблемы стоит сохранить два вывода. Страница **записывает свой штамп сборки** (ревизию и хеш страницы): статический хост кеширует данные, браузер — ещё сильнее, и час ушёл на исправление, которое так и не загружалось. Каждый шаг входа **ограничен тайм-аутом**: оставшийся в адресе уже использованный `?code=` заставляет `oauthHandleRedirectIfPresent` ждать бесконечно, а все сообщения страницы об ошибке находились бы после `await`.

GitHub Pages, предпочтённый ранним черновиком, проигрывает по той же причине: потребовалось бы вручную регистрировать OAuth-приложение с собственным URI перенаправления и затем поддерживать его ради того, что Space даёт одной строкой метаданных README. Возможность остаётся: страница принимает client ID из `?client_id=`, так его пробуют до записи. Это тот же довод §2.3 за официальный Device Code-клиент HF вместо собственной регистрации.

**Дополнительных прав сверх значений по умолчанию мы не запрашиваем.** `openid profile` включены всегда, и этого достаточно: токен нужен только для подтверждения личности посреднику, как доказывает §2.4 для токена робота. Было бы странно убрать `write-repos` у робота, но выдать его браузеру.

**Это не маршрут в `reachy_mini_central`.** Один хост и одно развёртывание потребовали бы поместить интерфейс Microduck внутрь службы, от которой зависит парк Mini. У довода §4 «мы поддерживаем её, значит изменения вносим pull request» есть обратная сторона: наша страница стала бы их операционным риском.

**Исходник страницы остаётся в этом репозитории**, рядом с отдаваемой роботом версией. Он должен согласовываться с протоколом сигнализации и именами методов проекта, а копия в репозитории Space со временем разошлась бы с обоими. Это **та самая** страница, которую отдаёт робот: `mediad/webclient/index.html`, один файл; транспорт определяется тем, подставлен ли токен `{{SIGNALLING_PORT}}`. `web.rs` подставляет его, а тест проверяет, что в отдаваемой странице он не остался. Копия Space оставляет токен; так страница понимает, что её отдал не робот.

Space — цель публикации `pollen-robotics/microduck-console`. `scripts/publish-console.sh` отправляет туда страницу, `Dockerfile` и `entrypoint.sh`. Скрипт подставляет версию API из `duck-ipc-proto`, ставит штамп сборки и не публикует страницу, потерявшую токен порта (копия Space попыталась бы открыть WebSocket) либо client ID (вход был бы невозможен). Пока Space один — ручной запуск; при росте числа — CI.

Установленный факт, а не предпочтение: `EventSource` **не умеет устанавливать заголовки**. Поэтому браузерный клиент SSE должен либо передать токен в строке запроса, либо читать поток через `fetch` и самостоятельно делить SSE на события. `reachy-mini-js` использует первое, но **сервер собирается удалить этот вариант**: `_resolve_hf_token` принимает `?token=` только как переходный путь, записывает предупреждение с IP клиента и прямо говорит в docstring, что после обновления известных клиентов останется только заголовок. Bearer-токен в URL попадёт в журнал доступа Space и каждого промежуточного прокси. Поэтому страница использует `fetch` и несколько строк разбора потока SSE.

Таким образом, страница зеркальна `mediad::relay`: входящий SSE, исходящий `POST /send`, конверты сигнализации gst с локальными идентификаторами на каждом переходе и непрозрачными SDP/ICE. Преобразование в обратную сторону то же; поэтому перед реализацией полезна таблица §3.2.

<a id="51-a-duck-in-a-minis-client-which-is-a-conversation-rather-than-a-commit"></a>
### 5.1 Microduck в клиенте Mini: вопрос к команде, а не изменение этого репозитория

Размещение Microduck в посреднике, чьи остальные клиенты — `reachy_mini_mobile_app` и настольный вариант, означает, что робот может появиться в приложении Mini. Его попытаются вести как Mini, командами методов, которых этот проект не предоставляет. Видео придёт, а остальное нет, и это будет выглядеть как неисправный робот.

`meta.kind` позволяет различать семьи (§3.7), и страница этого проекта фильтрует список по нему. Клиентов Mini отсюда изменить нельзя: нужно говорить с их владельцами. §4 рассматривал, что Microduck нужно от службы, но не обратное влияние появления Microduck на существующих клиентов.

**Потребитель без браузера уже работает; препятствие для команд — метка канала.** `ReachyCentralConsumer`, их клиент aiortc, соединяется с Microduck через посредника и декодирует кадры без изменений на любой стороне: `pip install "reachy_mini[central-consumer]"`, `robot_name="olducky"`, а `latest_frame()` возвращает `(720, 1280, 3) uint8`. Проверено. При этом он сообщает `ignoring unexpected data channel: 'control'`, потому что ищет метку канала демона Mini, тогда как наш канал называется `control` (§5 `remote-webrtc.md`). Для потребителя изображений это не помеха; для управления сначала нужно исправить метку, а затем более существенное несовпадение имён методов. Обе части разобраны в §5.2 на нашей стороне.

**Два клиента Mini выбирают робот по `meta.name` и не читают `kind`.** Выборщик host shell перечисляет всех онлайн-роботов; `ReachyCentralConsumer` сопоставляет `robot_name` с `meta.name`, но имеет **резервный вариант**: если для токена виден только один производитель, он выбирается независимо от имени. Облачный сервер, написанный для Mini, на учётной записи, где единственный онлайн-робот — Microduck, выберет его и начнёт слать неподдерживаемые команды. Команде Mini стоит сообщить об этом до возникновения проблемы. Для них это двухстрочное изменение: `kind` уже передаётся.

<a id="52-a-consumer-that-drives-a-duck-and-the-one-line-of-theirs-it-has-to-get-past"></a>
### 5.2 Потребитель, управляющий Microduck, и одна строка в чужом клиенте

`spaces/policy-playground` — второй потребитель в этом репозитории и первый, который *посылает* команды: вход, список роботов Microduck в учётной записи, установка политики из Hub одним нажатием. Порядок `policy.fetch`, `robot.setSkill`, `robot.policies`, `robot.do` — такой же, как у `robotctl policy add`, но через канал данных вместо Unix-сокета.

Вся цена перехода от «смотреть» к «управлять» сначала упирается в метку. `ReachyCentralConsumer` обрабатывает `pc.on("datachannel")` условием `if channel.label != "data": ignoring unexpected data channel`, а `mediad` открывает `control` (§5 `remote-webrtc.md`). Потребителю изображений ничего добавлять не нужно, но послать вызов без канала нельзя. `RTCPeerConnection` использует emitter pyee: `pc.on` *добавляет* обработчик, а не заменяет. Подкласс, переопределяющий `_build_pc`, регистрирует второй обработчик; исходный продолжает выдавать предупреждение о незнакомой метке, наш принимает отброшенный им канал. Чужой пакет не изменяется, поэтому решение переживёт их исправленную версию: когда исходный обработчик начнёт принимать `control`, наш больше не понадобится и обёртку можно удалить.

Их `send_command` используется повторно, и это осознанно: `RTCDataChannel.send` не потокобезопасен. Их код уже переносит каждую отправку в event loop, владеющий peer connection, тогда как callback Gradio выполняется в одном из рабочих потоков, принявшем запрос.

**Два вида отказа и ответственность сторон за них — главный результат реализации.** `policy.fetch` проверяет свойства робота — `obs_len`, `action_len`, `model_api`, `robot.model` — *до загрузки*. Клиент не должен повторять проверки, а должен показать ответ робота. `robot.setSkill` не проверяет кодирование команды: фазовая политика, установленная как разовое действие, **принимается**, после чего робот подаёт постоянную величину сети, обученной на фазе. Движение выглядит правдоподобно, но неверно. Это правило есть в `robotctl`, который не участвует в нажатии кнопки. Поэтому `catalogue.refusal` повторяет проверку второй раз; любому следующему клиенту с такой кнопкой придётся добавить её в третий раз.

**`401` посредника означает только проблему токена; доказать это удалось чтением `app.py` после неверного предположения.** Первая версия страницы получала список роботов через `GET /api/robot-status`, встретила `401` и решила, что endpoint требует открытого соединения участника. Это выглядело правдоподобно: `POST /send` действительно требует его (примечание §3.1), а робот вызывает проверку состояния лишь при работающем потоке. Но маршруту нужен только `Depends(_resolve_hf_token)` и затем `validate_hf_token`: один запрос `whoami-v2` без проверки прав, типа токена и наличия участника, с фильтром `p.username == username`. Собственный docstring называет назначение: «пассивный индикатор состояния без занятия слота сеанса».

Это **лучше** вызова `list` консоли по причине из §3.7: участник определяется токеном, так что поток `/events`, открытый браузером ради списка, вытеснил бы соединение текущего сеанса. Страница с таким способом списка не может обновить его, не прерывая собственный сеанс. `/api/robot-status` вообще не открывает участника.

Причиной `401` оказался **фиктивный вход Gradio**. Вне Space, когда `SPACE_ID` не задан, `gr.LoginButton` ведёт себя нормально и показывает реальный профиль, но `_get_mocked_oauth_info` выставляет `access_token` в буквальную строку `mock-oauth-token-for-local-dev`. Служба проверяет токен через `whoami-v2` и справедливо отказывает. Симптом — страница просит «войти снова» рядом с консолью, показывающей того же робота. Локальный запуск должен предпочесть `HF_TOKEN` либо токен из `hf auth login`; подделка распознаётся по значению, а не по отсутствию `SPACE_ID`, ведь настоящий токен может прийти и вне Space.

**Общий урок объясняет, почему страница теперь пишет всё сразу в двух местах.** В одной кнопке встречаются четыре слоя: токен, посредник, пара ICE-кандидатов и собственный отказ робота. Ошибки каждого выглядят как «ничего не произошло». Записываются каждый HTTP-статус, кадр сигнализации, строка JSON-RPC и отказ; называется *источник* токена, но никогда не записывается сам токен. `DUCK_LOG=DEBUG` добавляет потоковые уведомления и строки каждого ICE-кандидата. Панель находится и на странице, и в терминале: журналы Space никто может не смотреть, а браузер не имеет stderr. Каждый слой можно запустить отдельно — `uv run rendezvous.py`, `uv run catalogue.py`, `uv run lan.py`. Это превращает «не работает» в конкретную строку вместо переписки.

`IntentResult` — ещё одна ловушка для клиента: `robot.setSkill`, `robot.do`, `robot.init` и `robot.relax` отвечают `accepted: false` с причиной вместо ошибки JSON-RPC намеренно. Отказ системы безопасности запустить политику на упавшем роботе — не поломка вызова. Страница, обрабатывающая только ошибки протокола, сообщает об успехе и оставляет неподвижного робота без объяснения.

**Именно транспорт создаёт главную зависимость при работе из Space.** Канал управления — SCTP поверх той же пары кандидатов, что и медиа. Недоступный релей унесёт и нажатие кнопки; из центра обработки данных сеанс может согласоваться, но не передать данные. Теперь endpoint из §6 отвечает и обычный случай покрыт. Но тарифицируемая зависимость остаётся зависимостью, поэтому строка состояния называет достигнутый этап, а не просто «подключение…», а у страницы есть второй путь.

**`lan.py` — второй путь, это другой транспорт, а не другая архитектура.** Робот уже предоставляет сервер сигнализации `webrtcsink` на `ws://<robot>:8443`, с которым говорит консоль. Он переносит те же конверты gst, что посредник передаёт через SSE и `POST /send`. Заменяется один переход, а всё выше остаётся прежним: канал `control`, JSON-RPC, кнопки. Страница использует любого из двух потребителей, не выясняя его тип. Разницу исчерпывает таблица §3.2; при переходе к LAN удаляются лишние части — учётная запись, аренда, посредник, релей; обе стороны получают host-кандидатов.

Это полезнее обхода неработающей DNS-записи и остаётся нужным после исправления §6: **так можно отделить транспорт от остального**. Если кнопка работает в LAN, но не через посредника, сразу известен проблемный слой; раньше приходилось гадать.

Цена одна: LAN-путь написан вручную, тогда как сторона посредника наследует готовую реализацию. Несколько форм конвертов прочитаны из `net/webrtc/protocol` и страницы консоли; ошибка в одной даёт молчание, а не отказ. Поэтому `uv run lan.py` поднимает на loopback производителя с тем же протоколом и проводит настоящий сеанс: приветствие, список, `startSession`, ответ на offer, DTLS, SCTP, канал, сопоставление вызова и ответа. Два aiortc-участника на `127.0.0.1` — не робот, но протокол у них тот самый, где ошибки иначе остаются незаметными.

<a id="53-frames-out-of-the-robot-which-is-what-6-was-blocking"></a>
### 5.3 Кадры из робота: препятствие из §6

Цель Space из §5.2 — **обрабатывать изображение камеры на оборудовании Hugging Face**. Именно этого не может канал управления: для пикселей нужен медиапуть. Получение кадров требует WebRTC; WebRTC через два NAT требует релей-кандидата, которого, согласно §6, не было. Поэтому `vision-demo` документировал «сигнализация работает, медиа нет» как ожидаемый исход.

**Поэтому робот сам подключается к Space и отправляет видео.** `media.stream {url}` — вызов самого `mediad`, как и `media.video`, потому что он владеет конвейером — задаёт роботу адрес `wss://` для исходящего соединения и передачи кадров. Исходящий WebSocket работает везде; робот доказывает это каждую секунду своей доступности. Не нужны релей и ICE, а **посредник переносит указание, а не кадры**. Это позволяет масштабировать путь, в отличие от передачи пикселей через службу парка Mini.

    Space ──media.stream {url}──► rendezvous ──► robot
    robot ═══════ H.264, outbound wss, direct ═══════► Space

**H.264 вместо JPEG, хотя сначала применялся JPEG.** Плата содержит аппаратный кодировщик, поэтому кодирование загружает VPU, а не ядро CPU. Предсказание сокращает объём примерно на порядок: 0.5 KB на единицу доступа против 6.5 KB на кадр JPEG для синтетического содержимого; на реальном видео меньше, но соотношение сохраняется. Для безопасной работы пришлось решить две незаметно проявляющиеся проблемы:

- **Приёмник, подключившийся посреди потока, не декодирует ничего до ключевого кадра.** Space перезапускается при каждой публикации, поэтому повторное подключение — обычный случай. `h264parse config-interval=-1` повторяет SPS и PPS перед каждым ключевым кадром; открытие клапана отправляет вверх по конвейеру `force-key-unit`, чтобы первый полученный кадр можно было декодировать.
- **Удалять старейший кадр и оставлять новый правильно для JPEG, но неверно здесь.** Кадр предсказания без отброшенной опоры декодируется в мусор, похожий на неисправность камеры, а не транспорта. Поэтому при пропуске поток отбрасывается до следующего ключевого кадра в двух местах: очереди ветки и канале отправителя.

JPEG остаётся доступным через `media.stream {"encoding": "jpeg"}`: независимость каждого кадра полезна при частых переподключениях приёмника.

**Ветка закрывается клапаном, а не создаётся условно.** `webrtcsink` сам владеет кодировщиком видеодорожки и намеренно получает сырое видео: готовые закодированные кадры лишили бы его возможности управлять кодировщиком при перегрузке сети; такой вариант пробовали и отменили. Значит, использовать его выход нельзя, нужен *второй* кодировщик после того же разветвления сырого видеопотока. На плате, где кодировщик ограничивает ресурсы, отсутствие потребителя не должно иметь цены. Поэтому ветка строится один раз за `valve drop=true` и открывается изменением свойства. Альтернативой было добавление и удаление элементов живого конвейера; история `pipeline.rs` с `videoflip` показывает, почему здесь так делать не стоит.

Это **не** показывает браузеру изображение робота, не переносит аудио и не замыкает цикл телеуправления. Для этих целей нужен WebRTC и всё ещё нужен §6. Поток кадров предназначен программному потребителю.

<a id="6-nat-stun-on-both-ends-and-the-robot-offers-the-relay--decided"></a>
## 6. NAT: STUN на обеих сторонах, релей предлагает робот — **решено**

`stun.l.google.com:19302` — значение по умолчанию самого `webrtcsink`; теперь его запрашивает и удалённая консоль. Вторая часть раньше отсутствовала и имела значение: страница, предлагающая роботу в другой сети только свои адреса `192.168.…`, успешно согласует сеанс, но ничего не передаст — подходящей пары кандидатов нет.

**TURN обязателен и распределён несимметрично.** Между роботом за домашним маршрутизатором и потребителем за сетью облачного контейнера соединение двух srflx-кандидатов требует, чтобы оба NAT разрешили пробить отверстие. Часто это получается, но достаточно часто нет. Релей работает всегда, расходуя чей-то трафик; поэтому ICE пробует его последним.

**Достаточно одного релей-кандидата, и он не обязательно принадлежит роботу.** Соединению нужен *один*, не два. STUN-клиент `aiortc` работает там, где его TURN-клиент не работает. Поэтому Python-потребитель не может стать релейной стороной — ею должен быть робот. Issue #1182 в `reachy_mini` установил такую схему; `mediad::turn` повторяет её.

**Этот довод упускал способность сторон вообще адресовать друг друга**, и исходной гипотезой стал iPhone в мобильной сети. У него якобы нет IPv4-сокета: он достигает *имени хоста* через DNS64/NAT64; STUN-сервер сообщает IPv4 reflexive-адрес, который телефон включает в кандидаты. Но ICE-кандидат содержит буквальный адрес, а релей-кандидат робота — IPv4-адрес на плате без глобального IPv6. Телефон не смог бы отправить по нему пакет. На olducky измерили шесть сеансов: каждый раз `offering relay candidates relays=5`, каждый раз `Ice connection state … failed`, примерно с восьмисекундным интервалом.

**Однако измерению приписали больше, чем оно доказывало; у телефона оказался IPv4.** `relays=5` считало URI TURN-серверов, которые `webrtcbin` принял внутри `consumer-added`, *до* попытки выделить релей-адрес. Неудачная и успешная аллокации давали у робота одинаковую строку. Все шесть сеансов столь же совместимы с обычной причиной: релей-кандидата не было ни на одной стороне. Теперь строка названа `added TURN servers for this consumer servers=N` соответственно своему смыслу. `count_gathered_candidates` записывает недостающую половину один раз для потребителя после завершения сбора:

```
gathered ICE candidates host=2 srflx=1 prflx=0 relay=0 unparsed=0
TURN servers were added and no relay candidate came back …
```

`relay=0` рядом с ненулевым `servers` — отказ без иных признаков; второе сообщение выдаётся только для этой пары. Пока такой вывод не получен с нужного робота, причина остаётся неподтверждённой. Абзац про DNS64/NAT64 следует читать как гипотезу, а не установленный факт.

Поэтому **консоль получает собственный релей** (`refreshRelays` в `mediad/webclient/index.html`), и только её аллокация способна соединить эти сети: `turn.cloudflare.com` — имя, разрешаемое через IPv6, а выданный Cloudflare релейный адрес — IPv4, доступный роботу. Это проверили на телефоне до реализации: те же учётные данные в странице Trickle ICE на 4G дали `relay`-кандидата с IPv4-адресом там, где кандидаты самого робота ни с чем не соединялись.

Страница выдаёт их по токену **посетителя**, а не робота. Это правильно по двум причинам: лимит робота должен расходоваться на передачу с него, а не на просмотр; браузер после `hf_oauth` уже имеет собственный токен. Для сеанса LAN релей не запрашивается: с обеих сторон есть host-кандидаты, и релей не понадобился бы.

Учётные данные Cloudflare создаёт прокси Hugging Face для конкретной учётной записи; он принимает **тот же токен, с которым релей входит в службу**. Значит, робот с владельцем может предложить релей, а робот без владельца — нет. Это соответствует правилу §2. Токены короткоживущие: фоновая задача обновляет их на половине срока 600 s, после *временного* сбоя повторяет запрос через тридцать секунд. Роботу без вошедшего владельца нечего повторять; предупреждение каждые тридцать секунд до конца жизни демона сделало бы журнал бесполезным.

**Получение учётных данных не должно задерживать соединение.** Единственная точка использования — обработчик `consumer-added` GStreamer; до его возврата SDP offer не создаётся. HTTP-запрос в обработчике задержал бы каждое подключение, включая LAN-сеансы, которым релей никогда не нужен, на всё время ответа прокси. Поэтому `Relays::uris` читает кеш без ожидания (`try_read` возвращает пустой результат вместо блокировки) и без отказов. Пустой ответ нормален первые секунды после запуска и всегда на роботе без учётной записи. Тогда предлагаются только host- и srflx-кандидаты, достаточные для локальной сети.

**Робот действительно собирает релей-кандидаты: это измерено, а не предположено.** На `lavandiere` (0.12.0-dev.1007.3c8e681, владелец `PierreRouanet`) при сеансе LAN через собственный сервер сигнализации `webrtcsink`:

```
added TURN servers for this consumer  servers=5
gathered ICE candidates  host=6 srflx=3 prflx=0 relay=6 unparsed=0 complete=false
```

Независимо у потребителя наблюдались шесть строк `typ relay` на `104.30.…`. Значит, `add-turn-server` работает, `libnice` завершает выделение адреса Cloudflare с учётными данными этого пользователя, и роботская часть §6 исправна. **LAN**-сеанс достаточен для проверки, поскольку сбор кандидатов не зависит от партнёра: релей-адрес выделяется независимо от того, появится ли подходящая пара. От партнёра зависит только образование пары. Это дешёвый первый тест на будущее — без посредника, Space и второй сети.

Но такой тест не объясняет отдельный *неудачный* сеанс. Счётчик нужно читать на роботе, где произошёл сбой, во время него. `relay=6` здесь доказывает работоспособность механизма, а не каждого робота.

**Релей действительно перенёс целый сеанс.** На `lavandiere` с `0.12.0-dev.1011.cb17b40`, управляемым из приватного HF Space через посредника:

```
ICE connection state  state=Checking → Connected (2.0 s) → Completed (2.2 s)
gathered ICE candidates  host=6 srflx=3 prflx=0 relay=9 unparsed=0 complete=true
selected candidate pair  local=relay 104.30.144.144:29840/udp via 141.101.90.1
                         remote=prflx 54.225.144.144:11854/udp
```

Релей Cloudflare робота стал локальной стороной победившей пары. Следовательно, схема §6 не просто возможна: через неё передавалось видео. Потребитель не предоставлял собственных TURN-учётных данных, они ему не потребовались — именно на этом свойстве построен раздел.

Тип удалённого кандидата **`prflx`** также показателен: робот узнал адрес Space из входящей STUN-проверки, а не из кандидата, переданного сигнализацией. Это нормальная форма для потребителя, чей srflx-кандидат непригоден; дополнительных действий не потребовалось.

Поэтому при недоступности конкретного робота надо собрать с него эти три строки, а не пересматривать проект. Первой проверкой остаётся версия сборки: робот старше исправления endpoint вообще не получает учётных данных и сообщает об этом каждые тридцать секунд.

**Текущая ветка `reachy_mini` не даёт подтверждённо работающий эталон для копирования**: схема та же, но отсутствие подтверждения тоже то же. При сравнении с `mediad` на `9d364df` функции `webrtc_utils.TurnCredentials` и `media_server._apply_turn_servers` совпадают с `turn.rs` и `offer_relay_candidates` по пунктам: тот же endpoint Space, тот же срок 600 s с обновлением на половине, повтор через 30 s только после временного сбоя, пропуск записей `stun:` и записей без учётных данных, тот же URL `turn://user:pass@host:port` с экранированием символов, `add-turn-server` внутри `consumer-added` до создания offer, неблокирующее чтение кеша. Ни один демон не задаёт `stun-server`, оба полагаются на значение `webrtcsink` по умолчанию. **Ни один не наблюдает кандидата**: в `src/reachy_mini/` нет `on-ice-candidate` и `ice-gathering-state`. Утверждение `rf-detr-realtime-webcam/app.py`, что исправленный демон предлагает свой релей, хотя стороне робота передан только STUN, основано на том же прежнем предположении: `add-turn-server` завершился успешно, значит есть кандидат. Переносить исправление нечего; если Mini работает, а Microduck нет, причина в среде (лимите, сети платы или сборке `libnice`), не в коде.

У Mini есть то, чего пока нет у `mediad`: **сторож согласования**. Он ждёт 12 s от `consumer-added` до `connection-state == connected`, затем завершает сеанс с названной причиной вместо бесконечного вращения индикатора. Комментарий указывает повод: «`libnice` зависает посреди `CHECKING` (известный режим сбоя некоторых версий `libnice`)». Это второй способ получить идеально согласованный, но бездействующий сеанс, отличающийся от отсутствия подходящей пары кандидатов. Сторож полезен по той же причине, что счётчик кандидатов: он разделяет внешне одинаковые отказы.

**Прокси — сам Space; неработающим оказалось имя перед ним.** `turn.fastrtc.org` — адрес из кода `fastrtc`, скопированный в схему `reachy_mini` #1182 — имеет осиротевшую делегацию, а не временный сбой. Реестр `.org` указывает четыре DNS-сервера Route53 для зоны, регистрация действует и защищена до 2027 года, но все четыре отвечают `REFUSED` за зону, за которую должны отвечать. По правилам Route53 это происходит, когда размещённая у них зона удалена. `fastrtc/turn-service`, Space, на который указывал псевдоним, всё время отвечал. Поэтому `DEFAULT_TURN_ENDPOINT` обращается напрямую к `https://fastrtc-turn-service.hf.space/credentials`, обходя декоративное имя.

**Это также закрывает путь утечки токена, более важный, чем сама недоступность.** Осиротевшая делегация Route53 — известный сценарий захвата: злоумышленник создаёт hosted zones, пока AWS не выделит один из четырёх делегированных серверов. Одного достаточно, поскольку резолверу нужен лишь один авторитетный ответ. Получив контроль над именем, он выдаст DNS-записи, подтвердит право на сертификат и получит bearer-заголовок с токеном учётной записи, который каждый вошедший робот отправляет каждые пять минут. Этот токен — полные учётные данные робота; §2.4 показывает широту их прав.

**Адрес проверяется до возможной отправки токена.** `turn::parse_endpoint` — `clap` `value_parser` для `--turn-url`: требуется `https`, кроме loopback, запрещены userinfo, query и fragment. Неверное значение останавливает демон на разборе аргументов, а не превращается в предупреждение каждые тридцать секунд. Отдельно запрещать перенаправления не нужно: `reqwest` удаляет `Authorization`, когда redirect меняет схему, хост или порт (`src/redirect.rs`, `remove_sensitive_headers`), поэтому токен не уйдёт стороннему источнику.

**Лимит релея принадлежит владельцу робота и конечен:** 10 GB в месяц на бесплатной учётной записи Hugging Face. Видео через релей расходует примерно гигабайт в час; при активном управлении лимит может закончиться. Тогда прокси отвечает без релей-серверов, а `turn.rs` записывает на уровне info «the TURN proxy offered no relay servers». От робота, которому релей никогда не предлагали, случай не отличается; при первой реальной проблеме стоит улучшить диагностику. Это также довод `stream.rs` за исходящую отправку кадров вместо релея.

**Теперь за состоянием endpoint следят; отсутствие такой проверки позволило не замечать сбой три месяца.** Endpoint был уже нерабочим, когда #1182 внесла его, но симптом оставался лишь предупреждением в журнале и типом кандидата, который никто не считал. `.github/workflows/turn-endpoint.yml` ежедневно выполняет один аутентифицированный `GET` к `DEFAULT_TURN_ENDPOINT` и требует ответ 200 хотя бы с одной записью `turn:`/`turns:`. Все остальные проверки репозитория проходят независимо, поскольку соединяют участников в одной сети, где релей не используется.

Форма проверки выбрана сознательно. URL считывается **из `turn.rs` командой `sed`**, а не дублируется: проверка со своим адресом со временем могла бы зелёным цветом подтверждать URL, которым демон не пользуется. Это хуже отсутствия проверки, потому что воспринимается как доказательство. Workflow **не запускается на `pull_request`**: он должен поймать ситуацию «месяцами никто это не трогал», невидимую для PR, а чужая недоступность не должна блокировать другую работу. **Отсутствующий секрет `HF_TOKEN` приводит к ошибке**, а не пропуску: молча отключившаяся проверка повторила бы именно тот режим отказа, ради которого создана.

Две вещи сознательно остаются вне реализации:

- **Собственный прокси.** Нынешний endpoint — маленькая служба с ключом Cloudflare Calls, выдающая короткоживущие учётные данные владельцу действительного токена HF. Собственный вариант снял бы зависимость от Space малоактивного проекта; подключить его можно через уже существующий `--turn-url`. Это полезно, но не повод откладывать доступ через релей. Адрес `*.hf.space` складывается из `{owner}-{space}` и сломается при переименовании или удалении Space `fastrtc`, а CNAME для перенаправления больше нет. Риск остаётся открытым и назван прямо.
- **Ключ Cloudflare на роботе** через `TURN_KEY_ID` и `TURN_KEY_API_TOKEN`. Быстрее всего и хуже всего: долгоживущий API-токен на каждой плате, от подобной ошибки и предостерегает §2.4.

Сбой релея не должен останавливать робота. Наличие `add-turn-server` проверяется до вызова — panic в C-замыкании аварийно завершает весь процесс вместо раскрутки стека, что уже выяснили в `pipeline.rs`. Отказанный URI становится строкой журнала. Робот без собственного релея доступен из большинства сетей, а не полностью недоступен. **URI TURN содержит пароль**, поэтому в журнал попадает только часть с именем хоста.

<a id="7-authorisation-restated-now-that-there-is-an-account"></a>
## 7. Авторизация после появления учётной записи

§4 `remote-webrtc.md` объясняет, почему роботу не нужна собственная проверка: у сеанса через мост уже дважды проверена подлинность — клиента перед службой и робота при исходящем входе по токену. Доверие не исчезло, а переместилось в службу. Здесь довод сохраняется; добавляется то, чего §4 не мог назвать: **когда устанавливается связь с владельцем и кто это делает**.

- До `account.login` робот недоступен вне LAN. Цели для удалённого нападения нет.
- После входа он принадлежит одной учётной записи. Перенос владения возможен через `account.login`/`account.logout`. Оба вызова доступны через все транспорты, включая WebRTC. §2.6 обосновывает это тремя свойствами: занятый робот отказывает, привязку может увидеть каждый, отозвать её можно не только с робота.
- **Удалённая перепривязка опасна меньше, чем кажется.** Удалённо добраться до робота могут только клиенты учётной записи, *которой он уже принадлежит*. Поэтому удалённый `account.login` приходит от клиента самого владельца. Реальное открытое место — LAN, для него и предназначен `force`.
- При передаче робота новому владельцу надо выполнить выход из учётной записи. Это ещё один пункт наряду с PIN сопряжения и калибровкой в процедуре передачи на этапе M6. Добавить его следует сейчас, пока список составляется, а не после того, как подержанный робот начнёт передавать видео прежнему владельцу.
- Токен — bearer-учётные данные в файле; похищенная плата отдаёт его. Ответом служат права только на чтение из §2.4, а не шифрование: робот должен читать файл сам при запуске. Всё, что он может расшифровать без человека, сможет расшифровать и похититель. Это самый сильный довод ограничить права: сейчас похищенный робот выдаёт токен с правом записи в репозитории владельца.

<a id="8-order-of-work"></a>
## 8. Порядок работ

Пять этапов; первые два полезны сами по себе и не требуют клиента:

1. **`account login`** — Device Flow, файл токена, `account status`. `updaterd`. **Готово**: три вызова, три транспорта, два CLI и токен с автоматическим обновлением. Результат проверяется отдельно — печатается имя пользователя Hugging Face, — поэтому этап выполнен первым.
2. **Релей только для регистрации** — регистрация производителя, согласованный heartbeat, переподключение с нарастающей задержкой, опрос при раздвоении состояния. `mediad`. **Готово**: `mediad::relay`, задача без GStreamer, неактивная до появления `/etc/robot/hf-token` и подхватывающая файл без перезапуска. Клиент не нужен для проверки: панель службы считает производителя, `/api/robot-status` показывает робота.
3. **Размещённый клиент.** §5. Его делают до преобразования сеансов, изменив первоначальный порядок ради проверки. У службы нет собственного интерфейса — `GET /` показывает только число участников, производителей и сеансов. Её потребители — мобильное и настольное приложения Mini — посылали бы роботу несовместимые команды. Без нашего клиента подключаться и испытывать преобразование пришлось бы только на подделке.
4. **Преобразование сеанса:** удалённый потребитель получает видео и канал `control`. **Готово**: `relay::bridge` открывает `ws://127.0.0.1:<--port>` как потребитель при запросе сеанса, переписывает `sessionId` для каждого перехода, не разбирает полезную нагрузку, явно отказывает второму сеансу и сообщает службе о завершении, какова бы ни была причина. В том числе когда нет производителя для моста: конвейер робота не достиг PLAYING.
5. **STUN выбран; TURN предлагает робот.** §6. **Готово**: `stun.l.google.com:19302` на обеих сторонах; `mediad::turn` поддерживает действующие учётные данные Cloudflare, чтобы offer каждого потребителя содержал `relay`-кандидата. Их предоставляет непосредственно Space `fastrtc-turn-service.hf.space`: псевдоним перед ним имеет осиротевшую делегацию. Главное из §6: учётные данные нужны только роботу; их чтение не должно блокировать поток создания offer; обычные проверки репозитория не заметят повторного сбоя endpoint.

<a id="9-what-is-open-and-who-can-close-it"></a>
## 9. Открытые вопросы и ответственные

| Вопрос | Что требуется |
|---|---|
| §2.4 слишком широкие права токена | Публичный Device Code-клиент в организации HF `pollen-robotics` с `openid profile read-repos`, созданный администратором организации. Работу не блокирует: изменение прав потребует повторного входа. Но выпускать робота без этого не следует. |
| калибровка камеры | `media.video` публикует проектные параметры модуля с `calibrated: false`: достаточно для построения карты комнаты, недостаточно для метрологии. Измерение одного робота и запись `[media.intrinsics]` закрывает вопрос для него; калибровка каждого устройства при настройке — для всей семьи. См. §11 `remote-webrtc.md`. |
| всё в протоколе нужно отмечать временем в источнике | §11 `remote-webrtc.md`: `abs-capture-time` для медиа, с проверкой доступности поля в `webrtcsink`, браузере и `aiortc`; монотонная отметка плюс эпоха в каждом уведомлении канала управления, относящемся к определённому моменту. Это нужно любому потребителю, сопоставляющему увиденное роботом с его ощущениями; визуально-инерциальный SLAM — конкретный случай. Требуется собственное повышение версии, а не попутное изменение транспорта. |
| §2.6 `logout` ничего не отзывает | Проверить, принимает ли Hugging Face запрос отзыва для официального Device Code-клиента, а не предполагать. Не блокирует работу: выход прекращает доступность робота, а похищенная плата обрабатывается через hf.co. Но есть разница между «забыт» и «отозван». |
| §6 проверке релея нужен токен | `.github/workflows/turn-endpoint.yml` уже есть и выполняется ежедневно, но завершится ошибкой, пока для репозитория не задан секрет `HF_TOKEN`: токен Hugging Face без прав сверх входа, используемый только для получения учётных данных TURN. Явная ошибка сознательна; альтернатива — проверка, незаметно отключившая себя навсегда. |
| §6 релей находится в чужом Space | Собственный прокси учётных данных с ключом Cloudflare в одном месте вместо зависимости от имени Space малоактивного проекта. Для замены предусмотрен `--turn-url`. Не блокирует работу: Space отвечает. Однако имя `*.hf.space` образуется как `{owner}-{space}`, и при перемещении псевдонима для перенаправления больше нет. |

После появления этой страницы закрыты вопросы: OAuth-клиент (§2.3 — он предоставляется Hugging Face), срок токена (§2.7 — тридцать дней с меняющимся refresh-токеном), выбор посредника (§4 — служба Mini), доступ к его коду (§4 — мы поддерживаем его; прежнее утверждение о «приватном репозитории» вызвано 401 из-за неверного имени), размещение клиента (§5 — статический Space с `hf_oauth`, поскольку главное было не размещение, а получение токена страницей) и выбор endpoint релея (§6 — сам Space, поскольку псевдоним перед ним имеет осиротевшую делегацию).

> **Примечание переводчика:** историческая сводка выше называет Space статическим, но более позднее подробное решение в §5.0 — **Docker Space**: для статического варианта не удалось получить `OAUTH_CLIENT_ID` в браузере. Оба утверждения оригинала сохранены.

Один вопрос страница открыла и закрыла: **участники определяются по токену**, поэтому две стороны с общим токеном по очереди становятся доступными. Это не проблема первичной настройки: образы собираются заново, не клонируются, и вторая плата не получает копию токена. Но это ограничение для потребителей: облачный сервер должен входить со своим токеном, не с токеном робота, иначе подключением удалит робота из списка. См. §3.7.

<a id="10-not-doing"></a>
## 10. Что не делаем

- **Канал данных `teleop`.** Его описывает §6 `remote-webrtc.md`; удалённый сеанс делает блокировку головы очереди заметнее, но не срочнее.
- **Изменяющие вызовы `update.*` через удалённый сеанс.** В §8 `remote-webrtc.md` сказано, что потребуется: клиент, переживающий перезапуск, а не изменения этой схемы.
- **Несколько участников.** По-прежнему один медиасеанс одновременно.
- **Согласие на каждый сеанс.** Задача этапа M5, отдельная от этого документа; теперь она очевиднее: поток из другого континента — именно случай, для которого писали §7 `architecture.md`.
- **Специальное мобильное приложение Microduck.** Issue #107 проектирует его; мобильный прототип относится к M6. На вопрос о клиенте (§5) можно ответить без такого приложения.
