# Сборка на компьютере и установка на плату

Цикл от изменения строки до выполнения её роботом без push, запуска CI и тега. Одна команда из клона репозитория собирает код для платы, подписывает результат и устанавливает по SSH: около минуты для инкрементальной сборки вместо нескольких минут на push и CI.

Эта команда — `scripts/dev-push.sh`. Всё ниже — её параметры.

<a id="once-before-the-first-push"></a>
## Однократная подготовка перед первой отправкой

Три условия, которые достаточно выполнить один раз.

**Плата должна быть платой разработчика.** Артефакт подписывается командным ключом разработки, поэтому пользовательский робот отклоняет его так же, как `--ref`. Подготовка описана в [`install-dev.md`](install-dev.ru.md).

**Закрытый ключ подписи разработки** поместите в `~/.duck-keys/team.dev.key`. Это секретная часть ключа, которым CI подписывает сборки веток; она есть у участника команды. Если файл находится в другом месте, задайте `DUCK_DEV_SECRET_KEY`.

**Инструментарий для сборки под плату.** Установите кросс-компилятор:

```bash
cargo install cargo-zigbuild --locked
```

```bash
brew install zig
```

Либо ничего не устанавливайте и добавляйте `--docker` ко всем вызовам `dev-push.sh` ниже: нужен только работающий Docker daemon. Этот вариант медленнее запускается и полезен ещё до появления платы; см. [сборку в контейнере](#build-in-a-container-instead).

<a id="the-loop"></a>
## Рабочий цикл

Укажите имя робота, а поиск адреса поручите команде:

```bash
scripts/dev-push.sh --name duck-c51b
```

Или один раз на сеанс оболочки:

```bash
export DUCK_ROBOT=duck-c51b
```

```bash
scripts/dev-push.sh
```

Имя — то же, которое показывает `duckctl scan` и задаёт `robotctl system set-name`. Используется та же `DUCK_ROBOT`, которую читает этот инструмент ([`duckctl.md`](duckctl.ru.md)). Адрес запрашивается через Bluetooth: робот отвечает своим `net.status`. Ответ кешируется, поэтому повторное обращение к радио происходит лишь при недоступности сохранённого адреса. Новая DHCP-аренда, перезапись образа или другая сеть поэтому не требуют ручного сопровождения.

Пользователь SSH — `microduck`. Если у вас другой:

```bash
export DUCK_BOARD_USER=pierre
```

Адрес тоже можно указать напрямую, полностью минуя радио:

```bash
scripts/dev-push.sh microduck@192.168.1.42
```

```bash
export DUCK_BOARD=microduck@192.168.1.42
```

Команда кросс-компилирует workspace, упаковывает тот же артефакт, что используется в выпуске, подписывает ключом разработки, копирует в `~/duck-sideload` на плате и применяет через `robotctl update apply --from`. Затем ждёт, пока службы сообщат новый выпуск:

```
==> building 0.5.1-dev.local.1763400000.g7fc1444 for the board (zigbuild)
==> packaging
==> signing with /Users/you/.duck-keys/team.dev.key
==> copying to microduck@192.168.1.42:/home/microduck/duck-sideload
==> applying on microduck@192.168.1.42
==> 0.5.1-dev.local.1763400000.g7fc1444 is live on microduck@192.168.1.42
==> checking every daemon is running it
    current -> 0.5.1-dev.local.1763400000.g7fc1444
    [ok] robotd
    [ok] configd
    [ok] padd
    [ok] updaterd
    [ok] btd
    [ok] mediad
    [ok] tofd
==> every daemon on microduck@192.168.1.42 is running 0.5.1-dev.local.1763400000.g7fc1444
```

`updaterd` и `btd` перезапускаются через пять секунд после ответа apply, поэтому две соответствующие строки появляются с задержкой. `[--] padd published nothing` — не ошибка: так выглядит остановленная или намеренно отключённая служба, а также `mediad` на плате без камеры.

`[--] tofd published nothing` означает выпуск, созданный до появления публикации идентификатора у `tofd`; ещё одна отправка это исправит. Это не означает отсутствие датчика: `tofd` работает и без него.

На плате эту версию показывает `robotctl version`:

```bash
robotctl version
```

Две отправки одного и того же дерева с незакоммиченными изменениями не конфликтуют: версия содержит метку времени отправки, а не только коммит. Незакоммиченные изменения здесь ожидаемы.

**Это обычное обновление.** Проверяются подпись, хеш артефакта, совместимость и работоспособность; действует автоматический откат. Не запускающаяся сборка откатывается, и плата возвращается к прежнему состоянию. Намеренный возврат тоже выполняется обычной командой:

```bash
sudo robotctl update rollback daemon
```

<a id="watching-what-you-just-pushed"></a>
## Наблюдение за отправленной сборкой

Во втором терминале, ещё до отправки, чтобы увидеть перезапуск:

```bash
ssh microduck@192.168.1.42 'journalctl -f -u robotd -u configd -u btd -u padd'
```

Только `-u updaterd` показывает само обновление: этапы, проверку работоспособности и запланированные перезапуски:

```bash
ssh microduck@192.168.1.42 'journalctl -f -u updaterd'
```

Паника службы попадает туда с полным стеком: символы из этих исполняемых файлов не удалены, поэтому кадры имеют имена.

```bash
ssh microduck@192.168.1.42 robotctl health
```

Проверка работы контура управления и выпуска каждой службы. Другие запросы к роботу описаны в [`cheatsheet.md`](cheatsheet.ru.md).

<a id="more-than-info"></a>
### Подробнее, чем `info`

Каждая служба задаёт `RUST_LOG=info`. Чтобы увидеть строки `debug!`, переопределите значение через drop-in на плате; здесь для `robotd`:

```bash
sudo mkdir -p /etc/systemd/system/robotd.service.d
```

```bash
sudo tee /etc/systemd/system/robotd.service.d/log.conf > /dev/null <<'EOF'
[Service]
Environment=RUST_LOG=debug
EOF
```

```bash
sudo systemctl daemon-reload && sudo systemctl restart robotd
```

Drop-in находится в `/etc` и переживает все последующие отправки. По завершении удалите его:

```bash
sudo rm /etc/systemd/system/robotd.service.d/log.conf
```

```bash
sudo systemctl daemon-reload && sudo systemctl restart robotd
```

<a id="verify-without-installing"></a>
## Проверка без установки

```bash
scripts/dev-push.sh --dry-run microduck@192.168.1.42
```

Собирает, подписывает, копирует и выполняет все действия настоящего apply, кроме переключения: проверяет подпись, хеш, совместимость, распаковку и отсутствие установленных служб, указывающих на исполняемый файл, которого нет в этой сборке. Останавливается до изменения `current`, поэтому плата продолжает работать на прежнем выпуске, службы не перезапускаются.

<a id="build-in-a-container-instead"></a>
## Сборка в контейнере

```bash
scripts/dev-push.sh --docker microduck@192.168.1.42
```

Не нужны zig, `cargo-zigbuild` и плата, с которой можно скопировать libudev. На Mac с Apple Silicon целевая архитектура контейнера совпадает с хостом, поэтому кросс-компиляции нет; на ноутбуке x86 используется эмуляция, о чём скрипт сообщает. Артефакт тот же, `--dry-run` и `--bootstrap` работают так же.

У двух режимов раздельные каталоги `target/`, поэтому переключение требует одной полной пересборки. Режим по умолчанию быстрее для повседневной работы; его использует CI.

<a id="re-install-what-is-already-on-the-board"></a>
## Повторная установка уже отправленного на плату

После отправки артефакт остаётся в `~/duck-sideload` на плате, и его можно установить повторно без сборки:

```bash
sudo robotctl update apply daemon --from ~/duck-sideload
```

Та же команда принимает любой каталог выпуска, например на USB-накопителе. Каждая отправка заменяет содержимое каталога, а не дополняет его.

<a id="compile-for-the-board-without-a-robot"></a>
## Сборка для платы без робота

Чтобы проверить целевую сборку изменений — crates с C-зависимостями и ветви только для Linux — без доступной платы:

```bash
cargo board --bins
```

`cargo board` — это `cargo zigbuild` с целевой архитектурой платы и нижней границей glibc, заданными в `.cargo/config.toml`. Нужен тот же инструментарий zig, что для обычной отправки; `padd` нужна копия libudev, которую первая отправка получает с платы. Для `--docker` не нужно ни то, ни другое.

<a id="the-first-push-to-a-board-below-050"></a>
## Первая отправка на плату с версией ниже 0.5.0

`apply --from` требует API версии 7, впервые выпущенного в 0.5.0. Более старый `updaterd` не понимает этот запрос и отклоняет вызов, а не устанавливает молча из своего настроенного источника. Один раз доставьте выпуск способом без проверки работоспособности:

```bash
scripts/dev-push.sh --bootstrap microduck@192.168.1.42
```

Это останавливает `robotd` и отключает проверку работоспособности только для этой установки. Все последующие отправки выполняются обычной командой.

<a id="when-it-does-not-work"></a>
## Если не работает

**`no dev signing key at ...`** — плата проверяет артефакт как любой выпуск, поэтому нужна подпись. Получите `team.dev.key` у участника команды или укажите файл в `DUCK_DEV_SECRET_KEY`.

**`cargo-zigbuild is not installed`** — установите его и zig либо используйте `--docker`.

**`no libudev.so.1 on <board>`** — первая отправка копирует эту библиотеку с платы для линковки `padd`. Ещё не запущенная плата её предоставить не может; `--docker` в ней не нуждается.

**Ошибки линковщика о libudev после перезаписи образа платы** — копия закеширована. Удалите её, и следующая отправка загрузит свежую:

```bash
rm -rf ~/.cache/duck-cross/aarch64
```

**`apply failed (exit 2)` с сообщением о несовпадении API от `robotctl` и `updaterd`** — установленный выпуск старше поддержки `apply --from`. Один раз используйте `--bootstrap`.

**`preflight check failed: SideloadDir: ... is not there for updaterd`** — выпуск находится в `/tmp` или `/var/tmp`, например из-за `DUCK_SIDELOAD_DIR` или вручную заданного `--from`. В `updaterd.service` установлено `PrivateTmp=yes`, поэтому служба видит собственные `/tmp` и `/var/tmp`, отличающиеся от каталогов вашей оболочки. Подойдёт любой другой путь; значение по умолчанию `~/duck-sideload` — один из них. На плате с выпуском до появления этой проверки та же ошибка выглядит как `no manifest for version <version> in <dir>`, хотя `ls` каталога показывает именно этот манифест.

**`verification failed: signature did not verify against any of N usable trusted key(s)`** — похоже на повреждённый выпуск, но обычно означает, что плата не настроена для разработки: ключ не установлен или `allow_dev_keys` выключен. В обоих случаях ключ исключён из допустимого набора. На плате:

```bash
grep -c 'DEV BOARD' /var/lib/robot/provision.log
```

`0` означает отсутствие ключа; обе части исправления описаны в [`install-dev.md`](install-dev.ru.md).

**`could not reach <name> over Bluetooth`** — для поиска адреса по имени робот должен передавать рекламные объявления и быть в зоне действия.

```bash
duckctl scan
```

Пустой список означает, что робот выключен, вне зоны действия или уже подключён к телефону. Укажите адрес напрямую, чтобы не использовать радио:

```bash
scripts/dev-push.sh microduck@192.168.1.42
```

**`<name> answered over Bluetooth but has no wifi address`** — робот работает, но не подключён к сети, поэтому SSH недоступен. Подключите его через тот же радиоканал:

```bash
duckctl --name duck-c51b wifi connect <ssid> --psk <passphrase>
```

**`still <address>, which ssh could not reach`** — адрес не изменился, и причина отказа SSH в другом. Часто это перезапись образа; см. ключи хоста ниже.

**SSH отказывается подключаться после перезаписи образа** — плата создала новые ключи хоста.

```bash
./scripts/provision-board.sh microduck@192.168.1.42 --forget-host-key
```

**`the release is live but not everything is running it`** — переключение выполнено, проверка работоспособности пройдена, но одна из служб ещё работает со старым исполняемым файлом. Это выглядит как неработающее исправление. Скрипт перечисляет такие службы. На плате:

```bash
robotctl health
```

Блок `units` указывает выпуск каждой службы.

```bash
journalctl -u updaterd -b | tail
```

Ищите `restart scheduled` или причину отсутствия перезапуска.

```bash
sudo systemctl restart updaterd
```

Обычно это не требуется, поэтому стоит изучить причину в журнале. Все ловушки перезапуска описаны в [`cheatsheet-dev.md`](cheatsheet-dev.ru.md), а последовательность по шагам — в [`../design/restart-order.md`](../design/restart-order.ru.md).

<a id="settings"></a>
## Настройки

| | |
|---|---|
| `DUCK_ROBOT` | Имя робота. Адрес находится по Bluetooth и кешируется. |
| `DUCK_BOARD_USER` | Пользователь SSH на плате при поиске по имени. По умолчанию `microduck`. Его также читают `duckctl ssh` и `duckctl scp`. |
| `DUCK_PIN` | PIN сопряжения робота, если отличается от заводского `000000`. Читает `duckctl`. |
| `DUCK_BOARD_CACHE` | Каталог кеша найденных адресов. По умолчанию `~/.cache/duck/boards`. |
| `DUCK_BOARD` | Адрес платы вместо аргумента. `microduck@192.168.1.42`. |
| `DUCK_DEV_SECRET_KEY` | Ключ подписи разработки. По умолчанию `~/.duck-keys/team.dev.key`. |
| `DUCK_SIDELOAD_DIR` | Каталог артефакта на плате. По умолчанию `~/duck-sideload`. Никогда не внутри `/tmp` или `/var/tmp`: у `updaterd` собственные экземпляры этих каталогов. |
| `DUCK_CROSS_SYSROOT` | Кешированная копия libudev. По умолчанию `~/.cache/duck-cross/aarch64`. |

<a id="what-this-deliberately-does-not-do"></a>
## Что намеренно не выполняется

Ничего из того, что выпуск делает для подтверждения происхождения. Версия содержит метку времени вместо тега; артефакт подписан ключом, который пользовательские роботы не принимают; ничего не публикуется, поэтому никто другой не может установить только что запущенную вами сборку. Для выпуска по-прежнему нужны тег и `release.yml` ([`../../README.md`](../../README.ru.md)).
