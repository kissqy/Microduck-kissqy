# Симулируемый робот

Робот в MuJoCo, управляемый настоящими службами. Разработка ведётся так же, как с роботом на столе: те же `robotd`, политики, цикл 50 Hz, `robotctl` и консоль. Отличается только тело.

Эта страница объясняет использование. [`design/simulation.md`](../design/simulation.ru.md) описывает границы соответствия цифрового двойника и причины выбранного устройства.

<a id="what-it-is"></a>
## Устройство

`robotd --sim host:port` запускает службу с `duck_control::sim::RemoteIo` вместо шины сервоприводов. На каждом такте положения и скорости суставов и IMU приходят через TCP из процесса MuJoCo, а целевые значения политики отправляются обратно. Всё выше этой границы — контур управления, политика, безопасность, обнаружение падения, кинематика, одометрия и весь IPC — является неизменённым кодом настоящего робота и не различает тело. `tofd --sim` получает кадры глубины 8×8 из того же симулятора; `mediad --sim-camera` получает визуализированное изображение камеры головы, повёрнутой на четверть оборота, как настоящая.
`configd` и `updaterd` также работают без изменений, давая симулируемому роботу серийный номер, имя и учётную запись Hugging Face для доступа извне сети.

Часть MuJoCo находится в [`microduck_rl`](https://github.com/pollen-robotics/microduck_rl) под именем `duck-body`: один процесс, одно окно, N тел роботов в одной сцене с моделями приводов BAM, на которых обучались политики.

**Для чего подходит:** всё в службах и клиентах — IPC, `robotctl`, консоль, обновления, хорал, стояние и ходьба политик, построение карты. **Чего не проверяет:** любые драйверы. Шина Dynamixel, BLE-радио, ISP камеры, NPU и аппаратный кодировщик отсутствуют, а не моделируются; их ошибки видны только на настоящем роботе.

<a id="what-you-need"></a>
## Что нужно

- Этот репозиторий, собранный для вашего компьютера (`cargo build` запускается автоматически).
- Копия `microduck_rl` с её venv рядом с этим репозиторием или по адресу `DUCK_SIM_RL`. Она предоставляет `duck-body`, сцены и `libonnxruntime`, которого обычно нет на ноутбуке. Камера находится в ветке `develop`.
- Для камеры вне Linux: `brew install gstreamer libnice-gstreamer`. Первая формула объединяет `webrtcsink`, srtp и x264. Вторая содержит ICE-агент для `webrtcbin`; первая от неё не зависит. Без неё робот запускается, но поток никуда не идёт, а ошибка возникает только при запросе видео браузером. `scripts/duck-sim` проверяет обе зависимости.
- Только для контейнерного режима: `sudo`, `systemd-nspawn` (пакет `systemd-container`) и `mmdebstrap`. Скрипт сообщает отсутствующую зависимость и печатает команду установки.

<a id="up-or-boot"></a>
## `up` или `boot`?

Оба варианта управляют одним и тем же телом MuJoCo через одинаковый `robotd`. Разница — в окружении запуска служб.

| | `scripts/duck-sim` (`up`) | `scripts/duck-sim boot N` |
|---|---|---|
| Как запускаются службы | Обычные процессы вашего пользователя, каждый со своим pidfile. | Службы systemd в отдельном `systemd-nspawn` для каждого робота, с настоящими unit-файлами. |
| Требования | Только репозиторий и `microduck_rl`. | `sudo`, однократная сборка Debian rootfs. |
| Время запуска | Секунды. | Около минуты первый раз, затем секунды. |
| Идентичность | Идентичность ноутбука; несколько роботов — одно дерево процессов. | Свои machine-id, голос и сокет у каждого робота, между ними `duck-ether`. |
| Что проверяется | Контур управления, политики, IPC, `robotctl`, консоль. | Всё перечисленное плюс `User=`, группы, `RuntimeDirectory=`, защитные настройки, apply обновлений, проверка работоспособности, откат, порядок перезапуска и `journalctl`. |

Практическое правило: **`up`** — для контура управления, политики, IPC или клиента. **`boot`** — для всего, что затрагивает systemd, обновления или подготовку системы, а также общения нескольких роботов. Две найденные симулятором ошибки были связаны с несуществующим пользователем службы, из-за которого unit не запускался. Режим `up` принципиально этого не видит.

<a id="one-duck-no-container"></a>
## Один робот без контейнера

```sh
scripts/duck-sim                # a MuJoCo window opens, the duck stands up, and it is yours
scripts/duck-sim status         # health, and whether it is standing
scripts/duck-sim drive          # walk forward for 8 s (args: vx vyaw, default 0.15 0)
scripts/duck-sim ctl health     # anything robotctl does, aimed at this duck
scripts/duck-sim monitor        # robotctl monitor: joints, IMU, ToF, sticks
scripts/duck-sim log            # robotd's log
scripts/duck-sim simlog         # the MuJoCo side
scripts/duck-sim realtime       # how fast the world is running (see below)
scripts/duck-sim down
```

Без аргументов скрипт собирает службы текущей ветки, записывает параметры с политиками из этого репозитория, запускает `duck-body`, `tofd --sim` и `robotd --sim` в `~/.cache/duck-sim` и включает политику стояния. `ctl` — это `robotctl`, направленный на сокеты данного робота. Это единственное отличие от платы: там сокеты в `/run`, здесь — в каталоге состояния.

Для своих инструментов используйте `~/.cache/duck-sim/duck-a.sock` (robotd; `duck.sock` — ссылка на робота, выбранного для `ctl`) и `~/.cache/duck-sim/duck-a-tof.sock`. Тело доступно на TCP-порту 7801.

<a id="several-ducks-each-a-machine-you-log-into"></a>
## Несколько роботов, каждый как отдельная машина

```sh
scripts/duck-sim boot 4         # four ducks in one world, each in its own container (sudo)
scripts/duck-sim shell          # you are on duck-a
scripts/duck-sim shell duck-c   # or any other
duck-a # robotctl health
duck-a # journalctl -u robotd -f
scripts/duck-sim down
```

`boot` запускает службы каждого робота под настоящим systemd в контейнере `systemd-nspawn`, загруженном из одного Debian 13 rootfs. Он собирается один раз примерно за три минуты, хранится в каталоге состояния и получает отдельный overlay на робота. Это даёт то, чего не имитирует обычный режим: реальные unit-файлы с `User=`, группами, `RuntimeDirectory=` и защитными настройками под настоящим init. Поэтому `robotctl update apply`, проверка работоспособности и порядок перезапусков ведут себя как на реальном роботе. Имена — `duck-a`, `duck-b`, …; у каждого свои machine-id и голос.

При нескольких роботах скрипт запускает `duck-ether`, имитирующий радио и передающий BLE-маяки хорала между контейнерами. Радио намеренно *плохое*, с потерями и задержками: идеальное скрывало бы ошибки реального.

При первом `boot` собирается rootfs и может потребоваться установить `mmdebstrap`. Каждый робот — служба systemd, поэтому `down` выполняет `systemctl stop`, а не сочетание клавиш.

<a id="a-room-to-look-at-and-eyes-to-look-with"></a>
## Комната для наблюдения и камера для зрения

```sh
DUCK_SIM_SCENE=apartment DUCK_SIM_CAMERAS=a scripts/duck-sim boot 2
```

По умолчанию мир — пустой пол. `apartment` содержит шесть комнат на площади 7×6 m с намеренно смещёнными дверными проёмами, чтобы поза распознавалась по переднему обзору робота на 45°. Значение со слешем считается путём к собственной сцене; встроенные сцены — файлы `scene_*.xml` в `microduck_rl`.

Камеры включаются отдельно для каждого робота (`a`, `a,c` или `all`), потому что рендер кадра занимает 12 ms против 0.3 ms на шаг физики четырёх роботов: одна камера требует треть ядра, четыре — почти целое. Каждый робот с камерой получает собственный `mediad`, а его консоль доступна на `http://127.0.0.1:8080`, `8081`, … по индексу. Это та же страница, которую отдаёт настоящий робот.

<a id="reaching-it-from-anywhere"></a>
## Доступ откуда угодно

Симулируемый робот входит в учётную запись Hugging Face и появляется в её списке роботов так же, как робот на столе. После этого консоль, приложение или Space подключаются по WebRTC, не находясь в той же сети.

```bash
DUCK_SIM_CAMERAS=a scripts/duck-sim
```

```bash
scripts/duck-sim ctl account login
```

Откройте `hf.co/oauth/device`, введите напечатанный код, и через несколько секунд робот появится в списке. `scripts/duck-sim ctl account status` показывает связанную учётную запись, а `scripts/duck-sim ctl system info` — серийный номер и строку `body MuJoCo`.

В списке у него есть флаг `simulated` и имя из серийного номера (`duck-eb55`), чтобы не спутать его с роботом на полке. В остальном это обычный робот: тот же канал управления, H.264 и политики.

Из того, что rendezvous идентифицирует участника по токену, следуют два правила:

- **Один робот на учётную запись одновременно.** Второй `login` с той же учётной записью вытесняет первого; явной ошибки не видно, роботы лишь попеременно появляются в списке. Второму роботу нужна вторая учётная запись.
- **Потребляющему поток Space нужен собственный токен**, не токен робота; опубликованный Space использует вход самого посетителя.

`scripts/duck-sim ctl account logout` убирает робота из списка.

<a id="knobs"></a>
## Параметры

Все переменные окружения необязательны:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DUCK_SIM_RL` | `~/Pollen/microduck_rl` | Расположение `duck-body`, сцен и ONNX Runtime. |
| `DUCK_SIM_STATE` | `~/.cache/duck-sim` | Сокеты, журналы, параметры, rootfs и overlays роботов. Путь намеренно короткий: Unix-сокет ограничен примерно 108 байтами. |
| `DUCK_SIM_DUCKS` | `1` | Количество роботов; задаётся также `boot N`. |
| `DUCK_SIM_SCENE` | Пустой пол | Имя сцены (`apartment`) или путь. |
| `DUCK_SIM_CAMERAS` | Нет | Какие роботы рендерят камеру: `a`, `a,c`, `all`. |
| `DUCK_SIM_DUCK` | `duck-a` | Робот, с которым работают `ctl` и `monitor`. |
| `DUCK_SIM_KEYFRAME` | `SIT` | Начальная поза: `SIT` — сложенный на полу робот (политика стояния поднимает его), `HOME`, `STAND`, `FOLD`. |
| `DUCK_SIM_VIEWER` | `1` | `0` запускает MuJoCo без окна. |
| `DUCK_SIM_PORT` | `7801` | Порт тела первого робота; +1 на робота. |
| `DUCK_SIM_FRAME_PORT` | `7901` | Порт кадров первой камеры; +1 на камеру. |

<a id="things-worth-knowing"></a>
## Полезные особенности

**Реальное время важно.** Циклы служб работают по настенным часам. Симулятор медленнее 1.0× реального времени не просто медленно выглядит: политики управляют телом, которое движется меньше ожидаемого, и не могут удерживать равновесие. `scripts/duck-sim realtime` сообщает коэффициент, `boot` тоже его выводит. При избытке роботов или камер они не замедляются, а становятся *unhealthy* по порогу 45 Hz; в контейнерном режиме обновлятор начинает откатывать выпуски. Решения по порядку: меньше роботов, меньше камер, отключение окна просмотра.

**Роботы не подключаются на лету.** MuJoCo компилирует модель, поэтому изменение числа роботов перезапускает симулятор. Службы это переживают: `RemoteIo` переподключается на следующем такте, а временно потерявший тело робот сообщает unhealthy вместо завершения процесса, как настоящий робот с обесточенной шиной.

**`--sim` не равен `--fake`.** `robotd --fake` — робот без физики: положения идеально отражают команды, ничто не падает. Он нужен для модульных тестов и работы на ноутбуке, не требующей тела. `--sim` — цифровой двойник. Флаги взаимоисключающие.

**Робот не должен считать себя ноутбуком.** Голос и идентичность хорала вычисляются из аппаратного серийного номера, который у нескольких роботов на одной машине был бы общим. Скрипт задаёт каждому собственный `DUCK_IDENTITY`; на настоящем роботе переменная не устанавливается.

<a id="by-hand-without-the-script"></a>
## Вручную, без скрипта

Каждая половина принимает `host:port` и может запускаться отдельно, что полезно при поиске неисправности:

```sh
# the body, from the RL repo's venv
duck-body --ducks 1 --port 7801 --keyframe SIT
# the daemons, from this repo
target/debug/tofd --sim 127.0.0.1:7801 --socket /tmp/d/duck-a-tof.sock
DUCK_RUNTIME_DIR=/tmp/d ORT_DYLIB_PATH=<libonnxruntime.so> \
    target/debug/robotd --sim 127.0.0.1:7801 --params <params.toml> --socket /tmp/d/duck-a.sock
# who it is, and which account it belongs to
target/debug/configd --socket /tmp/d/duck-a-config.sock --state-dir /tmp/d/duck-a \
    --simulated sim-duck-a --fake-net --fake-pads
target/debug/updaterd --config /tmp/d/updater.toml --socket /tmp/d/duck-a-updater.sock \
    --token /tmp/d/duck-a/hf-token
# a camera, if duck-body was started with --cameras a
printf '[media]\nquality = "360p30"\n' > /tmp/d/mediad.toml
target/debug/mediad --sim-camera 127.0.0.1:7901 --config /tmp/d/mediad.toml \
    --robot-socket /tmp/d/duck-a.sock --tof-socket /tmp/d/duck-a-tof.sock \
    --config-socket /tmp/d/duck-a-config.sock --updater-socket /tmp/d/duck-a-updater.sock \
    --token /tmp/d/duck-a/hf-token
```

Вне Linux `mediad` нужно собирать с конвейером: `cargo build -p mediad --features gstreamer`. Без этой возможности он запускается, сообщает о её отсутствии и завершается.

`--token` должен указывать на один файл у обеих служб: `updaterd` пишет туда учётные данные, `mediad` читает. При разных файлах робот войдёт в учётную запись, но никогда не зарегистрируется.

Геометрия камеры должна совпадать на обеих сторонах. `mediad` передаёт размер ступени `[media] quality` (`360p30` — 640×360), и тело должно рендерить тот же размер: сырые кадры приходят без согласования, а `mediad` отклоняет неправильный размер вместо показа нечитаемого изображения. Остальные аргументы зафиксированы в `scripts/duck-sim`; прочитайте его перед самостоятельным подбором.
